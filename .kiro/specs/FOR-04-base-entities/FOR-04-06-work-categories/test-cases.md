# Тест-кейсы: FOR-04-06 Work Categories (справочник категорий работ)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерный экран**: справочник категорий работ раздаётся через REST `/api/work-categories` **и** через админ-страницу CRUD по маршруту `/work-categories` (страница + её роут поставляются в этой спеке; группа меню «Справочники» — отдельно в FOR-04-15). Поэтому набор тест-кейсов, согласно стандарту `.kiro/steering/test-cases.md`, включает **оба типа**:

- **Часть A. API-тесты** — против работающего в Docker приложения (не Testcontainers/юнит-слой, а поднятый docker-стек). Каждый шаг — HTTP-запрос к API `/api/work-categories` с проверкой статуса, тела и заголовков.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда `http://localhost:3000`, исполняются браузерным движком (browser automation / headless), под ролью ADMIN. Каждый шаг — действие в браузере (переход, ввод, клик, ожидание).

Результат прогона для **обеих частей** — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус). **Скриншоты не требуются.**

Отличие от FOR-04-02 (единицы измерения): у сущности есть одно дополнительное не-i18n поле — `orderNo` (целочисленный порядок сортировки, `INT NOT NULL`, например 1..13). i18n остаётся только на `name` (`nameRU`/`namePL`, PL fallback). Код `code` — короткий идентификатор в верхнем регистре `UPPER_SNAKE_CASE` (например `PRELIMINARY`, `PLUMBING_ROUGH`, `OTHER`), уникальный и иммутабельный. Полные польские названия категорий — источник истины.

Покрываемые требования: R1 (сущность/таблица с `order_no`), R2 (CRUD + i18n + сортировка/фильтр + иммутабельный `code` + обновляемый `orderNo` + валидация), R3 (ABAC-ресурс `WORK_CATEGORIES` и гранты), R4 (сид 13 дефолтных категорий с `orderNo` 1..13), R6 (админ-страница CRUD), R7 (UI-тесты).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`.
3. Auth-эндпоинты — под `/api/auth`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
5. Дождаться готовности `backend` (health/readiness) и завершения миграций `liquibase` перед запуском кейсов.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые категории получают уникальный `code` вида `WC{run-id}` (например `WC1718123456`, `WC1718123456B`), чтобы не конфликтовать с уникальным индексом `code` и с seed-кодами (`PRELIMINARY`, `TILING`, `OTHER` и т.д.). Так как паттерн кода — `UPPER_SNAKE`, `run-id` при необходимости приводится к верхнему регистру.
- **Teardown (обязательный шаг в конце каждого набора):** удалить все созданные на прогон категории через `DELETE /api/work-categories/{id}` и разлогинить выданные токены (`POST /api/auth/logout`). Отдельной ручной чистки БД не требуется.
- **Seed-данные и системные ресурсы/роли НЕ изменяются** — все манипуляции идут только над созданными на прогон категориями. Это делает набор запускаемым многократно без ручной чистки БД.
- Для i18n-проверок используется заголовок `Accept-Language: ru` / `pl`; отсутствие заголовка эквивалентно PL (fallback).

### Замечание про non-ADMIN роли (ABAC)

Приложение при старте бутстрапит **только ADMIN**. Полноценная проверка гранта READ у ролей MANAGER/FOREMAN/WORKER/FINANCIER требует активного пользователя соответствующей роли (создание такого пользователя через API — вне скоупа быстрого API-прогона). Поэтому:

- Кейсы с ADMIN и «без токена» исполняются напрямую API-прогоном.
- Кейсы для non-ADMIN ролей задокументированы с **ожидаемыми результатами** и помечены как покрываемые seed-интеграционным тестом (`WorkCategoriesResourceSeedIntegrationTest`), который проверяет точную матрицу грантов. Если в окружении есть засиженный ACTIVE-пользователь нужной роли — кейс исполняется API-прогоном.

## Фича 1. CRUD категорий работ

Проверяет полный жизненный цикл категории через generic admin-фреймворк на базовом пути `/api/work-categories`. Покрывает R2.1, R2.4, R2.5.

**Стратегия повторяемости:** генератор `code = WC{run-id}` + teardown (DELETE в конце).

### TC-CRUD-01 — Создание категории (POST) → 200

**Предусловия:** ADMIN залогинен (TC-SETUP-01); сформирован `run-id`.

**Шаги:**
1. `POST /api/work-categories` (Bearer ADMIN) с телом `{"code": "WC{run-id}", "orderNo": 5, "nameRU": "тестовая рус", "namePL": "test pl", "active": true}` → **200**; в теле `id`, `code == "WC{run-id}"`, `orderNo == 5`, `nameRU`, `namePL`, `active == true`.
2. Сохранить `id` созданной категории для дальнейших шагов.

**Ожидаемый результат:** категория создана, `id` присвоен, поля (включая `orderNo`) соответствуют запросу.

### TC-CRUD-02 — Категория присутствует в списке (GET list)

**Предусловия:** выполнен TC-CRUD-01.

**Шаги:**
1. `GET /api/work-categories?size=1000` (Bearer ADMIN) → **200**; ответ пагинированный (`content`/`totalElements` контракта фреймворка).

**Ожидаемый результат:** созданная категория найдена в списке.

### TC-CRUD-03 — Чтение расширенной модели (GET /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `GET /api/work-categories/{id}` (Bearer ADMIN) → **200**; в теле расширенная модель: `id`, `code`, `orderNo == 5`, `nameRU == "тестовая рус"`, `namePL == "test pl"`, `active == true`.

**Ожидаемый результат:** возвращена расширенная модель со всеми локалями, `code` и `orderNo`.

### TC-CRUD-04 — Обновление orderNo/имён/active без изменения code (PUT /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `PUT /api/work-categories/{id}` (Bearer ADMIN) с телом `{"orderNo": 9, "nameRU": "рус обновл", "namePL": "pl updated", "active": false}` → **200**; в теле `orderNo == 9`, `nameRU == "рус обновл"`, `namePL == "pl updated"`, `active == false`.
2. `GET /api/work-categories/{id}` → **200**; убедиться, что `code` **не изменился** (равен `WC{run-id}`), а `orderNo`, имена и `active` обновлены.
3. (Опционально) Отправить в PUT поле `code` с иным значением → значение `code` игнорируется, `code` остаётся прежним (иммутабельность, R2.4); при этом `orderNo` меняется как обычное обновляемое поле.

**Ожидаемый результат:** `orderNo`/имена/`active` обновлены; `code` остаётся неизменным.

### TC-CRUD-05 — Удаление категории (DELETE /{id}) → 200, затем 404

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `DELETE /api/work-categories/{id}` (Bearer ADMIN) → **200**.
2. `GET /api/work-categories/{id}` (Bearer ADMIN) → **404** (категория отсутствует).

**Ожидаемый результат:** категория удалена; повторное чтение возвращает 404.

### TC-CRUD-06 — Валидация обязательных полей при создании → 400

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/work-categories` (Bearer ADMIN) с телом без `code` — `{"orderNo": 1, "nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotBlank code`).
2. `POST /api/work-categories` без `orderNo` — `{"code": "WC{run-id}X", "nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotNull orderNo`).
3. `POST /api/work-categories` с пустым `nameRU` — `{"code": "WC{run-id}Y", "orderNo": 1, "nameRU": "", "namePL": "pl"}` → **400**.
4. `POST /api/work-categories` с отсутствующим `namePL` — `{"code": "WC{run-id}Z", "orderNo": 1, "nameRU": "рус"}` → **400**.

**Ожидаемый результат:** каждый запрос с отсутствующим/пустым обязательным полем (`code`, `orderNo`, `nameRU`, `namePL`) отклоняется с 400.

**Teardown набора:** удалить все созданные на прогон категории (`DELETE /api/work-categories/{id}`), кроме уже удалённой в TC-CRUD-05.

## Фича 2. i18n имени (PL fallback)

Проверяет, что локализованное поле `name` в списочной/краткой модели резолвится в `nameRU` для `Accept-Language: ru` и в `namePL` иначе. Поле `orderNo` не локализуется и возвращается одинаково независимо от локали. Покрывает R2.2.

**Стратегия повторяемости:** генератор `code = WC{run-id}` + teardown.

### TC-I18N-01 — name == nameRU при Accept-Language: ru

**Предусловия:** ADMIN залогинен; создана категория `{code: WC{run-id}I, orderNo: 3, nameRU: "имя-рус", namePL: "nazwa-pl", active: true}`.

**Шаги:**
1. `GET /api/work-categories?size=1000` с заголовком `Accept-Language: ru` → **200**.
2. Найти элемент с `code == "WC{run-id}I"`; проверить `name == "имя-рус"` (значение `nameRU`), `orderNo == 3`.

**Ожидаемый результат:** при `ru` `name` берётся из `nameRU`, `orderNo` не зависит от локали.

### TC-I18N-02 — name == namePL при Accept-Language: pl

**Предусловия:** та же категория, что в TC-I18N-01.

**Шаги:**
1. `GET /api/work-categories?size=1000` с заголовком `Accept-Language: pl` → **200**.
2. Найти элемент с `code == "WC{run-id}I"`; проверить `name == "nazwa-pl"` (значение `namePL`).

**Ожидаемый результат:** при `pl` `name` берётся из `namePL`.

### TC-I18N-03 — PL fallback при отсутствии Accept-Language

**Предусловия:** та же категория.

**Шаги:**
1. `GET /api/work-categories?size=1000` **без** заголовка `Accept-Language` → **200**.
2. Найти элемент с `code == "WC{run-id}I"`; проверить `name == "nazwa-pl"` (PL fallback).

**Ожидаемый результат:** без заголовка локали `name` резолвится в `namePL`.

**Teardown набора:** `DELETE /api/work-categories/{id}` для категории `WC{run-id}I`.

## Фича 3. Сортировка и фильтрация (orderNo и локализованный name)

Проверяет, что сортировка/фильтр по `name` резолвятся в колонку локали (`nameRU`/`namePL`), а сортировка по `orderNo` идёт по числовой колонке. Грамматика фильтра — тильдо-обёрнутая (`~ct~`, а НЕ `=ct=`). Покрывает R2.3.

**Стратегия повторяемости:** генератор с общим префиксом `code = WC{run-id}S{n}` + teardown.

### TC-SORTFILTER-01 — Сортировка по name (asc) резолвится в колонку локали

**Предусловия:** ADMIN залогинен; созданы три категории одного прогона:
- `{code: WC{run-id}S1, orderNo: 101, nameRU: "ааа-рус", namePL: "ccc-pl"}`
- `{code: WC{run-id}S2, orderNo: 102, nameRU: "ббб-рус", namePL: "bbb-pl"}`
- `{code: WC{run-id}S3, orderNo: 103, nameRU: "ввв-рус", namePL: "aaa-pl"}`

**Шаги:**
1. `GET /api/work-categories?size=1000&sort=name,asc` с `Accept-Language: ru` → **200**; среди трёх созданных порядок по `nameRU` восходящий: `ааа-рус`, `ббб-рус`, `ввв-рус` (то есть `S1, S2, S3`).
2. `GET /api/work-categories?size=1000&sort=name,asc` с `Accept-Language: pl` → **200**; среди трёх созданных порядок по `namePL` восходящий: `aaa-pl`, `bbb-pl`, `ccc-pl` (то есть `S3, S2, S1`).

**Ожидаемый результат:** сортировка по `name` применяется к колонке активной локали; порядок различается по локали.

### TC-SORTFILTER-02 — Сортировка по orderNo (asc/desc)

**Предусловия:** те же три категории из TC-SORTFILTER-01 (`orderNo` 101/102/103).

**Шаги:**
1. `GET /api/work-categories?size=1000&sort=orderNo,asc` → **200**; среди трёх созданных порядок по `orderNo` восходящий: `S1` (101), `S2` (102), `S3` (103).
2. `GET /api/work-categories?size=1000&sort=orderNo,desc` → **200**; порядок нисходящий: `S3`, `S2`, `S1`.

**Ожидаемый результат:** сортировка по `orderNo` выполняется по числовой колонке и корректно меняет порядок.

### TC-SORTFILTER-03 — Фильтр по name (~ct~, contains) резолвится в колонку локали

**Предусловия:** те же три категории из TC-SORTFILTER-01.

**Шаги:**
1. `GET /api/work-categories?size=1000&query=name~ct~ааа` с `Accept-Language: ru` → **200**; в результате присутствует `S1` (`nameRU == "ааа-рус"`), отсутствуют `S2`/`S3`.
2. `GET /api/work-categories?size=1000&query=name~ct~aaa` с `Accept-Language: pl` → **200**; в результате присутствует `S3` (`namePL == "aaa-pl"`), отсутствуют `S1`/`S2`.
3. Убедиться, что используется именно тильдо-обёрнутая грамматика `~ct~` (contains), а не `=ct=`.

**Ожидаемый результат:** фильтр `name~ct~<term>` применяется к колонке активной локали; выборка различается по локали.

**Teardown набора:** удалить `S1`, `S2`, `S3` через `DELETE /api/work-categories/{id}`.

## Фича 4. ABAC-доступ (WORK_CATEGORIES)

Проверяет, что эндпоинт защищён ресурсом `WORK_CATEGORIES`: без токена — 401; ADMIN — полный CRUD; держатель роли только с READ — GET разрешён, но POST/PUT/DELETE запрещены (403). Покрывает R3.1, R3.3.

**Стратегия повторяемости:** генератор `code = WC{run-id}A` + teardown.

### TC-ABAC-01 — 401 без токена

**Предусловия:** стек поднят.

**Шаги:**

2. `POST /api/work-categories` без токена с любым телом → **401**.

**Ожидаемый результат:** неаутентифицированный доступ к защищённому ресурсу отклоняется с 401.

### TC-ABAC-02 — ADMIN имеет полный CRUD

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/work-categories` (Bearer ADMIN) `{code: WC{run-id}A, orderNo: 7, nameRU: "рус", namePL: "pl", active: true}` → **200**.
2. `GET /api/work-categories/{id}` (Bearer ADMIN) → **200**.

**Ожидаемый результат:** ADMIN выполняет CREATE/READ/UPDATE/DELETE без ограничений.

### TC-ABAC-03 — Роль с READ: GET разрешён, запись запрещена (403)

**Предусловия:** активный пользователь роли MANAGER/FOREMAN/WORKER/FINANCIER (только READ на `WORK_CATEGORIES`). *Если такого пользователя нет в окружении — кейс покрывается seed-интеграционным тестом (`WorkCategoriesResourceSeedIntegrationTest`), проверяющим матрицу грантов; ниже — ожидаемые результаты.*

**Шаги:**
1. `POST /api/auth/login` пользователем READ-роли → **200**, получить его access-токен.
2. `GET /api/work-categories` (Bearer READ-роль) → **200** (чтение разрешено).
3. `POST /api/work-categories` (Bearer READ-роль) → **403**.
4. `PUT /api/work-categories/{id}` (Bearer READ-роль) → **403**.
5. `DELETE /api/work-categories/{id}` (Bearer READ-роль) → **403**.

**Ожидаемый результат:** роль с грантом READ читает справочник, но операции записи запрещены с 403.

### TC-ABAC-04 — CLIENT не имеет доступа (deny-by-default)

**Предусловия:** активный пользователь роли `CLIENT` (грант на `WORK_CATEGORIES` не выдан). *Если такого пользователя нет — кейс покрыт seed-интеграционным тестом, где у CLIENT нет строки `role_resources` на `WORK_CATEGORIES`.*

**Шаги:**
1. `GET /api/work-categories` (Bearer CLIENT) → **403** (нет гранта READ).

**Ожидаемый результат:** CLIENT не читает справочник категорий работ (deny-by-default).

**Teardown набора:** удалить категорию `WC{run-id}A` (если не удалена в TC-ABAC-02), разлогинить выданные токены.

## Фича 5. Сид справочника (дефолтные категории работ)

Проверяет, что после старта приложения присутствуют 13 дефолтных категорий с `orderNo` 1..13. Покрывает R4.1.

**Стратегия повторяемости:** только чтение, данные не создаются — teardown не требуется.

### TC-SEED-01 — Тринадцать дефолтных кодов присутствуют с orderNo 1..13

**Предусловия:** ADMIN залогинен; миграции `liquibase` завершены.

**Шаги:**
1. `GET /api/work-categories?size=1000` (Bearer ADMIN) → **200**.
2. Убедиться, что в `content` присутствуют все 13 кодов: `PRELIMINARY`, `CONSTRUCTIONS_GK`, `PLUMBING_ROUGH`, `PLUMBING_FINISH`, `ELECTRICAL_ROUGH`, `ELECTRICAL_FINISH`, `TILING`, `PLASTERING`, `PAINTING_DECOR`, `FLOORS`, `CARPENTRY`, `EXTRAS`, `OTHER`.
3. Для каждого сид-кода проверить `active == true` и непустые `nameRU`/`namePL`.
4. Проверить значения `orderNo`: `PRELIMINARY == 1`, ..., `OTHER == 13` (значения `orderNo` образуют последовательность 1..13 без пропусков и дубликатов).

**Ожидаемый результат:** все 13 дефолтных категорий засижены, активны, с корректными `orderNo` 1..13 и польскими названиями как источником истины.

# Часть B. Браузерные (UI) сценарии

### TC-UI-02 — Поиск, сортировка и фильтрация (общий DataTable)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**
1. Ввести в поиск подстроку кода/имени существующей категории (например `TILING` или часть `nameRU`/`namePL`) → список сокращается до совпадающих строк.
2. Очистить поиск → список восстанавливается.
3. Кликнуть заголовок колонки `orderNo` для сортировки → порядок строк меняется по `orderNo` (asc/desc); запрос сортировки уходит на бэкенд (серверная сортировка `sort=orderNo,...`).
4. Кликнуть заголовок колонки `name` для сортировки → порядок меняется по локализованному `name`; запрос `sort=name,...` уходит на бэкенд.

6. Снять фильтр → список восстанавливается.

**Ожидаемый результат:** поиск, сортировка и фильтр корректно сокращают/меняют список; сортировка выполняется на бэкенде (не клиентская).

### TC-UI-04 — Валидация формы создания (пустые/невалидные обязательные поля)

**Ожидаемый результат:** при пустых/невалидных обязательных полях (`code`, `orderNo`, `nameRU`, `namePL`) показываются инлайновые локализованные ошибки, отправка формы заблокирована.

## Регрессия

Небольшой регрессионный набор: перепроверка сквозного сида и ABAC-гарда, а также отсутствия влияния на смежные ресурсы.

**Стратегия повторяемости:** только чтение — teardown не требуется.

### TC-REG-01 — Сид-категории на месте после повторного прогона

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/work-categories?size=1000` (Bearer ADMIN) → **200**; все 13 сид-кодов присутствуют (см. TC-SEED-01) — сид идемпотентен, дубликатов нет.
2. Убедиться, что число элементов с сид-кодами не выросло между прогонами (по одному экземпляру каждого кода), а `orderNo` образуют последовательность 1..13.

**Ожидаемый результат:** сид стабилен и идемпотентен, дубликаты не появляются, значения `orderNo` сохранены.

### TC-REG-02 — ABAC-гард по-прежнему действует

**Предусловия:** нет.

**Шаги:**
1. `GET /api/work-categories` без токена → **401** (гард сохранён).

**Ожидаемый результат:** защита эндпоинта не регрессировала.

### TC-REG-03 — Смежные ресурсы не затронуты

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/roles` (Bearer ADMIN) → **200**; список ролей не изменён появлением нового ресурса.
2. `GET /api/resources` (Bearer ADMIN) → **200**; присутствует новый ресурс `WORK_CATEGORIES` наряду с ранее существующими (`ROOM_TYPES`, `VAT_RATES`, `CURRENCIES`, `MEASUREMENT_UNITS`, `USERS`, `AUDIT`, `PROJECT_MEMBERS` и т.д.), прежние ресурсы на месте.

**Ожидаемый результат:** добавление `WORK_CATEGORIES` не сломало и не удалило смежные ресурсы/роли.
