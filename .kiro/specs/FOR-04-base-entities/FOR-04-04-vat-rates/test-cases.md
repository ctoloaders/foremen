# Тест-кейсы: FOR-04-04 VAT Rates (справочник ставок НДС)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерный экран**: справочник ставок НДС раздаётся через REST `/api/vat-rates` **и** через админ-страницу CRUD по маршруту `/vat-rates` (страница + её роут поставляются в этой спеке; группа меню «Справочники» — отдельно в FOR-04-15). Поэтому набор тест-кейсов, согласно стандарту `.kiro/steering/test-cases.md`, включает **оба типа**:

- **Часть A. API-тесты** — против работающего в Docker приложения (не Testcontainers/юнит-слой, а поднятый docker-стек). Каждый шаг — HTTP-запрос к API `/api/vat-rates` с проверкой статуса, тела и заголовков.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда `http://localhost:3000`, исполняются браузерным движком (browser automation / headless), под ролью ADMIN. Каждый шаг — действие в браузере (переход, ввод, клик, ожидание).

Результат прогона для **обеих частей** — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус). **Скриншоты не требуются.**

Отличие от FOR-04-03 (валюты): у сущности вместо `symbol` два дополнительных не-i18n поля — `rate` (числовой процент `NUMERIC(5,2)`, например 23.00) и `isDefault` (булев флаг ставки по умолчанию). i18n остаётся только на `name` (`nameRU`/`namePL`, PL fallback). Код `code` — короткий буквенно-цифровой идентификатор (например `23`/`8`/`5`/`0`), уникальный и иммутабельный.

Покрываемые требования: R1 (сущность/таблица), R2 (CRUD + i18n + сортировка/фильтр + иммутабельный `code` + обновляемые `rate`/`isDefault` + валидация), R3 (ABAC-ресурс `VAT_RATES` и гранты), R4 (сид дефолтных ставок 23/8/5/0 с 23 по умолчанию), R6 (админ-страница CRUD), R7 (UI-тесты).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`.
3. Auth-эндпоинты — под `/api/auth`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
5. Дождаться готовности `backend` (health/readiness) и завершения миграций `liquibase` перед запуском кейсов.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые ставки получают уникальный `code` вида `vr{run-id}` (например `VR1718123456`, `VR1718123456B`), чтобы не конфликтовать с уникальным индексом `code` и с seed-кодами (`23`, `8`, `5`, `0`).
- **Teardown (обязательный шаг в конце каждого набора):** удалить все созданные на прогон ставки через `DELETE /api/vat-rates/{id}` и разлогинить выданные токены (`POST /api/auth/logout`). Отдельной ручной чистки БД не требуется.
- **Seed-данные и системные ресурсы/роли НЕ изменяются** — все манипуляции идут только над созданными на прогон ставками. Это делает набор запускаемым многократно без ручной чистки БД.
- Для i18n-проверок используется заголовок `Accept-Language: ru` / `pl`; отсутствие заголовка эквивалентно PL (fallback).

### Замечание про non-ADMIN роли (ABAC)

Приложение при старте бутстрапит **только ADMIN**. Полноценная проверка гранта READ у ролей MANAGER/FOREMAN/WORKER/FINANCIER требует активного пользователя соответствующей роли (создание такого пользователя через API — вне скоупа быстрого API-прогона). Поэтому:

- Кейсы с ADMIN и «без токена» исполняются напрямую API-прогоном.
- Кейсы для non-ADMIN ролей задокументированы с **ожидаемыми результатами** и помечены как покрываемые seed-интеграционным тестом (`VatRatesResourceSeedIntegrationTest`), который проверяет точную матрицу грантов. Если в окружении есть засиженный ACTIVE-пользователь нужной роли — кейс исполняется API-прогоном.

## Фича 1. CRUD ставок НДС

Проверяет полный жизненный цикл ставки через generic admin-фреймворк на базовом пути `/api/vat-rates`. Покрывает R2.1, R2.4, R2.5.

**Стратегия повторяемости:** генератор `code = vr{run-id}` + teardown (DELETE в конце).

### TC-CRUD-01 — Создание ставки (POST) → 200

**Предусловия:** ADMIN залогинен (TC-SETUP-01); сформирован `run-id`.

**Шаги:**
1. `POST /api/vat-rates` (Bearer ADMIN) с телом `{"code": "VR{run-id}", "rate": 12.50, "nameRU": "тестовая рус", "namePL": "test pl", "isDefault": true, "active": true}` → **200**; в теле `id`, `code == "VR{run-id}"`, `rate == 12.50`, `nameRU`, `namePL`, `isDefault == true`, `active == true`.
2. Сохранить `id` созданной ставки для дальнейших шагов.

**Ожидаемый результат:** ставка создана, `id` присвоен, поля (включая `rate` и `isDefault`) соответствуют запросу.

### TC-CRUD-02 — Ставка присутствует в списке (GET list)

**Предусловия:** выполнен TC-CRUD-01.

**Шаги:**
1. `GET /api/vat-rates?size=100` (Bearer ADMIN) → **200**; ответ пагинированный (`content`/`totalElements` или аналог контракта фреймворка).
2. Убедиться, что в `content` присутствует элемент с `code == "VR{run-id}"` (с `rate == 12.50` и `isDefault == true`).

**Ожидаемый результат:** созданная ставка найдена в списке.

### TC-CRUD-03 — Чтение расширенной модели (GET /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `GET /api/vat-rates/{id}` (Bearer ADMIN) → **200**; в теле расширенная модель: `id`, `code`, `rate == 12.50`, `nameRU == "тестовая рус"`, `namePL == "test pl"`, `isDefault == true`, `active == true`.

**Ожидаемый результат:** возвращена расширенная модель со всеми локалями, `code`, `rate` и `isDefault`.

### TC-CRUD-04 — Обновление rate/isDefault/имён/active без изменения code (PUT /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `PUT /api/vat-rates/{id}` (Bearer ADMIN) с телом `{"rate": 20.00, "nameRU": "рус обновл", "namePL": "pl updated", "isDefault": false, "active": false}` → **200**; в теле `rate == 20.00`, `nameRU == "рус обновл"`, `namePL == "pl updated"`, `isDefault == false`, `active == false`.
2. `GET /api/vat-rates/{id}` → **200**; убедиться, что `code` **не изменился** (равен `VR{run-id}`), а `rate`, `isDefault`, имена и `active` обновлены.
3. (Опционально) Отправить в PUT поле `code` с иным значением → значение `code` игнорируется, `code` остаётся прежним (иммутабельность, R2.4); при этом `rate` и `isDefault` меняются как обычные обновляемые поля.

**Ожидаемый результат:** `rate`/`isDefault`/имена/`active` обновлены; `code` остаётся неизменным.

### TC-CRUD-05 — Удаление ставки (DELETE /{id}) → 200, затем 404

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `DELETE /api/vat-rates/{id}` (Bearer ADMIN) → **200**.
2. `GET /api/vat-rates/{id}` (Bearer ADMIN) → **404** (ставка отсутствует).

**Ожидаемый результат:** ставка удалена; повторное чтение возвращает 404.

### TC-CRUD-06 — Валидация обязательных полей при создании → 400

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/vat-rates` (Bearer ADMIN) с телом без `code` — `{"rate": 12.50, "nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotBlank code`).
2. `POST /api/vat-rates` без `rate` — `{"code": "VR{run-id}X", "nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotNull rate`).
3. `POST /api/vat-rates` с пустым `nameRU` — `{"code": "VR{run-id}Y", "rate": 12.50, "nameRU": "", "namePL": "pl"}` → **400**.
4. `POST /api/vat-rates` с отсутствующим `namePL` — `{"code": "VR{run-id}Z", "rate": 12.50, "nameRU": "рус"}` → **400**.

**Ожидаемый результат:** каждый запрос с отсутствующим/пустым обязательным полем (`code`, `rate`, `nameRU`, `namePL`) отклоняется с 400.

**Teardown набора:** удалить все созданные на прогон ставки (`DELETE /api/vat-rates/{id}`), кроме уже удалённой в TC-CRUD-05.

## Фича 2. i18n имени (PL fallback)

Проверяет, что локализованное поле `name` в списочной/краткой модели резолвится в `nameRU` для `Accept-Language: ru` и в `namePL` иначе. Поля `rate` и `isDefault` не локализуются и возвращаются одинаково независимо от локали. Покрывает R2.2.

**Стратегия повторяемости:** генератор `code = vr{run-id}` + teardown.

### TC-I18N-01 — name == nameRU при Accept-Language: ru

**Предусловия:** ADMIN залогинен; создана ставка `{code: VR{run-id}I, rate: 3.00, nameRU: "имя-рус", namePL: "nazwa-pl", isDefault: false, active: true}`.

**Шаги:**
1. `GET /api/vat-rates?size=100` с заголовком `Accept-Language: ru` → **200**.
2. Найти элемент с `code == "VR{run-id}I"`; проверить `name == "имя-рус"` (значение `nameRU`), `rate == 3.00`.

**Ожидаемый результат:** при `ru` `name` берётся из `nameRU`, `rate`/`isDefault` не зависят от локали.

### TC-I18N-02 — name == namePL при Accept-Language: pl

**Предусловия:** та же ставка, что в TC-I18N-01.

**Шаги:**
1. `GET /api/vat-rates?size=100` с заголовком `Accept-Language: pl` → **200**.
2. Найти элемент с `code == "VR{run-id}I"`; проверить `name == "nazwa-pl"` (значение `namePL`).

**Ожидаемый результат:** при `pl` `name` берётся из `namePL`.

### TC-I18N-03 — PL fallback при отсутствии Accept-Language

**Предусловия:** та же ставка.

**Шаги:**
1. `GET /api/vat-rates?size=100` **без** заголовка `Accept-Language` → **200**.
2. Найти элемент с `code == "VR{run-id}I"`; проверить `name == "nazwa-pl"` (PL fallback).

**Ожидаемый результат:** без заголовка локали `name` резолвится в `namePL`.

**Teardown набора:** `DELETE /api/vat-rates/{id}` для ставки `VR{run-id}I`.

## Фича 3. Сортировка и фильтрация по локализованному name

Проверяет, что сортировка и фильтр по `name` резолвятся в колонку локали (`nameRU`/`namePL`) через существующую i18n-резолюцию сортировки/фильтра. Грамматика фильтра — тильдо-обёрнутая (`~ct~`, а НЕ `=ct=`). Покрывает R2.3.

**Стратегия повторяемости:** генератор с общим префиксом `code = vr{run-id}S{n}` + teardown.

### TC-SORTFILTER-01 — Сортировка по name (asc) резолвится в колонку локали

**Предусловия:** ADMIN залогинен; созданы три ставки одного прогона:
- `{code: VR{run-id}S1, rate: 1.00, nameRU: "ааа-рус", namePL: "ccc-pl"}`
- `{code: VR{run-id}S2, rate: 2.00, nameRU: "ббб-рус", namePL: "bbb-pl"}`
- `{code: VR{run-id}S3, rate: 3.00, nameRU: "ввв-рус", namePL: "aaa-pl"}`

**Шаги:**
1. `GET /api/vat-rates?size=100&sort=name,asc` с `Accept-Language: ru` → **200**; среди трёх созданных порядок по `nameRU` восходящий: `ааа-рус`, `ббб-рус`, `ввв-рус` (то есть `S1, S2, S3`).
2. `GET /api/vat-rates?size=100&sort=name,asc` с `Accept-Language: pl` → **200**; среди трёх созданных порядок по `namePL` восходящий: `aaa-pl`, `bbb-pl`, `ccc-pl` (то есть `S3, S2, S1`).

**Ожидаемый результат:** сортировка по `name` применяется к колонке активной локали (`nameRU` для ru, `namePL` для pl), порядок различается по локали.

### TC-SORTFILTER-02 — Фильтр по name (~ct~, contains) резолвится в колонку локали

**Предусловия:** те же три ставки из TC-SORTFILTER-01.

**Шаги:**
1. `GET /api/vat-rates?size=100&query=name~ct~ааа` с `Accept-Language: ru` → **200**; в результате присутствует `S1` (`nameRU == "ааа-рус"`), отсутствуют `S2`/`S3`.
2. `GET /api/vat-rates?size=100&query=name~ct~aaa` с `Accept-Language: pl` → **200**; в результате присутствует `S3` (`namePL == "aaa-pl"`), отсутствуют `S1`/`S2`.
3. Убедиться, что используется именно тильдо-обёрнутая грамматика `~ct~` (contains), а не `=ct=`.

**Ожидаемый результат:** фильтр `name~ct~<term>` применяется к колонке активной локали; выборка различается по локали.

**Teardown набора:** удалить `S1`, `S2`, `S3` через `DELETE /api/vat-rates/{id}`.

## Фича 4. ABAC-доступ (VAT_RATES)

Проверяет, что эндпоинт защищён ресурсом `VAT_RATES`: без токена — 401; ADMIN — полный CRUD; держатель роли только с READ — GET разрешён, но POST/PUT/DELETE запрещены (403). Покрывает R3.1, R3.3.

**Стратегия повторяемости:** генератор `code = vr{run-id}A` + teardown.

### TC-ABAC-01 — 401 без токена

**Предусловия:** стек поднят.

**Шаги:**
1. `GET /api/vat-rates` **без** заголовка `Authorization` → **401**.
2. `POST /api/vat-rates` без токена с любым телом → **401**.

**Ожидаемый результат:** неаутентифицированный доступ к защищённому ресурсу отклоняется с 401.

### TC-ABAC-02 — ADMIN имеет полный CRUD

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/vat-rates` (Bearer ADMIN) `{code: VR{run-id}A, rate: 7.00, nameRU: "рус", namePL: "pl", isDefault: false}` → **200**.
2. `GET /api/vat-rates/{id}` (Bearer ADMIN) → **200**.
3. `PUT /api/vat-rates/{id}` (Bearer ADMIN) `{rate: 9.00, nameRU: "рус2", namePL: "pl2", isDefault: true, active: false}` → **200**.
4. `DELETE /api/vat-rates/{id}` (Bearer ADMIN) → **200**.

**Ожидаемый результат:** ADMIN выполняет CREATE/READ/UPDATE/DELETE без ограничений.

### TC-ABAC-03 — Роль с READ: GET разрешён, запись запрещена (403)

**Предусловия:** активный пользователь роли MANAGER/FOREMAN/WORKER/FINANCIER (только READ на `VAT_RATES`). *Если такого пользователя нет в окружении — кейс покрывается seed-интеграционным тестом (`VatRatesResourceSeedIntegrationTest`), проверяющим матрицу грантов; ниже — ожидаемые результаты.*

**Шаги:**
1. `POST /api/auth/login` пользователем READ-роли → **200**, получить его access-токен.
2. `GET /api/vat-rates` (Bearer READ-роль) → **200** (чтение разрешено).
3. `POST /api/vat-rates` (Bearer READ-роль) → **403**.
4. `PUT /api/vat-rates/{id}` (Bearer READ-роль) → **403**.
5. `DELETE /api/vat-rates/{id}` (Bearer READ-роль) → **403**.

**Ожидаемый результат:** роль с грантом READ читает справочник, но операции записи запрещены с 403.

### TC-ABAC-04 — CLIENT не имеет доступа (deny-by-default)

**Предусловия:** активный пользователь роли `CLIENT` (грант на `VAT_RATES` не выдан). *Если такого пользователя нет — кейс покрыт seed-интеграционным тестом, где у CLIENT нет строки `role_resources` на `VAT_RATES`.*

**Шаги:**
1. `GET /api/vat-rates` (Bearer CLIENT) → **403** (нет гранта READ).

**Ожидаемый результат:** CLIENT не читает справочник ставок (deny-by-default).

**Teardown набора:** удалить ставку `VR{run-id}A` (если не удалена в TC-ABAC-02), разлогинить выданные токены.

## Фича 5. Сид справочника (дефолтные ставки НДС)

Проверяет, что после старта приложения присутствуют четыре дефолтные ставки, причём ставка `23` помечена по умолчанию. Покрывает R4.1.

**Стратегия повторяемости:** только чтение, данные не создаются — teardown не требуется.

### TC-SEED-01 — Четыре дефолтных кода присутствуют, 23 по умолчанию

**Предусловия:** ADMIN залогинен; миграции `liquibase` завершены.

**Шаги:**
1. `GET /api/vat-rates?size=1000` (Bearer ADMIN) → **200**.
2. Убедиться, что в `content` присутствуют все четыре кода: `23`, `8`, `5`, `0`.
3. Для каждого сид-кода проверить `active == true` и непустые `nameRU`/`namePL` (`23%`, `8%`, `5%`, `0%`), а также `rate` (23.00 / 8.00 / 5.00 / 0.00).
4. Проверить, что у ставки `23` `isDefault == true`, а у `8`/`5`/`0` `isDefault == false` (ровно одна ставка по умолчанию).

**Ожидаемый результат:** все четыре дефолтные ставки засижены, активны, с корректными `rate`; ставка 23 — единственная по умолчанию.

## Фича UI-1. Страница «Ставки VAT» (/vat-rates)

Проверяет рендер, поиск/сортировку/фильтр, CRUD через UI, пермишн-гейтинг и i18n админ-страницы на базе общего `DataTable`. Покрывает R6.1–R6.7, R7.1.

**Стратегия повторяемости:** генератор `code = vr{run-id}` (уникальный код на каждый прогон) + teardown (удалить созданные ставки через UI-диалог удаления в конце набора). Кейсы «только чтение» (открытие страницы, поиск/сортировка/фильтр по сид-данным, i18n, пермишн-гейтинг READ-роли) teardown не требуют.

### TC-UI-01 — Открытие страницы и рендер таблицы

**Предусловия:** выполнен TC-UI-SETUP-01.

**Шаги:**
1. Перейти на `http://localhost:3000/vat-rates`.
2. Дождаться загрузки таблицы (`DataTable` для `entityKey="vat-rates"`).
3. Проверить заголовок страницы (`vatRates.pageTitle`, локализованный, не сырой ключ).
4. Проверить, что таблица содержит колонки `code`, `rate`, `name`, `isDefault` и `active`.
5. Проверить, что колонка `active` отображается локализованным бейджем (Активна/Неактивна), а колонка `isDefault` — локализованным бейджем (По умолчанию/Нет), а не булевым `true/false`.
6. Убедиться, что в списке присутствуют четыре сид-ставки: `23`, `8`, `5`, `0`, и у строки `23` бейдж «По умолчанию».

**Ожидаемый результат:** страница открыта, таблица отрендерена с колонками code/rate/name/isDefault/active, бейджи локализованы, четыре сид-ставки видны, у 23 бейдж по умолчанию.

### TC-UI-02 — Поиск, сортировка и фильтрация (общий DataTable)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**
1. Ввести в поиск подстроку имени/кода существующей ставки (например `23` или часть `nameRU`/`namePL`) → список сокращается до совпадающих строк.
2. Очистить поиск → список восстанавливается.
3. Кликнуть заголовок колонки `code` для сортировки → порядок строк меняется по `code` (asc), повторный клик — desc; запрос сортировки уходит на бэкенд (серверная сортировка `sort=code,...`).
4. Кликнуть заголовок колонки `name` для сортировки → порядок меняется по локализованному `name`; запрос `sort=name,...` уходит на бэкенд.
5. Применить фильтр по колонке (например `name` contains или `rate`) → список сужается до строк, удовлетворяющих условию.
6. Снять фильтр → список восстанавливается.

**Ожидаемый результат:** поиск, сортировка и фильтр корректно сокращают/меняют список; сортировка выполняется на бэкенде (не клиентская).

### TC-UI-03 — Создание ставки через форму-sheet

**Предусловия:** выполнен TC-UI-01; сформирован `run-id`.

**Шаги:**
1. Убедиться, что кнопка «Создать» видна (ADMIN имеет `CREATE`).
2. Нажать «Создать» → открывается форма-sheet с полями `code`, `rate`, `nameRU`, `namePL`, `isDefault`, `active`.
3. Заполнить `code = VR{run-id}`, `rate = 12.5` (числовое поле), `nameRU = "тест рус"`, `namePL = "test pl"`, включить чекбокс `isDefault`, оставить `active` включённым.
4. Нажать «Сохранить».
5. Дождаться закрытия sheet и появления тоста успеха (`vatRates.toast.createSuccess`).
6. Проверить, что строка с `code = VR{run-id}` (с `rate = 12.5` и бейджем «По умолчанию») появилась в списке.

**Ожидаемый результат:** ставка создана через UI, показан тост успеха, новая строка присутствует в таблице.

### TC-UI-04 — Валидация формы создания (пустые/невалидные обязательные поля)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**
1. Нажать «Создать» → открыть форму-sheet.
2. Оставить `code` пустым, попытаться отправить форму → отображается инлайновая ошибка валидации у поля `code` (локализованная, `vatRates.validation.*`), сабмит заблокирован (запрос на бэкенд не уходит).
3. Заполнить `code`, но ввести пустой/отрицательный `rate` → инлайновая ошибка у поля `rate` (`vatRates.validation.rateRequired`), сабмит заблокирован.
4. Заполнить `rate`, но оставить пустым `nameRU` (и/или `namePL`) → инлайновая ошибка у соответствующего поля имени, сабмит заблокирован.
5. Закрыть форму без сохранения.

**Ожидаемый результат:** при пустых/невалидных обязательных полях (`code`, `rate`, `nameRU`, `namePL`) показываются инлайновые локализованные ошибки, отправка формы заблокирована.

### TC-UI-05 — Редактирование ставки (code read-only, rate/isDefault редактируемы)

**Предусловия:** выполнен TC-UI-03 (создана ставка `VR{run-id}`).

**Шаги:**

3. Проверить, что поле `code` отображается **read-only** (иммутабельно, редактировать нельзя), а поля `rate` и чекбокс `isDefault` доступны для редактирования.
4. Изменить `rate` на `20`, `nameRU` на `"рус обновл"`, `namePL` на `"pl updated"`, снять чекбокс `isDefault`, переключить `active` в выключенное состояние.
5. Нажать «Сохранить» → тост успеха (`vatRates.toast.updateSuccess`).
6. Проверить, что строка `VR{run-id}` в списке обновлена (новый `rate`, бейдж «Нет» у isDefault, новое имя и бейдж «Неактивна»), а `code` остался прежним.

**Ожидаемый результат:** форма предзаполнена, `code` неизменяем, `rate`/`isDefault`/имена/`active` обновлены, показан тост успеха, строка обновлена в таблице.

### TC-UI-06 — Удаление ставки через диалог подтверждения

**Ожидаемый результат:** после подтверждения ставка удалена, показан тост успеха, строка отсутствует в таблице.

### TC-UI-07 — Пермишн-гейтинг (роль только с READ)

**Предусловия:** активный пользователь роли с грантом только `READ` на `VAT_RATES` (например MANAGER/FOREMAN/WORKER/FINANCIER), залогинен в браузере. *Если такого пользователя нельзя создать в окружении — кейс документируется ожидаемым поведением и помечается как покрытый компонентным тестом `VatRatesList.test.tsx` (мок permissions в auth-store, проверка скрытия create/edit/delete).*

## Регрессия

Небольшой регрессионный набор: перепроверка сквозного сида и ABAC-гарда, а также отсутствия влияния на смежные ресурсы.

**Стратегия повторяемости:** только чтение — teardown не требуется.

### TC-REG-01 — Сид-ставки на месте после повторного прогона

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/vat-rates?size=1000` (Bearer ADMIN) → **200**; все четыре сид-кода присутствуют (см. TC-SEED-01) — сид идемпотентен, дубликатов нет.
2. Убедиться, что число элементов с сид-кодами не выросло между прогонами (по одному экземпляру каждого кода `23`/`8`/`5`/`0`), и ровно у одной ставки (`23`) `isDefault == true`.

**Ожидаемый результат:** сид стабилен и идемпотентен, дубликаты не появляются, флаг по умолчанию сохранён на 23.

### TC-REG-02 — ABAC-гард по-прежнему действует

**Предусловия:** нет.

**Шаги:**
1. `GET /api/vat-rates` без токена → **401** (гард сохранён).

**Ожидаемый результат:** защита эндпоинта не регрессировала.

### TC-REG-03 — Смежные ресурсы не затронуты

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/roles` (Bearer ADMIN) → **200**; список ролей не изменён появлением нового ресурса.
2. `GET /api/resources` (Bearer ADMIN) → **200**; присутствует новый ресурс `VAT_RATES` наряду с ранее существующими (`CURRENCIES`, `MEASUREMENT_UNITS`, `USERS`, `AUDIT`, `PROJECT_MEMBERS` и т.д.), прежние ресурсы на месте.

**Ожидаемый результат:** добавление `VAT_RATES` не сломало и не удалило смежные ресурсы/роли.
