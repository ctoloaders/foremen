# Тест-кейсы — FOR-04-bugs

Спека объединяет 11 багфиксов, сгруппированных на **Frontend** и **Backend / cross-cutting**.
Тест-кейсы разделены по характеру:

- **Frontend-кейсы** исполняются браузерным движком (headless / browser automation) против фронтенда
  `http://localhost:3000`. Результат прогона — MD-репорт с таблицами (шаг → ожидание → факт →
  статус), скриншоты не требуются.
- **Backend / API-кейсы** — HTTP-запросы к поднятому в Docker приложению `http://localhost:8080`
  (не Testcontainers). Результат прогона — MD-репорт с таблицами (шаг → запрос → ожидание → факт →
  статус).

## Окружение и повторяемость

- Docker-стек: `docker compose up` в корне поднимает `postgres` (:5432), `liquibase`, `backend`
  (:8080, профиль `docker`), `frontend` (:3000). Первый ADMIN — через `FOREMEN_ADMIN_CREATE=true`,
  `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Auth — под `/api/auth`.
- Для бага 4 (Google Places) требуется локальный (gitignored) `docker-compose.override.yml` с
  `GOOGLE_PLACES_ENABLED=true` и `GOOGLE_PLACES_API_KEY=<ключ>`. Ключ НЕ коммитится.
- **Стратегия повторяемости: генератор + teardown.** `run-id` = timestamp/uuid на каждый прогон.
  Все создаваемые сущности именуются с `run-id` (например, проект `E2E Project {run-id}`, email
  клиента `client+{run-id}@example.com`). Созданные в API-кейсах проекты/пользователи удаляются
  (или деактивируются) в шаге teardown. Frontend-кейсы, создающие данные, используют тот же генератор
  и удаляют созданное через UI или API в конце сценария.

## Группа: Frontend

### Фича: Прозрачные выпадающие списки (Баги 1, 2)

**TC-F01 — Выпадающие списки формы непрозрачны (светлая и тёмная тема)**
Предусловия: залогинен, открыта форма проекта.
1. Открыть форму проекта → открыть выпадающий список (статус/тип комнаты/селект). Ожидание: панель
   полностью непрозрачна, текст читаем.
2. Переключить тему на тёмную, повторить. Ожидание: панель непрозрачна в тёмной теме.
3. Проверить `GoogleAddressAutocomplete`, `TeamMemberSelect`, `ClientBlock`. Ожидание: все панели
   непрозрачны.
Ожидаемый результат: ни одна панель не просвечивает содержимое страницы.

**TC-F02 — Фильтры таблиц непрозрачны**
Предусловия: открыт список с фильтрами (например, проекты/комнаты).
1. Открыть поповер фильтра `DateFilter`. Ожидание: панель непрозрачна.
2. Проверить, что `DataTableHeader`/`FilterPopover` (жёстко `bg-background`) остаются непрозрачными
   (регресс не допущен).
Ожидаемый результат: все фильтр-поповеры непрозрачны в обеих темах.

### Фича: Отсутствующие ключи i18n (Баг 3)

**TC-F03 — Нет «сырых» ключей перевода**
1. Открыть форму проекта. Ожидание: подписи полей команды/адреса — локализованные строки, не
   `projects.form.team.label` и т.п.
2. Вызвать тосты создания/обновления/удаления с ошибкой. Ожидание: сообщения локализованы
   (`projects.toast.*`).
3. Открыть сводку фильтров таблицы. Ожидание: `dataTable.filters.summaryFilters/summarySorts`
   локализованы.
Ожидаемый результат: ни один экран не показывает точечный ключ; наборы ключей pl/ru идентичны.

### Фича: Датапикеры формы проекта (Баг 5)

**TC-F04 — Выбор дат через календарь**
1. Открыть форму проекта. Ожидание: поля начала/конца — датапикер (Popover + Calendar), а не нативный
   `<input type="date">`.
2. Выбрать дату из календаря, сохранить. Ожидание: дата сохранена корректно.
Ожидаемый результат: единый датапикер, консистентный с `DateFilter`.

### Фича: Асинхронные комбобоксы в формах (Баг 7)

**TC-F05 — Async-поиск и бесконечный скролл**
1. Открыть форму комнаты. Ожидание: поля «проект» и «тип комнаты» — комбобокс с поиском, а не
   нативный `<select>`.
2. Ввести часть названия. Ожидание: серверный поиск фильтрует опции.
3. Проскроллить список до конца. Ожидание: подгружается следующая страница (infinite scroll).
4. Повторить для формы работ (`workCategoryId`, `unitId`).
Ожидаемый результат: все указанные поля — async-комбобоксы.

### Фича: Десятичный разделитель (Баг 8)

**TC-F06 — Точка и запятая принимаются**
Предусловия: форма комнаты / редактор проёмов.
1. В числовое поле ввести `12,5`. Ожидание: значение принято, нормализовано в `12.5`.
2. Ввести `12.5`. Ожидание: значение принято без изменений.
3. Сохранить. Ожидание: сохранено предполагаемое число.
Ожидаемый результат: оба разделителя работают, значение не теряется.

### Фича: Удаление стены + ручной ввод площадей (Баг 9)

**TC-F07 — Ручные площади сохраняются при оставшихся стенах**
Предусловия: форма комнаты с ≥2 стенами.
1. Удалить одну стену (остаётся ≥1). 
2. Включить ручной ввод и ввести площади пола/стен вручную.
3. Сохранить. Ожидание: в отправленном payload присутствуют ручные площади (не null).
4. Регресс: собрать комнату только из стен без ручного режима. Ожидание: метрики считаются из
   геометрии, ручные — null (поведение не изменилось).
Ожидаемый результат: ручные площади сохраняются; геометрический режим не сломан.

### Фича: Порядок категорий работ (Баг 10)

**TC-F08 — Категории сортируются по orderNo**
1. Открыть форму работ → выпадающий список категорий. Ожидание: опции идут по `orderNo` по возрастанию
   (не по алфавиту).
Ожидаемый результат: порядок соответствует `orderNo,asc`.

### Фича: Фильтры проектов по команде/клиенту как колоночные (Баг 11)

**TC-F09 — Колоночные nested-фильтры вместо тулбар-панелей**
1. Открыть список проектов. Ожидание: панелей `ProjectMembersFilter`/`ProjectClientFilter` в тулбаре
   нет.
2. Открыть фильтр колонки «команда» через иконку фильтра. Ожидание: nested-фильтр (`members.user.id`),
   работает как прочие reference-фильтры.
3. Открыть фильтр колонки «клиент». Ожидание: nested-фильтр по CLIENT-пути; результаты те же, что
   давали старые панели.
4. Регресс: reference-фильтр в `WorkCatalogList` работает как раньше.
Ожидаемый результат: члены/клиент фильтруются из иконки колонки; семантика запроса неизменна.

## Группа: Backend / cross-cutting (API)

### Фича: Google Places автокомплит (Баг 4)

**TC-B01 — Автокомплит через Places API (New), фича включена**
Предусловия: `GOOGLE_PLACES_ENABLED=true`, ключ задан в локальном override; получен JWT ADMIN.
1. `GET /api/address/autocomplete?query=<строка>` (или соответствующий путь). Ожидание: 200, список
   предсказаний; бэкенд обращается к `places.googleapis.com/v1/places:autocomplete` c `X-Goog-Api-Key`
   и `X-Goog-FieldMask`.
2. `GET /api/address/details?placeId=<id>`. Ожидание: 200, `formattedAddress`/`location`/компоненты.
3. `POST /api/projects` c `googlePlaceId` без адреса/координат. Ожидание: 201; сервер резолвит детали,
   заполняет `formattedAddress`/`latitude`/`longitude`.
Teardown: удалить созданный проект.
Ожидаемый результат: автокомплит и детали работают end-to-end; ключ не залогирован/не возвращён.

**TC-B02 — Фича выключена деградирует мягко**
Предусловия: `GOOGLE_PLACES_ENABLED=false`.
1. `GET /api/address/autocomplete?query=<строка>`. Ожидание: обработанный пустой результат, БЕЗ вызова
   Google, без 5xx.
Ожидаемый результат: отключённая фича не обращается к Google.

### Фича: Аудит создания проекта (Баг 6)

**TC-B03 — CREATE проекта пишет строку аудита**
Предусловия: JWT ADMIN; `run-id` сгенерирован.
1. `POST /api/projects` с `name = "E2E Project {run-id}"`. Ожидание: 201, получен `id` проекта.
2. `GET /api/audit?...` (фильтр по `entityClass=ProjectEntity`, `entityId=<id>`). Ожидание: ровно одна
   строка `operation=CREATE`, `performedBy` = текущий пользователь, `snapshotAfter` заполнен.
Teardown: удалить проект.
Ожидаемый результат: создание проекта аудируется в той же транзакции.

**TC-B04 — Регресс: UPDATE проекта и аудит комнат/сущностей**
1. `PUT /api/projects/{id}` (изменить поле). Ожидание: строка аудита `UPDATE` записана (через
   `AdminService.update`).
2. Создать/обновить комнату `POST/PUT /api/rooms`. Ожидание: строки аудита `CREATE`/`UPDATE` как
   раньше.
3. Создать/обновить любую generic-сущность. Ожидание: аудит без изменений.
Teardown: удалить созданные сущности.
Ожидаемый результат: существующий аудит не сломан.

## Регрессия

- **RG-01** (Баги 1/2): `DataTableHeader`/`FilterPopover` остаются непрозрачными.
- **RG-02** (Баг 3): существующие ключи pl/ru резолвятся; паритет наборов ключей сохранён.
- **RG-03** (Баг 9): геометрический режим комнаты (только стены) считает и сохраняет метрики как
  раньше.
- **RG-04** (Баг 11): reference-фильтр `WorkCatalogList` — прежняя семантика запроса.
- **RG-05** (Баг 6): аудит generic-сущностей, комнат и project UPDATE/DELETE не изменён.
- **RG-06** (Баг 4): server-side резолв места при создании проекта (фича включена) не изменён.
