# Тест-кейсы: FOR-04-03 Currencies (справочник валют)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерный экран**: справочник валют раздаётся через REST `/api/currencies` **и** через админ-страницу CRUD по маршруту `/currencies` (страница + её роут поставляются в этой спеке; группа меню «Справочники» — отдельно в FOR-04-15). Поэтому набор тест-кейсов, согласно стандарту `.kiro/steering/test-cases.md`, включает **оба типа**:

- **Часть A. API-тесты** — против работающего в Docker приложения (не Testcontainers/юнит-слой, а поднятый docker-стек). Каждый шаг — HTTP-запрос к API `/api/currencies` с проверкой статуса, тела и заголовков.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда `http://localhost:3000`, исполняются браузерным движком (browser automation / headless), под ролью ADMIN. Каждый шаг — действие в браузере (переход, ввод, клик, ожидание).

Результат прогона для **обеих частей** — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус). **Скриншоты не требуются.**

Отличие от FOR-04-02: у сущности есть дополнительное скалярное поле `symbol` (не i18n, например `zł`/`€`/`$`), а i18n остаётся только на `name` (`nameRU`/`namePL`, PL fallback). Код `code` — ISO-4217 (например PLN/EUR/USD), уникальный и иммутабельный.

Покрываемые требования: R1 (сущность/таблица), R2 (CRUD + i18n + сортировка/фильтр + иммутабельный `code` + обновляемый `symbol` + валидация), R3 (ABAC-ресурс и гранты), R4 (сид дефолтных валют), R6 (админ-страница CRUD), R7 (UI-тесты).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`.
3. Auth-эндпоинты — под `/api/auth`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
5. Дождаться готовности `backend` (health/readiness) и завершения миграций `liquibase` перед запуском кейсов.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые валюты получают уникальный `code` вида `cu{run-id}` (например `CU1718123456`, `CU1718123456B`), чтобы не конфликтовать с уникальным индексом `code` и с seed-кодами (`PLN`, `EUR`, `USD`).
- **Teardown (обязательный шаг в конце каждого набора):** удалить все созданные на прогон валюты через `DELETE /api/currencies/{id}` и разлогинить выданные токены (`POST /api/auth/logout`). Отдельной ручной чистки БД не требуется.
- **Seed-данные и системные ресурсы/роли НЕ изменяются** — все манипуляции идут только над созданными на прогон валютами. Это делает набор запускаемым многократно без ручной чистки БД.
- Для i18n-проверок используется заголовок `Accept-Language: ru` / `pl`; отсутствие заголовка эквивалентно PL (fallback).

### Замечание про non-ADMIN роли (ABAC)

Приложение при старте бутстрапит **только ADMIN**. Полноценная проверка гранта READ у ролей MANAGER/FOREMAN/WORKER/FINANCIER требует активного пользователя соответствующей роли (создание такого пользователя через API — вне скоупа быстрого API-прогона). Поэтому:

- Кейсы с ADMIN и «без токена» исполняются напрямую API-прогоном.
- Кейсы для non-ADMIN ролей задокументированы с **ожидаемыми результатами** и помечены как покрываемые seed-интеграционным тестом (`CurrenciesResourceSeedIntegrationTest`), который проверяет точную матрицу грантов. Если в окружении есть засиженный ACTIVE-пользователь нужной роли — кейс исполняется API-прогоном.

## Фича 1. CRUD валют

Проверяет полный жизненный цикл валюты через generic admin-фреймворк на базовом пути `/api/currencies`. Покрывает R2.1, R2.4, R2.5.

**Стратегия повторяемости:** генератор `code = cu{run-id}` + teardown (DELETE в конце).

### TC-CRUD-01 — Создание валюты (POST) → 200

**Предусловия:** ADMIN залогинен (TC-SETUP-01); сформирован `run-id`.

**Шаги:**
1. `POST /api/currencies` (Bearer ADMIN) с телом `{"code": "CU{run-id}", "symbol": "₸", "nameRU": "тестовая рус", "namePL": "test pl", "active": true}` → **200**; в теле `id`, `code == "CU{run-id}"`, `symbol == "₸"`, `nameRU`, `namePL`, `active == true`.
2. Сохранить `id` созданной валюты для дальнейших шагов.

**Ожидаемый результат:** валюта создана, `id` присвоен, поля (включая `symbol`) соответствуют запросу.

### TC-CRUD-02 — Валюта присутствует в списке (GET list)

**Предусловия:** выполнен TC-CRUD-01.

**Шаги:**
1. `GET /api/currencies?size=100` (Bearer ADMIN) → **200**; ответ пагинированный (`content`/`totalElements` или аналог контракта фреймворка).
2. Убедиться, что в `content` присутствует элемент с `code == "CU{run-id}"` (и `symbol == "₸"`).

**Ожидаемый результат:** созданная валюта найдена в списке.

### TC-CRUD-03 — Чтение расширенной модели (GET /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `GET /api/currencies/{id}` (Bearer ADMIN) → **200**; в теле расширенная модель: `id`, `code`, `symbol == "₸"`, `nameRU == "тестовая рус"`, `namePL == "test pl"`, `active == true`.

**Ожидаемый результат:** возвращена расширенная модель со всеми локалями, `code` и `symbol`.

### TC-CRUD-04 — Обновление symbol/имён/active без изменения code (PUT /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `PUT /api/currencies/{id}` (Bearer ADMIN) с телом `{"symbol": "€", "nameRU": "рус обновл", "namePL": "pl updated", "active": false}` → **200**; в теле `symbol == "€"`, `nameRU == "рус обновл"`, `namePL == "pl updated"`, `active == false`.
2. `GET /api/currencies/{id}` → **200**; убедиться, что `code` **не изменился** (равен `CU{run-id}`), а `symbol`, имена и `active` обновлены.
3. (Опционально) Отправить в PUT поле `code` с иным значением → значение `code` игнорируется, `code` остаётся прежним (иммутабельность, R2.4); при этом `symbol` меняется как обычное обновляемое поле.

**Ожидаемый результат:** `symbol`/имена/`active` обновлены; `code` остаётся неизменным.

### TC-CRUD-05 — Удаление валюты (DELETE /{id}) → 200, затем 404

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `DELETE /api/currencies/{id}` (Bearer ADMIN) → **200**.
2. `GET /api/currencies/{id}` (Bearer ADMIN) → **404** (валюта отсутствует).

**Ожидаемый результат:** валюта удалена; повторное чтение возвращает 404.

### TC-CRUD-06 — Валидация обязательных полей при создании → 400

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/currencies` (Bearer ADMIN) с телом без `code` — `{"symbol": "₸", "nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotBlank code`).
2. `POST /api/currencies` без `symbol` — `{"code": "CU{run-id}X", "nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotBlank symbol`).
3. `POST /api/currencies` с пустым `nameRU` — `{"code": "CU{run-id}Y", "symbol": "₸", "nameRU": "", "namePL": "pl"}` → **400**.
4. `POST /api/currencies` с отсутствующим `namePL` — `{"code": "CU{run-id}Z", "symbol": "₸", "nameRU": "рус"}` → **400**.

**Ожидаемый результат:** каждый запрос с отсутствующим/пустым обязательным полем (`code`, `symbol`, `nameRU`, `namePL`) отклоняется с 400.

**Teardown набора:** удалить все созданные на прогон валюты (`DELETE /api/currencies/{id}`), кроме уже удалённой в TC-CRUD-05.

## Фича 2. i18n имени (PL fallback)

Проверяет, что локализованное поле `name` в списочной/краткой модели резолвится в `nameRU` для `Accept-Language: ru` и в `namePL` иначе. Поле `symbol` не локализуется и возвращается одинаково независимо от локали. Покрывает R2.2.

**Стратегия повторяемости:** генератор `code = cu{run-id}` + teardown.

### TC-I18N-01 — name == nameRU при Accept-Language: ru

**Предусловия:** ADMIN залогинен; создана валюта `{code: CU{run-id}I, symbol: "₸", nameRU: "имя-рус", namePL: "nazwa-pl", active: true}`.

**Шаги:**
1. `GET /api/currencies?size=100` с заголовком `Accept-Language: ru` → **200**.
2. Найти элемент с `code == "CU{run-id}I"`; проверить `name == "имя-рус"` (значение `nameRU`), `symbol == "₸"`.

**Ожидаемый результат:** при `ru` `name` берётся из `nameRU`, `symbol` не зависит от локали.

### TC-I18N-02 — name == namePL при Accept-Language: pl

**Предусловия:** та же валюта, что в TC-I18N-01.

**Шаги:**
1. `GET /api/currencies?size=100` с заголовком `Accept-Language: pl` → **200**.
2. Найти элемент с `code == "CU{run-id}I"`; проверить `name == "nazwa-pl"` (значение `namePL`).

**Ожидаемый результат:** при `pl` `name` берётся из `namePL`.

### TC-I18N-03 — PL fallback при отсутствии Accept-Language

**Предусловия:** та же валюта.

**Шаги:**
1. `GET /api/currencies?size=100` **без** заголовка `Accept-Language` → **200**.
2. Найти элемент с `code == "CU{run-id}I"`; проверить `name == "nazwa-pl"` (PL fallback).

**Ожидаемый результат:** без заголовка локали `name` резолвится в `namePL`.

**Teardown набора:** `DELETE /api/currencies/{id}` для валюты `CU{run-id}I`.

## Фича 3. Сортировка и фильтрация по локализованному name

Проверяет, что сортировка и фильтр по `name` резолвятся в колонку локали (`nameRU`/`namePL`) через существующую i18n-резолюцию сортировки/фильтра. Грамматика фильтра — тильдо-обёрнутая (`~ct~`, а НЕ `=ct=`). Покрывает R2.3.

**Стратегия повторяемости:** генератор с общим префиксом `code = cu{run-id}S{n}` + teardown.

### TC-SORTFILTER-01 — Сортировка по name (asc) резолвится в колонку локали

**Предусловия:** ADMIN залогинен; созданы три валюты одного прогона:
- `{code: CU{run-id}S1, symbol: "₸", nameRU: "ааа-рус", namePL: "ccc-pl"}`
- `{code: CU{run-id}S2, symbol: "₸", nameRU: "ббб-рус", namePL: "bbb-pl"}`
- `{code: CU{run-id}S3, symbol: "₸", nameRU: "ввв-рус", namePL: "aaa-pl"}`

**Шаги:**
1. `GET /api/currencies?size=100&sort=name,asc` с `Accept-Language: ru` → **200**; среди трёх созданных порядок по `nameRU` восходящий: `ааа-рус`, `ббб-рус`, `ввв-рус` (то есть `S1, S2, S3`).
2. `GET /api/currencies?size=100&sort=name,asc` с `Accept-Language: pl` → **200**; среди трёх созданных порядок по `namePL` восходящий: `aaa-pl`, `bbb-pl`, `ccc-pl` (то есть `S3, S2, S1`).

**Ожидаемый результат:** сортировка по `name` применяется к колонке активной локали (`nameRU` для ru, `namePL` для pl), порядок различается по локали.

### TC-SORTFILTER-02 — Фильтр по name (~ct~, contains) резолвится в колонку локали

**Предусловия:** те же три валюты из TC-SORTFILTER-01.

**Шаги:**
1. `GET /api/currencies?size=100&query=name~ct~ааа` с `Accept-Language: ru` → **200**; в результате присутствует `S1` (`nameRU == "ааа-рус"`), отсутствуют `S2`/`S3`.
2. `GET /api/currencies?size=100&query=name~ct~aaa` с `Accept-Language: pl` → **200**; в результате присутствует `S3` (`namePL == "aaa-pl"`), отсутствуют `S1`/`S2`.
3. Убедиться, что используется именно тильдо-обёрнутая грамматика `~ct~` (contains), а не `=ct=`.

**Ожидаемый результат:** фильтр `name~ct~<term>` применяется к колонке активной локали; выборка различается по локали.

**Teardown набора:** удалить `S1`, `S2`, `S3` через `DELETE /api/currencies/{id}`.

## Фича 4. ABAC-доступ (CURRENCIES)

Проверяет, что эндпоинт защищён ресурсом `CURRENCIES`: без токена — 401; ADMIN — полный CRUD; держатель роли только с READ — GET разрешён, но POST/PUT/DELETE запрещены (403). Покрывает R3.1, R3.3.

**Стратегия повторяемости:** генератор `code = cu{run-id}A` + teardown.

### TC-ABAC-01 — 401 без токена

**Предусловия:** стек поднят.

**Шаги:**
1. `GET /api/currencies` **без** заголовка `Authorization` → **401**.
2. `POST /api/currencies` без токена с любым телом → **401**.

**Ожидаемый результат:** неаутентифицированный доступ к защищённому ресурсу отклоняется с 401.

### TC-ABAC-02 — ADMIN имеет полный CRUD

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/currencies` (Bearer ADMIN) `{code: CU{run-id}A, symbol: "₸", nameRU: "рус", namePL: "pl"}` → **200**.
2. `GET /api/currencies/{id}` (Bearer ADMIN) → **200**.
3. `PUT /api/currencies/{id}` (Bearer ADMIN) `{symbol: "€", nameRU: "рус2", namePL: "pl2", active: false}` → **200**.
4. `DELETE /api/currencies/{id}` (Bearer ADMIN) → **200**.

**Ожидаемый результат:** ADMIN выполняет CREATE/READ/UPDATE/DELETE без ограничений.

### TC-ABAC-03 — Роль с READ: GET разрешён, запись запрещена (403)

**Предусловия:** активный пользователь роли MANAGER/FOREMAN/WORKER/FINANCIER (только READ на `CURRENCIES`). *Если такого пользователя нет в окружении — кейс покрывается seed-интеграционным тестом (`CurrenciesResourceSeedIntegrationTest`), проверяющим матрицу грантов; ниже — ожидаемые результаты.*

**Шаги:**
1. `POST /api/auth/login` пользователем READ-роли → **200**, получить его access-токен.
2. `GET /api/currencies` (Bearer READ-роль) → **200** (чтение разрешено).
3. `POST /api/currencies` (Bearer READ-роль) → **403**.
4. `PUT /api/currencies/{id}` (Bearer READ-роль) → **403**.
5. `DELETE /api/currencies/{id}` (Bearer READ-роль) → **403**.

**Ожидаемый результат:** роль с грантом READ читает справочник, но операции записи запрещены с 403.

**Teardown набора:** удалить валюту `CU{run-id}A` (если не удалена в TC-ABAC-02), разлогинить выданные токены.

# Часть B. Браузерные (UI) сценарии

## Фича UI-1. Страница «Валюты» (/currencies)

Проверяет рендер, поиск/сортировку/фильтр, CRUD через UI, пермишн-гейтинг и i18n админ-страницы на базе общего `DataTable`. Покрывает R6.1–R6.7, R7.1.

**Стратегия повторяемости:** генератор `code = cu{run-id}` (уникальный код на каждый прогон) + teardown (удалить созданные валюты через UI-диалог удаления в конце набора). Кейсы «только чтение» (открытие страницы, поиск/сортировка/фильтр по сид-данным, i18n, пермишн-гейтинг READ-роли) teardown не требуют.

### TC-UI-01 — Открытие страницы и рендер таблицы

**Предусловия:** выполнен TC-UI-SETUP-01.

**Шаги:**
1. Перейти на `http://localhost:3000/currencies`.
2. Дождаться загрузки таблицы (`DataTable` для `entityKey="currencies"`).
3. Проверить заголовок страницы (`currencies.pageTitle`, локализованный, не сырой ключ).
4. Проверить, что таблица содержит колонки `code`, `symbol`, `name` и `active`.
5. Проверить, что колонка `active` отображается локализованным бейджем (Активна/Неактивна), а не булевым `true/false`.
6. Убедиться, что в списке присутствуют три сид-валюты: `PLN` (`zł`), `EUR` (`€`), `USD` (`$`).

**Ожидаемый результат:** страница открыта, таблица отрендерена с колонками code/symbol/name/active, бейдж активности локализован, три сид-валюты видны с их символами.

### TC-UI-02 — Поиск, сортировка и фильтрация (общий DataTable)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**
1. Ввести в поиск подстроку имени/кода существующей валюты (например `EUR` или часть `nameRU`/`namePL`) → список сокращается до совпадающих строк.
2. Очистить поиск → список восстанавливается.
3. Кликнуть заголовок колонки `code` для сортировки → порядок строк меняется по `code` (asc), повторный клик — desc; запрос сортировки уходит на бэкенд (серверная сортировка `sort=code,...`).
4. Кликнуть заголовок колонки `name` для сортировки → порядок меняется по локализованному `name`; запрос `sort=name,...` уходит на бэкенд.
5. Применить фильтр по колонке (например `name` contains или `symbol`) → список сужается до строк, удовлетворяющих условию.
6. Снять фильтр → список восстанавливается.

**Ожидаемый результат:** поиск, сортировка и фильтр корректно сокращают/меняют список; сортировка выполняется на бэкенде (не клиентская).

### TC-UI-03 — Создание валюты через форму-sheet

4. Нажать «Сохранить».
5. Дождаться закрытия sheet и появления тоста успеха (`currencies.toast.createSuccess`).

**Ожидаемый результат:** валюта создана через UI, показан тост успеха, новая строка присутствует в таблице.

### TC-UI-04 — Валидация формы создания (пустые обязательные поля)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**

2. Оставить `code` пустым, попытаться отправить форму → отображается инлайновая ошибка валидации у поля `code` (локализованная, `currencies.validation.*`), сабмит заблокирован (запрос на бэкенд не уходит).
3. Заполнить `code`, но оставить пустым `symbol` → инлайновая ошибка у поля `symbol`, сабмит заблокирован.
4. Заполнить `symbol`, но оставить пустым `nameRU` (и/или `namePL`) → инлайновая ошибка у соответствующего поля имени, сабмит заблокирован.

**Ожидаемый результат:** при пустых обязательных полях (`code`, `symbol`, `nameRU`, `namePL`) показываются инлайновые локализованные ошибки, отправка формы заблокирована.

## Регрессия

Небольшой регрессионный набор: перепроверка сквозного сида и ABAC-гарда, а также отсутствия влияния на смежные ресурсы.

**Стратегия повторяемости:** только чтение — teardown не требуется.

### TC-REG-01 — Сид-валюты на месте после повторного прогона

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/currencies?size=1000` (Bearer ADMIN) → **200**; все три сид-кода присутствуют (см. TC-SEED-01) — сид идемпотентен, дубликатов нет.
2. Убедиться, что число элементов с сид-кодами не выросло между прогонами (по одному экземпляру каждого кода `PLN`/`EUR`/`USD`).

**Ожидаемый результат:** сид стабилен и идемпотентен, дубликаты не появляются.

### TC-REG-02 — ABAC-гард по-прежнему действует

**Предусловия:** нет.

**Шаги:**
1. `GET /api/currencies` без токена → **401** (гард сохранён).

**Ожидаемый результат:** защита эндпоинта не регрессировала.

### TC-REG-03 — Смежные ресурсы не затронуты

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/roles` (Bearer ADMIN) → **200**; список ролей не изменён появлением нового ресурса.
2. `GET /api/resources` (Bearer ADMIN) → **200**; присутствует новый ресурс `CURRENCIES` наряду с ранее существующими (`MEASUREMENT_UNITS`, `USERS`, `AUDIT`, `PROJECT_MEMBERS` и т.д.), прежние ресурсы на месте.

**Ожидаемый результат:** добавление `CURRENCIES` не сломало и не удалило смежные ресурсы/роли.
