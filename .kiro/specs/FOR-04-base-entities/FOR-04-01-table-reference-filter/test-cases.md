# Тест-кейсы: FOR-04-01 — Фильтрация таблиц по связанным сущностям

## Назначение и характер спеки

Спека **смешанная**: есть и API-поверхность (метаданные с reference-дескриптором, options-эндпоинт, фильтры `role.id==` / `role.id=in=(...)`), и браузерные экраны (выпадающий reference-фильтр в таблице). Поэтому тест-кейсы двух типов:

- **API-кейсы** — HTTP-запросы против поднятого в Docker приложения (`http://localhost:8080`). Результат прогона — MD-репорт с таблицами (шаг → запрос → ожидание → факт → статус).
- **UI-кейсы** — сценарии для браузерного движка (headless-браузер): переходы, ввод, клики, ожидания. Результат прогона — MD-репорт с таблицами (шаг → действие → ожидание → факт → статус), без скриншотов.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase`, `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL API: `http://localhost:8080`. Frontend: `http://localhost:3000`.
3. Первый ADMIN: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
4. Токен — через `POST /api/auth/login`, заголовок `Authorization: Bearer <accessToken>`.
5. Локаль ответов — через `Accept-Language: ru|pl`.

## Стратегия повторяемости

**Комбинированная — генератор + teardown.** На каждый прогон `run-id` (timestamp/uuid). Создаваемые сущности уникальны: роли `TESTROLE_{run-id}_{seq}`, пользователи `refflt+{run-id}+{seq}@example.com`. Teardown в конце набора: разлогинить (`POST /api/auth/logout`), удалить созданных пользователей (`/api/users`) и несистемные роли (`DELETE /api/roles/{id}`). Системные роли/справочники не меняются.

### Предусловие-хелпер: набор ролей для фильтра

Логин ADMIN → создать N несистемных ролей с именами, дающими предсказуемый алфавитный порядок (например `TESTROLE_{run-id}_A`, `_B`, `_C`) → создать пользователей с этими ролями → использовать их в кейсах фильтрации.

---

## Фича 1. Reference-дескриптор в метаданных (API, Req 1)

### TC-META-01 — Метаданные Users содержат reference-дескриптор для поля role
Предусловия: ADMIN залогинен.
1. `GET /api/users/metadata` (ADMIN) → 200; поле `role` имеет reference: `idPath=role.id`, `targetResource=ROLES`, `optionsPath=/api/roles`, `labelField=name`, `labelI18n=true`. (Req 1.1, 1.2, 1.3)

### TC-META-02 — Скалярные поля без reference-дескриптора
1. `GET /api/users/metadata` → 200; у `email`/`name` `reference=null`; атрибуты `name`/`dataType`/`i18n`/`nested` не изменены. (Req 1.4, 1.5)

---

## Фича 2. Options-эндпоинт: порядок, поиск, пагинация, доступ (API, Req 2)

Предусловия набора: созданы роли `_A`, `_B`, `_C` (хелпер).

### TC-OPT-01 — Опции по имени, asc, в локали
1. Логин ADMIN → 200.
2. `GET /api/roles?sort=name,asc&page=0&size=100` c `Accept-Language: ru` → 200; локализованные имена по возрастанию; `_A`,`_B`,`_C` в этом порядке. (Req 2.1, 2.3)

### TC-OPT-02 — Бекенд-поиск по подстроке имени (case-insensitive)
1. `GET /api/roles?query=name=ct=testrole_{run-id}&sort=name,asc` → 200; вернулись только роли прогона; регистр не важен. (Req 2.2, 2.3)

### TC-OPT-03 — Пагинация (инфинит-скролл)
1. `GET /api/roles?sort=name,asc&page=0&size=1` → 200; `content.length==1`, `last==false`, `totalPages>1`.
2. `GET /api/roles?sort=name,asc&page=1&size=1` → 200; другая запись. (Req 2.4)

### TC-OPT-04 — Доступ к опциям по READ целевого ресурса
1. `GET /api/roles` без токена → 401.
2. Токеном роли без гранта `ROLES/READ` → 403 `error.access.denied`.
3. Токеном роли с `ROLES/READ` или ADMIN → 200. (Req 2.5)

## Фича 3. Фильтр по связанной сущности — запросы (API, Req 3, 4, 5)

Предусловия: пользователи с ролями `_A` (u1), `_B` (u2), `_C` (u3) (хелпер).

### TC-FLT-01 — Single: `role.id==<idA>`
1. `GET /api/users?query=role.id=={idA}` (ADMIN) → 200; в выдаче есть u1, нет u2/u3. (Req 3.4)

### TC-FLT-02 — Multi: `role.id=in=(<idA>,<idB>)`
1. `GET /api/users?query=role.id=in=({idA},{idB})` → 200; есть u1 и u2, нет u3. (Req 4.2)

### TC-FLT-03 — Один элемент в multi сворачивается в ==
1. Эмиттер/клиент при одном выбранном id формирует `role.id=={id}` (а не `=in=({id})`); проверяется как UI-кейс (TC-UI-05) и/или юнит-тестом эмиттера. (Req 4.3)

### TC-FLT-04 — Композиция с другим фильтром через AND
1. `GET /api/users?query=role.id=={idA};name=ct=refflt` (или актуальный AND-разделитель) → 200; только пользователи с ролью A и подходящим именем. (Req 5.2)

### TC-FLT-05 — Пустой выбор → нет фрагмента
1. Без reference-фильтра `GET /api/users` → 200 (полный список по правам). (Req 3.5, 4.4)

## Фича 4. Reference-фильтр в таблице — UI (браузерный движок, Req 3, 4, 6)

Предусловия: залогинен ADMIN в вебе (`/login`), открыта таблица Users; созданы роли `_A`/`_B`/`_C` и пользователи с ними.

### TC-UI-01 — Reference-фильтр рендерится для колонки Role
1. Открыть `/users`, вызвать фильтр колонки Role → отображается reference-дропдаун (не текстовый/enum фильтр). (Req 3.1, 5.1)

### TC-UI-02 — Инфинит-скролл и алфавитный порядок
1. Открыть дропдаун Role → грузится 1-я страница опций, порядок по локали (asc).
2. Проскроллить в конец списка → подгружается следующая страница. (Req 3.2, 6.3)

### TC-UI-03 — Бекенд-поиск (debounced)
1. Ввести в поиск дропдауна `TESTROLE_{run-id}_A` → после дебаунса запрос `?query=name=ct=...`, список сузился до совпадений, страница сброшена на 0. (Req 3.3)

### TC-UI-04 — Single select фильтрует таблицу
1. Выбрать роль `_A` → таблица показывает только пользователей с ролью A; выбранное значение отображается локализованным именем. (Req 3.4, 3.6)

### TC-UI-05 — Clear убирает фильтр
1. Очистить выбор → таблица возвращается к нефильтрованному по этой колонке состоянию. (Req 3.5)

### TC-UI-06 — Multi select (чекбоксы) → in
1. Переключить дропдаун в multi, отметить `_A` и `_B` → таблица показывает пользователей с A или B (фильтр `role.id=in=(...)`).
2. Снять до одного выбранного → фильтр сворачивается в `role.id==<id>`. (Req 4.1, 4.2, 4.3)

### TC-UI-07 — Тоггл single/multi сохраняет совместимый выбор
1. В single выбрана `_A` → переключить в multi → `_A` остаётся отмеченной; поведение поиска/скролла/порядка идентично. (Req 4.5, 4.6)

### TC-UI-08 — Деградация при отсутствии READ на целевой ресурс
1. Залогиниться ролью без `ROLES/READ`, открыть таблицу с reference-колонкой Role → дропдаун опций отключён/пуст с локализованной подсказкой, сама таблица грузится. (Req 5.5)

### TC-UI-09 — Локализация UI-хрома фильтра (PL/RU)
1. Переключить язык RU/PL → плейсхолдер поиска, loading, empty-state, select/clear, тоггл single/multi локализованы; порядок опций совпадает с языком. (Req 6.1, 6.2, 6.3, 6.4)

### TC-UI-10 — Таблица без reference-полей не изменилась
1. Открыть таблицу без `@ManyToOne`/`@OneToOne` полей → фильтры как раньше, reference-дропдаун не появляется. (Req 5.3)

---

## Teardown (в конце каждого прогона)

1. Разлогинить созданных пользователей (`POST /api/auth/logout`).
2. Удалить/деактивировать созданных пользователей (`/api/users`).
3. Удалить созданные несистемные роли (`DELETE /api/roles/{id}`).
4. Проверить отсутствие остаточных сущностей с текущим `run-id`. Системные роли/справочники не трогались.

---

## Регрессия

### REG-01 — Обратная совместимость метаданных
Существующие потребители метаданных не ломаются: `name`/`dataType`/`i18n`/`nested` присутствуют; `reference` — дополнительное необязательное поле. _Покрывает: TC-META-02._

### REG-02 — Существующие фильтры таблиц работают
Текстовый/enum/числовой/датовый фильтры и их AND-композиция не изменились; таблицы без reference-полей ведут себя как раньше. _Покрывает: TC-FLT-04, TC-UI-10._

### REG-03 — Доступ к опциям соответствует ABAC
Options-эндпоинт защищён READ целевого ресурса (401/403/200). _Покрывает: TC-OPT-04, TC-UI-08._

### REG-04 — Локализация PL/RU
Имена опций и UI-хром фильтра локализованы, порядок совпадает с языком. _Покрывает: TC-UI-09, TC-OPT-01._
