# Тест-кейсы — FOR-04-01: Фильтрация таблиц по ссылочным сущностям

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерные экраны**, поэтому набор тест-кейсов делится на две части:

- **API-тесты** против поднятого docker-стека (метаданные ссылочного дескриптора, эндпоинт опций с сортировкой/поиском/пагинацией/правами, фильтрация `role.id==` и `role.id~in~`).
- **Браузерные (UI) сценарии** для ссылочного выпадающего списка (infinite scroll, поиск, single/multi select, очистка, переключение режима) и для мобильных/табличных UX-фиксов (Requirement 7).

Результат прогона — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус). Скриншоты не требуются.

> **Важно про операторы запроса.** Реальная грамматика запросов проекта использует операторы, обёрнутые тильдами (подтверждено в задачах 3.x и зафиксировано в `design.md`), а НЕ RSQL-стиль `=ct=`/`=in=(...)`:
> - равенство: `==` (например `role.id==5`);
> - содержит (регистронезависимо): `~ct~` (например `name~ct~foreman`);
> - вхождение в множество: `~in~` с перечислением через запятую **без скобок** (например `role.id~in~5,7`);
> - композиция условий — ключевым словом `AND` (например `role.id==5 AND name~ct~ivan`).
>
> Во всех API-шагах ниже используются именно эти символы.

---

## Окружение и запуск

Docker-стек (`docker compose up` в корне репозитория) поднимает:

- `postgres` (:5432);
- `liquibase` (миграции changelog);
- `backend` (:8080, профиль `docker`);
- `frontend` (:3000).

Базовый URL для API-тестов: `http://localhost:8080`. Auth-эндпоинты — под `/api/auth`.

Первый ADMIN поднимается переменными окружения: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.

### Получение токена (общий Setup для API-кейсов)

1. `POST /api/auth/login` с телом `{ "email": "<FOREMEN_ADMIN_EMAIL>", "password": "<FOREMEN_ADMIN_PASSWORD>" }`.
2. Из ответа `200` извлечь `accessToken` → далее передавать заголовком `Authorization: Bearer <accessToken>`.

Заголовок локали: `Accept-Language: ru` (или `pl` — для проверки локализованной сортировки/меток).

---

## Стратегия повторяемости

Каждый набор кейсов ниже явно указывает свою стратегию. Общие правила по спеке:

- **Генератор данных (run-id):** для всех создаваемых сущностей (роли, пользователи) в имени/коде/email использовать уникальный суффикс `{run-id}` — timestamp или uuid, например роль с кодом `ROLE_{run-id}` и `nameRU`/`namePL`, содержащими токен `refflt{run-id}`; пользователь с email `test+{run-id}@example.com`.
- **Teardown:** в конце сценариев, создающих данные, удалить/деактивировать созданные сущности (сначала пользователей, затем роли — из-за FK) либо оставить их «промаркированными» уникальным `{run-id}`, чтобы прогон не зависел от чистки БД.
- Прогон **не должен** требовать ручной очистки БД: за счёт `{run-id}` поиск/фильтры находят только сущности текущего прогона.

Метаданные/пермишн-кейсы (не создают доменных данных) повторяемы без чистки по своей природе.

# Часть A. API-тесты (docker-стек)

## Группа A1 — Метаданные: ссылочный дескриптор (Requirement 1)

**Стратегия повторяемости:** запросы к метаданным без создания данных — повторяемы «как есть», чистка не требуется.

### TC-A1-01 — `role` в метаданных Users помечен как ссылочный дескриптор

**Предусловия:** есть токен ADMIN (см. общий Setup).

**Шаги:**
1. `GET /api/users/metadata` с `Authorization: Bearer <admin>` и `Accept-Language: ru`.
   - Ожидание: `200`; тело содержит массив `fields`.
2. Найти в `fields` элемент с `name == "role"`.
   - Ожидание: у поля присутствует объект `reference` (не `null`).
3. Проверить поля дескриптора `reference`.
   - Ожидание: `targetResource == "ROLES"`, `optionsPath == "/api/roles"`, `labelField == "name"`, `labelI18n == true`, `idPath == "role.id"`.
4. Проверить, что базовые поля метадаты сохранены.
   - Ожидание: у поля `role` по-прежнему присутствуют `name`, `dataType`, `i18n`, `nested` (обратная совместимость, Req 1.5).

**Ожидаемый результат:** ссылочный дескриптор для `role` корректен и дополняет, а не заменяет существующую метадату.

### TC-A1-02 — Скалярное поле НЕ имеет ссылочного дескриптора (обратная совместимость)

**Предусловия:** токен ADMIN.

**Шаги:**
1. `GET /api/users/metadata`.
   - Ожидание: `200`.
2. Найти скалярное поле (например `email` или `firstName`).
   - Ожидание: у поля `reference` отсутствует или равен `null` (Req 1.4).
3. Убедиться, что структура `name`/`dataType`/`i18n`/`nested` у скалярного поля не изменилась.
   - Ожидание: поля присутствуют в прежнем виде.

**Ожидаемый результат:** дескриптор эмитится только для `@ManyToOne`/`@OneToOne`, у скаляров метадата без изменений.

## Группа A2 — Эндпоинт опций: сортировка / поиск / пагинация / права (Requirement 2)

**Стратегия повторяемости:** генератор `{run-id}` для создаваемых ролей + teardown в конце. Поиск ведётся по токену `refflt{run-id}`, поэтому прогоны не мешают друг другу.

### Setup для группы A2 (генератор данных)

1. Создать 3 роли через `POST /api/roles` (ADMIN), где локализованные имена начинаются с разных букв в нужном порядке, но все содержат токен `refflt{run-id}`, например:
   - `nameRU = "Alpha refflt{run-id}"`, `namePL = "Alpha refflt{run-id}"`;
   - `nameRU = "Beta refflt{run-id}"`;
   - `nameRU = "Gamma refflt{run-id}"`.
   - Ожидание: три `201`/`200`, сохранить их `id`.

### TC-A2-01 — Опции отсортированы по локализованному имени (asc)

**Предусловия:** выполнен Setup A2; токен ADMIN; `Accept-Language: ru`.

**Шаги:**
1. `GET /api/roles?sort=name,asc&query=name~ct~refflt{run-id}&page=0&size=50`.
   - Ожидание: `200`; в `content` присутствуют созданные роли.
2. Проверить порядок ролей текущего прогона в ответе.
   - Ожидание: `Alpha…` → `Beta…` → `Gamma…` (по возрастанию локализованного имени, Req 2.1, 2.3).

**Ожидаемый результат:** список опций отсортирован по имени в локали вызывающего.

### TC-A2-02 — Регистронезависимый поиск «содержит»

**Предусловия:** выполнен Setup A2; токен ADMIN.

**Шаги:**
1. `GET /api/roles?sort=name,asc&query=name~ct~ALPHA refflt{run-id}&page=0&size=50` (термин в верхнем регистре).
   - Ожидание: `200`; в результате присутствует роль `Alpha refflt{run-id}` (совпадение регистронезависимо, Req 2.2).
2. `GET /api/roles?sort=name,asc&query=name~ct~refflt{run-id}` (общий токен прогона).
   - Ожидание: `200`; возвращаются все 3 роли прогона, сортировка по имени сохранена.

**Ожидаемый результат:** поиск нечувствителен к регистру и сохраняет сортировку.

### TC-A2-03 — Пагинация сообщает о наличии следующих страниц

**Предусловия:** выполнен Setup A2 (3 роли прогона); токен ADMIN.

**Шаги:**
1. `GET /api/roles?sort=name,asc&query=name~ct~refflt{run-id}&page=0&size=2`.
   - Ожидание: `200`; `content` содержит 2 элемента; `totalElements >= 3`; `last == false` (есть ещё страницы, Req 2.4).
2. `GET /api/roles?sort=name,asc&query=name~ct~refflt{run-id}&page=1&size=2`.
   - Ожидание: `200`; `content` содержит оставшийся элемент; `last == true`; `number == 1`.

**Ожидаемый результат:** пагинация корректно раскрывает наличие следующих страниц (для infinite scroll).

### TC-A2-04 — Эндпоинт опций защищён правом READ целевого ресурса

**Предусловия:** токен ADMIN; отдельно — пользователь без гранта `ROLES/READ` (создать роль без грантов на `ROLES` и пользователя с этой ролью — через генератор `{run-id}`), его `accessToken`.

**Шаги:**
1. `GET /api/roles?page=0&size=10` **без** заголовка `Authorization`.
   - Ожидание: `401` (нет токена, Req 2.5).
2. `GET /api/roles?page=0&size=10` с токеном пользователя **без** гранта `ROLES/READ`.
   - Ожидание: `403` (нет права, Req 2.5).
3. `GET /api/roles?page=0&size=10` с токеном ADMIN (или пользователя с грантом).
   - Ожидание: `200`.

**Ожидаемый результат:** доступ к опциям контролируется существующим правом `ROLES/READ`.

### Teardown группы A2

1. Удалить/деактивировать созданного пользователя без гранта (если создавался).
2. Удалить созданные роли прогона (`DELETE /api/roles/{id}` для трёх ролей и роли-без-грантов).
   - Ожидание: `200`/`204`. При невозможности удаления — сущности остаются промаркированы `{run-id}` и не мешают следующим прогонам.

## Группа A3 — Сквозная фильтрация по ссылке (Requirements 3.4, 4.2, 5.2)

**Стратегия повторяемости:** генератор `{run-id}` — создаём 2 роли и пользователей, ссылающихся на них; teardown в конце.

### Setup для группы A3 (генератор данных)

1. Создать роль R1 (`nameRU = "R1 refflt{run-id}"`) и роль R2 (`nameRU = "R2 refflt{run-id}"`) через `POST /api/roles` → сохранить `id1`, `id2`.
2. Создать пользователей через `POST /api/users` с генератором email:
   - U1 `test+u1-{run-id}@example.com` с ролью `id1`;
   - U2 `test+u2-{run-id}@example.com` с ролью `id2`;
   - U3 `test+u3-{run-id}@example.com` с ролью `id1`.
   - Ожидание: три успешных создания, сохранить `id` пользователей.

### TC-A3-01 — Фильтр по одному значению `role.id==<id>`

**Предусловия:** выполнен Setup A3; токен ADMIN.

**Шаги:**
1. `GET /api/users?query=role.id==<id1>&page=0&size=50`.
   - Ожидание: `200`; в `content` присутствуют U1 и U3 (роль `id1`) и отсутствует U2 (Req 3.4).
2. Проверить, что все возвращённые пользователи прогона имеют `role.id == id1`.
   - Ожидание: условие выполняется для всех строк текущего прогона.

**Ожидаемый результат:** фильтр `==` возвращает только пользователей с указанной ролью.

### TC-A3-02 — Фильтр по множеству `role.id~in~<id1>,<id2>`

**Предусловия:** выполнен Setup A3; токен ADMIN.

**Шаги:**
1. `GET /api/users?query=role.id~in~<id1>,<id2>&page=0&size=50`.
   - Ожидание: `200`; в `content` присутствуют U1, U2 и U3 (обе роли, Req 4.2).
2. Проверить, что все пользователи прогона имеют `role.id` в множестве `{id1, id2}`.
   - Ожидание: условие выполняется.

**Ожидаемый результат:** фильтр `~in~` (через запятую, без скобок) возвращает пользователей с любой из ролей.

### TC-A3-03 — Композиция фильтров через `AND`

**Предусловия:** выполнен Setup A3; токен ADMIN. У U1 имя/поле, по которому применим `~ct~` (например `firstName` содержит `u1`).

**Шаги:**
1. `GET /api/users?query=role.id==<id1> AND firstName~ct~u1&page=0&size=50` (подставить реальное текстовое поле пользователя).
   - Ожидание: `200`; в `content` присутствует только U1 (роль `id1` И совпадение по тексту), отсутствуют U2, U3 (Req 5.2).

**Ожидаемый результат:** ссылочный фильтр корректно комбинируется с текстовым через `AND` в один `query`.

### Teardown группы A3

1. Удалить пользователей U1–U3 (`DELETE /api/users/{id}`).
2. Удалить роли R1, R2 (`DELETE /api/roles/{id}`).
   - Ожидание: `200`/`204`. Иначе — сущности остаются промаркированы `{run-id}`.

# Часть B. Браузерные (UI) сценарии

> Исполняются браузерным движком (headless / browser automation) против фронтенда на `http://localhost:3000`. Результат — MD-репорт с таблицами (шаг → действие → ожидание → факт → статус).

## Группа B1 — Ссылочный выпадающий список на колонке Role (Requirements 3, 4, 5, 6)

**Стратегия повторяемости:** генератор `{run-id}` — создать несколько ролей (>1 страницы для infinite scroll) с токеном `refflt{run-id}`; teardown в конце. UI-фильтрация не изменяет данные, поэтому повторный прогон безопасен.

**Общий предусловие-Setup:** авторизоваться в UI как ADMIN, перейти на таблицу Users, открыть панель фильтров, найти фильтр колонки Role.

### TC-B1-01 — Открытие списка: первая страница, алфавитный порядок

**Шаги:**
1. Открыть выпадающий список фильтра Role.
   - Ожидание: загружается первая страница опций; отображается индикатор загрузки, затем список ролей (Req 3.2).
2. Проверить порядок.
   - Ожидание: опции отсортированы по локализованному имени по возрастанию (Req 6.3).

**Ожидаемый результат:** список открывается, показывает первую страницу в алфавитном порядке локали.

### TC-B1-02 — Infinite scroll подгружает следующую страницу

**Предусловия:** ролей больше одной страницы (обеспечить Setup-генератором).

**Шаги:**
1. Прокрутить список опций до конца.
   - Ожидание: подгружается следующая страница опций (infinite scroll), список расширяется (Req 3.2).

**Ожидаемый результат:** при скролле к концу подгружаются новые опции без перезагрузки.

### TC-B1-03 — Бэкенд-поиск (debounced)

**Шаги:**
1. Ввести в поле поиска токен `refflt{run-id}`.
   - Ожидание: после debounce выполняется запрос к эндпоинту опций с `query=name~ct~refflt{run-id}`, список сбрасывается на первую страницу и показывает совпадения (Req 3.3).
2. Ввести заведомо несуществующий термин.
   - Ожидание: показывается локализованный empty-state (Req 6.4).

**Ожидаемый результат:** поиск идёт на бэкенде, регистронезависимо, с корректным empty-state.

### TC-B1-04 — Single-select применяет `role.id==<id>`

**Шаги:**
1. В режиме single выбрать одну роль.
   - Ожидание: выпадающий список закрывается; таблица обновляется; активный фильтр — `role.id==<id>` (Req 3.4).
2. Проверить отображение выбранного значения.
   - Ожидание: показано локализованное имя выбранной роли (Req 3.6).

**Ожидаемый результат:** одиночный выбор фильтрует таблицу по равенству.

### TC-B1-05 — Очистка выбора убирает фильтр

**Предусловия:** применён single-фильтр (TC-B1-04).

**Шаги:**
1. Нажать «очистить».
   - Ожидание: фильтр по колонке Role снимается; таблица возвращается к состоянию без этого фильтра (Req 3.5, 4.4).

**Ожидаемый результат:** очистка снимает ссылочный фильтр и обновляет таблицу.

### TC-B1-06 — Multi-select применяет `role.id~in~<id1>,<id2>`

**Шаги:**
1. Переключить режим в multi (чекбоксы у опций, Req 4.1).
2. Отметить две роли.
   - Ожидание: таблица обновляется; активный фильтр — `role.id~in~<id1>,<id2>` (Req 4.2).
3. Снять одну из двух отметок (остаётся одна).
   - Ожидание: фильтр схлопывается до `role.id==<id>` (Req 4.3).

**Ожидаемый результат:** множественный выбор эмитит `~in~`, а один выбранный — равенство.

### TC-B1-07 — Переключение режима сохраняет совместимый выбор

**Шаги:**
1. В single выбрать роль, затем переключить в multi.
   - Ожидание: ранее выбранная роль остаётся отмеченной (Req 4.5).
2. Переключить обратно в single.
   - Ожидание: выбор сохраняется, где совместимо; переэмитится корректное выражение фильтра.

**Ожидаемый результат:** тумблер single/multi сохраняет совместимый выбор.

### TC-B1-08 — Деградация при отсутствии права READ на ROLES (403)

**Предусловия:** войти в UI под пользователем без гранта `ROLES/READ`.

**Шаги:**
1. Открыть фильтр колонки Role.
   - Ожидание: контрол отрисован как отключённый с локализованной подсказкой «нет доступа»; таблица при этом загружается (Req 5.5).

**Ожидаемый результат:** отсутствие права не ломает таблицу — фильтр деградирует «мягко».

### Teardown группы B1

Удалить созданные Setup-ом роли `refflt{run-id}` через API (или UI). При невозможности — они остаются промаркированы `{run-id}`.

## Группа B2 — Мобильные и табличные UX-фиксы DataTable (Requirement 7)

**Стратегия повторяемости:** данные не создаются (используются существующие строки таблицы); прогон повторяем «как есть». Для гарантированного наличия строк можно один раз выполнить Setup генератором `{run-id}` из группы A3 и teardown после.

**Общий предусловие-Setup:** открыть таблицу (Users) в мобильном брейкпоинте браузера (эмуляция узкого экрана).

### TC-B2-01 — Метка тумблера фильтров локализована (нет сырого ключа)

**Шаги:**
1. Открыть таблицу, посмотреть на тумблер фильтров.
   - Ожидание: отображается локализованная строка, а не сырой ключ `dataTable.filters.toggle` (Req 7.1).
2. Проверить в локалях RU и PL.
   - Ожидание: в обеих локалях метка резолвится; сырых i18n-ключей в UI нет.

**Ожидаемый результат:** все контролы DataTable имеют локализованные метки.

### TC-B2-02 — Контролы внутри развёрнутой панели фильтров кликабельны

**Шаги:**
1. Развернуть панель фильтров.
2. Кликнуть/ввести во все контролы: текстовый инпут, выпадающие списки, чекбоксы, ссылочный фильтр, кнопки apply/clear.
   - Ожидание: все контролы получают клики и изменяют состояние фильтра; нет перекрывающего оверлея / z-index-ловушки / `pointer-events:none` (Req 7.2, 7.9).

**Ожидаемый результат:** развёрнутая панель полностью интерактивна.

### TC-B2-03 — Sticky-регионы: поиск/тумблер сверху, пагинация снизу при скролле середины списка

**Предусловия:** в таблице достаточно строк для скролла.

**Шаги:**
1. Прокрутить тело таблицы к середине списка (не крайние позиции).
   - Ожидание: строка поиска и тумблер фильтров остаются закреплёнными сверху; пагинация — закреплённой снизу (Req 7.5).
2. Повторить на мобильном и десктопном брейкпоинтах.
   - Ожидание: sticky-поведение работает на мобильном; десктопная раскладка не регрессирует (Req 7.8).

**Ожидаемый результат:** верхние контролы и пагинация видны из любой точки скролла.

### TC-B2-04 — Единообразная высота и выравнивание карточек (мобайл), плейсхолдер «—»

**Предусловия:** в списке есть строки с разной заполненностью полей (часть значений пустые).

**Шаги:**
1. Просмотреть список карточек.
   - Ожидание: карточки имеют единообразную высоту и согласованное выравнивание меток и значений (Req 7.4).
2. Найти карточку с пустым значением поля.
   - Ожидание: пустое значение отрисовано плейсхолдером «—»; высота/выравнивание не зависят от заполненности.

**Ожидаемый результат:** карточки единообразны по высоте и выравниванию, пустые значения показывают «—».

### TC-B2-05 — Apply → сворачивание → сводка применённого (счётчики)

**Шаги:**
1. Ввести один фильтр и выбрать одну сортировку, нажать Apply.
   - Ожидание: панель фильтров сворачивается (тумблер возвращается в закрытое состояние, Req 7.6).
2. Проверить сводку в шапке.
   - Ожидание: показана локализованная сводка вида «N фильтров · M сортировок» с корректными счётчиками (ссылочный фильтр с ≥1 выбранным id считается за 1 фильтр); плюрализация корректна в RU/PL.

**Ожидаемый результат:** после применения панель сворачивается и показывает сводку с верными счётчиками.

### TC-B2-06 — Сводка переоткрывает панель и позволяет «очистить всё»

**Предусловия:** есть применённые фильтры/сортировки (TC-B2-05).

**Шаги:**
1. Кликнуть по сводке.
   - Ожидание: панель фильтров разворачивается для просмотра/изменения (Req 7.7).
2. Нажать «Очистить всё» из свёрнутого состояния сводки.
   - Ожидание: все фильтры и сортировки сбрасываются, таблица обновляется (Req 7.7).

**Ожидаемый результат:** сводка является контролом переоткрытия и очистки.

### TC-B2-07 — UX сортировки (asc/desc, `sort=field,dir`)

**Шаги:**
1. Выбрать сортировку по колонке по возрастанию.
   - Ожидание: применяется `sort=<field>,asc`; активное направление отражено в UI-индикаторе (Req 7.3).
2. Переключить на убывание.
   - Ожидание: применяется `sort=<field>,desc`; индикатор обновляется.
3. Добавить вторую сортировку (мульти-сорт).
   - Ожидание: добавляется второй параметр `sort=...`; счётчик сортировок в сводке увеличивается.

**Ожидаемый результат:** явный контрол сортировки маппится на `sort=field,dir` и отражается в сводке.

### TC-B2-08 — Ссылочный фильтр работает внутри свёрнуто/раскрываемой панели на мобильном

**Шаги:**
1. На мобильном раскрыть панель фильтров и открыть ссылочный фильтр Role.
   - Ожидание: infinite scroll и бэкенд-поиск работают внутри скролл-контекста панели (Req 7.9).

**Ожидаемый результат:** ссылочный фильтр (Req 3–6) полностью функционален внутри мобильной панели фильтров.

# Регрессия

**Стратегия повторяемости:** без создания данных (кроме генератора там, где явно указано) — повторяемо «как есть».

### TC-REG-01 — Таблица без ссылочных полей не изменилась

**Шаги:**
1. Открыть таблицу, метадата которой не содержит ссылочных полей (или проверить `GET /api/{resource}/metadata` без `reference`).
   - Ожидание: таблица рендерится как до фичи; ссылочные контролы не появляются; поведение фильтров/сортировки прежнее (Req 5.3).

### TC-REG-02 — Обратная совместимость метаданных

**Шаги:**
1. `GET /api/users/metadata`.
   - Ожидание: у всех полей сохранены `name`/`dataType`/`i18n`/`nested`; `reference` добавлен только для `@ManyToOne`/`@OneToOne` (Req 1.4, 1.5).

### TC-REG-03 — Существующие текстовые/enum-фильтры и AND-композиция не сломаны

**Шаги:**
1. Применить существующий текстовый фильтр (`name~ct~...`) без ссылочного.
   - Ожидание: работает как прежде.
2. Скомбинировать ссылочный и текстовый фильтр (`role.id==<id> AND name~ct~<term>`).
   - Ожидание: композиция через `AND` возвращает корректный результат (Req 5.2).

### TC-REG-04 — Десктопная раскладка DataTable не регрессировала

**Шаги:**
1. Открыть таблицу на десктопном брейкпоинте.
   - Ожидание: sticky-хедер, тело со скроллом, фиксированный футер работают; прежняя desktop-раскладка сохранена (Req 7.8).
