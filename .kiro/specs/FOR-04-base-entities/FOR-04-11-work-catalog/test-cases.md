# Тест-кейсы: FOR-04-11 Work Catalog (каталог работ, сущность WorkItem)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерный экран**: каталог работ раздаётся через REST `/api/work-items` **и** через админ-страницу CRUD по маршруту `/catalog/works` (страница + её роут поставляются в этой спеке; группа меню «Каталог» — отдельно в FOR-04-15). В отличие от плоских справочников, `WorkItem` содержит ДВА внешних ключа: `workCategory` (→ WorkCategory) и `unit` (→ MeasurementUnit). Набор тест-кейсов включает **оба типа**:

- **Часть A. API-тесты** — против работающего в Docker приложения. Каждый шаг — HTTP-запрос к `/api/work-items`.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда `http://localhost:3000`, browser automation / headless, под ролью ADMIN.

Результат прогона для обеих частей — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус). **Скриншоты не требуются.**

Покрываемые требования: R1 (сущность/таблица с FK), R2 (CRUD с FK-полями, i18n, reference-фильтр, metadata), R3 (ABAC-ресурс и гранты, **MANAGER CRU без DELETE, FINANCIER READ, CLIENT none**), R4 (нет дефолтного сида позиций — сидятся в FOR-04-12), R6 (админ-страница CRUD с reference-колонками), R7 (UI-тесты).

## Запуск окружения

1. В корне репозитория: `docker compose up` — `postgres` (:5432), `liquibase`, `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`; auth — под `/api/auth`.
3. Первый ADMIN — через `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
4. Дождаться готовности `backend` и завершения миграций перед прогоном.
5. **Предзависимость по данным:** для создания WorkItem нужны существующие `WorkCategory` (засижены в FOR-04-06, 13 категорий) и `MeasurementUnit` (засижены в FOR-04-02). Получить их id через `GET /api/work-categories?size=1000` и `GET /api/measurement-units?size=1000`.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на прогон формируется `run-id`; создаваемые позиции получают уникальные `nameRU`/`namePL` вида `wi{run-id}` (у WorkItem нет `code`; уникальность не требуется на уровне БД, но удобна для поиска).
- **Teardown:** удалить созданные позиции (`DELETE /api/work-items/{id}`) и разлогинить токены в конце набора.
- **Seed-данные (категории/единицы) и системные ресурсы/роли НЕ изменяются** — только читаются для получения FK-id.
- i18n-проверки — `Accept-Language: ru`/`pl`; без заголовка → PL (fallback).

### Замечание про non-ADMIN роли (ABAC)

Бутстрапится только ADMIN. Кейсы non-ADMIN ролей документируются ожидаемыми результатами и покрываются seed-интеграционным тестом (`WorkCatalogResourceSeedIntegrationTest`). Матрица `WORK_CATALOG`: **ADMIN — CRUD; MANAGER — CREATE/READ/UPDATE (без DELETE); FOREMAN/WORKER/FINANCIER — READ; CLIENT — без гранта**.

## Фича C1. Внутренняя цена работы (задачи 1–2)

### TC-IP-01 — Создание и чтение внутренней цены (API)
Предусловия: Setup. Шаги:
1. `PUT /api/work-items/{wA}` с телом `{workCategoryId, unitId, nameRU, namePL, active:true, internalPrice: 55.50}` → 200.
2. `GET /api/work-items/{wA}` → в теле `internalPrice == 55.50`.
3. `GET /api/work-items?query=id=={wA}` → у строки `internalPrice == 55.50`.
Ожидание: цена сохранена и возвращается в обеих моделях.

### TC-IP-02 — Валидация внутренней цены (API)
Шаги:
1. `PUT /api/work-items/{wA}` с `internalPrice: -1` → 400 (ошибка валидации), значение в БД не изменилось (`GET` возвращает 55.50).
2. `PUT` с `internalPrice: 0` → 200 (ноль допустим и означает «оплата от нулевой базы», а не «не задана»).
3. `PUT` с `internalPrice: null` (или без поля) → 200, `GET` возвращает `internalPrice == null`.

### TC-IP-03 — База оплаты: внутренняя цена вместо базовой (API)
Предусловия: у `wA` есть цена работы (`POST /api/work-prices`, `netPrice=100`), проект в статусе, допускающем отчёты о работах, `wA` назначена в смету, есть работник с покрытием категории (см. сценарии FOR-06-01/FOR-06-10). Шаги:
1. Для `wA` задать `internalPrice = 60`, создать отчёт о работе на 3 ед. (`POST /api/projects/{pid}/work-reports`).
2. `GET /api/projects/{pid}/worker-costs` → стоимость строки считается от 60 (а не от 100): `workItemRate` отчёта для клиента остаётся 100, а оплата работнику = `60 × доля уровня × 3`.
3. Изменить `internalPrice` у `wA` на 80 → уже созданный отчёт НЕ пересчитывается (база заморожена в отчёте, `payroll_base_price = 60`); новый отчёт использует 80.
4. Очистить `internalPrice` у `wA`, создать ещё один отчёт → оплата считается от клиентской цены (100).
Ожидание: база оплаты = внутренняя цена на момент создания отчёта, иначе клиентская; выручка (`revenueValue`) не меняется.

### TC-IP-04 — Aggregate-сохранение вместе с остальными правками (API)
Шаги: `PUT /api/work-items/{wA}/aggregate` с `workItem.internalPrice = 70` и `relatedWorkIds = [wB]` → 204; затем `GET` работы и `GET /api/work-items/{wA}/related-works` показывают оба изменения. Повторный `PUT` с `internalPrice = -5` и `relatedWorkIds = [wC]` → 400, **ни одно** из изменений не применилось (атомарность).

### TC-UI-IP-01 — Поле «Внутренняя цена» на странице работы (UI)
Шаги:
1. Открыть `/catalog/works/{wA}` под ADMIN. Ожидание: поле «Внутренняя цена / Cena wewnętrzna» с подсказкой («необязательно, база оплаты работников; если пусто — базовая цена»), значение подгружено.
2. Ввести `20,75`. Ожидание: поле подсвечено как изменённое.
3. Нажать «Сохранить». Ожидание: диалог «Было → Стало» содержит строку «Внутренняя цена: 12.5 → 20.75»; отмена ничего не сохраняет, черновик остаётся.
4. Подтвердить. Ожидание: одно сохранение, после перезагрузки страницы значение `20.75`.
5. Ввести `-1`, «Сохранить». Ожидание: ошибка «Внутренняя цена должна быть неотрицательным числом», диалог не открывается.
6. Очистить поле, сохранить. Ожидание: после перезагрузки поле пустое (используется базовая цена).
7. Попытка уйти со страницы с несохранённым значением → диалог подтверждения ухода.

## Фича C2. Связанные работы (задачи 3–5)

### TC-RW-01 — Задание и чтение связей (API)
Шаги:
1. `GET /api/work-items/{wA}/related-works` → `{"relatedWorkIds": []}`.
2. `PUT /api/work-items/{wA}/related-works` `{"relatedWorkIds":[wB,wC]}` → 200, тело содержит `[wB,wC]`.
3. `PUT` с `[wC]` → 200, `GET` возвращает `[wC]` (полная замена).
4. `GET /api/work-items/{wC}/related-works` → `[]` (связь односторонняя, обратной нет).
5. `PUT` с `[]` → очищает.

### TC-RW-02 — Валидация связей (API)
Шаги:
1. `PUT` `{"relatedWorkIds":[wA]}` на `wA` (связь с самой собой) → 400 `error.work.related.self`.
2. `PUT` `[wB,wB]` → 400 `error.work.related.duplicate`.
3. `PUT` `[999999999]` → 404.
4. `PUT /api/work-items/999999999/related-works` → 404.
Ожидание: в БД состояние связей не менялось (проверка `GET`).

### TC-RW-03 — Расширение в смете: один уровень (API)
Предусловия: Setup, связи `wA → wB`, `wB → wC`. Шаги:

### TC-RW-04 — Циклы и односторонность (API)

### TC-RW-06 — Тип помещения связанной работы учитывается (API)
Шаги: у `wB` задать привязку к другому типу помещения (`PUT /api/work-items/{wB}/room-types`), связь `wA → wB`; `ASSIGN(wA, roomId)` → назначена только `wA`. После снятия привязки (`[]`) — назначаются обе.

### TC-RW-07 — Один шаг отмены на странице сметы (UI)

## Фича C3a. Матричное сохранение набора: `PUT /api/standard-work-sets/matrix` (API, задача 12)

### TC-SWM-01 — Матричное сохранение: добавление пар (API)
Предусловия: Setup; тип помещения `rtM` (код `SWS_{RUN}`, `POST /api/room-types`), работы `wA`, `wB`; набор для `rtM` пуст. Шаги:
1. `PUT /api/standard-work-sets/matrix` `{"add":[{"roomTypeId":rtM,"workItemId":wA},{"roomTypeId":rtM,"workItemId":wB}]}` → 200, `added == 2`, `removed == 0`, `pairs` содержит обе пары (полный текущий набор).
2. `GET /api/standard-work-sets?query=roomType.id==rtM` → ровно две строки (`wA`, `wB`).

### TC-SWM-02 — Удаление пар, порядок «сначала удаления, затем добавления» (API)
Шаги:
1. `PUT .../matrix` `{"remove":[{rtM,wA}],"add":[{rtM,wC}]}` → 200, `added == 1`, `removed == 1`; `pairs` для `rtM`: `wB`, `wC`.
2. `PUT .../matrix` `{"remove":[{rtM,wC}],"add":[{rtM,wC}]}` → 200, `removed == 1`, `added == 1`; итоговый набор содержит `wC` (удаление выполнено до добавления, конфликта уникальности нет).

### TC-SWM-03 — Идемпотентность (API)
Шаги:
1. Повторить `add` уже существующей пары `{rtM,wB}` → 200, `added == 0`, `removed == 0`, набор не изменился.
2. `remove` отсутствующей пары `{rtM,wA}` → 200, `added == 0`, `removed == 0`.
3. Тело `{}` и тела только с `add` / только с `remove` (списки необязательны) → 200, счётчики 0 для отсутствующих списков.

### TC-SWM-04 — Неизвестные идентификаторы: 400 и откат (API)
Шаги:
1. `PUT .../matrix` `{"add":[{rtM,wA},{"roomTypeId":999999999,"workItemId":wB}]}` → 400, код `error.standard.work.set.matrix.unknown`; `GET ...?query=roomType.id==rtM` — пара `{rtM,wA}` **не** добавлена (ничего не изменилось).
2. `remove` с неизвестным `workItemId` (999999999) → 400 тот же код, состояние не изменилось.
3. `null`-идентификатор (`{"roomTypeId":null,"workItemId":wA}`) → 400 тот же код.
4. Смешанный запрос: валидное `remove` + невалидное `add` → 400, валидное удаление **не** применено (атомарность).

### TC-SWM-05 — Права доступа на матричный эндпоинт (API)
Шаги: без токена `PUT .../matrix` → 401; ADMIN → 200 (всегда разрешён); роль без `UPDATE` на `STANDARD_WORK_SETS` (например READ-only) → 403, набор не изменён. Ожидаемые результаты по non-ADMIN ролям — как в замечании выше (seed-тест + матрица ролей).

### TC-SWM-06 — Существующий CRUD не изменился (API)
Шаги: `POST /api/standard-work-sets` (пара `{rtM,wA}`) → 200; дубликат → 409 `error.standard.work.set.duplicate`; `GET` list возвращает строку; `DELETE /{id}` → 200. Поведение идентично TC-SW-01.

**Teardown (C3a):** `PUT .../matrix` с `remove` всех пар `rtM` (или `DELETE` строк), затем удалить работы и тип помещения `rtM` (`DELETE /api/work-items/{id}`, `DELETE /api/room-types/{id}`); пары удаляются каскадно вместе с работой/типом.

Примечание: TC-SW-03…06 (применение набора при добавлении помещения) не меняются; набор, заданный через матрицу, применяется к новому помещению так же, как набор, заданный строками CRUD.
