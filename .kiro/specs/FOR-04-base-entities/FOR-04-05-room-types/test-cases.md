# Тест-кейсы: FOR-04-05 Room Types (справочник типов помещений)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерный экран**: справочник типов помещений раздаётся через REST `/api/room-types` **и** через админ-страницу CRUD по маршруту `/room-types` (страница + её роут поставляются в этой спеке; группа меню «Справочники» — отдельно в FOR-04-15). Поэтому набор тест-кейсов, согласно стандарту `.kiro/steering/test-cases.md`, включает **оба типа**:

- **Часть A. API-тесты** — против работающего в Docker приложения (не Testcontainers/юнит-слой, а поднятый docker-стек). Каждый шаг — HTTP-запрос к API `/api/room-types` с проверкой статуса, тела и заголовков.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда `http://localhost:3000`, исполняются браузерным движком (browser automation / headless), под ролью ADMIN. Каждый шаг — действие в браузере (переход, ввод, клик, ожидание).

Результат прогона для **обеих частей** — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус). **Скриншоты не требуются.**

Покрываемые требования: R1 (сущность/таблица), R2 (CRUD + i18n + сортировка/фильтр + иммутабельный `code` + валидация), R3 (ABAC-ресурс и гранты, **FINANCIER без гранта**), R4 (сид дефолтных типов помещений), R6 (админ-страница CRUD), R7 (UI-тесты).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`.
3. Auth-эндпоинты — под `/api/auth`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
5. Дождаться готовности `backend` (health/readiness) и завершения миграций `liquibase` перед запуском кейсов.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые типы помещений получают уникальный `code` вида `rt{run-id}` (например `rt1718123456`, `rt1718123456b`), чтобы не конфликтовать с уникальным индексом `code` и с seed-кодами (`przedpokoj`, `hol`, `kuchnia`, `salon`, `biuro`, `master`, `pokoj`, `lazienka`).
- **Teardown (обязательный шаг в конце каждого набора):** удалить все созданные на прогон типы помещений через `DELETE /api/room-types/{id}` и разлогинить выданные токены (`POST /api/auth/logout`). Отдельной ручной чистки БД не требуется.
- **Seed-данные и системные ресурсы/роли НЕ изменяются** — все манипуляции идут только над созданными на прогон типами. Это делает набор запускаемым многократно без ручной чистки БД.
- Для i18n-проверок используется заголовок `Accept-Language: ru` / `pl`; отсутствие заголовка эквивалентно PL (fallback).

### Замечание про non-ADMIN роли (ABAC)

Приложение при старте бутстрапит **только ADMIN**. Полноценная проверка гранта READ у ролей MANAGER/FOREMAN/WORKER требует активного пользователя соответствующей роли (создание такого пользователя через API — вне скоупа быстрого API-прогона). Поэтому:

- Кейсы с ADMIN и «без токена» исполняются напрямую API-прогоном.
- Кейсы для non-ADMIN ролей задокументированы с **ожидаемыми результатами** и помечены как покрываемые seed-интеграционным тестом (`RoomTypesResourceSeedIntegrationTest`), который проверяет точную матрицу грантов. Если в окружении есть засиженный ACTIVE-пользователь нужной роли — кейс исполняется API-прогоном.
- **Важное отличие от MEASUREMENT_UNITS:** роль **FINANCIER на `ROOM_TYPES` НЕ имеет гранта** (deny-by-default). CLIENT также без гранта. Гранты READ есть только у MANAGER/FOREMAN/WORKER; полный CRUD — у ADMIN.

## Фича 1. CRUD типов помещений

Проверяет полный жизненный цикл типа помещения через generic admin-фреймворк на базовом пути `/api/room-types`. Покрывает R2.1, R2.4, R2.5.

**Предусловия:** ADMIN залогинен (TC-SETUP-01); сформирован `run-id`.

**Шаги:**
1. `POST /api/room-types` (Bearer ADMIN) с телом `{"code": "rt{run-id}", "nameRU": "тестовая рус", "namePL": "test pl", "active": true}` → **200**; в теле `id`, `code == "rt{run-id}"`, `nameRU`, `namePL`, `active == true`.
2. Сохранить `id` созданного типа для дальнейших шагов.

**Ожидаемый результат:** тип помещения создан, `id` присвоен, поля соответствуют запросу.

### TC-CRUD-02 — Тип присутствует в списке (GET list)

**Предусловия:** выполнен TC-CRUD-01.

**Шаги:**
1. `GET /api/room-types?size=100` (Bearer ADMIN) → **200**; ответ пагинированный (`content`/`totalElements` или аналог контракта фреймворка).
2. Убедиться, что в `content` присутствует элемент с `code == "rt{run-id}"`.

**Ожидаемый результат:** созданный тип найден в списке.

### TC-CRUD-03 — Чтение расширенной модели (GET /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `GET /api/room-types/{id}` (Bearer ADMIN) → **200**; в теле расширенная модель: `id`, `code`, `nameRU == "тестовая рус"`, `namePL == "test pl"`, `active == true`.

**Ожидаемый результат:** возвращена расширенная модель со всеми локалями и `code`.

### TC-CRUD-04 — Обновление имён и active без изменения code (PUT /{id})

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `PUT /api/room-types/{id}` (Bearer ADMIN) с телом `{"nameRU": "рус обновл", "namePL": "pl updated", "active": false}` → **200**; в теле `nameRU == "рус обновл"`, `namePL == "pl updated"`, `active == false`.
2. `GET /api/room-types/{id}` → **200**; убедиться, что `code` **не изменился** (равен `rt{run-id}`), имена и `active` обновлены.
3. (Опционально) Отправить в PUT поле `code` с иным значением → значение `code` игнорируется, `code` остаётся прежним (иммутабельность, R2.4).

**Ожидаемый результат:** имена/`active` обновлены; `code` остаётся неизменным.

### TC-CRUD-05 — Удаление типа (DELETE /{id}) → 200, затем 404

**Предусловия:** выполнен TC-CRUD-01, есть `id`.

**Шаги:**
1. `DELETE /api/room-types/{id}` (Bearer ADMIN) → **200**.
2. `GET /api/room-types/{id}` (Bearer ADMIN) → **404** (тип отсутствует).

**Ожидаемый результат:** тип удалён; повторное чтение возвращает 404.

### TC-CRUD-06 — Валидация обязательных полей при создании → 400

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/room-types` (Bearer ADMIN) с телом без `code` — `{"nameRU": "рус", "namePL": "pl"}` → **400** (нарушение `@NotBlank code`).
2. `POST /api/room-types` с пустым `nameRU` — `{"code": "rt{run-id}x", "nameRU": "", "namePL": "pl"}` → **400**.
3. `POST /api/room-types` с отсутствующим `namePL` — `{"code": "rt{run-id}y", "nameRU": "рус"}` → **400**.

**Ожидаемый результат:** каждый запрос с отсутствующим/пустым обязательным полем (`code`, `nameRU`, `namePL`) отклоняется с 400.

**Teardown набора:** удалить все созданные на прогон типы (`DELETE /api/room-types/{id}`), кроме уже удалённого в TC-CRUD-05.

## Фича 2. i18n имени (PL fallback)

Проверяет, что локализованное поле `name` в списочной/краткой модели резолвится в `nameRU` для `Accept-Language: ru` и в `namePL` иначе. Покрывает R2.2.

**Стратегия повторяемости:** генератор `code = rt{run-id}` + teardown.

### TC-I18N-01 — name == nameRU при Accept-Language: ru

**Предусловия:** ADMIN залогинен; создан тип `{code: rt{run-id}i, nameRU: "имя-рус", namePL: "nazwa-pl", active: true}`.

**Шаги:**
1. `GET /api/room-types?size=100` с заголовком `Accept-Language: ru` → **200**.
2. Найти элемент с `code == "rt{run-id}i"`; проверить `name == "имя-рус"` (значение `nameRU`).

**Ожидаемый результат:** при `ru` `name` берётся из `nameRU`.

### TC-I18N-02 — name == namePL при Accept-Language: pl

**Предусловия:** тот же тип, что в TC-I18N-01.

**Шаги:**
1. `GET /api/room-types?size=100` с заголовком `Accept-Language: pl` → **200**.
2. Найти элемент с `code == "rt{run-id}i"`; проверить `name == "nazwa-pl"` (значение `namePL`).

**Ожидаемый результат:** при `pl` `name` берётся из `namePL`.

### TC-I18N-03 — PL fallback при отсутствии Accept-Language

**Предусловия:** тот же тип.

**Шаги:**
1. `GET /api/room-types?size=100` **без** заголовка `Accept-Language` → **200**.
2. Найти элемент с `code == "rt{run-id}i"`; проверить `name == "nazwa-pl"` (PL fallback).

**Ожидаемый результат:** без заголовка локали `name` резолвится в `namePL`.

**Teardown набора:** `DELETE /api/room-types/{id}` для типа `rt{run-id}i`.

## Фича 3. Сортировка и фильтрация по локализованному name

Проверяет, что сортировка и фильтр по `name` резолвятся в колонку локали (`nameRU`/`namePL`) через существующую i18n-резолюцию сортировки/фильтра. Грамматика фильтра — тильдо-обёрнутая (`~ct~`, а НЕ `=ct=`). Покрывает R2.3.

**Стратегия повторяемости:** генератор с общим префиксом `code = rt{run-id}s{n}` + teardown.

### TC-SORTFILTER-01 — Сортировка по name (asc) резолвится в колонку локали

**Предусловия:** ADMIN залогинен; созданы три типа одного прогона:
- `{code: rt{run-id}s1, nameRU: "ааа-рус", namePL: "ccc-pl"}`
- `{code: rt{run-id}s2, nameRU: "ббб-рус", namePL: "bbb-pl"}`
- `{code: rt{run-id}s3, nameRU: "ввв-рус", namePL: "aaa-pl"}`

**Шаги:**
1. `GET /api/room-types?size=100&sort=name,asc` с `Accept-Language: ru` → **200**; среди трёх созданных порядок по `nameRU` восходящий: `ааа-рус`, `ббб-рус`, `ввв-рус` (то есть `s1, s2, s3`).
2. `GET /api/room-types?size=100&sort=name,asc` с `Accept-Language: pl` → **200**; среди трёх созданных порядок по `namePL` восходящий: `aaa-pl`, `bbb-pl`, `ccc-pl` (то есть `s3, s2, s1`).

**Ожидаемый результат:** сортировка по `name` применяется к колонке активной локали (`nameRU` для ru, `namePL` для pl), порядок различается по локали.

### TC-SORTFILTER-02 — Фильтр по name (~ct~, contains) резолвится в колонку локали

**Предусловия:** те же три типа из TC-SORTFILTER-01.

**Шаги:**
1. `GET /api/room-types?size=100&query=name~ct~ааа` с `Accept-Language: ru` → **200**; в результате присутствует `s1` (`nameRU == "ааа-рус"`), отсутствуют `s2`/`s3`.
2. `GET /api/room-types?size=100&query=name~ct~aaa` с `Accept-Language: pl` → **200**; в результате присутствует `s3` (`namePL == "aaa-pl"`), отсутствуют `s1`/`s2`.
3. Убедиться, что используется именно тильдо-обёрнутая грамматика `~ct~` (contains), а не `=ct=`.

**Ожидаемый результат:** фильтр `name~ct~<term>` применяется к колонке активной локали; выборка различается по локали.

**Teardown набора:** удалить `s1`, `s2`, `s3` через `DELETE /api/room-types/{id}`.

## Фича 4. ABAC-доступ (ROOM_TYPES)

Проверяет, что эндпоинт защищён ресурсом `ROOM_TYPES`: без токена — 401; ADMIN — полный CRUD; держатель роли только с READ (MANAGER/FOREMAN/WORKER) — GET разрешён, но POST/PUT/DELETE запрещены (403); **FINANCIER и CLIENT — без гранта вовсе (403 на всё, включая GET)**. Покрывает R3.1, R3.3.

**Стратегия повторяемости:** генератор `code = rt{run-id}a` + teardown.

### TC-ABAC-01 — 401 без токена

**Предусловия:** стек поднят.

**Шаги:**
1. `GET /api/room-types` **без** заголовка `Authorization` → **401**.
2. `POST /api/room-types` без токена с любым телом → **401**.

**Ожидаемый результат:** неаутентифицированный доступ к защищённому ресурсу отклоняется с 401.

### TC-ABAC-02 — ADMIN имеет полный CRUD

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `POST /api/room-types` (Bearer ADMIN) `{code: rt{run-id}a, nameRU: "рус", namePL: "pl"}` → **200**.
2. `GET /api/room-types/{id}` (Bearer ADMIN) → **200**.
3. `PUT /api/room-types/{id}` (Bearer ADMIN) `{nameRU: "рус2", namePL: "pl2", active: false}` → **200**.
4. `DELETE /api/room-types/{id}` (Bearer ADMIN) → **200**.

**Ожидаемый результат:** ADMIN выполняет CREATE/READ/UPDATE/DELETE без ограничений.

### TC-ABAC-03 — Роль с READ (MANAGER/FOREMAN/WORKER): GET разрешён, запись запрещена (403)

**Предусловия:** активный пользователь роли MANAGER/FOREMAN/WORKER (только READ на `ROOM_TYPES`). *Если такого пользователя нет в окружении — кейс покрывается seed-интеграционным тестом (`RoomTypesResourceSeedIntegrationTest`), проверяющим матрицу грантов; ниже — ожидаемые результаты.*

**Шаги:**
1. `POST /api/auth/login` пользователем READ-роли → **200**, получить его access-токен.
2. `GET /api/room-types` (Bearer READ-роль) → **200** (чтение разрешено).
3. `POST /api/room-types` (Bearer READ-роль) → **403**.
4. `PUT /api/room-types/{id}` (Bearer READ-роль) → **403**.
5. `DELETE /api/room-types/{id}` (Bearer READ-роль) → **403**.

**Ожидаемый результат:** роль с грантом READ читает справочник, но операции записи запрещены с 403.

### TC-ABAC-04 — FINANCIER и CLIENT без гранта: доступ запрещён (403 на всё)

**Предусловия:** активный пользователь роли FINANCIER и/или CLIENT. *Если таких пользователей нет в окружении — кейс покрывается seed-интеграционным тестом (`RoomTypesResourceSeedIntegrationTest`), который явно проверяет, что у FINANCIER и CLIENT НЕТ строки `role_resources` на `ROOM_TYPES` (deny-by-default); ниже — ожидаемые результаты.*

**Шаги:**
1. `POST /api/auth/login` пользователем FINANCIER → **200**, получить его access-токен.
2. `GET /api/room-types` (Bearer FINANCIER) → **403** (нет гранта READ — в отличие от `MEASUREMENT_UNITS`, где FINANCIER имеет READ).
3. `POST /api/room-types` (Bearer FINANCIER) → **403**.
4. (Аналогично для CLIENT, если доступен активный пользователь) `GET /api/room-types` (Bearer CLIENT) → **403**.

**Ожидаемый результат:** FINANCIER и CLIENT не имеют доступа к `ROOM_TYPES` (ни чтения, ни записи), запросы отклоняются с 403 — deny-by-default.

**Teardown набора:** удалить тип `rt{run-id}a` (если не удалён в TC-ABAC-02), разлогинить выданные токены.

## Фича UI-1. Страница «Типы помещений» (/room-types)

Проверяет рендер, поиск/сортировку/фильтр, CRUD через UI, пермишн-гейтинг и i18n админ-страницы на базе общего `DataTable`. Покрывает R6.1–R6.7, R7.1.

**Стратегия повторяемости:** генератор `code = rt{run-id}` (уникальный код на каждый прогон) + teardown (удалить созданные типы через UI-диалог удаления в конце набора). Кейсы «только чтение» (открытие страницы, поиск/сортировка/фильтр по сид-данным, i18n, пермишн-гейтинг READ-роли) teardown не требуют.

### TC-UI-01 — Открытие страницы и рендер таблицы

**Предусловия:** выполнен TC-UI-SETUP-01.

**Шаги:**
1. Перейти на `http://localhost:3000/room-types`.
2. Дождаться загрузки таблицы (`DataTable` для `entityKey="room-types"`).
3. Проверить заголовок страницы (`roomTypes.pageTitle`, локализованный, не сырой ключ).
4. Проверить, что таблица содержит колонки `code`, `name` и `active`.
5. Проверить, что колонка `active` отображается локализованным бейджем (Активен/Неактивен), а не булевым `true/false`.
6. Убедиться, что в списке присутствуют восемь сид-типов: `przedpokoj`, `hol`, `kuchnia`, `salon`, `biuro`, `master`, `pokoj`, `lazienka`.

**Ожидаемый результат:** страница открыта, таблица отрендерена с колонками code/name/active, бейдж активности локализован, восемь сид-типов видны.

### TC-UI-02 — Поиск, сортировка и фильтрация (общий DataTable)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**
1. Ввести в поиск подстроку имени существующего типа (например часть `nameRU`/`namePL` для `kuchnia`) → список сокращается до совпадающих строк.
2. Очистить поиск → список восстанавливается.
3. Кликнуть заголовок колонки `code` для сортировки → порядок строк меняется по `code` (asc), повторный клик — desc; запрос сортировки уходит на бэкенд (серверная сортировка `sort=code,...`).
4. Кликнуть заголовок колонки `name` для сортировки → порядок меняется по локализованному `name`; запрос `sort=name,...` уходит на бэкенд.
5. Применить фильтр по колонке (например `name` contains) → список сужается до строк, удовлетворяющих условию.
6. Снять фильтр → список восстанавливается.

**Ожидаемый результат:** поиск, сортировка и фильтр корректно сокращают/меняют список; сортировка выполняется на бэкенде (не клиентская).

### TC-UI-03 — Создание типа через форму-sheet

**Предусловия:** выполнен TC-UI-01; сформирован `run-id`.

**Шаги:**
1. Убедиться, что кнопка «Создать» видна (ADMIN имеет `CREATE`).
2. Нажать «Создать» → открывается форма-sheet с полями `code`, `nameRU`, `namePL`, `active`.
3. Заполнить `code = rt{run-id}`, `nameRU = "тест рус"`, `namePL = "test pl"`, оставить `active` включённым.
4. Нажать «Сохранить».
5. Дождаться закрытия sheet и появления тоста успеха (`roomTypes.toast.createSuccess`).
6. Проверить, что строка с `code = rt{run-id}` появилась в списке.

**Ожидаемый результат:** тип создан через UI, показан тост успеха, новая строка присутствует в таблице.

### TC-UI-04 — Валидация формы создания (пустые обязательные поля)

**Предусловия:** выполнен TC-UI-01.

**Шаги:**
1. Нажать «Создать» → открыть форму-sheet.
2. Оставить `code` пустым, попытаться отправить форму → отображается инлайновая ошибка валидации у поля `code` (локализованная, `roomTypes.validation.*`), сабмит заблокирован (запрос на бэкенд не уходит).
3. Заполнить `code`, но оставить пустым `nameRU` (и/или `namePL`) → инлайновая ошибка у соответствующего поля имени, сабмит заблокирован.
4. Закрыть форму без сохранения.

**Ожидаемый результат:** при пустых обязательных полях (`code`, `nameRU`, `namePL`) показываются инлайновые локализованные ошибки, отправка формы заблокирована.

### TC-UI-05 — Редактирование типа (code read-only)

**Предусловия:** выполнен TC-UI-03 (создан тип `rt{run-id}`).

**Шаги:**

6. Проверить, что строка `rt{run-id}` в списке обновлена (новое имя и бейдж «Неактивен»), а `code` остался прежним.

**Ожидаемый результат:** форма предзаполнена, `code` неизменяем, имена/`active` обновлены, показан тост успеха, строка обновлена в таблице.

### TC-UI-06 — Удаление типа через диалог подтверждения

### TC-UI-07 — Пермишн-гейтинг (роль только с READ)

**Предусловия:** активный пользователь роли с грантом только `READ` на `ROOM_TYPES` (например MANAGER/FOREMAN/WORKER), залогинен в браузере. *Если такого пользователя нельзя создать в окружении — кейс документируется ожидаемым поведением и помечается как покрытый компонентным тестом `RoomTypesList.test.tsx` (мок permissions в auth-store, проверка скрытия create/edit/delete).*

**Шаги:**
1. Войти в браузере под пользователем READ-роли (или переключить сессию).
2. Перейти на `/room-types` → список доступен для чтения, строки рендерятся.
3. Проверить, что кнопка «Создать» **отсутствует/скрыта**.
4. Проверить, что в строках **нет** действий «Редактировать» и «Удалить».

**Ожидаемый результат:** пользователь с READ видит список, но контролы создания/редактирования/удаления скрыты (гейтинг через `usePermission`).

### TC-UI-08 — Пермишн-гейтинг (FINANCIER без доступа — 403/редирект)

**Предусловия:** активный пользователь роли FINANCIER, залогинен в браузере. *Если такого пользователя нет в окружении — кейс документируется ожидаемым поведением; отсутствие гранта подтверждается seed-интеграционным тестом.*

**Шаги:**
1. Войти в браузере под пользователем FINANCIER.
2. Перейти на `/room-types` → интерим-гард маршрута (`ROUTE_REQUIREMENTS['/room-types'] = { resource: 'ROOM_TYPES', operation: 'READ' }`) блокирует доступ: редирект на `/403` (Forbidden), т.к. у FINANCIER нет READ на `ROOM_TYPES`.

**Ожидаемый результат:** FINANCIER не попадает на страницу типов помещений (в отличие от единиц измерения), маршрут закрыт гардом — deny-by-default.

### TC-UI-09 — i18n: переключение локали PL/RU

**Предусловия:** выполнен TC-UI-SETUP-01 (ADMIN), открыта страница `/room-types`.

**Шаги:**
1. Переключить локаль интерфейса на PL → заголовок страницы, заголовки колонок (`code`/`name`/`active`), бейджи активности и подписи формы (при открытии формы-sheet) отображаются на польском.
2. Переключить локаль на RU → те же элементы отображаются на русском; локализованный `name` в списке резолвится в `nameRU`.
3. Во всех состояниях убедиться, что **сырые ключи** вида `roomTypes.*` (напр. `roomTypes.pageTitle`, `roomTypes.table.code`) **не отображаются** ни в одном элементе UI.

**Ожидаемый результат:** переключение PL/RU меняет все пользовательские надписи (заголовок, колонки, подписи формы, бейджи); сырые i18n-ключи нигде не видны (паритет `pl.json`/`ru.json`).

**Teardown набора (UI):** удалить все созданные на прогон типы (`rt{run-id}` и т.п.) через UI-диалог удаления (TC-UI-06); при необходимости выйти из сессии. Кейсы «только чтение» (TC-UI-01, TC-UI-02, TC-UI-04, TC-UI-07, TC-UI-08, TC-UI-09 в части чтения) teardown не требуют.

## Регрессия

Небольшой регрессионный набор: перепроверка сквозного сида и ABAC-гарда, а также отсутствия влияния на смежные ресурсы.

**Стратегия повторяемости:** только чтение — teardown не требуется.

### TC-REG-01 — Сид-типы на месте после повторного прогона

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/room-types?size=1000` (Bearer ADMIN) → **200**; все восемь сид-кодов присутствуют (см. TC-SEED-01) — сид идемпотентен, дубликатов нет.
2. Убедиться, что число элементов с сид-кодами не выросло между прогонами (по одному экземпляру каждого кода).

**Ожидаемый результат:** сид стабилен и идемпотентен, дубликаты не появляются.

### TC-REG-02 — ABAC-гард по-прежнему действует

**Предусловия:** нет.

**Шаги:**
1. `GET /api/room-types` без токена → **401** (гард сохранён).

**Ожидаемый результат:** защита эндпоинта не регрессировала.

### TC-REG-03 — Смежные ресурсы не затронуты; FINANCIER-грант отсутствует

**Предусловия:** ADMIN залогинен.

**Шаги:**
1. `GET /api/roles` (Bearer ADMIN) → **200**; список ролей не изменён появлением нового ресурса.
2. `GET /api/resources` (Bearer ADMIN) → **200**; присутствует новый ресурс `ROOM_TYPES` наряду с ранее существующими (`USERS`, `AUDIT`, `MEASUREMENT_UNITS`, `CURRENCIES`, `VAT_RATES` и т.д.), прежние ресурсы на месте.
3. (Опционально, при наличии соответствующего API) Убедиться, что у роли FINANCIER НЕТ гранта на `ROOM_TYPES` (в отличие от `MEASUREMENT_UNITS`) — соответствует seed-интеграционному тесту.

**Ожидаемый результат:** добавление `ROOM_TYPES` не сломало и не удалило смежные ресурсы/роли; FINANCIER остаётся без гранта на `ROOM_TYPES`.
