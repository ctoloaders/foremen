# Тест-кейсы: FOR-04-19 — Расход материалов work-каталога (нормы + вычисляемая денежная вилка)

> Тип спеки: **смешанная (API + UI)**.
>
> - **API-кейсы** — это HTTP-тесты против поднятого в Docker приложения (не Testcontainers/юнит-слой,
>   а живой docker-стек). Базовый URL бэкенда — `http://localhost:8080`, auth-эндпоинты под `/api/auth`.
>   Каждый шаг — HTTP-запрос с проверкой статуса/тела/заголовков.
> - **UI-кейсы** — браузерные сценарии против фронтенда `http://localhost:3000`; исполняются
>   браузерным движком (headless-браузер / browser automation). Каждый шаг — действие в браузере
>   (переход, ввод, клик, ожидание).
> - **Артефакт прогона — MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус).
>   Скриншоты не требуются.
>
> Спека вводит ЕДИНСТВЕННУЮ новую операционную сущность **WorkMaterialConsumption** (ресурс
> `WORK_MATERIAL_CONSUMPTION`, таблица `work_material_consumptions`, путь
> `/api/work-material-consumptions`) — одну норму `(work item, offer package, material TYPE)` с branch,
> ровно одним типом-аналогом (construction XOR finishing), единицей материала, `normQty`, двуязычным
> `justification` и цитатой. Денежная **вилка** нигде не хранится — она вычисляется на чтении из
> аналоговой партии (все материалы типа в пакете) как `normQty × [MIN..MAX retailNet]`. Каталог работ
> получает синтетические пивот-колонки на пакет с ТРЕМЯ ценами (труд + construction-вилка +
> finishing-вилка) и drill-in по клику на ячейку пакета.

Покрываемые требования: **3, 4, 5, 6, 7, 8, 9**.

---

## Запуск окружения (API-кейсы)

`docker compose up` в корне поднимает `postgres` (:5432), `liquibase` (миграции), `backend`
(:8080, профиль `docker`), `frontend` (:3000). Первый ADMIN создаётся переменными
`FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Логин — `POST /api/auth/login`,
далее `Authorization: Bearer <accessToken>` на всех защищённых запросах.

Переменные прогона (заполняются на этапе Setup, ниже):

- `ADMIN_TOKEN` — Bearer-токен ADMIN;
- `MANAGER_TOKEN`, `FOREMAN_TOKEN`, `WORKER_TOKEN`, `FINANCIER_TOKEN`, `CLIENT_TOKEN` — токены прочих ролей;
- `WORK_ID`, `PKG_ID` — id существующего `WorkItem` и `OfferPackage` (из seed);
- `CMT_ID` — id `ConstructionMaterialType` (construction), `FMT_ID` — id finishing `MaterialType`;
- `UNIT_ID` — id `MeasurementUnit` (например `kg`);
- `RUN_ID` — уникальный токен прогона (timestamp/uuid, например `20260101-120000-ab12`);
- `CREATED_IDS[]` — список id созданных за прогон норм (для teardown).

## Стратегия повторяемости (обязательно)

У `WorkMaterialConsumption` **нет `name`/`code`** — уникальность строки задаётся набором ссылок +
`normQty`. Поэтому применяем **комбинацию генератора `RUN_ID` + явный teardown**:

1. **Run-id генератор.** В начале прогона формируется `RUN_ID` = timestamp/uuid. Все создаваемые нормы
   помечаются уникальным токеном прогона в поле **`sourceRef`** (например `sourceRef = "TC-{RUN_ID}-{n}"`)
   и, при наличии, в `sourceDoc`. Это делает созданные строки узнаваемыми и не пересекающимися между прогонами.
2. **Setup (однократно перед всеми API-кейсами).**
   - Залогиниться ADMIN → `ADMIN_TOKEN`; при наличии — залогиниться прочими ролями (или создать их
     инвайтом/сидом) → соответствующие токены.
   - Через `GET /api/work-items?size=1`, `GET /api/offer-packages?size=200`,
     `GET /api/measurement-units?size=200`, `GET /api/construction-material-types?size=200`,
     `GET /api/material-types?size=200` получить и зафиксировать `WORK_ID`, `PKG_ID`, `UNIT_ID`,
     `CMT_ID`, `FMT_ID`. Все id берутся из уже присутствующего seed (Требование 7), тестовые кейсы
     ничего в справочники не пишут.
3. **Teardown (в конце каждого создающего кейса И финально по всему прогону).**
   - Для каждого id из `CREATED_IDS[]` выполнить `DELETE /api/work-material-consumptions/{id}` под `ADMIN_TOKEN`.
   - Контрольная зачистка «висяков»: `GET /api/work-material-consumptions?sourceRef=@=TC-{RUN_ID}`
     (подстрочный фильтр по токену прогона) → удалить все найденные строки.
   - Справочники (`work_items`, `offer_packages`, материалы, типы) НЕ трогаем — они read-only для этой спеки.
4. **UI-кейсы** стартуют с чистого браузерного контекста (новый контекст или `localStorage.clear()` на
   домене приложения) и, где создают нормы через форму, наследуют тот же `sourceRef = TC-{RUN_ID}-*`
   и удаляют созданное диалогом удаления (или API-teardown) по завершении.

Каждый кейс ниже явно указывает предусловия и, если создаёт данные, шаг teardown.

## Фича 3: Вычисляемая денежная вилка + drill-in чтение — API

_Покрывает Требования 4 (4.1–4.7) и 5.4/5.5: type-level batch range, суммирование по branch,
явный `0` при отсутствии branch, исключение null-`retailNet`, детерминизм; drill-in через
generic list endpoint с большим `size`, возвращающий `typeBatchRange {min,max}` и `materials[]`
с `moneyCost = normQty × retailNet` + justification/citation._

Стратегия повторяемости: **read-only проверки против seed** (Требование 7) — не пишем данные, чистка
не нужна; кейсы, создающие вспомогательные нормы, помечают их `TC-{RUN_ID}` и делают teardown.

### TC-RNG-01 — Drill-in читает исчерпывающий список для `(work, package)`
**Требования:** 5.4, 5.5
**Предусловия:** `ADMIN_TOKEN`; выбран `(WORK_ID, PKG_ID)`, у которого в seed есть нормы (при
необходимости — предварительно создать помеченные `TC-{RUN_ID}` нормы обоих branch и удалить в конце).

| Шаг | Действие / Запрос | Ожидаемый результат |
|-----|-------------------|---------------------|
| 1 | `GET /api/work-material-consumptions?workItem.id=={WORK_ID}&offerPackage.id=={PKG_ID}&size=1000` | 200; возвращены ВСЕ строки этого `(work, package)` без пагинации-обрезки |
| 2 | Осмотреть строку | Есть `branch`, `materialType` (аналоговая группа), `normQty`, `typeBatchRange {min,max}`, массив `materials[]`, `justification`, поля цитаты (`sourceType`/`sourceDoc`/`sourceRef`) |
| 3 | Проверить `materials[]` | Каждый материал несёт `name`, `producer`, `seller`, `unit`, `retailNet`, `moneyCost` |
| 4 | Проверить арифметику `moneyCost` | Для материала `moneyCost == normQty × retailNet` (с точностью округления) |

### TC-RNG-02 — `typeBatchRange` = `normQty × [MIN..MAX retailNet]`
**Требования:** 4.2, 4.6
**Предусловия:** `ADMIN_TOKEN`; строка, чей тип имеет несколько материалов в пакете.

| Шаг | Действие / Запрос | Ожидаемый результат |
|-----|-------------------|---------------------|
| 1 | Взять строку drill-in с ≥2 материалами в `materials[]` | Есть валидные `retailNet` |
| 2 | Вычислить ожидаемое: `min = normQty × min(retailNet)`, `max = normQty × max(retailNet)` | — |
| 3 | Сравнить с `typeBatchRange` строки | `typeBatchRange.min`/`.max` совпадают с вычисленными |
| 4 | Найти строку с одним материалом в партии | `typeBatchRange.min == typeBatchRange.max` (вилка схлопнута) |

### TC-RNG-03 — Пустая партия и null-`retailNet` дают `0`, но норма видна
**Требования:** 4.6, 5.2
**Предусловия:** `ADMIN_TOKEN`; тип без материалов в пакете (или все `retailNet` = null).

| Шаг | Действие / Запрос | Ожидаемый результат |
|-----|-------------------|---------------------|
| 1 | Найти в drill-in строку, у которой `materials[]` пуст (нет материала типа в пакете) | Строка присутствует (норма видна) |
| 2 | Осмотреть `typeBatchRange` | `min == 0` и `max == 0` (явный ноль, не blank/`null`) |
| 3 | Найти материал с `retailNet == null` | Он исключён из расчёта MIN/MAX (не влияет на вилку) |

### TC-RNG-04 — Явный `0` для branch без норм; branch-range = сумма по типам
**Требования:** 4.3, 4.4, 4.5
**Предусловия:** `ADMIN_TOKEN`; `(work, package)`, где есть construction-нормы, но нет finishing (или наоборот).

| Шаг | Действие / Запрос | Ожидаемый результат |
|-----|-------------------|---------------------|
| 1 | Получить агрегированную ячейку пакета в каталоге (см. Фича 4) для `(WORK_ID, PKG_ID)` | Есть `construction {min,max}` и `finishing {min,max}` |
| 2 | Для branch без норм | Диапазон = `{min:0, max:0}` (явный ноль, отличим от «нет вычисления») |
| 3 | Для branch с несколькими типами | `branch.min` = сумма type-level `min` по РАЗЛИЧНЫМ типам, `branch.max` = сумма type-level `max` |
| 4 | Проверить смешанные единицы (kg + szt + m²) | Физические `normQty` НЕ суммируются между единицами; суммируются только деньги |

### TC-RNG-05 — Детерминизм: повторное чтение даёт идентичные `{min,max}`
**Требования:** 4.7
**Предусловия:** `ADMIN_TOKEN`; данные в этом окне прогона не меняются.

| Шаг | Действие / Запрос | Ожидаемый результат |
|-----|-------------------|---------------------|
| 1 | Дважды подряд `GET` агрегированную ячейку `(WORK_ID, PKG_ID)` | Оба ответа получены (200) |
| 2 | Сравнить `construction`/`finishing` `{min,max}` двух ответов | Полностью идентичны |

## Фича 4: Пивот-агрегация каталога работ + `/metadata` — API

_Покрывает Требование 5 (5.1, 5.2, 5.3, 5.6): `/metadata` рекламирует по одному дескриптору

пагинированным по различным `WorkItem`._

Стратегия повторяемости: **read-only против seed** — не пишем, чистка не нужна.
