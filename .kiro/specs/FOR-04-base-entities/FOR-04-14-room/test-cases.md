# Тест-кейсы — FOR-04-14: Room (сущность помещения, движок геометрических расчётов, project-scoped CRUD, admin UI)

Документ описывает ручные/автоматизируемые тест-кейсы для спеки FOR-04-14. Спека
смешанного типа (**API + UI**):

- **API-кейсы** исполняются HTTP-запросами против поднятого в Docker приложения
  (не Testcontainers/юнит-слой, а реальный docker-стек). Каждый шаг — запрос к API
  с проверкой статуса/тела/заголовков.
- **UI-кейсы** исполняются браузерным движком (headless-браузер / browser
  automation) против фронтенда `http://localhost:3000`. Каждый шаг — действие в
  браузере (переход, ввод, клик, ожидание).

Результат прогона — **MD-репорты с таблицами** (см. раздел «Шаблон MD-репорта»),
скриншоты не требуются.

Покрываемые требования: **1, 2, 3, 4, 5, 6, 8** (`requirements.md`).

## Окружение и запуск

### Docker-стек

В корне репозитория:

```
docker compose up
```

Поднимает:

| Сервис | Порт | Назначение |
|---|---|---|
| `postgres` | 5432 | БД `foremen` |
| `liquibase` | — | применение миграций (в т.ч. `042-create-rooms.xml`, `043-seed-rooms-resource.xml`) |
| `backend` | 8080 | Spring Boot, профиль `docker` |
| `frontend` | 3000 | React admin UI |

- Базовый URL API: `http://localhost:8080`.
- Auth-эндпоинты: под `/api/auth`.
- Первый ADMIN поднимается автоматически через переменные `FOREMEN_ADMIN_CREATE=true`,
  `FOREMEN_ADMIN_EMAIL=cto+1@loaders.dev`, `FOREMEN_ADMIN_PASSWORD=alejano123`
  (значения из `docker-compose.yml`).
- Фронтенд admin UI: `http://localhost:3000`.

### Предварительные общие предусловия (Setup)

Перед каждым набором кейсов:

1. Docker-стек поднят и здоров (backend отвечает `200` на `GET /api/health` или
   на любой публичный эндпоинт; frontend отдаёт страницу логина).
2. Миграции применены: таблица `rooms` существует, ресурс `ROOMS` засеян с
   матрицей грантов из Requirement 6.
3. Получен ADMIN access-token:

   ```
   POST /api/auth/login
   { "email": "cto+1@loaders.dev", "password": "alejano123" }
   → 200 + { accessToken, refreshToken }
   ```

   Далее ADMIN-запросы идут с заголовком `Authorization: Bearer <accessToken>`.
4. Для проектно-скоуповых кейсов заранее подготовлены:
   - минимум один `project` (через `POST /api/projects`),
   - минимум один активный `room_type` (через `GET /api/room-types`, взять
     существующий `id`; при необходимости создать),
   - для scoping-кейсов — не-ADMIN пользователь (роль MANAGER/FOREMAN/WORKER) и
     его членство в конкретных проектах через `project_members`.

## Стратегия повторяемости (обязательно)

Кейсы должны запускаться многократно без ручной чистки БД. Применяется
**комбинированная стратегия «генератор + teardown»**:

- **Генератор данных (run-id).** На каждый прогон формируется уникальный
  `run-id` — timestamp/uuid, например `run-id = 20240605T101530Z-abc123`.
  Все создаваемые сущности получают уникальные различающие поля на основе `run-id`:
  - `Room.label` вида `Room {run-id} #{n}` (напр. `Room 20240605T101530Z-abc123 #1`);
  - при необходимости создания проекта — его имя/код с `run-id`;
  - не-ADMIN пользователь для scoping — email вида
    `tester+{run-id}@example.com`.
- **Teardown.** В конце каждого сценария создания явно удаляются созданные
  сущности:
  - `DELETE /api/rooms/{id}` для всех созданных в сценарии комнат;
  - удаление/деактивация вспомогательных проектов и пользователей, если они
    создавались только для сценария.
- Идемпотентные сущности (ресурс `ROOMS`, гранты) **не удаляются** — их кейсы
  (Фича F) проверяются только на чтение и на идемпотентность повторного
  применения сидов.

Каждый набор кейсов ниже указывает свою стратегию повторяемости в поле
«Повторяемость».

## API-кейсы

Базовый URL: `http://localhost:8080`. Все запросы (кроме `/api/auth`) требуют
`Authorization: Bearer <token>`. Тело — `application/json`.

Полезные фикстуры для тела запроса:

- **Валидная геометрия (квадрат 4×5, единица — м):**

  ```json
  {
    "vertices": [ {"x":0,"y":0}, {"x":4,"y":0}, {"x":4,"y":5}, {"x":0,"y":5} ],
    "walls": [
      { "wallGap": 0, "finishGap": 0, "openings": [ {"type":"DOOR","count":1,"height":2.0,"width":0.9} ] },
      { "wallGap": 0, "finishGap": 0, "openings": [] },
      { "wallGap": 0, "finishGap": 0, "openings": [ {"type":"WINDOW","count":2,"height":1.2,"width":1.5} ] },
      { "wallGap": 0, "finishGap": 0, "openings": [] }
    ]
  }
  ```

  Ожидаемые расчётные метрики при `ceilingHeight = 3.0`:
  - `floorArea` = |shoelace| = `20.00` м²;
  - `perimeter` = 4+5+4+5 = `18.00` mb;
  - `doorArea` = 1×2.0×0.9 = `1.80` м²; `doorCount` = 1;
  - `windowArea` = 2×1.2×1.5 = `3.60` м²; `windowCount` = 2;
  - `wallArea` = max(0, 18×3 − 1.80 − 3.60 − 0×3) = `48.60` м².

### Фича A. Создание комнаты с геометрией → расчётные метрики (`POST /api/rooms`)

_Требования: 1, 2, 3, 4.2, 4.3, 5.1_
Повторяемость: генератор `run-id` для `label` + teardown (`DELETE /api/rooms/{id}`).

#### TC-A1. Создание комнаты с валидной геометрией стамп-ится как CALCULATED

- **Предусловия:** ADMIN-token; известны валидные `projectId` и `roomTypeId`;
  сформирован `run-id`.
- **Шаги:**
  1. `POST /api/rooms` с телом `{ projectId, roomTypeId, label: "Room {run-id} #1", ceilingHeight: 3.0, geometry: <валидная геометрия 4×5> }`.
     Ожидание: `201`/`200`, в теле `id`, `projectId`, `roomTypeId`, `label`.
  2. Проверить расчётные метрики в ответе:
     `floorArea.value = 20.00`, `perimeter.value = 18.00`, `wallArea.value = 48.60`,
     `doorArea.value = 1.80`, `windowArea.value = 3.60`.
     Ожидание: все значения совпадают с ожидаемыми (± округление до 2 знаков).
  3. Проверить source-флаги: `floorArea.source = CALCULATED`, `wallArea.source = CALCULATED`,
     `perimeter.source = CALCULATED`, `doorArea.source = CALCULATED`, `windowArea.source = CALCULATED`.
     Ожидание: все пять флагов = `CALCULATED`.
  4. Проверить счётчики: `doorCount = 1`, `windowCount = 2`.
     Ожидание: значения совпадают.
  5. **Teardown:** `DELETE /api/rooms/{id}`. Ожидание: `200`/`204`.
- **Ожидаемый результат:** комната создана, метрики рассчитаны из геометрии и
  помечены `CALCULATED`, счётчики выведены из openings.

#### TC-A2. Геометрия авторитетна над переданными вручную значениями

- **Предусловия:** ADMIN-token; валидные `projectId`/`roomTypeId`; `run-id`.
- **Шаги:**
  1. `POST /api/rooms` с телом, где ОДНОВРЕМЕННО передана `geometry` (валидная 4×5,
     `ceilingHeight: 3.0`) И ручные значения `floorArea: 999`, `wallArea: 999`,
     `perimeter: 999`, `doorArea: 999`, `windowArea: 999`.
     Ожидание: `201`/`200`.
  2. Проверить, что в ответе метрики равны расчётным из геометрии
     (`floorArea.value = 20.00`, `perimeter.value = 18.00`, `wallArea.value = 48.60`,
     `doorArea.value = 1.80`, `windowArea.value = 3.60`), а НЕ переданным `999`.
     Ожидание: ручные значения проигнорированы для этих пяти метрик.
  3. Проверить, что source всех пяти = `CALCULATED`.
     Ожидание: подтверждено.
  4. **Teardown:** `DELETE /api/rooms/{id}`.
- **Ожидаемый результат:** при наличии геометрии переданные вручную значения пяти
  метрик перезаписаны расчётными и помечены `CALCULATED` (Req 4.2).

#### TC-A3. Детерминизм: повторное создание той же геометрии даёт те же метрики

- **Предусловия:** ADMIN-token; валидные ссылки; `run-id`.
- **Шаги:**
  1. `POST /api/rooms` с валидной геометрией (комната #1). Ожидание: `201`, запомнить метрики.
  2. `POST /api/rooms` с той же геометрией и `ceilingHeight` (комната #2). Ожидание: `201`.
  3. Сравнить метрики комнаты #1 и #2. Ожидание: идентичны (Req 3.5).
  4. **Teardown:** `DELETE` обеих комнат.
- **Ожидаемый результат:** расчёт детерминирован — одинаковая геометрия даёт
  одинаковые значения.

### Фича B. Валидация геометрии и openings

_Требования: 2.3, 2.4, 4.4, 4.5, 5.6_
Повторяемость: сценарии отказа ничего не создают; teardown не требуется (если
что-то создалось — удалить).

#### TC-B1. Полигон с менее чем 3 вершинами отклоняется

- **Предусловия:** ADMIN-token; валидные ссылки.
- **Шаги:**
  1. `POST /api/rooms` c `geometry.vertices` из 2 точек.
     Ожидание: `400`, код ошибки указывает на невалидную геометрию
     (`error.room.geometry.invalid`).
  2. `GET /api/rooms` (или `count`) — убедиться, что комната не создана.
     Ожидание: новых строк нет (ничего не персистится, Req 2.3).
- **Ожидаемый результат:** запрос отклонён `400`, ничего не сохранено.

#### TC-B2. Опенинг с невалидным type/count/height/width отклоняется

- **Предусловия:** ADMIN-token; валидные ссылки.
- **Шаги:**
  1. `POST /api/rooms` с валидным полигоном, но опенингом `type: "GATE"` (вне
     `{DOOR,WINDOW}`). Ожидание: `400`, код указывает на невалидный опенинг
     (`error.room.opening.invalid`).
  2. Повторить с `count: 0`. Ожидание: `400`.
  3. Повторить с `height: 0`. Ожидание: `400`.
  4. Повторить с `width: -1`. Ожидание: `400`.
  5. `GET /api/rooms/count` — убедиться, что ничего не создано.
     Ожидание: без изменений (Req 2.4).
- **Ожидаемый результат:** каждый невалидный опенинг отклоняется `400`, ничего не
  сохраняется.

#### TC-B3. Числовая метрика вне диапазона / отрицательный счётчик отклоняются

- **Предусловия:** ADMIN-token; валидные ссылки.
- **Шаги:**
  1. `POST /api/rooms` без геометрии с ручным `floorArea: 10000000000.00`
     (> 9 999 999 999.99). Ожидание: `400`, `error.room.metric.range` (Req 4.5).
  2. Повторить с `floorArea: -5`. Ожидание: `400`.
  3. Повторить с `doorCount: -1`. Ожидание: `400` (`error.room.count.negative`).
  4. Повторить с `internalCorners: -2`. Ожидание: `400`.
  5. `GET /api/rooms/count` — без изменений. Ожидание: подтверждено.
- **Ожидаемый результат:** значения вне диапазона и отрицательные счётчики
  отклоняются `400`, ничего не сохраняется.

#### TC-B4. Невалидное значение source отклоняется

- **Предусловия:** ADMIN-token; валидные ссылки.
- **Шаги:**
  1. `POST /api/rooms` с явно переданным source-флагом со значением вне
     `{CALCULATED, MANUAL}` (например `"ESTIMATED"`).
     Ожидание: `400`, `error.room.source.invalid` (Req 4.4).
  2. `GET /api/rooms/count` — без изменений.
- **Ожидаемый результат:** невалидный source отклонён `400`.

### Фича D. Generic CRUD и project-scoping (`/api/rooms`)

_Требования: 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 5.7_
Повторяемость: генератор `run-id` + teardown; вспомогательный не-ADMIN
пользователь и членства создаются на прогон и убираются в teardown.

#### TC-D1. Полный жизненный цикл read/update/delete

- **Предусловия:** ADMIN-token; валидные ссылки; `run-id`.
- **Шаги:**
  1. `POST /api/rooms` (ручная комната). Ожидание: `201`, запомнить `id`.
  2. `GET /api/rooms/{id}`. Ожидание: `200`, тело содержит созданную комнату.
  3. `PUT /api/rooms/{id}` с изменённым `label: "Room {run-id} updated"`.
     Ожидание: `200`, поле обновлено.
  4. `GET /api/rooms/{id}` — проверить, что `label` обновлён. Ожидание: совпадает.
  5. `DELETE /api/rooms/{id}`. Ожидание: `200`/`204`.
  6. `GET /api/rooms/{id}` — Ожидание: `404` (удалено).
- **Ожидаемый результат:** CRUD-жизненный цикл работает через generic контроллер
  (Req 5.1, 7.6).

#### TC-D2. Reference-фильтр по `project.id`

- **Предусловия:** ADMIN-token; два проекта `P1`, `P2`; по комнате в каждом; `run-id`.
- **Шаги:**
  1. Создать комнату в `P1` и комнату в `P2`. Ожидание: обе `201`.
  2. `GET /api/rooms?filter=project.id==<P1.id>` (в синтаксисе FOR-04-01 фильтра).
     Ожидание: `200`, в выдаче только комната(ы) `P1`, комнаты `P2` отсутствуют.
  3. `GET /api/rooms?filter=project.id==<P2.id>`. Ожидание: только комнаты `P2`.
  4. **Teardown:** `DELETE` обеих комнат.
- **Ожидаемый результат:** фильтр по `project.id` возвращает только совпадающие
  комнаты (Req 5.7).

#### TC-D3. Reference-фильтр по `roomType.id`

- **Предусловия:** ADMIN-token; два разных `roomType` `RT1`, `RT2`; по комнате
  каждого типа; `run-id`.
- **Шаги:**
  1. Создать комнату типа `RT1` и комнату типа `RT2`. Ожидание: обе `201`.
  2. `GET /api/rooms?filter=roomType.id==<RT1.id>`.
     Ожидание: `200`, только комнаты `RT1`.
  3. `GET /api/rooms?filter=roomType.id==<RT2.id>`. Ожидание: только комнаты `RT2`.
  4. **Teardown:** `DELETE` обеих комнат.
- **Ожидаемый результат:** фильтр по `roomType.id` возвращает только совпадающие
  комнаты (Req 5.7).

#### TC-D4. Несуществующая ссылка `projectId`/`roomTypeId` отклоняется

- **Предусловия:** ADMIN-token.
- **Шаги:**
  1. `POST /api/rooms` с `projectId` несуществующего проекта.
     Ожидание: `404`, ошибка указывает на поле `project`
     (`error.entity.not.found`), ничего не создано (Req 5.6).
  2. `POST /api/rooms` с `roomTypeId` несуществующего типа.
     Ожидание: `404`, ошибка указывает на поле `roomType`, ничего не создано.
- **Ожидаемый результат:** ссылки на несуществующие строки отклоняются `404`.

#### TC-D5. Не-ADMIN LIST фильтруется по членству в проекте

- **Предусловия:** ADMIN-token; не-ADMIN пользователь `U` (роль MANAGER/FOREMAN);
  проекты `PA` (U — член), `PB` (U — НЕ член); по комнате в каждом; token
  пользователя `U`; `run-id`.
- **Шаги:**
  1. (ADMIN) Создать комнату в `PA` и комнату в `PB`. Ожидание: обе `201`.
  2. (ADMIN) Обеспечить членство `U` в `PA` через `project_members`, но не в `PB`.
  3. `POST /api/auth/login` под `U` → получить token `U`.
  4. (U) `GET /api/rooms`. Ожидание: `200`, в выдаче комната(ы) `PA`, комнат `PB`
     нет (Req 5.3).
  5. **Teardown:** `DELETE` обеих комнат; убрать членство/пользователя.
- **Ожидаемый результат:** не-ADMIN видит только комнаты проектов своего членства.

#### TC-D6. ADMIN обходит ABAC и membership-фильтрацию

- **Предусловия:** ADMIN-token; комнаты в проектах, где ADMIN формально не член;
  `run-id`.
- **Шаги:**
  1. (не-ADMIN) Создать/подготовить комнату в проекте `PX`.
  2. (ADMIN) `GET /api/rooms`. Ожидание: `200`, комната `PX` присутствует в выдаче
     (Req 5.4).
  3. (ADMIN) `GET /api/rooms/{id}` этой комнаты. Ожидание: `200`.
  4. **Teardown:** `DELETE`.
- **Ожидаемый результат:** ADMIN видит и читает все комнаты независимо от членства.

#### TC-D7. Не-член by-id read/update/delete отклоняется

- **Предусловия:** не-ADMIN `U`; комната в проекте `PB`, где `U` НЕ член; token `U`;
  `run-id`.
- **Шаги:**
  1. (ADMIN) Создать комнату в `PB`. Ожидание: `201`, запомнить `id`.
  2. (U) `GET /api/rooms/{id}`. Ожидание: `403`/`404` (доступ запрещён, тело
     комнаты не возвращается) (Req 5.5).
  3. (U) `PUT /api/rooms/{id}`. Ожидание: `403`/`404`, комната не изменена.
  4. (U) `DELETE /api/rooms/{id}`. Ожидание: `403`/`404`, комната не удалена.
  5. (ADMIN) `GET /api/rooms/{id}` — убедиться, что комната цела. Ожидание: `200`.
  6. **Teardown:** `DELETE` (ADMIN).
- **Ожидаемый результат:** by-id операции над не-членской комнатой запрещены,
  цель не изменяется и не возвращается.

### Фича E. Метаданные и reference-дескрипторы

_Требования: 5.7, 8.2_
Повторяемость: только чтение, teardown не требуется.
