> Документ следует стандарту `.kiro/steering/test-cases.md`. Спека **смешанного типа (API + UI)**,

## Окружение и предусловия (общие)

**Запуск стека.** В корне репозитория: `docker compose up`. Поднимаются `postgres` (:5432),
`liquibase` (миграции, включая `040-create-projects.xml` и `041-seed-projects-resource.xml`),
`backend` (:8080, профиль `docker`), `frontend` (:3000).

**Базовые URL.**
- API: `http://localhost:8080`
- UI: `http://localhost:3000`
- Auth: `POST http://localhost:8080/api/auth/login`

**Первый ADMIN.** Поднимается через переменные окружения `FOREMEN_ADMIN_CREATE=true`,
`FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD` (см. `.env`/`docker-compose.yml`).

**Получение токена (используется во всех API-кейсах).**
```
POST /api/auth/login
Content-Type: application/json
{ "email": "<FOREMEN_ADMIN_EMAIL>", "password": "<FOREMEN_ADMIN_PASSWORD>" }
→ 200 { "accessToken": "<JWT>", ... }
```
Далее заголовок `Authorization: Bearer <JWT>` во всех защищённых запросах.

### Стратегия повторяемости (обязательно, общая для всех наборов)

Выбранная стратегия — **генератор уникальных данных + teardown**:

- **Генератор `run-id`.** На каждый прогон формируется `run-id` = UNIX-timestamp или UUID.
  Все создаваемые сущности используют `run-id` в уникальных полях:
  - имя проекта: `Project {run-id}`;
  - email нового клиента: `test+{run-id}@example.com`;
  - при нескольких проектах в одном прогоне добавляется порядковый суффикс: `Project {run-id}-1`,
    `Project {run-id}-2`.
- **Teardown.** В конце каждого сценария созданные проекты удаляются
  (`DELETE /api/projects/{id}` под ADMIN). Созданные INVITED-клиенты деактивируются/удаляются
  штатным admin-эндпоинтом пользователей (`DELETE /api/users/{id}` под ADMIN), либо остаются с
  уникальным `run-id`-email и не мешают повторным прогонам.
- Благодаря уникальности `run-id` сценарии запускаются многократно без ручной чистки БД: даже без
  teardown повторный прогон не конфликтует по имени/email.

Каждая группа ниже дополнительно указывает, какие сущности она создаёт и удаляет.

# API-тесты

## Группа A. Кастомное создание проекта `POST /api/projects` (Requirements 2, 3.1)

**Предусловия группы:** ADMIN-токен получен; известны минимум два существующих `userId`
(например, сам ADMIN и один MANAGER/FOREMAN) и их `projectRoleId` (роли из `roles`); известен
`roleId`/`code=CLIENT` (для сценария existing-client — существующий CLIENT-пользователь).
**Повторяемость:** генератор `run-id`; teardown — удаление созданного проекта и (для newClient)
созданного клиента.

### TC-A1. Создание проекта с командой и существующим клиентом (existing-client)
**Требования:** 2.1, 2.2, 2.3, 2.4, 2.6, 2.7, 2.10
**Предусловия:** есть существующий CLIENT-пользователь `existingClientUserId`.
**Шаги:**
1. `POST /api/projects` с телом:
   ```json
   {
     "name": "Project {run-id}",
     "area": 120.50,
     "status": "ACTIVE",
     "members": [ { "userId": <U1>, "projectRoleId": <R1> } ],
     "client": { "existingClientUserId": <existingClientUserId> }
   }
   ```
   — Ожидание: **201 Created**, тело содержит сгенерированный `id` и `status": "ACTIVE"`.
2. `GET /api/projects/{id}` под ADMIN.
   — Ожидание: 200; `members` содержит участника `<U1>` и участника-клиента с `roleCode == "CLIENT"`;
   поле `client` заполнено (userName клиента).
3. Teardown: `DELETE /api/projects/{id}` → 204/200.
**Ожидаемый результат:** проект создан транзакционно; команда и клиент назначены через `project_members`.

### TC-A2. Создание с новым клиентом (newClient → INVITED + приглашение)
**Требования:** 2.5, 2.8, 2.6, 2.10
**Шаги:**
1. `POST /api/projects`:
   ```json
   {
     "name": "Project {run-id}",
     "members": [ { "userId": <U1>, "projectRoleId": <R1> } ],
     "client": { "newClient": { "name": "Client {run-id}", "email": "test+{run-id}@example.com" } }
   }
   ```
   — Ожидание: **201 Created**; в теле проект с `id`, `status": "DRAFT"` (по умолчанию).
2. `GET /api/users?filter=email==test+{run-id}@example.com` (или admin-поиск).
   — Ожидание: создан пользователь со статусом `INVITED`, без пароля, роль `CLIENT`.
3. `GET /api/projects/{id}`.
   — Ожидание: у проекта есть участник-клиент `roleCode == "CLIENT"`; поле `client` = новый клиент.
4. Teardown: удалить проект и созданного клиента.
**Ожидаемый результат:** создан INVITED CLIENT, отправлено письмо-приглашение (FOR-03-02),
клиент назначен под серверной ролью CLIENT.

### TC-A3. Статус по умолчанию = DRAFT при отсутствии `status`
**Требования:** 2.3
**Шаги:**
1. `POST /api/projects` c телом без поля `status` (только `name` + пустой/минимальный `members`).
   — Ожидание: 201; `status": "DRAFT"`.
2. Teardown: удалить проект.

### TC-A4. Откат транзакции при неизвестном участнике (all-or-nothing)
**Требования:** 2.9, 3.7
**Шаги:**
1. `POST /api/projects` с `members: [{ "userId": 999999999, "projectRoleId": <R1> }]` (несуществующий userId).
   — Ожидание: **4xx** (404 `error.entity.not.found`), в теле указано проблемное поле.
2. `GET /api/projects?filter=name==Project {run-id}` под ADMIN.
   — Ожидание: 200, пустой список — проект НЕ создан.
3. Проверить (admin-поиск пользователей), что новый клиент не создан.
**Ожидаемый результат:** ни `projects`, ни `project_members`, ни `users` не изменились.

### TC-A5. Откат при дублировании участника `(userId, projectId)`
**Требования:** 2.9, 3.8
**Шаги:**
1. `POST /api/projects` с двумя одинаковыми элементами `members` (один и тот же `userId`).
   — Ожидание: **409** `error.project.member.duplicate`; проект не создан (откат).
2. Проверить отсутствие проекта по `name`.

### TC-A6. Откат при дублирующемся email нового клиента
**Требования:** 2.9, 3.9
**Предусловия:** уже существует пользователь с email `dup+{run-id}@example.com` (создать в setup).
**Шаги:**
1. `POST /api/projects` с `newClient.email = dup+{run-id}@example.com`.
   — Ожидание: **409** (duplicate-email), откат; проект не создан.

### TC-A7. Отказ generic-create (create не поддерживается)
**Требования:** 3.1, 2.1
**Замечание:** кастомный `POST /api/projects` — единственный вход; generic bulk/generic create отключён на уровне сервиса.
**Шаги:**
1. Выполнить generic-create путь (bulk create payload, если контракт `AdminController` его допускает).
   — Ожидание: **400** `error.project.create.unsupported`; ничего не сохранено.

### TC-A8. Валидация базовых полей на создание
**Требования:** 3.5
**Шаги (по одному запросу на кейс):**
1. `name` пустое/blank → **4xx**, поле `name` в ошибке, ничего не сохранено.
2. `name` длиной > 255 → **4xx**.
3. `area = 0` или `area < 0.01` → **4xx**, поле `area`.
4. `area > 999999999.99` → **4xx**.
5. `status = "WRONG"` → **4xx**, поле `status`.

### TC-A9. Валидация диапазона дат `endDate >= startDate`
**Требования:** 3.6, 8.8
**Шаги:**
1. `POST /api/projects` с `startDate = 2025-06-01`, `endDate = 2025-05-01`.
   — Ожидание: **4xx** `error.project.date.range`; ничего не сохранено.

## Группа B. Generic read/update/delete (Requirements 3.2, 3.3, 3.4)

**Предусловия:** создан проект через TC-A1 (или отдельный setup-проект).
**Повторяемость:** генератор `run-id`; teardown удаляет проект (сам delete-кейс и служит teardown).

### TC-B1. Чтение проекта по id
**Требования:** 3.2, 3.4
**Шаги:**
1. `GET /api/projects/{id}` под ADMIN.
   — Ожидание: 200; тело содержит `name, address, googlePlaceId, formattedAddress, latitude,
   longitude, area, startDate, endDate, status`, а также `members` и производный `client`.

### TC-B2. Обновление базовых полей
**Требования:** 3.2, 3.3
**Шаги:**
1. `PUT /api/projects/{id}` с изменёнными `name`, `area`, `status = "ON_HOLD"`.
   — Ожидание: 200; изменения сохранены.
2. `GET /api/projects/{id}` — новые значения присутствуют.

### TC-B3. Валидация на обновление (диапазон дат / базовые поля)
**Требования:** 3.5, 3.6
**Шаги:**
1. `PUT` с `endDate < startDate` → **4xx** `error.project.date.range`, изменений нет.
2. `PUT` с `status = "WRONG"` → **4xx**, изменений нет.

### TC-B4. Удаление проекта
**Требования:** 3.2
**Шаги:**
1. `DELETE /api/projects/{id}` под ADMIN → 204/200.
2. `GET /api/projects/{id}` → **404** (проекта нет).

## Группа C. Project-scoped anchor: фильтрация по членству (Requirements 4)

**Предусловия:** ADMIN-токен; отдельный non-ADMIN пользователь (например FOREMAN) с известными
кредами; известен проект, где non-ADMIN является участником, и проект, где он НЕ участник.
**Повторяемость:** генератор `run-id`; setup создаёт два проекта (member/non-member), teardown их удаляет.

### TC-C1. Non-ADMIN LIST возвращает только «свои» проекты
**Требования:** 4.2
**Шаги:**
1. Логин под non-ADMIN.
2. `GET /api/projects`.
   — Ожидание: 200; в списке только проекты, где есть строка `project_members` с этим пользователем;
   проект-«чужой» отсутствует.

### TC-C2. ADMIN обходит фильтрацию членства
**Требования:** 4.3
**Шаги:**
1. `GET /api/projects` под ADMIN.
   — Ожидание: 200; видны все проекты, включая те, где ADMIN не участник.

### TC-C3. Non-ADMIN без членства получает пустой список (не ошибку)
**Требования:** 4.4
**Предусловия:** non-ADMIN пользователь не состоит ни в одном проекте.
**Шаги:**
1. `GET /api/projects` под таким пользователем.
   — Ожидание: **200**, пустая коллекция (0 проектов), без ошибки.

### TC-C4. Non-ADMIN по id «чужого» проекта: read/update/delete запрещены
**Требования:** 4.5
**Шаги:**
1. `GET /api/projects/{foreignId}` под non-ADMIN → отказ (404, без данных проекта).
2. `PUT /api/projects/{foreignId}` → отказ (404), данные не изменены.
3. `DELETE /api/projects/{foreignId}` → отказ (404/403), проект не удалён.

## Группа D. Фильтры LIST: `status`, member-фильтр, client-фильтр (Requirement 8.1, 8.2, 3.4)

**Предусловия:** через кастомный create созданы несколько проектов с разными `status`, разными
участниками и разными клиентами. Все имена содержат `run-id`.
**Повторяемость:** генератор `run-id`; teardown удаляет все созданные проекты.

### TC-D1. Фильтр по `status`
**Требования:** 7.7, 8.2
**Шаги:**
1. `GET /api/projects?filter=status==ACTIVE` под ADMIN.
   — Ожидание: 200; только проекты со `status == ACTIVE`.

### TC-D2. Member-фильтр `members.user.id~in~<ids>`
**Требования:** 8.2, 3.4
**Шаги:**
1. `GET /api/projects?filter=members.user.id~in~<U1>,<U2>`.
   — Ожидание: 200; ровно те проекты, где есть участник из `{U1,U2}`, без дублей (distinct).
2. Одиночный вариант `members.user.id==<U1>` — только проекты с участником `U1`.

### TC-D3. Client-фильтр (составной предикат)
**Требования:** 8.1, 8.2
**Шаги:**
1. `GET /api/projects?filter=members.user.id~in~<clientUserId> AND members.projectRole.code==CLIENT`.
   — Ожидание: 200; только проекты, чей CLIENT-участник входит в выбранные; проекты, где `clientUserId`
   является НЕ-CLIENT-участником, исключены.
2. Проверить, что list/read DTO содержит `members` и производное `client`.

## Группа E. Прокси Google Places `/api/addresses/*` (Requirement 5)

**Замечание по расхождению (design Change 1):** прокси перенесён с `/api/projects/address/*`
(под `PROJECTS`/`READ`) на нейтральный **`/api/addresses/*`** с правилом **authenticated-any-user**
(без ABAC-привязки к `PROJECTS`). Ниже кейсы проверяют актуальный контракт.
**Предусловия:** в docker-стеке `foremen.google-places.enabled=true`, задан валидный (или тестовый)
`GOOGLE_PLACES_API_KEY`. Реальные вызовы Google в docker-прогоне допускаются как smoke; детерминизм
формы ответа покрыт бэкенд-интеграционными тестами (`AddressProxyIT`) с моком клиента.
**Повторяемость:** запросы идемпотентны, данные не создаются — teardown не требуется.

### TC-E1. Autocomplete возвращает предсказания (description + placeId)
**Требования:** 5.1, 5.3
**Шаги:**
1. `GET /api/addresses/autocomplete?query=Warsaw` под аутентифицированным пользователем.
   — Ожидание: 200; массив предсказаний, каждое с `description` и `placeId`; **ключ API отсутствует** в теле.

### TC-E2. Details возвращает адресную геометрию
**Требования:** 5.2, 5.3
**Шаги:**
1. Взять `placeId` из TC-E1; `GET /api/addresses/details?placeId=<placeId>`.
   — Ожидание: 200; `formattedAddress`, `latitude`, `longitude` (+ компоненты при наличии);
   ключ API отсутствует в теле.

### TC-E3. Доступ authenticated-any-user, анонимный → 401
**Требования:** 5.6 (в редакции design Change 1)
**Шаги:**
1. `GET /api/addresses/autocomplete?query=Warsaw` под пользователем БЕЗ грантов `PROJECTS`
   (любой аутентифицированный).
   — Ожидание: 200 (доступ есть — не привязан к `PROJECTS`).
2. Тот же запрос БЕЗ заголовка `Authorization`.
   — Ожидание: **401** (security-chain требует аутентификацию).

### TC-E4. Серверное дорешение адреса при создании (googlePlaceId без formatted/lat/lng)
**Требования:** 5.7
**Шаги:**
1. `POST /api/projects` с непустым `googlePlaceId` и БЕЗ `formattedAddress`/`latitude`/`longitude`.
   — Ожидание: 201; после `GET /api/projects/{id}` поля `formattedAddress`/`latitude`/`longitude`
   заполнены серверным дорешением через details-lookup.
2. Teardown: удалить проект.

**Требования:** 6.4
**Шаги:**
1. Под каждой ролью: `GET /api/projects` (своих) → 200; `POST`/`PUT`/`DELETE` → 403.

**Требования:** 6.1, 6.2

# Браузерные (headless) сценарии — админ-страница `/projects`

> Исполняются браузерным движком (headless-browser / automation). Результат — MD-репорт с таблицами
> (шаг → действие → ожидание → факт → статус). Скриншоты не требуются.
> **Предусловия групп U*:** UI поднят на `http://localhost:3000`; выполнен вход под ADMIN; для кейсов
> гейтинга — дополнительно учётки non-ADMIN ролей.
> **Повторяемость:** генератор `run-id` (имена проектов/клиентов уникальны); teardown — удаление
> созданных проектов через UI-диалог удаления или API.

## Группа U1. Список проектов (Requirements 8.1, 8.2, 8.3)

### TC-U1.1. Рендер таблицы и колонок
**Требования:** 8.1
**Шаги:**
1. Перейти на `/projects`.
   — Ожидание: лениво загружается `ProjectsPage`, отрисован `DataTable` (resource `PROJECTS`).
2. Проверить заголовки колонок: `name`, `address`/`formattedAddress`, `area`, `startDate`,
   `endDate`, `status`, а также колонки `members` и `client`.
   — Ожидание: все перечисленные колонки видимы; **нет** колонки-ссылки client_id/manager_id как FK.

### TC-U1.2. Бейдж статуса на каждую из пяти величин
**Требования:** 8.2
**Предусловия:** в списке есть проекты со статусами DRAFT/ACTIVE/ON_HOLD/COMPLETED/CANCELLED.
**Шаги:**
1. Для каждой строки проверить ячейку `status`.
   — Ожидание: ровно один локализованный бейдж, соответствующий значению `ProjectStatus`.

### TC-U1.3. Пустое состояние
**Требования:** 8.3
**Шаги:**
1. Применить фильтр, дающий 0 строк (например `name` с уникальным несуществующим `run-id`).
   — Ожидание: локализованное сообщение пустого состояния (`projects.*`), 0 строк данных.

### TC-U1.4. Ячейки members и client
**Требования:** 8.1, 8.2
**Шаги:**
1. Для проекта с участниками проверить ячейку `members`.
   — Ожидание: по строке на участника в формате `"{userName} — {roleName}"`.
2. Проверить ячейку `client`.
   — Ожидание: имя участника-CLIENT; плейсхолдер, если клиента нет.

### TC-U1.5. Серверные search/sort/filter/pagination

# Регрессия

Обязательная регрессионная группа. Прогоняется после изменений в проекте, ABAC-матрице,
project-scoping (FOR-03-04/04a) или фильтр-грамматике (FOR-04-01).

### RG-1. Сквозной путь создания → скоупинг → чтение
**Покрывает:** 2.6, 4.2, 3.4
**Шаги:**
1. ADMIN создаёт проект с командой (в т.ч. non-ADMIN участник) и клиентом → 201.
2. non-ADMIN участник `GET /api/projects` → видит этот проект (членство).
3. non-ADMIN `GET /api/projects/{id}` → 200, DTO содержит `members` и `client`.
4. Teardown: ADMIN удаляет проект.

### RG-2. DELETE только ADMIN не «утёк» на другие роли
**Покрывает:** 6.5
**Шаги:**
1. Под каждой не-ADMIN ролью `DELETE /api/projects/{id}` → 403.
2. Под ADMIN → успех.

**Покрывает:** 1.6, 1.7, 6.6
**Шаги:**

   — Ожидание: `040-create-projects.xml` и `041-seed-projects-resource.xml` помечены `MARK_RAN`,
   дублей `resources`/`role_resources`/`role_resource_operations` не добавлено; таблица не изменена.

### RG-4. Прокси адресов остаётся доступен без грантов `PROJECTS`
**Покрывает:** 5.6 (design Change 1)
**Шаги:**
1. Аутентифицированный пользователь без `PROJECTS` вызывает `/api/addresses/autocomplete` → 200.
2. Анонимный → 401.
