# Тест-кейсы: FOR-05-01 — Оболочка рабочего пространства проекта

> Тип спеки: **UI (фронтенд-only)**. Тест-кейсы предназначены для «живого тестировщика», но
> исполняются браузерным движком (headless-браузер / browser automation). **Артефакт прогона —
> MD-репорты с таблицами** (шаг → ожидание → факт → статус), скриншоты не требуются.
>
> Спека не добавляет бэкенд-сущностей, таблиц, миграций и ABAC-ресурсов. Проверяется только
> клиентское поведение: маршрут `/projects/:projectId/:tab`, клиентское состояние «рабочего
> проекта», всегда-видимая поверхность рабочего проекта, стадийно-зависимый набор вкладок,
> URL-driven активная вкладка с памятью по проекту, виджет готовности, подпись режима, переопределение
> клика по строке в списке проектов и i18n с единственным активным языком.

## Общие предусловия для всех кейсов

- Приложение фронтенда запущено и доступно в браузере (dev-сервер `http://localhost:3000` либо
  собранный фронт из docker-стека). Бэкенд с проектами доступен по `/api/projects` (зависимость от
  FOR-04-13). Там, где проверяется деградация, бэкенд/эндпоинт намеренно недоступен.
- Тестировщик аутентифицирован. По умолчанию используется пользователь с ролью **ADMIN**
  (полный набор ABAC-грантов), кроме кейсов, где явно указан пользователь с ограниченными правами.
- Активный язык интерфейса зафиксирован в начале кейса (RU или PL). По умолчанию — RU.
- Ключевые `localStorage`-ключи, затрагиваемые спекой:
  - `foremen.workingProjectId` — id рабочего проекта;
  - `foremen.projectTab.<projectId>` — последняя активная вкладка конкретного проекта.

## Стратегия повторяемости (обязательно)

Спека не пишет в БД, поэтому основной источник «грязи» между прогонами — это `localStorage` браузера
и созданные при подготовке проекты. Применяем **комбинацию генератора и teardown**:

1. **Run-id генератор.** В начале прогона формируется `run-id` = timestamp/uuid (например,
   `20260101-120000-ab12`). Все создаваемые в подготовке проекты именуются с `run-id`
   (`Проект TC {run-id} [design]`, `Проект TC {run-id} [execution]`), чтобы прогоны не путались.
   Реальные `projectId` фиксируются в переменные прогона `PID_DESIGN`, `PID_EXEC`, `PID_OTHER`.
2. **Изоляция состояния через чистый профиль.** Каждый кейс стартует с **чистого браузерного
   контекста** (новый контекст headless-браузера или предварительная очистка `localStorage`).
   Обязательный шаг Setup каждого кейса — удалить ключи `foremen.workingProjectId` и все
   `foremen.projectTab.*` (например, выполнить `localStorage.clear()` на домене приложения) до
   начала сценария.
3. **Teardown.** По завершении кейса:
   - очистить `foremen.workingProjectId` и `foremen.projectTab.<PID_*>`;
   - созданные для прогона проекты либо переиспользуются между кейсами (они read-only для этой
     спеки), либо деактивируются/удаляются штатным API проектов в конце всего прогона.
   Поскольку FOR-05-01 ничего в проекты не записывает, достаточно очистки `localStorage`; удаление
   проектов — опциональный финальный teardown прогона, а не каждого кейса.

Каждый кейс ниже явно указывает в предусловиях требуемое состояние `localStorage` и стадию проекта.

### Подготовка данных прогона (однократно перед всеми кейсами)

- Создать штатным способом (через `/projects` или API) минимум три проекта:
  - `PID_DESIGN` — статус из стадии **design** (`DRAFT`);
  - `PID_EXEC` — статус из стадии **execution** (`ACTIVE`);
  - `PID_OTHER` — любой доступный проект для проверки независимости памяти вкладок.
- Убедиться, что тестовый пользователь имеет `PROJECTS`/`READ` (для ADMIN — гарантировано).
- Для кейсов ограниченных прав подготовить пользователя без `PROJECTS`/`READ` и, отдельно,
  пользователя с `PROJECTS`/`READ`, но без части ресурсов вкладок.
