# Тест-кейсы: FOR-05-13 — совместное редактирование сметы (presence + общий черновик)

## Назначение и характер

Вкладка «Kosztorys» редактируется несколькими пользователями одновременно: STOMP поверх WebSocket
(`/api/ws`), состояние — в Redis. Набор включает:

- **Часть A. API/WS-тесты** против поднятого Docker-стека (`http://localhost:8080`, Redis в стеке):
  REST-снимок `GET /api/estimates/project/{id}/collab` и STOMP-кадры (`CONNECT` с
  `Authorization: Bearer`, `SUBSCRIBE /topic/estimate/{id}`, `SEND /app/estimate/{id}/focus|op`).
- **Часть B. Браузерные сценарии** — **два изолированных браузерных контекста** (две сессии)
  против `http://localhost:3000`, исполняются браузерным движком.

Результат — **MD-репорт с таблицами**. Скриншоты не требуются.

## Запуск окружения

1. `docker compose up -d redis backend frontend` (backend с `FOREMEN_COLLAB_ENABLED=true`,
   `REDIS_HOST=redis`).
2. Два пользователя с доступом к одному DRAFT-проекту и `ESTIMATE` UPDATE (например ADMIN + MANAGER
   проекта).

## Стратегия повторяемости

**Teardown.** Сценарии не создают сущностей в БД, кроме сохранений сметы в Фиче 4; черновик и
presence живут в Redis с TTL. В конце набора:
- Discard всех staged-правок в обеих сессиях;
- изменения, сохранённые в Фиче 4, откатываются обратной правкой (тот же work × room, исходный
  объём) и Save;
- `redis-cli DEL collab:est:{pid}:presence collab:est:{pid}:order collab:est:{pid}:edits` (при
  необходимости).

## Фича 1. Транспорт и авторизация (API/WS)

### TC-COL-01 — Апгрейд WebSocket
- Шаги: `GET /api/ws` с заголовками `Upgrade: websocket` → `101 Switching Protocols`; обычный GET →
  400 `Can "Upgrade" only to "WebSocket"`.

### TC-COL-02 — CONNECT без токена отклоняется
- Шаги: STOMP `CONNECT` без `Authorization` → кадр `ERROR`, соединение закрыто.

### TC-COL-03 — Подписка на чужой проект отклоняется
- Шаги: пользователь без доступа к проекту → `SUBSCRIBE /topic/estimate/{pid}` → сообщений нет;
  `GET /api/estimates/project/{pid}/collab` → 404.

## Фича 2. Presence (кто редактирует)

### TC-COL-04 — Появление в ростере
- Шаги:
  1. Сессия A: `CONNECT`, `SUBSCRIBE /topic/estimate/{pid}`, `SEND /app/estimate/{pid}/focus` с
     телом `{"workItemId":null,"roomId":null}` (**без** `content-type: application/json`).
  2. Получен `MESSAGE` с `{"type":"PRESENCE",...}`, в `presence` — сессия A.
  3. `HGETALL collab:est:{pid}:presence` в Redis — запись сессии A, у ключа есть TTL.
- _Покрывает: доп. задачи 2–3_

### TC-COL-05 — Уход из ростера при отключении
- Шаги: сессия A `DISCONNECT`/закрытие сокета → в Redis записи сессии A больше нет; сессия B
  получает PRESENCE без A.

## Фича 3. Общий черновик (UI, две сессии)

### TC-COL-UI-01 — Баннер «кто редактирует» и цветной курсор
- Шаги:
  1. Контекст A (ADMIN) и контекст B (MANAGER) открывают `/projects/{pid}/estimate`.
  2. В обоих виден баннер с именем другого пользователя.
  3. A фокусирует ячейку → в B эта ячейка обведена цветом A с подписью имени.

### TC-COL-UI-02 — Staged-правка видна другому
- Шаги:
  1. A меняет объём ячейки (staged, без Save).
  2. В B ячейка показывает ту же staged-правку и индикатор несохранённых изменений.

### TC-COL-UI-03 — Слияние и «последний выигрывает»
- Шаги:
  1. A и B меняют **разные** ячейки → обе правки в обоих контекстах (слияние).
  2. A и B меняют **одну** ячейку разными значениями → в обоих остаётся последнее значение.

## Фича 4. Сохранение

### TC-COL-UI-04 — Save одной сессии обновляет другую
- Шаги:
  1. A сохраняет.
  2. B получает SAVED и перезагружает матрицу: сохранённые значения видны, сохранённые правки
     исчезли из черновика B, несохранённые правки B (если были) остались.
- Teardown: обратная правка + Save.

### TC-COL-UI-05 — Пересчёт сметы из «Pomieszczenia» обновляет открытую смету (FOR-05-05)
- Шаги:
  1. B держит открытой смету; A на вкладке «Pomieszczenia» меняет размер помещения → диалог
     пересчёта → «Zatwierdź i przelicz».
  2. B получает SAVED и показывает пересчитанные значения без ручной перезагрузки.
- Teardown: вернуть исходный размер (повторное подтверждение).

## Регрессия

- **TC-REG-01** — однопользовательский Save сметы работает без Redis-ошибок (деградация: при
  недоступном Redis Save проходит, presence пуст, в логе WARN).
- **TC-REG-02** — Undo/Redo/Discard в одной сессии работают как раньше.
