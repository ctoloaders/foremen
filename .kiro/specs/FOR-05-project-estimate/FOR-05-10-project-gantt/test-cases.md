# Тест-кейсы: FOR-05-10 — Planning Gantt (Harmonogram, планировочный график проекта)

## Назначение и характер спеки

Спека имеет **и API, и браузерный экран**, поэтому набор включает оба типа:

- **Часть A. API-тесты** — против поднятого в Docker приложения (`http://localhost:8080`). Каждый
  шаг — HTTP-запрос к `Schedule_API` (`/api/project-schedules`) с проверкой статуса, тела и
  заголовков.
- **Часть B. Браузерные сценарии** — против фронтенда (`http://localhost:3000`), исполняются
  браузерным движком (headless / browser automation): вкладка «Harmonogram / График»
  (`/projects/:projectId/scheduleDesign`) и chip `schedule` в `ReadinessWidget`.

Результат прогона — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус).
**Скриншоты не требуются.**

### Покрытие требований

Каждое из требований R1–R17 покрыто минимум одним кейсом. R18 (регрессия и артефакты) покрыт
группой «Регрессия». Соответствие указано строкой `_Покрывает:_` в каждом кейсе.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции,
   включая changesets `152`–`153`), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL API: `http://localhost:8080`; auth — `/api/auth`.
3. Первый ADMIN — через `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
   Логин: `POST /api/auth/login {email, password}` → `accessToken`.
4. Значение `FOREMEN_SCHEDULE_DAILY_OUTPUT_PER_WORKER` не задаётся (используется дефолт `2000`).
5. Дождаться готовности `backend` (`GET /api/work-categories` → 200).

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown.** Единый на прогон `run-id` (timestamp/uuid)
встраивается во все создаваемые идентификаторы:

- проекты: `Gantt Test {run-id}`, `Gantt Locked {run-id}`, `Gantt Empty {run-id}`;
- пользователи: `manager+{run-id}@example.com`, `foreman+{run-id}@example.com`,
  `worker1+{run-id}@example.com`, `worker2+{run-id}@example.com`, `client+{run-id}@example.com`,
  `outsider+{run-id}@example.com`.

Каждый прогон создаёт **новые** проекты, поэтому график (`project_schedules`) и его версия
всегда начинаются с нуля. **Teardown** в конце набора: перевод тестовых проектов в `CANCELLED`
(или удаление admin-API — каскадно удаляет график и полосы), деактивация созданных пользователей.
Сид-данные (ресурс `WORK_SCHEDULE`, роли, категории работ) **только читаются**.

### Тестовые данные (Setup)

Проект `Gantt Test {run-id}`: `startDate = 2026-11-02` (понедельник), `endDate = 2026-11-27`,
статус `DRAFT`. В смете — строки работ в **трёх** категориях с разным `orderNo` (например,
«Prace wstępne, demontaże», «Ściany», «Malowanie»), с ненулевыми `valueNet`. Значения категорий
фиксируются в Setup (`V1`, `V2`, `V3`) из ответа `GET /api/project-schedules` под MANAGER.
Команда: MANAGER, FOREMAN, CLIENT, два WORKER (`ACTIVE`).
