# Тест-кейсы — FOR-05-10b Gantt Granularity (гранулярность графика по работникам)

Документ описывает тест-кейсы для спеки FOR-05-10b. Спека **смешанная (hybrid)**:

- **Бэкенд-часть** (категории работ у пользователя/участника, автосоздание, сохранение полос,
  готовность, ABAC, аудит) проверяется **API-тестами против приложения, поднятого в Docker**.
  Каждый шаг — HTTP-запрос к API с проверкой статуса/тела/заголовков.
- **Интерактивы графика** (цвета на работника, легенда, перетаскивание с каскадом, ресайз, ручное
  создание полоски, алерт автосоздания, мультиселект категорий в Team/invite) проверяются
  **браузерным движком** (headless browser). Каждый шаг — действие в браузере.

Результат любого прогона — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт →
статус). Скриншоты не требуются (ни для API, ни для UI).

---

## Окружение

- Поднять стек из корня репозитория: `docker compose up`. Поднимаются `postgres` (:5432),
  `liquibase` (миграции `154`–`156`), `backend` (:8080, профиль `docker`), `frontend` (:3000).
- Первый ADMIN поднимается через переменные `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
  `FOREMEN_ADMIN_PASSWORD`.
- Базовый URL API — `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
- Для API-прогонов получить JWT ADMIN через `POST /api/auth/login` и слать его в заголовке
  `Authorization: Bearer <token>`.
- UI-прогоны открывают `http://localhost:3000`, логинятся теми же учётными данными.

### Карта эндпоинтов (источник истины — контроллеры)

| Назначение | Метод + путь | Ресурс ABAC |
|---|---|---|
| Создание WORKER (user + membership атомарно) | `POST /api/users/worker` | `USERS` + `PROJECTS/EDIT` |
| Список/правка участников проекта | `GET` / `POST` / `PATCH` / `DELETE /api/project-members` | `PROJECT_MEMBERS` |
| Чтение графика | `GET /api/project-schedules?projectId` | `WORK_SCHEDULE` |
| Сохранение полос | `PUT /api/project-schedules/bars` | `WORK_SCHEDULE` |
| Автосоздание | `POST /api/project-schedules/auto-create` | `WORK_SCHEDULE` |
| Готовность графика | `GET /api/project-schedules/readiness?projectId` | `WORK_SCHEDULE` |
| Готовность команды | `GET /api/project-members/readiness?projectId` | `PROJECT_MEMBERS` |
| Агрегированная готовность | `GET /api/projects/{projectId}/readiness` | `PROJECTS` |

## Стратегия повторяемости (обязательно)

**Генератор `run-id` + teardown.** Каждый прогон использует `run-id = <unix-timestamp>` (или uuid).
Все создаваемые сущности именуются с `run-id`:

- email работника: `worker+{run-id}@example.com` (напр. `worker+1739550000@example.com`);
- если проект создаётся под прогон — его название содержит `run-id`; категории работ берём из
  существующего seed-каталога `work_categories` (не создаём, только читаем id активных C1, C2, C3).

**Teardown** в конце каждого набора:
1. удалить созданных участников проекта — `DELETE /api/project-members?userId&projectId`;
2. деактивировать/удалить созданных WORKER-пользователей;
3. при необходимости вернуть график проекта в исходное состояние (повторный `auto-create` или
   удаление черновых полос).

Каждый набор кейсов явно наследует эту стратегию. Прогоны запускаются многократно без ручной
чистки БД.

**Разовый кейс миграции.** Проверка конвертации существующих полос FOR-05-10 в полудни (changeset
`156`, `×2`) выполняется один раз на dev-базе с заранее созданным FOR-05-10 графиком; помечена
`once` и НЕ входит в повторяемый набор (см. РЕГ-04).

## Фича 1. Категории работ у пользователя-работника (user level, R1)

Тип: **API**. Стратегия повторяемости: генератор `run-id` + teardown (деактивация WORKER).

### TC-01 — Создание WORKER с упорядоченными категориями
**Предусловия:** JWT ADMIN; известны id двух активных `work_categories` (C1, C2); есть проект P.
**Шаги:**
1. `POST /api/users/worker` c `email=worker+{run-id}@example.com`, `projectId=P`,
   `workCategoryIds=[C1, C2]`.
2. Прочитать созданного пользователя для редактирования (user admin read).
**Ожидание:** 1 → 201, пользователь-WORKER создан (роль фиксируется WORKER сервером); 2 →
`workCategories = [C1, C2]` в том же порядке, каждый с локализованным именем (ru → pl → code
fallback). _(R1.1, R1.5)_

### TC-02 — Дубликат категории отклоняется
**Шаги:** `POST /api/users/worker` c `workCategoryIds=[C1, C1]`.
**Ожидание:** 400 `error.user.workCategories.duplicate` с указанием дублирующегося id; пользователь
не создан, строки `user_work_categories` не записаны. _(R1.2)_

### TC-03 — Неизвестная/неактивная категория отклоняется
**Шаги:**
1. `POST /api/users/worker` c `workCategoryIds=[999999]` (несуществующий id).
2. `POST /api/users/worker` c id неактивной категории.
**Ожидание:** оба → 400 `error.user.workCategories.invalid` с указанием id; ничего не изменено. _(R1.3)_

### TC-04 — Для не-WORKER список игнорируется / отклоняется
**Шаги:** создать/изменить пользователя роли MANAGER с попыткой передать `workCategoryIds=[C1]`.
**Ожидание:** список пользователя остаётся пустым (поле не предлагается в UI; API игнорирует или
отклоняет per D-worker-only); чтение не возвращает категорий. _(R1.4)_

### TC-05 — Пустой список допустим
**Шаги:** `POST /api/users/worker` без `workCategoryIds` (или `[]`).
**Ожидание:** 201; `workCategories = []`. _(R1.1 — 0..N)_

## Фича 2. Категории работ у участника проекта (project override, R2)

Тип: **API**. Стратегия повторяемости: генератор `run-id` + teardown (удаление участника).

### TC-06 — Копирование категорий при добавлении в команду
**Предусловия:** существует WORKER-пользователь с `User_Work_Categories = [C1, C2]`.
**Шаги:**
1. `POST /api/project-members` — добавить этого WORKER в проект P.
2. `GET /api/project-members?projectId=P`.
**Ожидание:** 1 → 201; 2 → у участника `workCategories = [C1, C2]` (ордер сохранён, копия из user
default). _(R2.1)_

### TC-07 — Правка категорий участника не меняет дефолт пользователя (независимость)
**Шаги:**
1. `PATCH /api/project-members` c `workCategoryIds=[C2]` для участника.
2. `GET /api/project-members?projectId=P` и чтение пользователя.
**Ожидание:** участник → `[C2]`; пользователь → по-прежнему `[C1, C2]`. _(R2.2, R2.3)_

### TC-08 — Валидация правки участника
**Шаги:**
1. `PATCH /api/project-members` c `workCategoryIds=[C2, C2]`.
2. `PATCH /api/project-members` c `workCategoryIds=[999999]`.
**Ожидание:** 1 → 400 `error.member.workCategories.duplicate`; 2 → 400
`error.member.workCategories.invalid`; в обоих случаях список участника не изменён. _(R2.2)_

### TC-09 — Опущенный список не трогает категории
**Шаги:** `PATCH /api/project-members` без поля `workCategoryIds` (меняем другой атрибут).
**Ожидание:** 200; `workCategories` участника без изменений. _(R2.2 — omitted = unchanged)_

### TC-10 — Team_Member_View возвращает упорядоченные локализованные категории
**Шаги:** `GET /api/project-members?projectId=P`.
**Ожидание:** каждый WORKER-участник несёт `workCategories` как список `{id, name}` в заданном
порядке, имя локализовано. _(R2.4)_

### TC-11 — Удаление участника сбрасывает его категории (cascade)
**Шаги:**
1. `DELETE /api/project-members?userId&projectId`.
2. Повторный `GET /api/project-members?projectId=P`.
**Ожидание:** участник отсутствует; строки `project_member_work_categories` удалены (ON DELETE
CASCADE). _(R2.5)_

## Фича 3. Сохранение полос и назначение (saveBars, R3)

Тип: **API**. Стратегия повторяемости: teardown — вернуть график через `auto-create`.

### TC-12 — Валидность пары (участник, категория)
**Предусловия:** участник M НЕ покрывает категорию C3.
**Шаги:** `PUT /api/project-schedules/bars` c `BarEntry {projectMemberId=M, workCategoryId=C3,
startDay, durationDays}`.
**Ожидание:** 400 `error.schedule.assignment.invalid`; ничего не изменено. _(R3.1, saveBars pairing)_

### TC-13 — Виртуальная полоса непокрытой категории (null member)
**Предусловия:** категория C3 без покрывающего работника.
**Шаги:** `PUT /api/project-schedules/bars` c `BarEntry {projectMemberId=null, workCategoryId=C3,
...}`.
**Ожидание:** 200; записана ровно одна полоса `project_member_id=null` для C3; попытка записать
вторую null-полосу для C3 отклоняется (partial unique index). _(R3.2)_

### TC-14 — Экспозиция полудней как дней, кратных 0.5
**Шаги:** сохранить полосу `durationDays=2.5` (= 5 полудней), затем `GET /api/project-schedules`.
**Ожидание:** 200; в ответе `startDay`, `durationDays`, `finishDay` — кратны 0.5;
`finishDay = (startHalfDays + durationHalfDays − 1)/2`. _(R3.3)_

### TC-15 — Сетка полудней и очистка полосы
**Шаги:**
1. сохранить полосу `durationDays=2.5` (валидно);
2. сохранить `durationDays=2.3` (вне сетки 0.5);
3. сохранить `startDay=null, durationDays=null` для той же пары (очистка).
**Ожидание:** 1 → 200; 2 → 400 `error.schedule.bar.invalid` с указанием полосы; 3 → 200 и полоса
удалена. _(R3.5)_

### TC-16 — Горизонт 3650 дней (7300 полудней)
**Шаги:** `PUT .../bars` c полосой, чей финиш выходит за 7300 полудней.
**Ожидание:** 409 (или 400) `error.schedule.too.long`; ничего не записано. _(R3.4)_

### TC-17 — Один bump версии и одна строка аудита на запись
**Шаги:**
1. `GET /api/project-schedules` — запомнить `version` = V.
2. `PUT .../bars` с валидным набором полос.
3. `GET /api/project-schedules` — прочитать новую версию; прочитать аудит графика.
**Ожидание:** версия = V+1 (ровно +1 на один запрос); добавлена ровно одна строка аудита.
_(R9.2)_

## Фича 4. Автосоздание по категориям работников (R4)

Тип: **API**. Стратегия повторяемости: teardown — повторный `auto-create` / удаление участников.

### TC-18 — Параллельное равное деление общей категории (D-split)
**Предусловия:** два активных WORKER на проекте, у обоих категория C1; оценка содержит работы C1.
**Шаги:** `POST /api/project-schedules/auto-create` c текущим `version`.
**Ожидание:** 200; для C1 — две полосы (по одной на работника), каждая длиной
`perWorkerHalfDays = ceil(ceil(categoryHalfDays)/2)` полудней (минимум 1), обе стартуют с одного
дня (параллельно). _(R4.1)_

### TC-19 — Последовательная раскладка по таймлайну одного работника (D-layout)
**Предусловия:** один WORKER с категориями C1 и C2 (обе в оценке).
**Шаги:** `auto-create`.
**Ожидание:** у работника полоса C2 начинается в полудень, следующий за финишем C1 (встык, без
нахлёста для одного работника). _(R4.3)_

### TC-20 — Нахлёст в 1 день между разными работниками (R-overlap)
**Предусловия:** C1 выполняет работник A, соседняя по ордеру C2 — работник B (множества
непересекающиеся).
**Шаги:** `auto-create`.
**Ожидание:** старт C2 может быть на 2 полудня (1 день) раньше финиша C1, но стартовый полудень
не меньше 1 и не отрицательный. _(R4.4)_

### TC-21 — Категория без работника → виртуальная полоса + алерт
**Предусловия:** в оценке есть категория C3 без покрывающего активного WORKER.
**Шаги:** `auto-create`.
**Ожидание:** 200; для C3 ровно одна полоса `projectMemberId=null` на полную длительность; в ответе
`alert.uncoveredCategories` содержит `{workCategoryId=C3, name}`. _(R4.2, R4.5)_

### TC-22 — Пустая команда не роняет автосоздание (не 409)
**Предусловия:** на проекте нет активных WORKER.
**Шаги:** `auto-create`.
**Ожидание:** 200 (НЕ 409 `error.schedule.crew.empty`); все категории разложены как виртуальные
полосы; `alert.crewEmpty = true`. _(R4.6)_

### TC-23 — Горизонт при автораскладке
**Шаги:** сконструировать оценку, где суммарная раскладка выходит за 7300 полудней.
**Ожидание:** 409 `error.schedule.too.long`; ничего не записано. _(R4 + R3.4)_

### TC-24 — Один bump версии и одна строка аудита на автосоздание
**Шаги:** запомнить `version` V → `auto-create` → прочитать версию и аудит.
**Ожидание:** версия = V+1 (ровно +1); ровно одна строка аудита. _(R4.7)_

## Фича 5. Готовность (readiness, R8)

Тип: **API**. Стратегия повторяемости: генератор + teardown.

### TC-25 — Нет активных работников → блокер team
**Предусловия:** на проекте нет активных WORKER.
**Шаги:**
1. `GET /api/project-schedules/readiness?projectId` (или `GET /api/projects/{id}/readiness`).
2. `GET /api/project-members/readiness?projectId`.
**Ожидание:** область `team` = BLOCKED, присутствует outstanding-item `readiness.team.noWorkers`,
targetTab `team`. _(R8.1)_

### TC-26 — Непокрытая категория → блокер schedule
**Предусловия:** в оценке есть категория C3 без покрывающего активного WORKER.
**Шаги:** `GET /api/project-schedules/readiness?projectId`; `GET /api/projects/{id}/readiness`.
**Ожидание:** область `schedule` = не-ready (BLOCKED), по одному
`readiness.schedule.noWorkerForCategory` на каждую непокрытую категорию (param = локализованное имя
категории), targetTab `team`; `uncoveredCategoryIds` содержит C3. _(R8.2)_

### TC-27 — Полное покрытие → новых блокеров нет
**Предусловия:** есть ≥1 активный WORKER и все категории оценки покрыты.
**Ожидание:** ни `readiness.team.noWorkers`, ни `readiness.schedule.noWorkerForCategory` не
присутствуют. _(R8.3)_

### TC-28 — Готовность — чистое чтение
**Шаги:** несколько раз подряд `GET .../readiness` для проекта без графика.
**Ожидание:** ответ стабилен; строка графика НЕ создаётся побочно (pure read). _(R8.4)_

## Фича 6. ABAC и локализация (R9)

Тип: **API**. Стратегия повторяемости: генератор + teardown.

### TC-29 — Гварды ресурсов
**Шаги:** вызвать от роли без нужных грантов:
1. правку user-категорий без `USERS`;
2. правку member-категорий без `PROJECT_MEMBERS`;
3. чтение/запись графика без `WORK_SCHEDULE`.
**Ожидание:** во всех случаях 403 `error.access.denied`; новый ресурс ABAC не вводится. _(R9.1)_

### TC-30 — Паритет локалей (pl + ru, идентичные наборы)
**Шаги:** проверить наличие всех новых ключей в `pl.json` и `ru.json`, а также в
`messages.properties` / `messages_ru.properties`: `workCategory.multiselect.*`,
`team.member.workCategories.label`, `worker.invite.workCategories.label`,
`schedule.manualBar.*`, `schedule.legend.title`, `schedule.bar.unassigned`,
`schedule.autoCreate.alert.*`, `readiness.team.noWorkers`,
`readiness.schedule.noWorkerForCategory`, и все новые `error.*`.
**Ожидание:** одинаковые наборы ключей в обеих локалях; в UI нет «сырых» ключей. _(R9.3)_

## Фича 7. UI графика — браузерный движок (R5, R6, R7)

Тип: **UI (headless browser)**. Стратегия повторяемости: генератор `run-id` для данных +
teardown; каждый сценарий начинается с чистого открытия вкладки «Harmonogram» проекта.

### TC-31 — Мультиселект категорий в Team / invite (R1, R2 UI)
**Шаги:**
1. открыть диалог приглашения/создания работника;
2. открыть `WorkCategoryMultiSelect`, выбрать C1, затем C2;
3. сохранить; открыть редактор участника в Team-табе.
**Ожидание:** мультиселект показан только для роли WORKER; порядок выбора сохраняется (chips
упорядочены); сохранённые категории видны в редакторе участника и шлются как `workCategoryIds`
в `PATCH`.

### TC-32 — Цвет на работника и легенда
**Шаги:** открыть «Harmonogram» проекта с несколькими работниками.
**Ожидание:** полосы каждого работника окрашены стабильным цветом (хеш от `projectMemberId`);
легенда (`WorkerLegend`) сопоставляет цвет ↔ имя работника. _(R7.1)_

### TC-33 — N полос на категорию (параллельно) + unassigned стиль
**Шаги:** открыть категорию с двумя покрывающими работниками и одну непокрытую категорию.
**Ожидание:** строка категории с двумя работниками показывает две полосы (могут идти параллельно/с
нахлёстом), каждая в своём цвете; виртуальная полоса непокрытой категории — нейтральный
«unassigned» стиль с меткой unassigned. _(R7.2, R7.3)_

### TC-34 — Ручное создание полоски по клику на пустую ячейку
**Шаги:**
1. клик по пустой ячейке (дата × категория) с покрывающими работниками;
2. в диалоге `ManualBarDialog` выбрать работника и подтвердить.
**Ожидание:** диалог предлагает только работников-носителей категории; предзаполняет
авто-длительность; допускает свободный ввод кратно 0.5 (минимум 0.5); после подтверждения полоса
создаётся на клике (snap к 0.5) и проходит валидацию R3. _(R5.1, R5.2, R5.4)_

### TC-35 — Ручное создание для непокрытой категории
**Шаги:** клик по пустой ячейке категории без покрывающих работников.
**Ожидание:** диалог показывает состояние «нет работника» и предлагает только «unassigned
(virtual)» вариант либо блокирует создание (per design). _(R5.3)_

### TC-36 — Каскад при перетаскивании (move)
**Шаги:** перетащить полосу работника на новый старт.
**Ожидание:** последующие полосы ЭТОГО работника сдвигаются — каждая начинается с правого края
предыдущей; полосы ДРУГИХ работников не двигаются; привязка к 0.5 дня, clamp `[0.5, 3650]`.
_(R6.1, R6.2, R5.5)_

### TC-37 — Каскад при ресайзе (resize)
**Шаги:** изменить длину полосы работника (ресайз, не перенос).
**Ожидание:** последующие полосы того же работника переукладываются от нового финиша; другие
работники не затронуты; snap 0.5. _(R6.4)_

### TC-38 — Каскад за горизонт отклоняется
**Шаги:** перетащить/растянуть так, чтобы хвост каскада ушёл за 3650 дней; сохранить.
**Ожидание:** сохранение отклонено `error.schedule.too.long`; черновик не применён. _(R6.3)_
