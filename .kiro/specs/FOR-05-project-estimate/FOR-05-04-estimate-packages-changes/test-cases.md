# Тест-кейсы: FOR-05-04 — Estimate packages & pricing model change

## Общая информация

- **Тип спеки:** API-only (без браузерных экранов). Все сценарии — HTTP-запросы к работающему в
  Docker стеку приложения, а не Testcontainers/юнит-слой.
- **Base URL:** `http://localhost:8080`.
- **Окружение:** `docker compose up` в корне репозитория поднимает `postgres` (:5432),
  `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
- **Auth:** эндпоинты аутентификации — под `/api/auth` (например, `POST /api/auth/login`).
  Первый ADMIN-пользователь поднимается через переменные окружения `FOREMEN_ADMIN_CREATE=true`,
  `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Все запросы ниже (если не указано иное)
  выполняются с Bearer-токеном ADMIN, полученным через `POST /api/auth/login`.
- **Стратегия повторяемости:** генератор данных. Каждый прогон использует уникальный `run-id`
  (timestamp или UUID), который подставляется в имена создаваемых сущностей (работы, пакеты
  сборки/override, группы и позиции ассортимента), например `Работа-облицовка-{run-id}`,
  `Группа-Сантехника-{run-id}`. Это позволяет запускать сценарии многократно без ручной чистки
  БД — коллизий по уникальным ограничениям (`work_item_id` UNIQUE на `work_volume_formulas`,
  `(work_item_id, offer_package_id)` UNIQUE на `work_package_overrides` и т.д.) не возникает,
  так как каждый прогон работает с новыми work item'ами. Явный teardown не требуется, но там где
  тест-кейс создаёт сущность специально для проверки cycle/404 и т.п., это отмечено в шагах.

## Обозначения

- `{run-id}` — уникальный суффикс прогона (например, `20250601-153000` или UUID v4).
- `{ADMIN_TOKEN}` — Bearer-токен ADMIN, полученный в предусловии окружения.
- Все запросы к защищённым ресурсам без токена или с токеном роли без прав ожидают `401`/`403`
  согласно ABAC-матрице.

## Фича 1: Единая цена работы (без fallback по пакетам)

Покрывает Requirement 1: `WorkPrice` — единая цена `(workItem, currency, netPrice)` без
пакетного измерения и без MAX-fallback на чтении.

### TC-01. Создание работы с единой ценой и её прямое чтение

**Предусловия:** есть ADMIN-токен; существует хотя бы одна валюта (`currency`) в каталоге.

**Шаги:**

1. `POST /api/work-items` с телом `{ "nameRu": "Штукатурка стен-{run-id}", "namePl": "..." }`.
   Ожидание: `201`, тело содержит `id` нового work item.
2. `POST /api/work-prices` с телом `{ "workItemId": <id из шага 1>, "currencyId": <id валюты>,
   "netPrice": 120.50 }`. Ожидание: `201`, тело содержит единственные поля `workItemId`,
   `currencyId`, `netPrice` — без массива `packagePrices` и без полей `validFrom`/`validTo`.
3. `GET /api/work-prices/{id из шага 2}`. Ожидание: `200`, `netPrice` = `120.50` возвращается
   напрямую, без какого-либо признака резолюции/fallback в ответе.
4. `GET /api/work-prices?workItemId=<id из шага 1>`. Ожидание: `200`, ровно один элемент в
   списке (одна цена на работу).

### TC-02. Повторное создание цены для того же work item запрещено (UNIQUE)

**Предусловия:** выполнен TC-01 (work item с ценой создан).

**Шаги:**

1. `POST /api/work-prices` с тем же `workItemId`, что и в TC-01, шаг 2, но другим `netPrice`.
   Ожидание: `400`/`409` (конфликт уникальности `work_item_id`), тело содержит i18n-ключ ошибки,
   не raw-сообщение.

### TC-03. Устаревший endpoint пер-пакетных цен работ отсутствует

**Предусловия:** нет.

**Шаги:**

1. `GET /api/work-package-prices` (или аналогичный путь, если ранее существовал). Ожидание:
   `404` — ресурс `WorkPackagePrice` удалён (Requirement 1.4/8.2).

## Фича 2: CRUD формул объёма + валидация + отклонение циклов

Покрывает Requirements 2, 3: `WorkVolumeFormula`, парсер/валидатор/планировщик, cross-work
ссылки, детект циклов при сохранении.

### TC-04. Создание корректной формулы объёма для работы

**Предусловия:** есть work item (создать новый `Работа-А-{run-id}` через
`POST /api/work-items`).

**Шаги:**

1. `POST /api/work-volume-formulas` с телом `{ "workItemId": <id>, "sourceText":
   "wallArea - windowArea" }`. Ожидание: `201`, тело содержит `sourceText` как передано и
   непустой `parsedAst` (сформированный сервером, не переданный клиентом).
2. `GET /api/work-volume-formulas/{id}`. Ожидание: `200`, `parsedAst` присутствует и
   структурно соответствует бинарной операции `-` над `Var(wallArea)` и `Var(windowArea)`.

### TC-05. Формула с неизвестной переменной отклоняется

**Предусловия:** есть work item `Работа-Б-{run-id}`.

**Шаги:**

1. `POST /api/work-volume-formulas` с `sourceText: "unknownDimension * 2"`. Ожидание: `400`,
   тело содержит i18n-ключ `error.formula.unknown.variable` (не raw-текст).

### TC-06. Формула со ссылкой на неизвестную работу отклоняется

**Предусловия:** есть work item `Работа-В-{run-id}`.

**Шаги:**

1. `POST /api/work-volume-formulas` с `sourceText: "WORKREF(999999999, volume) * 2"` (ссылка на
   несуществующий work item). Ожидание: `400`, тело содержит ключ
   `error.formula.unknown.work.reference`.

### TC-07. Формула с недопустимым оператором отклоняется

**Предусловия:** есть work item `Работа-Г-{run-id}`.

**Шаги:**

1. `POST /api/work-volume-formulas` с `sourceText: "wallArea ^ 2"` (оператор `^` не входит в
   грамматику). Ожидание: `400`, тело содержит ключ `error.formula.illegal.operator`.

### TC-08. Cross-work ссылка резолвится корректно и детерминированно

**Предусловия:** создать два work item — `Работа-Плитка-{run-id}` (без формулы) и
`Работа-Покраска-{run-id}`.

**Шаги:**

1. `POST /api/work-volume-formulas` для `Работа-Покраска-{run-id}` с `sourceText:
   "perimeter * ceilingHeight - WORKREF(<id Работа-Плитка>, volume)"`. Ожидание: `201`.
2. Выполнить эндпоинт производного расчёта объёма комнаты (например,
   `POST /api/rooms/{roomId}/derive-quantities`) для комнаты, где присутствует и
   `Работа-Плитка`, и `Работа-Покраска`, с заданными размерами и заранее известным объёмом
   плитки. Ожидание: `200`, значение `Работа-Покраска` равно `perimeter*ceilingHeight` минус
   уже вычисленный объём `Работа-Плитка` (наблюдается уже посчитанное значение, не 0).
3. Повторить шаг 2 с теми же входными данными. Ожидание: `200`, результат идентичен шагу 2
   (детерминированность, Requirement 3.5).

### TC-09. Ссылка на работу, отсутствующую в комнате, резолвится в 0

**Предусловия:** work item `Работа-Д-{run-id}` с формулой `sourceText: "WORKREF(<id несвязанной
работы, не добавленной в комнату>, volume) + 5"`.

**Шаги:**

1. Выполнить производный расчёт объёма для комнаты, где `Работа-Д` присутствует, но
   работа-ссылка НЕ добавлена в эту комнату. Ожидание: `200`, вычисленное значение равно `5`
   (ссылка на отсутствующую работу = 0, Requirement 3.4).

### TC-10. Циклическая ссылка отклоняется при сохранении

**Предусловия:** создать два work item — `Работа-Е-{run-id}` и `Работа-Ж-{run-id}`.

**Шаги:**

1. `POST /api/work-volume-formulas` для `Работа-Е` с `sourceText:
   "WORKREF(<id Работа-Ж>, volume) + 1"`. Ожидание: `201`.
2. `POST /api/work-volume-formulas` для `Работа-Ж` с `sourceText:
   "WORKREF(<id Работа-Е>, volume) + 1"` (замыкает цикл Е→Ж→Е). Ожидание: `409`, тело содержит
   ключ `error.formula.cycle` и перечисляет обе вовлечённые работы; формула для `Работа-Ж` НЕ
   сохранена (проверить шагом 3).
3. `GET /api/work-volume-formulas?workItemId=<id Работа-Ж>`. Ожидание: `200`, пустой список —
   отклонённая формула не была персистирована.

### TC-11. Деление на ноль в формуле возвращает предметную ошибку

**Предусловия:** work item `Работа-З-{run-id}` с формулой `sourceText: "wallArea / (doorCount -
doorCount)"` (заведомо ноль в знаменателе).

**Шаги:**

1. Выполнить производный расчёт объёма для комнаты с этой работой. Ожидание: `400`, тело
   содержит ключ `error.formula.division.by.zero`.

## Фича 3: Членство в пакете и override-формулы

Покрывает Requirement 4: `WorkPackageOverride` — флаг членства + опциональная override-формула,
без цены.

### TC-12. Override-формула помечает работу членом пакета

**Предусловия:** work item `Работа-И-{run-id}`; существующий `OfferPackage` (например,
`budget`).

**Шаги:**

1. `POST /api/work-package-overrides` с телом `{ "workItemId": <id>, "offerPackageId": <id
   budget>, "overrideSourceText": "wallArea * 1.5" }`. Ожидание: `201`, тело содержит `member:
   true` (установлен автоматически), `overrideParsedAst` заполнен сервером, и НЕТ поля цены.
2. `GET /api/work-package-overrides/{id}`. Ожидание: `200`, `member: true`,
   `overrideSourceText` = `"wallArea * 1.5"`.

### TC-13. Отсутствие override-формулы не устанавливает членство через этот механизм

**Предусловия:** work item `Работа-К-{run-id}`, пакет `norm`.

**Шаги:**

1. `GET /api/work-package-overrides?workItemId=<id>&offerPackageId=<id norm>`. Ожидание: `200`,
   пустой список — по Requirement 4.3 отсутствие override-строки не считается членством.

### TC-14. Override-формула имеет приоритет над формулой по умолчанию

**Предусловия:** work item `Работа-Л-{run-id}` с формулой по умолчанию `sourceText: "wallArea"`
(создать через `POST /api/work-volume-formulas`); тот же work item с override-формулой для
пакета `lux`: `sourceText: "wallArea * 2"`.

**Шаги:**

1. Выполнить производный расчёт объёма для комнаты в контексте пакета `lux` (например,
   `POST /api/rooms/{roomId}/derive-quantities?packageCode=lux`). Ожидание: `200`, вычисленное
   значение равно `wallArea * 2` (override, не формула по умолчанию) — Requirement 4.2/5.3.
2. Выполнить тот же расчёт без указания пакета (или для пакета без override, например
   `budget`). Ожидание: `200`, вычисленное значение равно просто `wallArea` (формула по
   умолчанию используется, когда override для этого пакета отсутствует).

### TC-15. Попытка передать цену в override отклоняется/игнорируется

**Предусловия:** work item `Работа-М-{run-id}`, пакет `budget`.

**Шаги:**

1. `POST /api/work-package-overrides` с телом, включающим лишнее поле `"netPrice": 999`.
   Ожидание: `201` (или `400` при строгой валидации схемы), но в любом случае ответ/сохранённая
   сущность НЕ содержит поля цены — override не может нести цену (Requirement 4.5).

## Фича 5: Пакетная цена zł/m² — ассортимент (CRUD + вычисление)

Покрывает Requirement 6: `AssortmentGroup`, `AssortmentLineItem`, `computePackageZlM2`.

### TC-19. Создание группы ассортимента и позиций с ценами по пакетам

**Предусловия:** ADMIN-токен; существуют `OfferPackage` коды `budget`/`norm`/`lux`.

**Шаги:**

1. `POST /api/assortment-groups` с телом `{ "nameRu": "Сантехника-{run-id}", "namePl": "...",
   "sortOrder": 1 }`. Ожидание: `201`, тело содержит `id`.
2. `POST /api/assortment-line-items` с телом `{ "groupId": <id из шага 1>, "offerPackageId": <id
   budget>, "nameRu": "Унитаз-{run-id}", "minPrice": 300, "avgPrice": 450, "maxPrice": 600,
   "qtyRef50": 1 }`. Ожидание: `201`.
3. `GET /api/assortment-line-items/{id}`. Ожидание: `200`, все поля соответствуют переданным;
   `typicalMaterialId` отсутствует/`null` (не задан).

### TC-20. Вычисление package zł/m² корректно суммирует вклад группы

**Предусловия:** создать группу `Группа-Р-{run-id}` с двумя позициями для пакета `budget`:
`avgPrice=100, qtyRef50=2` и `avgPrice=50, qtyRef50=4` (итог группы = 100*2 + 50*4 = 400,
вклад = 400/50 = 8).

**Шаги:**

1. `GET /api/assortment/compute-package-zl-m2?offerPackageCode=budget` (либо аналогичный
   `POST /api/assortment-groups/compute` — использовать реальный путь из контроллера).
   Ожидание: `200`, значение включает вклад группы `Группа-Р` равный `8.00` в общей сумме по
   пакету `budget`.
2. Изменить `avgPrice` одной из позиций через `PATCH /api/assortment-line-items/{id}` (например,
   на `avgPrice=200`) и повторить шаг 1. Ожидание: `200`, значение пересчитано (не закешировано
   старое) — новый вклад группы = (200*2+50*4)/50 = 12.00 (Requirement 6.5).

### TC-21. Typical product никогда не определяет вычисленное значение

**Предусловия:** позиция ассортимента `Позиция-С-{run-id}` без `typicalMaterialId`, значение
zł/m² вычислено (шаг baseline).

**Шаги:**

1. `GET /api/assortment/compute-package-zl-m2?offerPackageCode=<pkg>`. Зафиксировать значение
   `V1`.
2. `PATCH /api/assortment-line-items/{id}` с `{ "typicalMaterialId": <id существующего
   материала> }` (привязка assist-ссылки), НЕ меняя `minPrice`/`avgPrice`/`maxPrice`/`qtyRef50`.
   Ожидание: `200`.
3. Повторить `GET /api/assortment/compute-package-zl-m2?offerPackageCode=<pkg>`. Ожидание:
   `200`, значение равно `V1` — привязка типового продукта не изменила вычисленную величину
   (Requirement 6.6/6.7).

## Фича 6: Package-collapse норм расхода материалов (MAX)

Покрывает Requirement 7: `WorkMaterialConsumption` без пакетного измерения, MAX-collapse
проверяется через уже смигрированные данные (эндпоинт чтения нормы).

### TC-22. Норма расхода материала не содержит пакетного измерения

**Предусловия:** work item с существующей нормой расхода материала (например, из seed-данных
или созданной через `POST /api/work-material-consumptions` с телом `{ "workItemId": <id>,
"materialTypeId": <id>, "branch": "CONSTRUCTION", "normQty": 1.2 }`).

**Шаги:**

1. `POST /api/work-material-consumptions` как выше. Ожидание: `201`, тело ответа НЕ содержит
   поля `offerPackageId`/`offerPackage` (поле удалено из модели — Requirement 7.2).
2. `POST /api/work-material-consumptions` повторно с тем же `(workItemId, materialTypeId,
   branch)`, другим `normQty`. Ожидание: `400`/`409` — конфликт уникальности по
   `(work_item_id, material_type_id, branch)` (пакетное измерение больше не различает строки).

### TC-23. Итоговая стоимость работы — сумма ровно трёх частей, без 20%-fallback

**Предусловия:** work item с единой ценой, нормой на construction-материал и нормой на
finishing-материал (все три части определены).

**Шаги:**

1. Выполнить агрегированный расчёт стоимости работы, например
   `GET /api/works/{workItemId}/cost-breakdown`. Ожидание: `200`, тело содержит ровно три
   компонента (`workPrice`, `constructionMaterialCost`, `finishingMaterialCost`) и их сумма
   равна общему `totalCost`; никакого поля вида `fallback20Percent` или аналогичного
   присутствовать не должно.
2. Для work item, у которого норма на construction-материал отсутствует (не заведена),
   повторить запрос. Ожидание: `200`, соответствующий компонент помечен как `unpriced: true`
   (или аналогично), а не заменён эвристикой в 20% от стоимости работы (Requirement 7.5).

## Фича 8: ABAC (WORK_CATALOG / PACKAGE_ASSORTMENT) и i18n

Покрывает раздел ABAC дизайна (ресурсы `WORK_CATALOG` для контроллеров формул/override,
`PACKAGE_ASSORTMENT` для контроллеров ассортимента) и i18n-паритет PL/RU для ключей ошибок
формул.

> Примечание: в дизайн-документе рассматривался вариант использовать существующий ресурс
> `WORK_ITEMS` для контроллеров формул/override как альтернативу отдельному коду. Тест-кейсы
> ниже проверяют фактическое поведение через реальный код ресурса, возвращаемый сервером в
> `403`-ответах (`WORK_CATALOG` согласно заданию этой спеки), и должны быть скорректированы по
> факту реализации, если код ресурса иной.

### TC-25. ADMIN имеет полный CRUD-доступ к формулам/override и ассортименту

**Предусловия:** ADMIN-токен.

**Шаги:**

1. `POST /api/work-volume-formulas` с валидным телом. Ожидание: `201` (не `403`).
2. `POST /api/assortment-groups` с валидным телом. Ожидание: `201` (не `403`).

### TC-26. Роль без прав на WORK_CATALOG/PACKAGE_ASSORTMENT получает 403

**Предусловия:** получить токен пользователя роли `WORKER` (или иной роли без прав на эти
ресурсы, согласно матрице дизайна) через `POST /api/auth/login`.

**Шаги:**

1. `POST /api/work-package-overrides` с валидным телом, используя токен `WORKER`. Ожидание:
   `403`, тело содержит i18n-ключ ошибки доступа (не raw-текст).
2. `POST /api/assortment-line-items` с валидным телом, используя токен `WORKER`. Ожидание:
   `403` (сотрудники допускаются максимум к чтению зависит от фактической матрицы — если
   `WORKER` имеет `R`, использовать роль `CLIENT`, у которой нет доступа вовсе, согласно
   design.md).

### TC-27. Роли с правом чтения (MANAGER/FOREMAN/FINANCIER) могут читать ассортимент

**Предусловия:** токен роли `FOREMAN` (или `MANAGER`/`FINANCIER`).

**Шаги:**

1. `GET /api/assortment-groups`, используя токен `FOREMAN`. Ожидание: `200` (роль имеет `R` по
   матрице design.md).
2. `POST /api/assortment-groups` тем же токеном. Ожидание: `403` (только чтение).

### TC-28. Приложение запускается без нарушения ABAC-валидатора (нет полу-аннотированных контроллеров)

**Предусловия:** приложение поднято в Docker (профиль `docker`).

**Шаги:**

1. `GET /actuator/health` (или любой health-check эндпоинт). Ожидание: `200`, `status: UP` —
   если контроллеры формул/override/ассортимента были бы полу-аннотированы
   (`@PermissionResource` без соответствующего `@PermissionOperation` или наоборот), приложение
   не поднялось бы вовсе (`PermissionAnnotationValidator` валит старт).

### TC-29. i18n-паритет PL/RU для ключей ошибок формул

**Предусловия:** доступ к эндпоинтам, возвращающим локализованные сообщения (либо прямая
проверка через воспроизведение ошибки на PL и RU-локали).

**Шаги:**

1. Повторить сценарий TC-05 (`error.formula.unknown.variable`) с заголовком `Accept-Language:
   ru`. Ожидание: `400`, сообщение на русском, не пустое.
2. Повторить тот же запрос с заголовком `Accept-Language: pl`. Ожидание: `400`, сообщение на
   польском, не пустое, не совпадает с raw-ключом (`error.formula.unknown.variable` не должен
   отображаться пользователю напрямую).

## Регрессия

### TC-R01. Целостность архивных таблиц миграции (row count)

**Предусловия:** доступ к БД или к диагностическому эндпоинту, отображающему количество строк
таблицы (если прямого доступа к БД нет для API-тестировщика, этот кейс выполняется через
поддерживающий скрипт `psql`/аналог — отмечено как гибридный API+DB кейс).

**Шаги:**

1. Проверить количество строк в `work_package_prices_archive` — должно быть равно исходному
   количеству строк `work_package_prices` до миграции (зафиксировано в момент миграции;
   сверяется с журналом миграции/документацией релиза).
2. Аналогично для `estimate_line_package_prices_archive` и
   `estimate_line_package_price_history_archive`.
3. Аналогично для `work_material_consumptions_pkg_archive`.
4. Повторный запуск `liquibase update` (или перезапуск `docker compose up` с уже
   смигрированной БД) не создаёт новых строк ни в одной архивной таблице (идемпотентность,
   Requirement 8.4).

### TC-R02. Корректность MAX-collapse резолюции цены и нормы

**Предусловия:** данные до миграции содержали как минимум одну работу с разными ценами по
пакетам (доступно из архивной таблицы `work_package_prices_archive`).

**Шаги:**

1. Для работы, зафиксированной в `work_package_prices_archive` с ценами, например, `budget=100,
   norm=150, lux=200`, выполнить `GET /api/work-prices?workItemId=<id>`. Ожидание: `200`,
   `netPrice = 200` (MAX среди пакетных значений — Requirement 1.5/8.3).
2. Аналогично для нормы расхода материала: работа с нормами `budget=1.0, norm=1.5, lux=2.0` по
   `(materialType, branch)` — `GET /api/work-material-consumptions?workItemId=<id>` должно
   вернуть `normQty = 2.0` (MAX — Requirement 7.3).

### TC-R03. Typical product не влияет на вычисленное значение (повторная проверка)

**Предусловия:** та же настройка, что и TC-21, но выполняется как часть регресс-прогона после
изменений в смежных фичах ассортимента.

**Шаги:**

1. Повторить шаги TC-21 полностью. Ожидание: результат идентичен — привязка/отвязка
   `typicalMaterialId` не влияет на `computePackageZlM2`.

### TC-R04. Единая цена без fallback остаётся в силе после операций с пакетами/override

**Предусловия:** work item с единой ценой (`netPrice=150`) и добавленным override для пакета
`lux` (без цены, только формула).

**Шаги:**

1. `GET /api/work-prices?workItemId=<id>`. Ожидание: `200`, `netPrice = 150` независимо от
   наличия override-записей — override не создаёт и не влияет на цену работы (Requirement
   1.3/4.5).
2. Создать/удалить override-запись для того же work item и повторить шаг 1. Ожидание: значение
   цены не изменилось.
