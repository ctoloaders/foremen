# Тест-кейсы: FOR-05-02 — Интерактивная матрица помещений + полностраничный редактор комнаты

> Тип спеки: **смешанная (API + UI)**.
>
> - **API-часть** — тесты против поднятого в Docker приложения (`docker compose up`, backend на
>   `http://localhost:8080`, auth под `/api/auth`). Проверяются два generic-дополнения бэкенда,
>   переиспользующие существующий ресурс `ROOMS`: bulk-эндпоинты `POST /api/rooms/bulk`
>   (создание) и `PUT /api/rooms/bulk` (гетерогенное обновление в одной транзакции), пофайловый
>   MANUAL-override метрик у комнаты с геометрией и project-scoping/ABAC bulk-операций. Каждый шаг —
>   HTTP-запрос с проверкой статуса/тела. **Артефакт прогона — MD-репорт с таблицами**
>   (шаг → запрос → ожидание → факт → статус).
> - **UI-часть** — сценарии для «живого тестировщика», по факту исполняемые браузерным движком
>   (headless-браузер / browser automation). Проверяется поведение матрицы (inline-редактирование,
>   живая Σ, индикатор несохранённых изменений, undo/redo, discard-all, быстрое создание с
>   обязательным типом комнаты, удаление с подтверждением, bulk-Save очищает stores, read-only при
>   `ACTIVE`, изоляция `localStorage` по проектам) и полностраничного редактора комнаты. **Артефакт
>   прогона — MD-репорт с таблицами** (шаг → действие → ожидание → факт → статус). Скриншоты не
>   требуются.
>
> Спека **не добавляет** новых сущностей, таблиц, полей, ABAC-ресурсов или операций: переиспуются
> `Room`, `/api/rooms` и ресурс `ROOMS` с операциями `CREATE`/`UPDATE`/`READ`/`DELETE`.

## Общие предусловия для всех кейсов

### Окружение (API + UI)

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции),
   `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
3. Базовый URL для UI-тестов: `http://localhost:3000`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`,
   `FOREMEN_ADMIN_EMAIL` (в docker-compose: `cto+1@loaders.dev`), `FOREMEN_ADMIN_PASSWORD`
   (в docker-compose: `alejano123`).
5. Дождаться готовности `backend` (health/readiness) и завершения миграций `liquibase` перед
   запуском кейсов.

### Аутентификация

- **Логин ADMIN.** `POST /api/auth/login` с телом
  `{ "email": "<FOREMEN_ADMIN_EMAIL>", "password": "<FOREMEN_ADMIN_PASSWORD>" }` → **200**,
  в теле `accessToken` (+ `refreshToken`). Токен передаётся в заголовке
  `Authorization: Bearer <accessToken>` во всех последующих API-запросах.
- Для UI по умолчанию тестировщик залогинен под ADMIN (полный набор ABAC-грантов), кроме кейсов,
  где явно указан пользователь с ограниченными правами.
- Активный язык интерфейса зафиксирован в начале UI-кейса (RU или PL). По умолчанию — RU.

### Ключевые `localStorage`-ключи, затрагиваемые спекой

- `foremen.roomMatrix.edits.<projectId>` — store правок существующих комнат;
- `foremen.roomMatrix.newRooms.<projectId>` — store незакоммиченных новых комнат;
- `foremen.workingProjectId` — id рабочего проекта (из FOR-05-01);
- `foremen.projectTab.<projectId>` — последняя активная вкладка проекта (из FOR-05-01).

### Ресурсные предпосылки (FK для API)

- В системе есть ≥ 1 тип комнаты (`GET /api/room-types?size=1` → взять `roomTypeId`, обозначим
  `RT_ID`). Если типов нет — создать штатным способом.
- Тестовый проект в статусе `DRAFT` создаётся через `POST /api/projects` (обозначим `PID_DRAFT`).
- Для UI дополнительно нужен проект в статусе `ACTIVE` (обозначим `PID_ACTIVE`) для проверки
  read-only, и второй `DRAFT`-проект (`PID_OTHER`) для проверки изоляции `localStorage`.

## Стратегия повторяемости (обязательно)

Основные источники «грязи» между прогонами: строки в БД (`rooms`, `projects`) и `localStorage`
браузера. Применяем **комбинацию генератора уникальных меток и явного teardown**.

1. **Run-id генератор.** В начале прогона формируется `run-id` = timestamp/uuid (например,
   `20260101-120000-ab12`). Все создаваемые проекты и комнаты именуются с `run-id`:
   - проекты: `Проект TC {run-id} [draft]`, `Проект TC {run-id} [active]`, `Проект TC {run-id} [other]`;
   - метки комнат (`label`): `Комната {run-id}-{n}`.
   Реальные id фиксируются в переменные прогона: `PID_DRAFT`, `PID_ACTIVE`, `PID_OTHER`,
   `RID_A`, `RID_B`, `RID_GEOM` и т. п.
2. **Teardown API (в конце каждого набора/прогона).**
   - Удалить все созданные на прогон комнаты: `DELETE /api/rooms/{id}` для каждого `RID_*`
     (или bulk-удаление, если применимо).
   - Удалить/деактивировать созданные на прогон проекты (`PID_DRAFT`, `PID_ACTIVE`, `PID_OTHER`)
     штатным API проектов.
   - Разлогинить выданные токены (`POST /api/auth/logout`), если применимо.
   - Seed-данные и системные ресурсы/роли **НЕ изменяются** — все манипуляции идут только над
     созданными на прогон сущностями. Это делает набор запускаемым многократно без ручной чистки БД.
3. **Изоляция `localStorage` (UI).** Каждый UI-кейс стартует с **чистого браузерного контекста**
   (новый контекст headless-браузера либо предварительная очистка). Обязательный шаг Setup каждого
   UI-кейса — удалить ключи спеки на домене приложения:
   - `foremen.roomMatrix.edits.<PID_*>`,
   - `foremen.roomMatrix.newRooms.<PID_*>`,
   - `foremen.workingProjectId`,
   - `foremen.projectTab.<PID_*>`
   (проще всего `localStorage.clear()` на домене приложения). Teardown UI-кейса — та же очистка,
   чтобы pending-состояние прошлого прогона не влияло на следующий.

Каждый кейс ниже явно указывает в предусловиях требуемое состояние `localStorage`, стадию проекта и
созданные сущности прогона.
