# Тест-кейсы: FOR-05-05b — Вкладка «Материалы» (List of materials)

## Назначение и охват

Спека **полностековая**, поэтому тест-кейсы разбиты на два блока:

- **UI-сценарии (браузерный движок)** — проверка вкладки «Материалы» в рабочем пространстве проекта
  (`/projects/:projectId`): рендер матрицы «материалы × комнаты» и группировка по ветвям, ячейки
  комнат (кол-во + единица / брутто) и пустые плейсхолдеры, две цифры `Row_Total` + эффективное
  брутто, поповер деталей материала, панель-дашборд (по ветвям + общий итог) и процент наполнения,
  строки `Absolute_Per_Room_Material` с отключённым резервом, ввод резерва по материалу и массовое
  применение, Save/refetch, пустые состояния (нет материалов / нет комнат), read-only при
  не-DRAFT / отсутствии `ESTIMATE UPDATE`.
- **API-сценарии (поднятый в Docker стек)** — HTTP-проверки против `http://localhost:8080`:
  `GET /api/estimates/project/{id}/materials` (read-модель, passthrough процента наполнения,
  исключение строк с null-net, толерантность к устаревшим ключам резерва),
  `PUT /api/estimates/project/{id}/materials/reserve` с ABAC-гейтингом `ESTIMATE` READ/UPDATE,
  серверная валидация границ (отклонение всей записи), DRAFT-гейт (`409 error.estimate.locked`),
  и миграция `124`.

Артефакт прогона — **MD-репорты с таблицами** (шаг → действие/запрос → ожидание → факт → статус).
Скриншоты не требуются.

Покрываемые требования: **R1–R12** (`requirements.md`). Ссылки на конкретные критерии указаны в
каждом тест-кейсе.

## Окружение и предусловия для запуска

### Docker-стек (для API- и UI-прогонов)

`docker compose up` в корне проекта поднимает:

- `postgres` (:5432),
- `liquibase` (применяет все миграции, включая `124-add-estimate-materials-reserve-map.xml`),
- `backend` (:8080, профиль `docker`; auth-эндпоинты под `/api/auth`),
- `frontend` (:3000).

Первый ADMIN создаётся переменными `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
`FOREMEN_ADMIN_PASSWORD`. Базовый URL API: `http://localhost:8080`. UI: `http://localhost:3000`.

### Аутентификация (общий шаг для API)

```
POST http://localhost:8080/api/auth/login
{ "email": "<email>", "password": "<password>" }
→ 200, { accessToken, refreshToken }
```

Все защищённые запросы отправляются с заголовком `Authorization: Bearer <accessToken>`.

### Стратегия повторяемости (обязательно)

Для ВСЕХ групп ниже применяется **комбинированная стратегия**: **генератор `run-id` + teardown**.

- `run-id` = `Date.now()`/uuid, вычисляется один раз на прогон.
- Все создаваемые сущности именуются с суффиксом `run-id`, чтобы прогоны не конфликтовали:
  - проект: `Materials E2E {run-id}`;
  - пользователи-роли: `estim-reader+{run-id}@example.com`, `estim-editor+{run-id}@example.com`.
- **Teardown** в конце каждого сценария: удалить/деактивировать созданный проект (и связанную с ним
  смету) и временных пользователей. Резерв-мапа живёт на `estimates` (1:1 с проектом), поэтому удаление
  проекта снимает и её.
- Если удаление проекта недоступно тестовому пользователю — teardown сводится к сбросу резерва
  (`PUT .../reserve` с пустым `entries: []`) и переводу сметы в состояние, не мешающее следующему
  прогону; в отчёте фиксируется применённая стратегия.

Каждая группа ниже явно повторяет выбранную стратегию в поле «Повторяемость».

### Общий Setup-фикстур для матрицы (переиспользуется во многих кейсах)

`SETUP-FIXTURE` — подготовка проекта с ненулевой сметой:

1. Создать проект `Materials E2E {run-id}` с ≥2 комнатами.
2. В смете (Estimate tab / FOR-05-05) назначить работы с объёмами и выбрать **конкретные материалы**
   так, чтобы получить как минимум:
   - один `PER_UNIT` материал, используемый в **двух** комнатах (для проверки агрегации и `Row_Total`);
   - один `PER_UNIT` материал, используемый только в **одной** комнате (для проверки пустых
     плейсхолдеров в другой комнате);
   - один `PER_ROOM` материал (`Absolute_Per_Room_Material`), например «1 шт на комнату»;
   - хотя бы одну строку-`Placeholder` (материал не выбран) — должна быть исключена из матрицы;
   - хотя бы один продукт с `concreteNet == null` (для проверки `—` и исключения из итогов) —
     где это достижимо в тестовых данных.
3. Смета остаётся в состоянии **DRAFT**.

`SETUP-FIXTURE` — предусловие для кейсов, где явно указано.

- **Предусловия:** `SETUP-FIXTURE`; пользователь с `ESTIMATE READ`.

### TC-UI-03. Колонки комнат в стабильном порядке; ячейка показывает кол-во+единицу и брутто
- **Тип:** UI (браузер)
- **Требования:** R2.1, R2.2, R2.4, R2.5, R7.1, R7.2, R7.3
- **Предусловия:** `SETUP-FIXTURE`; `ESTIMATE READ`.
- **Шаги:**
  1. Открыть вкладку «Материалы».
     _Ожидание:_ одна колонка на комнату в стабильном порядке (совпадает с порядком комнат костори́са).
  2. Найти `PER_UNIT`-материал, используемый в двух комнатах; проверить его ячейки.
     _Ожидание:_ в каждой из двух комнат ячейка показывает агрегированное количество + единицу и
     **брутто**-цену для этой комнаты.
  3. Проверить агрегацию, когда материал используется несколькими работами в одной комнате.
     _Ожидание:_ количество в ячейке = сумма `Physical_Quantity` по всем ячейкам костори́са этой
     комнаты (R7.3); резерв/округление на уровне ячейки **не применяются** (R2.4).
  4. Сверить брутто ячейки с ручным расчётом.
     _Ожидание:_ `брутто = asIsCellQty × concreteNet × (1 + vat/100)`; net взят **дословно** (R2.5, R7.2).
- **Teardown:** удалить проект/смету.

- **Требования:** R3.1, R3.2, R3.3, R7.4

## Фича 4. Резерв по материалу и массовое применение (R4, R9-UI)

**Повторяемость:** генератор `run-id` + teardown (сброс резерва + удаление проекта).

### TC-UI-08. Ввод резерва по одному материалу стейджится и сохраняется
- **Тип:** UI (браузер)
- **Требования:** R4.1, R4.3, R4.5
- **Предусловия:** `SETUP-FIXTURE`; `ESTIMATE READ+UPDATE`, DRAFT.
- **Шаги:**
  1. Открыть вкладку «Материалы», в строке `PER_UNIT`-материала ввести резерв (например 10%).
     _Ожидание:_ значение застейджено (draft store), `Row_Total` пересчитывается **вживую** без
     запроса на сервер.
  2. Нажать Save.
     _Ожидание:_ выполнен `PUT .../reserve`, read-модель перезапрошена, draft store очищен, значение
     резерва сохранилось.
  3. Обновить страницу, открыть вкладку заново.
     _Ожидание:_ резерв persists; эффективное количество отражает сохранённое значение.
  4. Очистить поле резерва, сохранить.
     _Ожидание:_ резерв трактуется как **unset/identity** (никакого резерва), эффективное = `ceil(asIs)`

### TC-UI-09. Массовое применение раскрывается в записи по каждому материалу

     _Ожидание:_ процент проставлен всем `PER_UNIT`-материалам; `PER_ROOM`-материалы не затронуты (R4.6).
  3. Нажать Save и проверить тело запроса.
