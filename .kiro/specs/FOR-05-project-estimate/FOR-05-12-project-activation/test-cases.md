# Тест-кейсы: FOR-05-12 — Передача проекта в работу (активация с проверкой готовности)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерные экраны**, поэтому набор тест-кейсов включает **оба
типа**:

- **Часть A. API-тесты** — против поднятого в Docker приложения (`http://localhost:8080`). Каждый
  шаг — HTTP-запрос к выделенному эндпоинту активации (`POST /api/projects/{id}/activate`) и к
  общему апдейту (`PUT /api/projects/{id}` со статусом `ACTIVE`), с проверкой статуса, тела и
  структурного 409-ответа «проект не готов».
- **Часть B. Браузерные (UI) сценарии** — против фронтенда (`http://localhost:3000`), исполняются
  браузерным движком (headless-браузер / browser automation). Экраны: виджет готовности
  (`ReadinessWidget`) в шапке проекта стадии проектирования — кнопка «Отдать в работу» при 100%; и
  форма редактирования проекта (`ProjectFormSheet`) — смена статуса на «Активный», разбор 409 и
  кнопка «Всё равно отдать в работу».

Результат прогона для обеих частей — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание →
факт → статус). **Скриншоты не требуются.**

### Покрытие требований

Тест-кейсы покрывают R1 (явный эндпоинт активации), R2 (readiness-гейт, 100%, по всем областям),
R3 (force только ADMIN/MANAGER, обходит лишь готовность), R4 (структурный 409-ответ со списком
неготового), R5 (кнопка «Отдать в работу» в виджете при 100% + UPDATE), R6 (активация из формы
редактирования + «Всё равно отдать в работу»), R7 (гейт на общем `PUT`), R8 (локализация). R9
(нотификации отсутствуют) проверяется негативно (нотификации не эмитятся). Соответствие
«кейс ↔ требование» указано в каждом кейсе строкой `_Покрывает:_`.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции),
   `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
3. Первый ADMIN — через переменные окружения `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
   `FOREMEN_ADMIN_PASSWORD`. Логин: `POST /api/auth/login {email, password}` → `accessToken`.

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown.** Единый на прогон `run-id` (timestamp/uuid)
встраивается во все создаваемые идентификаторы (email пользователей `*+{run-id}@example.com`, имена
проектов `Activation Test {run-id}`), чтобы два последовательных прогона на одной БД не
конфликтовали. **Teardown** в конце набора: созданные проекты переводятся в `CANCELLED` / удаляются
доступным admin-API, тестовые пользователи деактивируются/удаляются. Сид (роли, ресурс `PROJECTS`,
гранты) **только читается, никогда не изменяется**.

> **Доменная предзависимость.** Готовность проекта (`GET /api/projects/{id}/readiness`,
> `overallPercentage`) агрегируется по шести областям (помещения, смета, оферта, документы, команда,
> график). Чтобы получить **100%**, тестовый проект нужно довести до полной готовности по всем
> областям (или замокать/подготовить домен так, чтобы агрегат был 100). Для сценариев «< 100%»
> достаточно проекта-черновика без заполненных областей. Группа `Setup` готовит оба состояния:
> `PROJECT_READY` (готовность = 100%) и `PROJECT_NOT_READY` (готовность < 100%).

## Фича 1. Выделенный эндпоинт активации — гейт готовности (R1, R2, R4)

**Повторяемость:** активация меняет статус; teardown переводит проект в `CANCELLED`/удаляет.

### TC-API-ACT-01 — Активация при 100% готовности → ACTIVE
**Предусловия:** TOKEN_MANAGER, `PROJECT_READY` (DRAFT, готовность 100%).
1. `POST /api/projects/{PROJECT_READY}/activate` (Bearer MANAGER, тело `{}` или без тела) →
   **200**; в ответе проект со `status = ACTIVE`.
2. `GET /api/projects/{PROJECT_READY}` → `status = ACTIVE`.

_Покрывает:_ R1.1, R2.2.

### TC-API-ACT-02 — Активация при < 100% без force → 409 со списком неготового
**Предусловия:** TOKEN_MANAGER, `PROJECT_NOT_READY` (DRAFT, готовность < 100%).
1. `POST /api/projects/{PROJECT_NOT_READY}/activate` (Bearer MANAGER, `{}`) → **409**; тело
   `ProjectNotReadyError`: `message` (локализован), непустой `areas[]`, в каждом — `key`, `name`
   (локализовано), `state`, `percentage`, `items[]` (локализованы).
2. Проверить: все области в `areas[]` имеют `state != DONE` (полностью готовые области **не**
   включаются); проект остался `DRAFT` (`GET …` → `status = DRAFT`).

_Покрывает:_ R2.1, R4.1, R4.2, R4.3, R4.4.

### TC-API-ACT-03 — Readiness-гейт считает по ВСЕМ областям (не по видимым вызывающему)
**Предусловия:** `PROJECT_NOT_READY`, у которого есть область, недоступная вызывающему на READ
(например, FOREMAN без READ на какую-то область); TOKEN_FOREMAN с `PROJECTS` UPDATE.
1. `POST /api/projects/{PROJECT_NOT_READY}/activate` (Bearer FOREMAN, `{}`) → **409** (гейт видит
   неготовность даже по области, которую вызывающий не читает).
2. Контроль: `GET /api/projects/{PROJECT_NOT_READY}/readiness` под тем же FOREMAN может показывать
   иной (суженный) процент — но активация всё равно заблокирована, т.к. гейт считает по всем
   областям.

_Покрывает:_ R2.3.

## Фича 2. Force-переход (R3)

**Повторяемость:** форс меняет статус; teardown чистит.

### TC-API-FORCE-01 — ADMIN форсит неготовый проект → ACTIVE
**Предусловия:** TOKEN_ADMIN, свежий `PROJECT_NOT_READY` (DRAFT, < 100%).
1. `POST /api/projects/{id}/activate` (Bearer ADMIN, тело `{"force": true}`) → **200**;
   `status = ACTIVE` несмотря на неготовность.

_Покрывает:_ R3.1, R3.4.

### TC-API-FORCE-02 — MANAGER форсит неготовый проект → ACTIVE
**Предусловия:** TOKEN_MANAGER, свежий `PROJECT_NOT_READY`.
1. `POST /api/projects/{id}/activate` (Bearer MANAGER, `{"force": true}`) → **200**;
   `status = ACTIVE`.

_Покрывает:_ R3.1.

### TC-API-FORCE-03 — Не-ADMIN/не-MANAGER с force всё равно получает 409
**Предусловия:** TOKEN_FOREMAN (роль с `PROJECTS` UPDATE, но не ADMIN/MANAGER); `PROJECT_NOT_READY`.
1. `POST /api/projects/{id}/activate` (Bearer FOREMAN, `{"force": true}`) → **409** (force
   проигнорирован для этой роли); `status = DRAFT` без изменений.

_Покрывает:_ R3.2.

### TC-API-FORCE-04 — Force не обходит доступ/права
**Предусловия:** TOKEN_CLIENT (без `PROJECTS` UPDATE) и проект, недоступный клиенту.
1. `POST /api/projects/{id}/activate` (Bearer CLIENT, `{"force": true}`) → **403** (нет UPDATE) или
   **404** (проект недоступен) — force не обходит ни права, ни доступ.

_Покрывает:_ R3.3, R1.3, R1.4.

**Предусловия:** TOKEN_ADMIN, проект в `COMPLETED`/`CANCELLED`.

_Покрывает:_ R1.3, R1.4.

# Часть B. Браузерные (UI) сценарии (frontend)

Экраны: шапка рабочего пространства проекта стадии проектирования (виджет `ReadinessWidget`) и форма
редактирования проекта (`ProjectFormSheet`, открывается из списка «Проекты» действием
«Редактировать»). Вход на фронтенд: `http://localhost:3000`.

**Повторяемость:** UI активирует проекты из `Setup`; teardown — те же переводы в `CANCELLED`/
удаление под ADMIN, что и в части A.

### TC-UI-WIDGET-01 — Кнопка «Отдать в работу» видна при 100% + UPDATE
**Предусловия:** логин MANAGER; `PROJECT_READY` (DRAFT, готовность 100%).
1. Открыть рабочее пространство `PROJECT_READY` → в шапке виджет готовности показывает 100%.
2. Рядом с пончиком видна кнопка **«Отдать в работу»** (`readiness-activate`).

_Покрывает:_ R5.1.

### TC-UI-WIDGET-02 — Кнопка скрыта при < 100% и без UPDATE
**Предусловия:** `PROJECT_NOT_READY` (< 100%); отдельно — роль без `PROJECTS` UPDATE.
1. Логин MANAGER, открыть `PROJECT_NOT_READY` → виджет показывает < 100%; кнопки
   «Отдать в работу» **нет**.
2. Логин роли без UPDATE, открыть `PROJECT_READY` (100%) → кнопки «Отдать в работу» **нет**.

_Покрывает:_ R5.2, R5.3.

### TC-UI-WIDGET-03 — Нажатие «Отдать в работу» активирует проект
**Предусловия:** логин MANAGER; `PROJECT_READY` (DRAFT, 100%).
1. Открыть рабочее пространство → нажать «Отдать в работу».
2. → тост успеха (`projects.activate.success`); проект переходит в стадию исполнения (виджет
   готовности, присущий стадии проектирования, больше не показывается).

_Покрывает:_ R5.4, R5.5.

### TC-UI-FORM-01 — Статус→ACTIVE при < 100% из формы → разбор неготового + «Всё равно отдать в работу»
**Предусловия:** логин MANAGER; `PROJECT_NOT_READY` (DRAFT).
1. «Проекты» → «Редактировать» на `PROJECT_NOT_READY` → в форме поле «Статус» → выбрать
   «Активный» → «Сохранить изменения».
2. → форма **не** закрывается; показан блок «Проект не готов к работе» (`project-not-ready`) со
   списком областей и пунктов «что не готово»; виден бейдж статуса/процент по каждой области.
3. Для MANAGER видна кнопка **«Всё равно отдать в работу»** (`project-activate-anyway`).

_Покрывает:_ R6.2, R6.4.

### TC-UI-FORM-02 — «Всё равно отдать в работу» (force) активирует проект
**Предусловия:** продолжение TC-UI-FORM-01 (блок неготового показан).
1. Нажать «Всё равно отдать в работу» → отправляется активация с `force: true`.
2. → тост успеха; форма закрывается/обновляется; в списке проектов бейдж статуса стал «Активный».

_Покрывает:_ R6.5, R6.6, R3.1.

### TC-UI-FORM-03 — Кнопка «Всё равно» недоступна не-ADMIN/MANAGER
**Предусловия:** логин роли с `PROJECTS` UPDATE, но не ADMIN/MANAGER (например FOREMAN, если у него
есть доступ к форме); `PROJECT_NOT_READY`.
1. Статус→ACTIVE → «Сохранить» → показан блок неготового, но кнопки «Всё равно отдать в работу»
   **нет** (бэкенд всё равно отклонит force для этой роли).

_Покрывает:_ R3.2, R6.4.

### TC-UI-FORM-04 — Статус→ACTIVE при 100% из формы → успех без разбора
**Предусловия:** логин MANAGER; `PROJECT_READY` (DRAFT, 100%).
1. «Редактировать» → «Статус» = «Активный» → «Сохранить изменения» → **успех** (тост обновления);
   блок неготового не показывается; бейдж статуса стал «Активный».

_Покрывает:_ R6.1.

# Регрессия

**Повторяемость:** регрессионные кейсы читают неизменяемый сид и системные флоу; созданные сущности
чистятся общим teardown.

### REG-01 — Виджет готовности и прочие переходы статуса не сломаны
1. Виджет готовности продолжает рендерить пончик + чипы областей + панель «что не готово» как
   прежде (FOR-05-11); новая кнопка не ломает его при < 100%.
2. Прочие смены статуса проекта через форму/PUT (DRAFT↔ON_HOLD, и т.п.) работают без readiness-гейта.

_Покрывает:_ R7.2.

### REG-02 — Автоматическая активация по подписанию контракта не затронута
1. Флоу FOR-05-08: подписание контракта при APPROVED-оферте по-прежнему автоматически переводит
   проект в `ACTIVE` (через `ProjectActivationSignal`), **без** интерактивного readiness-гейта.

_Покрывает:_ R7.3.

### REG-03 — Старт приложения без PermissionAnnotationValidator-ошибки
1. После добавления эндпоинта `POST /api/projects/{id}/activate` (гейт `PROJECTS`/UPDATE) backend
   стартует без ошибки валидатора аннотаций; контроллер `ProjectController` полностью аннотирован.

_Покрывает:_ R1.5.

### REG-04 — Локаль-паритет PL/RU
1. `pl.json` и `ru.json` содержат новые ключи `readiness.activate.action`,
   `projects.activate.anyway/success/notReadyTitle/notReadyHint` с реальными PL и RU значениями;
   locale-parity тест зелёный. Бэкенд-бандл содержит `error.project.not.ready` и
   `error.project.status.illegalTransition` в PL и RU.

_Покрывает:_ R8.1, R8.2.
