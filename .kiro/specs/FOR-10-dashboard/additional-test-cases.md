# Дополнительные тест-кейсы: FOR-10 — Настраиваемая панель (Dashboard)

Дополнение к `test-cases.md`. Кейсы закрывают пробелы, найденные при сверке `test-cases.md` с
`requirements.md` и при автоматизации частей B1–B3: пути добавления виджета, состояние выбора,
локализация подписей плиток, ошибки удаления и загрузки, а также поведение API на некорректный ввод.
Существующие кейсы не дублируются: где кейс уточняет существующий, указана ссылка на него.

- **Часть A — API-тесты** против Docker-стека (`http://localhost:8080`).
- **Часть B — UI-сценарии** для браузерного движка (headless, PL-интерфейс, окно 1440x900).
- Результат прогона — MD-репорт с таблицами (шаблон в конце файла).
- Автоматизация: `foremen-qa-auto/e2e/tests/for10/additional-api.e2e.ts` и `additional-ui.e2e.ts`
  (запуск `npx e2e run tests/for10` из `foremen-qa-auto/e2e`). Кейсы на открытые баги помечены
  `test.skip` со ссылкой `BUG-N` на `bug-report.md`.

## Окружение и стратегия повторяемости

Окружение как в `test-cases.md`: `docker compose up`, ADMIN из `FOREMEN_ADMIN_*`.

**Стратегия повторяемости: генератор данных + teardown.**
- `run-id` = base36-время + 4 hex-символа.
- Пользователи создаются прямым INSERT в `users` (bcrypt, cost 12), как в `TestUserFixture`:
  `dash+{run-id}-{tag}@example.com`. Раскладка готовится через API: все дефолтные размещения удаляются,
  нужные добавляются `POST /api/dashboard/items` с `cellIndex`.
- Проекты `DASH-{run-id}-*` создаются через `POST /api/projects` (обязательные участники MANAGER и CLIENT).
- Teardown (всегда, в `finally`): удаление проектов, затем пользователей (каскадно удаляет их
  размещения, внешние ключи без каскада чистятся явно). Сидовые данные и панель сидового ADMIN
  не меняются.

**Общие предусловия:** если не сказано иное, тест-пользователь с ролью ADMIN (видит все виджеты)
и пустой панелью.

# Часть A. API

## DX-A1. Некорректный ввод

### TC-DX-A01 Неверный формат даты — 400, а не 500 (Req 2.5, 6)
- Предусловия: у пользователя одно размещение `PAYMENTS_RECEIVED` @0.
- Шаги:
  1. `GET /api/dashboard/items/{id}/data?dateFrom=2026-13-01&dateTo=2026-13-30`. Ожидание: 400 `error.dashboard.date.invalid`.
  2. `GET .../data?dateFrom=abc&dateTo=def`. Ожидание: 400.

### TC-DX-A02 Нечисловой id размещения — 400, а не 500
- Шаги: `GET /api/dashboard/items/abc/data?dateFrom=2026-11-01&dateTo=2026-11-30`. Ожидание: 400.

### TC-DX-A03 Неверные типы и битый JSON — 400, а не 500
- Шаги (каждый — 400 с понятным сообщением):
  1. `POST /api/dashboard/items {"widgetId":1,"cellIndex":"abc"}`.
  2. `POST /api/dashboard/items` с телом `{"widgetId":` (оборванный JSON).
  3. `PUT /api/dashboard/items/{id}/move {"cellIndex":"x"}`.
  4. `POST /api/dashboard/items/swap {"firstId":"a","secondId":"b"}`.

### TC-DX-A04 Добавление без widgetId — ошибка валидации
- Шаги: `POST /api/dashboard/items {}`. Ожидание: 400 с ошибкой поля `widgetId` (обязательное поле),
  а не «Nie znaleziono widżetu» (виджет не найден).

## DX-A2. Доступ и границы

### TC-DX-A05 Все эндпоинты панели требуют токен
- Шаги: без `Authorization` вызвать `GET /api/dashboard`, `GET /api/dashboard/library`,
  `GET /api/dashboard/appearance`, `POST /api/dashboard/items`, `POST /api/dashboard/items/swap`.
  Ожидание: 401 у всех.

### TC-DX-A06 Граница 5 лет включительна (Req 2.5; уточняет TC-A4-04)
- Шаги: 1) `dateFrom=2021-11-14&dateTo=2026-11-14`. Ожидание: 200. 2) `dateFrom=2021-11-13&dateTo=2026-11-14`. Ожидание: 400.

### TC-DX-A07 Несуществующий проект неотличим от чужого (Req 12, 3.7; дополняет TC-A2-02)
- Шаги: `POST /api/dashboard/items {widgetId: <PROJECT_CARD>, projectId: 999999999}`. Ожидание: 403
  `error.dashboard.project.forbidden`, как для чужого проекта.

### TC-DX-A08 Цвет палитры в нижнем регистре (дополняет TC-A5a-01)
- Шаги: 1) `PUT /api/dashboard/appearance {palette:["#2563eb"]}`. Ожидание: 200. 2) `GET`. Ожидание: `["#2563EB"]`.

### TC-DX-A09 Язык сообщения об ошибке (Req 16.2)
- Шаги: `GET .../data` с `dateFrom > dateTo` и `Accept-Language: ru`, затем `pl`. Ожидание: 400,
  сообщение RU на кириллице, PL без кириллицы, тексты различаются.

# Часть B. UI

## DX-B1. Пути добавления виджета

### TC-DX-B01 Add_Slot открывает выбор для своей ячейки (Req 20.1, 21.2, 21.5; уточняет TC-B7-15)
- Предусловия: `PAYMENTS_RECEIVED` @0.
- Шаги:
  1. Нажать Add_Slot ячейки 6 (`dashboard-add-slot-6`). Ожидание: позиция «Wiersz 2, kolumna 3».
  2. Выбрать `BANK_PENDING` (1x1). Ожидание: запрос `POST /api/dashboard/items` с `cellIndex: 6`;
     `GET /api/dashboard` показывает `BANK_PENDING` @6.

### TC-DX-B02 Кнопка в шапке: без позиции, first-fit (Req 21.5, 3.3; уточняет TC-B7-18)
- Предусловия: `PAYMENTS_RECEIVED` @0, `BANK_PENDING` @5 (строки 0–1 закрыты для виджета шириной 4).
- Шаги:
  1. «Dodaj widżet» в шапке. Ожидание: блока позиции (`dashboard-picker-position`) нет.
  2. `ACTIVE_PROJECTS` (4x3) в списке доступен. Выбрать. Ожидание: запрос без `cellIndex`;
     виджет в первой подходящей позиции @8.

### TC-DX-B03 Полная сетка: сообщение «нет места» (Req 3.3; уточняет TC-B7-12)
- Предусловия: сетка заполнена через API (все 36 ячеек).
- Шаги: «Dodaj widżet» в шапке. Ожидание: в выборе «Brak wolnego miejsca» (ключ `dashboard.picker.noSpace`),
  а не «Żaden widżet nie mieści się w tym miejscu» (это сообщение для выбранной ячейки, Req 21.7).

## DX-B2. Состояние выбора

### TC-DX-B04 После добавления проектного виджета выбор открывается со списка (Req 3.4, 12)
- Предусловия: MANAGER с пустой панелью, участник проекта `DASH-{run-id}-A`.
- Шаги:
  1. «Dodaj widżet» → «Karta projektu» → снять «Tylko aktywne» → выбрать проект A. Ожидание: плитка добавлена, выбор закрыт.
  2. Без перезагрузки снова «Dodaj widżet». Ожидание: виден список виджетов с поиском; шага выбора проекта нет.

### TC-DX-B05 Поиск сбрасывается при повторном открытии (дополняет TC-B7-16 шаг 5)
- Шаги: открыть выбор, ввести «Fundusz», закрыть Escape, открыть снова. Ожидание: поле поиска пустое.

### TC-DX-B11 MANAGER видит в выборе проекта только свои проекты (Req 8, 12)
- Предусловия: MANAGER — участник одного проекта `DASH-{run-id}-OWN`; в системе есть другие проекты.
- Шаги: «Dodaj widżet» → «Karta projektu» → снять «Tylko aktywne». Ожидание: ровно один проект в списке — `DASH-{run-id}-OWN`.

## DX-B3. Ошибки и пустые состояния

### TC-DX-B07 Удаление последнего виджета (Req 3.5, 1; дополняет TC-B1-03, TC-B3-04)
- Предусловия: один `PAYMENTS_RECEIVED` @5.
- Шаги: удалить его с подтверждением. Ожидание: пустое состояние (`dashboard-empty`) и Add_Slot ячейки 0.

### TC-DX-B08 Ошибка удаления видна в диалоге (Req 3.5, 16.4)
- Шаги: перехватить `DELETE /api/dashboard/items/*` с ответом 500; «Usuń» → подтвердить.
- Ожидание: диалог остаётся открытым, внутри него сообщение об ошибке удаления (`role="alert"`), а не
  «Nie udało się załadować danych»; после «Anuluj» плитка на месте, на сервере размещение есть.

### TC-DX-B09 Отклонённое добавление (Req 3.3, 21.8)
- Шаги: перехватить `POST /api/dashboard/items` с ответом 409 `error.dashboard.cell.occupied`; выбрать виджет.
- Ожидание: выбор не закрывается, в нём `role="alert"` с сообщением; плитки нет; на сервере размещений нет.

### TC-DX-B10 Ошибка загрузки раскладки и «Повторить»
- Шаги: перехватить `GET /api/dashboard` с ответом 500; войти. Ожидание: `dashboard-error` с кнопкой.
  Снять перехват, нажать кнопку. Ожидание: плитки отрисованы.

## DX-B4. Локализация и сессия

### TC-DX-B06 Подписи элементов плитки на активном языке (Req 16.3, 16.4; дополняет TC-B6-01)
- Предусловия: PL-интерфейс; размещены `PAYMENTS_RECEIVED`, `USERS_BY_ROLE`.
- Шаги: прочитать `aria-label` каждого `dashboard-tile-style-*`. Ожидание: «Styl: {польское название}»,
  кириллицы нет. В RU-интерфейсе — русское название.

### TC-DX-B12 Диапазон дат не переходит к следующему пользователю (Req 2.4) — требует решения
- Шаги: пользователь A выбирает «Poprzedni» → выход («Wyloguj się») → в той же вкладке входит B.
- Ожидание (предлагаемое): у B текущий месяц. Факт: у B диапазон A. Требование 2.4 привязывает диапазон
  к сессии браузера, а не к пользователю; нужно решение владельца продукта (см. BUG-9).
