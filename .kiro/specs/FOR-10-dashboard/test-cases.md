# Тест-кейсы: FOR-10 — Настраиваемая панель (Dashboard)

Спека содержит и браузерные экраны (Panel, админка виджетов), и API. Поэтому:
- **Часть A — API-тесты** против работающего Docker-стека (`http://localhost:8080`).
- **Часть B — UI-сценарии**, исполняются браузерным движком (headless). Скриншоты не требуются.
- Результат прогона — MD-репорт с таблицами (шаблон в конце файла).

## Окружение и стратегия повторяемости

Окружение: `docker compose up` (postgres :5432, liquibase, backend :8080 профиль `docker`, frontend :3000).
Первый ADMIN: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
Для AI-кейсов: `FOREMEN_DASHBOARD_AI_ENABLED=true`, `FOREMEN_DASHBOARD_AI_LLM_STUB=true`.

**Стратегия повторяемости: генератор данных + teardown.**
- `run-id` = `yyyyMMddHHmmss` + 4 случайных символа. Все создаваемые сущности именуются с `run-id`:
  пользователи `dash+{run-id}-{role}@example.com`, проекты `DASH-{run-id}-A/B`, виджеты `TC_{RUN_ID}_*`
  (код в верхнем регистре, `RUN_ID` без дефисов).
- Teardown (выполняется всегда, даже при падении): удалить размещения тестовых пользователей,
  деактивировать и удалить тестовые виджеты (`DELETE /api/dashboard-widgets/{id}`), деактивировать
  тестовых пользователей и проекты (через существующие admin-эндпоинты).
- Сидовые виджеты и дефолты ролей тестами НЕ изменяются; тесты, меняющие матрицу прав, создают
  собственную тестовую роль `DASH_{RUN_ID}` и удаляют её в teardown.

**Общие предусловия (Setup):** токен ADMIN; пользователи по ролям MANAGER, FOREMAN, WORKER, FINANCIER,
CLIENT (создаются через admin API, при создании им должны быть выданы дефолтные виджеты); два проекта
`A` и `B` в статусе ACTIVE; пользователь WORKER и MANAGER добавлены в проект A; CLIENT добавлен в проект A.

## A9. Перемещение, обмен, добавление в ячейку, thumbnail (Amendment A1, Req 19, 21, 22)

**Стратегия повторяемости блока A9:** для каждого кейса создаётся отдельный пользователь
`dash+{run-id}-a9-{N}@example.com` (ADMIN для кейсов с `USERS_BY_ROLE`/`BANK_PENDING`, иначе MANAGER),
у которого первым шагом удаляются все дефолтные размещения (`DELETE /api/dashboard/items/{id}`), поэтому
раскладка детерминирована. Тестовые виджеты `TC_{RUN_ID}_2X1` (2x1, датасет `WORK_REPORTS`, KPI/COUNT) и
`TC_{RUN_ID}_NOACC` (датасет `PAYROLL`, в конфиге метки `SECRET_{RUN_ID}`) создаются в Setup админом.
Teardown: удалить размещения, деактивировать и удалить тестовые виджеты и роль `DASH_{RUN_ID}`,
деактивировать пользователей.

Размеры сидовых виджетов: `PAYMENTS_RECEIVED` 1x1, `BANK_PENDING` 1x1, `USERS_BY_ROLE` 1x2,
`WORK_REPORTS_BY_STATUS` 2x2, `WORK_REPORTS_PENDING` 2x3, `ACTIVE_PROJECTS` 4x3. Ячейка = `row*4+col`.

### TC-A9-01 Перемещение в свободную ячейку (Req 19.7)
- Предусловия: пустой дашборд; `PAYMENTS_RECEIVED` (P1) @0, `WORK_REPORTS_BY_STATUS` (P2) @2.
- Шаги:
  1. `PUT /api/dashboard/items/{P1}/move {cellIndex: 1}`. Ожидание: 200, `cellIndex=1`, `widgetId` и `projectId` без изменений.
  2. `GET /api/dashboard`. Ожидание: P1@1, P2@2, остальные поля обоих размещений не изменились.
  3. Переместить P2 (2x2) в `cellIndex=8`. Ожидание: 200, `cellIndex=8`.

### TC-A9-02 Выход за границы сетки → 400 (Req 19.8, 21.8)
- Предусловия: P2 (2x2) @0.
- Шаги:
  1. Move P2 в `cellIndex=3` (3+2 > 4 колонок). Ожидание: 400 `error.dashboard.cell.invalid`.
  2. Move P2 в `cellIndex=33` (строка 8 + 2 > 9). Ожидание: 400.
  3. Move P2 в `cellIndex=36` и `-1`. Ожидание: 400 для обоих.
  4. Тело без `cellIndex` / `{"cellIndex": null}`. Ожидание: 400 `error.dashboard.cell.invalid`.
  5. `GET /api/dashboard`. Ожидание: P2 по-прежнему @0.

### TC-A9-03 Пересечение → 409 (Req 19.8)
- Предусловия: P2 (2x2) @0, P1 (1x1) @2.
- Шаги:

# Регрессия

### TC-R-01 Права на панели не расширяются
Повторить TC-A3-01..05 и TC-A4-01..03 после любого изменения матрицы прав или датасетов.

### TC-R-02 Сквозной путь нового пользователя
Создать пользователя → логин → дефолтный дашборд (A1-01) → смена диапазона дат (B2-02) → добавление проектного виджета (B3-03) → клик по чипу (B4-01) → удаление (B3-04).

### TC-R-03 Не сломаны существующие экраны
Колокольчик уведомлений (список, прочитано/не прочитано, удаление), меню «Система», список проектов открываются без ошибок консоли.

### TC-R-04 Миграции
Повторный запуск Liquibase на уже заполненной БД: ошибок и дублей нет (сиды идемпотентны, бэкфилл не дублирует размещения).

### TC-R-05 Все пути добавления виджета (Req 3.1, 3.3, 20.7, 21.5, 21.9)
Повторять после любых изменений сетки, выбора или `DashboardLayoutService`:
1. Шапка «Добавить виджет» (десктоп): запрос без `cellIndex`, first-fit (TC-B7-18, TC-A1-03).
2. Add_Slot (десктоп): запрос с `cellIndex`, без first-fit fallback при 400/409 (TC-B7-15, TC-B7-19, TC-A9-10).
3. Одиночный «+» на планшете/мобильном: запрос без `cellIndex`, first-fit (TC-B7-13).
4. `POST /api/dashboard/items` без `cellIndex`: first-fit; полная сетка → 409 `grid.full` (TC-A1-03, TC-A1-06).
Дополнительно: дубликаты (TC-A1-07), проектный виджет (TC-B3-03), удаление (TC-B3-04) работают из каждого пути.

### TC-R-06 Перемещение и обмен не ломают раскладку (Req 19.17)
После серии ≥ 20 случайных валидных move/swap (генератор с фиксированным seed, seed пишется в репорт) `GET /api/dashboard`: нет пересечений, все футпринты внутри 4x9, число размещений прежнее, `widgetId`/`projectId` не изменились. Откат всех перемещений в обратном порядке восстанавливает исходную раскладку.

### TC-R-07 Контракт геометрии frontend и backend (Req 21.10, 21.11)
Прогнать `GridVectorsContractTest` и `grid-vectors.contract.test.ts` на одном `grid-vectors.json`; UI-проверкой убедиться, что список выбора для ячейки совпадает с результатами API TC-A9-11.

### TC-R-08 Библиотека не раскрывает данные (Req 22.2, 8.8)
Повторить TC-A9-13 после любого изменения `LibraryItem` или `ThumbnailShape`.
