# Тест-кейсы: FOR-06-12 — Коммуникация с клиентом

> Спека full-stack (есть и API, и браузерный экран Komunikacja), поэтому тест-кейсы разделены на
> **Часть A (API-тесты против поднятого в Docker приложения)** и **Часть B (сценарии браузерного
> движка для админ-панели)**. Результат прогона — MD-репорты с таблицами (см. шаблон в конце).
> Документ на русском (requirements/design/tasks — на английском, per `.kiro/steering/test-cases.md`).

## Окружение

- Docker-стек: `docker compose up` в корне — `postgres` (:5432), `liquibase` (миграции), `backend`
  (:8080, профиль `docker`), `frontend` (:3000). Базовый URL API: `http://localhost:8080`,
  аутентификация — `/api/auth`.
- Первый ADMIN поднимается через `FOREMEN_ADMIN_CREATE=true` + `FOREMEN_ADMIN_EMAIL` +
  `FOREMEN_ADMIN_PASSWORD`.
- **Автоперевод (R6/R10):** если `foremen.translation.*` не сконфигурирован, активен
  `DisabledMessageTranslationService` — сообщения остаются «только оригинал». Кейсы с переводом
  помечены `[требует translation-provider]`; при отключённом провайдере проверяется ветка
  оригинал-онли (TC-TR-02).
- **Локаль (R12):** все локали — стандартный `java.util.Locale`, хранятся как язык-тег в нижнем
  регистре (`pl`/`ru`) через общий `LocaleAttributeConverter`; `null`/пусто/неизвестное → `PL`.
  Поле `UserEntity.locale` мигрировано `String → Locale` без миграции БД (колонка остаётся
  `VARCHAR` с теми же значениями). Регрессия миграции — группа TC-LC.

## Стратегия повторяемости (обязательно)

**Генератор + Teardown.** Каждый прогон использует `run-id` = UNIX-timestamp/uuid:

- Пользователи создаются с уникальными email `qa.client+{run-id}@example.com`,
  `qa.manager+{run-id}@example.com`, `qa.foreman+{run-id}@example.com` (или переиспользуются
  предсозданные QA-учётки, если заданы).
- Проект создаётся на каждый прогон (`Проект QA {run-id}`), переводится в статус `ACTIVE`, в него
  заводятся участники с ролями CLIENT / MANAGER / FOREMAN.
- **Teardown:** в конце прогона удалить созданные сообщения клиента (ADMIN DELETE), затем
  деактивировать/удалить участников и проект. Сообщения каскадно уносят переводы и медиа
  (`ON DELETE CASCADE`), медиа-объекты чистятся `deleteIfOrphan`. Нотификации получателей —
  удаляются владельцем (bell delete) при необходимости.

Все сценарии запускаемы многократно без ручной чистки БД.

# Часть A — API-тесты

## Фича A1. Публикация сообщения и вывод треда

### TC-A1-01 — CLIENT публикует вопрос
**Предусловия:** проект `ACTIVE`; CLIENT — ACTIVE-участник; авторизован токеном CLIENT.
**Шаги:**
1. `POST /api/client-messages?projectId={pid}` (multipart: `body={"text":"Pytanie {run-id}"}`) →
   ожид. `200/201`, в ответе `authorSide=CLIENT`, `originalLocale` определён (PL/RU), `readAt=null`.
2. `GET /api/client-messages?projectId={pid}` токеном CLIENT → ожид. `200`, тред содержит это
   сообщение, текст — в локали читателя, присутствуют `originalText`+`originalLocale`.
**Ожидаемый результат:** сообщение сохранено как сторона CLIENT, непрочитано, видно в треде.

### TC-A1-02 — пустое сообщение без медиа отклоняется
**Шаги:** `POST` с `text=""` и без файлов → ожид. `400 error.clientMessage.empty`, тред не изменён.

### TC-A1-03 — публикация вне стадии ACTIVE отклоняется
**Предусловия:** проект в статусе `DRAFT` (или `COMPLETED`).
**Шаги:** CLIENT `POST` сообщение → ожид. отказ (тред read-only вне стадии исполнения, R2.4/R8.1).

### TC-A1-04 — authorSide не берётся из запроса
**Шаги:** MANAGER `POST` с попыткой передать `authorSide=CLIENT` в теле → ожид. сохранённое
`authorSide=STAFF` (сервер выводит сторону по роли, не из тела).

## Фича A2. Право ответа и прочтения (только MANAGER)

### TC-A2-01 — MANAGER отвечает
**Шаги:** MANAGER `POST` текст → ожид. `200`, `authorSide=STAFF`; в треде появляется ответ.

### TC-A2-02 — FOREMAN не может ответить
**Шаги:** FOREMAN `POST` текст → ожид. `403 error.clientMessage.reply.notManager`, тред не изменён.

### TC-A2-03 — FOREMAN читает тред (read-only)
**Шаги:** FOREMAN `GET /api/client-messages?projectId={pid}` → ожид. `200`, полный тред виден.

### TC-A2-04 — не-MANAGER не может пометить прочитанным
**Шаги:** FOREMAN `POST /api/client-messages/{id}/read` → ожид.
`403 error.clientMessage.read.notManager`, `readAt` не изменён.

## Фича A3. Первое прочтение менеджером (first-read-wins)

### TC-A3-01 — первое прочтение проставляет readAt/readBy
**Предусловия:** есть непрочитанное CLIENT-сообщение.
**Шаги:** MANAGER `POST /api/client-messages/{id}/read` → ожид. `200`, `readAt` != null,
`readBy` = менеджер; счётчик непрочитанных в `GET` уменьшился на 1.

### TC-A3-02 — повторное прочтение не меняет метку
**Шаги:** второй `POST .../read` другим MANAGER → ожид. `readAt`/`readBy` без изменений (first-read-wins).

### TC-A3-03 — STAFF-сообщение не участвует в непрочитанном
**Шаги:** `POST .../read` на STAFF-ответ → ожид. no-op; STAFF-сообщения не считаются непрочитанными.

## Фича A4. Медиа-вложения

### TC-A4-01 — вложение картинки (≤10 МБ)
**Шаги:** `POST` сообщение с `image/png` ~1 МБ → ожид. `200`, media `kind=IMAGE`; в треде ссылка —
подписанный временный URL; скачивание по URL возвращает байты.

### TC-A4-02 — вложение PDF (≤10 МБ)
**Шаги:** `POST` с `application/pdf` → ожид. `200`, `kind=DOCUMENT`.

### TC-A4-03 — вложение видео (≤100 МБ)
**Шаги:** `POST` с `video/mp4` ~5 МБ → ожид. `200`, `kind=VIDEO`.

### TC-A4-04 — недопустимый тип отклоняется
**Шаги:** `POST` с `application/zip` → ожид. `400 error.clientMessage.media.invalid`, ничего не сохранено.

### TC-A4-05 — превышение размера отклоняется
**Шаги:** `POST` с `image/png` > 10 МБ → ожид. `400 error.clientMessage.media.tooLarge`
(с указанием размера и лимита); аналогично видео > 100 МБ.

## Фича A5. Нотификации

### TC-A5-01 — сообщение клиента уведомляет MANAGER+FOREMAN
**Шаги:** CLIENT `POST` сообщение → `GET` bell у MANAGER и у FOREMAN → ожид. у обоих новое
уведомление `notification.clientMessage.fromClient` с deep-link
`/projects/{pid}/clientCommunication?message={id}`.

### TC-A5-02 — ответ менеджера уведомляет CLIENT
**Шаги:** MANAGER `POST` ответ → `GET` bell у CLIENT → ожид. `notification.clientMessage.fromStaff`
с deep-link.

### TC-A5-03 — нет получателей = не ошибка
**Предусловия:** проект без ACTIVE FOREMAN.
**Шаги:** CLIENT `POST` → ожид. `200`; уведомление ушло только MANAGER, ошибки нет.

## Фича A6. ABAC и изоляция проекта

### TC-A6-01 — WORKER не имеет доступа
**Шаги:** WORKER `GET`/`POST` на `/api/client-messages` → ожид. `403` (deny-by-default).

### TC-A6-02 — изоляция между проектами
**Шаги:** CLIENT проекта X делает `GET ?projectId={pidY}` чужого проекта → ожид. пустой/запрещённый
результат (project-scope, `getProjectIdPath=project.id`).

### TC-A6-03 — ADMIN полный доступ
**Шаги:** ADMIN `GET`/`POST`/`DELETE` → ожид. успех по всем операциям.

### TC-A6-04 — FINANCIER/ESTIMATOR только READ
**Предусловия:** проект `ACTIVE`; в проекте есть ACTIVE-участники с ролями FINANCIER и ESTIMATOR.
**Шаги:**
1. FINANCIER `GET /api/client-messages?projectId={pid}` → ожид. `200`, тред виден.
2. FINANCIER `POST /api/client-messages?projectId={pid}` (текст) → ожид. `403`
   (нет CREATE в матрице `CLIENT_MESSAGES`; READ-only).
3. ESTIMATOR `GET ...` → ожид. `200`; ESTIMATOR `POST ...` → ожид. `403`.
4. FINANCIER `POST /api/client-messages/{id}/read` → ожид. `403` (нет UPDATE).
**Ожидаемый результат:** прочие admin-staff роли видят тред, но не пишут и не помечают прочитанным.

### TC-A6-05 — матрица операций по ролям (CLIENT_MESSAGES)
**Шаги:** для каждой роли проверить (resource `CLIENT_MESSAGES`):
- ADMIN → CREATE/READ/UPDATE/DELETE = allow.
- CLIENT → CREATE/READ = allow; UPDATE/DELETE = deny.
- MANAGER → CREATE/READ/UPDATE = allow; DELETE = deny.
- FOREMAN/FINANCIER/ESTIMATOR → READ = allow; CREATE/UPDATE/DELETE = deny.
- WORKER → всё = deny (deny-by-default).
**Ожидаемый результат:** ответы соответствуют матрице; поверх ABAC CLIENT пишет только стороной
CLIENT, а reply/mark-read остаются MANAGER-only (см. A2).

## Фича A7. Автоперевод

### TC-A7-01 `[требует translation-provider]` — сообщение читается в локали читателя
**Шаги:** CLIENT (локаль PL) публикует польский текст; MANAGER (локаль RU) `GET` → ожид. текст в
`RU`, присутствуют `originalText` (PL) + `originalLocale=PL`.

### TC-TR-02 — провайдер отключён: оригинал-онли
**Предусловия:** `foremen.translation.*` не сконфигурирован.
**Шаги:** CLIENT (PL) публикует; MANAGER (RU) `GET` → ожид. текст = оригинал (PL),
`originalLocale=PL`, перевода нет, публикация прошла успешно (не заблокирована, R6.3/R10.3).

## Фича A8. Стандартный `Locale` и миграция `UserEntity.locale` (R12, регрессия)

> Проверяет обратную совместимость конвертации `String → Locale` без миграции БД. API-поверхность —
> существующие user-эндпоинты; значения в колонке `users.locale` остаются `pl`/`ru`.

### TC-LC-01 — существующая локаль пользователя сохраняется
**Шаги:** `GET` профиль/пользователя с заранее сохранённой локалью `ru` → ожид. локаль читается как
`Locale` ru; `GET` пользователя с `pl` → `Locale` pl. Значение в БД не изменилось (остаётся нижний
регистр).

### TC-LC-02 — создание/обновление пользователя с локалью
**Шаги:** ADMIN создаёт пользователя с `locale=pl`, затем обновляет на `ru` → ожид. `200`, значение
принято и прочитано как `Locale`; невалидная локаль (`en`) → ожид. `400 error.user.locale.invalid`
(набор PL/RU сохранён).

### TC-LC-03 — легаси/пустое значение читается как PL
**Предусловия:** в колонке `users.locale` искусственно оставлено пустое/неизвестное значение (или
проверяется юнит-тестом конвертера).
**Шаги:** прочитать пользователя → ожид. локаль резолвится в `PL` (фолбэк), ошибки нет.

### TC-LC-04 — локаль письма сохраняет поведение
**Шаги:** инициировать письмо-приглашение/OTP для пользователя с `ru` → ожид. письмо на русском;
для `pl`/пустого → польский (поведение `EmailLocaleResolver` не изменилось).

# Часть B — UI-сценарии (браузерный движок, админ-панель Komunikacja)

### TC-B1-01 — таб Komunikacja виден на ACTIVE-проекте
**Шаги:** войти MANAGER → открыть `ACTIVE`-проект → ожид. в пространстве проекта виден таб
«Komunikacja»; на `DRAFT`-проекте таб отсутствует.

### TC-B1-02 — рендер треда в локали читателя + «показать оригинал»
**Шаги:** открыть тред → ожид. у каждого сообщения автор, бейдж стороны (client/staff), время, текст
в локали читателя; при отличии от оригинала доступна иконка быстрого просмотра оригинала →
клик показывает `originalText` с подписью `originalLocale`.

### TC-B1-03 — композер только у MANAGER
**Шаги:** открыть панель под MANAGER → ожид. есть поле ввода + загрузка медиа + «Отправить»;
под FOREMAN → ожид. панель read-only, композера нет.

### TC-B1-04 — отметка прочтения при первом открытии менеджером
**Шаги:** MANAGER открывает непрочитанное сообщение → ожид. счётчик непрочитанных уменьшился,
сообщение помечено прочитанным.

### TC-B1-05 — инлайн-ошибки валидации
**Шаги:** MANAGER отправляет пустое сообщение / недопустимое медиа → ожид. инлайн-ошибка
(`error.clientMessage.empty` / `.media.invalid`), текст локализован.

### TC-B1-06 — бейдж счётчика непрочитанных
**Предусловия:** в треде есть N непрочитанных CLIENT-сообщений (N≥1).
**Шаги:**
1. MANAGER открывает пространство проекта (не заходя в таб) → ожид. на табе «Komunikacja» виден
   бейдж с числом непрочитанных = N.
2. MANAGER открывает первое непрочитанное сообщение → ожид. бейдж уменьшился до N−1 (отметка
   прочтения при первом открытии, R5/R9.4).
3. Все CLIENT-сообщения прочитаны → ожид. бейдж исчезает (0 непрочитанных).
**Ожидаемый результат:** бейдж непрочитанных отражает актуальный счётчик и реагирует на прочтение.

### TC-B1-07 — медиа в композере и в треде
**Шаги:** MANAGER прикрепляет картинку/PDF в композере и отправляет → ожид. сообщение появилось
в треде с превью/ссылкой на вложение; клик по вложению открывает/скачивает файл (подписанный URL).

# Регрессия

### TC-REG-01 — оболочка и резолвер табов не изменены
Табы FOR-05-01 и `resolveWorkspaceTabs`/`stageOf` работают как прежде; прочие execution-табы
(placeholder'ы) не затронуты.

### TC-REG-02 — общий notification-сервис и bell
Bell (unread count, mark read/unread, delete, own-only) FOR-05-07 работает; новые типы
`notification.clientMessage.*` отображаются локализованным заголовком, сырой ключ не показывается.

### TC-REG-03 — объектный стор и OCR/Gemini wiring
`ImageStorage` (другие медиа-поверхности) и FOR-06-03 OCR не затронуты добавлением
translation-сема.

### TC-REG-04 — миграция `UserEntity.locale` не ломает user/email-поверхности
Создание/обновление пользователя, валидация локали, резолв локали письма (RU→русский, иначе→PL)
работают как до миграции `String → Locale`; данные в `users.locale` не требуют ручной правки.
