# Тест-кейсы: FOR-06-00 — Execution foundation (фундамент стадии исполнения)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерные экраны**, поэтому набор включает **оба типа**:

- **Часть A. API-тесты** — против поднятого в Docker приложения (`http://localhost:8080`). Каждый
  шаг — HTTP-запрос к CRUD-эндпоинту мини-справочника `/api/unplanned-expense-categories` с
  проверкой статуса, тела и заголовков, а также проверка ABAC-матрицы под разными ролями.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда (`http://localhost:3000`), исполняются
  браузерным движком (headless-браузер / browser automation). Экраны: админ-страница
  «Категории неплановых расходов» (список + CRUD) и набор исполнительных табов воркспейса проекта
  в статусе `ACTIVE`.

Результат прогона для обеих частей — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание →
факт → статус). **Скриншоты не требуются.**

### Покрытие требований

Каждое из требований R1–R6 покрыто минимум одним кейсом. Соответствие «кейс ↔ требование» указано в
каждом кейсе строкой `_Покрывает:_`. R5 (отсутствие нотификаций) проверяется негативно — ни один
сценарий не порождает запись в колокольчике.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции,
   включая changesets `157`–`158`), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
3. Первый ADMIN — через `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
   Логин: `POST /api/auth/login {email, password}` → `accessToken`.
4. Дождаться готовности `backend` и завершения миграций перед прогоном (проверка:
   `GET /api/unplanned-expense-categories` отвечает 200 с пятью засиженными категориями).
5. Для проверки ABAC под не-ADMIN ролями — создать (или переиспользовать) пользователей
   MANAGER / FOREMAN / FINANCIER / WORKER и получить их `accessToken`.

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown.** Единый на прогон `run-id` (timestamp или uuid)
встраивается в `code` всех создаваемых категорий, чтобы прогоны не конфликтовали:

- `code` создаваемых категорий: `tc-{run-id}-a`, `tc-{run-id}-b` и т.п.;
- `name_ru`/`name_pl`: `Кат {run-id}` / `Kat {run-id}`.

**Teardown** в конце набора: удалить (`DELETE /api/unplanned-expense-categories/{id}`) все категории,
чей `code` начинается с `tc-{run-id}-`. Пять засиженных дефолтных категорий
(`reclamation/unforeseen/materials/fuel/other`) НЕ трогаются — они часть сид-данных и проверяются
только на чтение.

## Группа 2. Мини-справочник: CRUD под ADMIN (API)

### TC-UEC-03 — Создание категории
_Покрывает: R3.1, R3.4(ADMIN), R2.4_
1. `POST /api/unplanned-expense-categories {code:"tc-{run-id}-a", nameRU:"Кат {run-id}", namePL:"Kat {run-id}", active:true}` под ADMIN → **200/201**, в ответе `id`.
2. `GET /api/unplanned-expense-categories/{id}` → **200**, поля совпадают.

### TC-UEC-04 — Редактирование имён и active, неизменяемость code
_Покрывает: R2.4, R3.4(ADMIN)_
1. `PUT /api/unplanned-expense-categories/{id} {nameRU:"Кат {run-id} ред", namePL:"Kat {run-id} red", active:false}` → **200**.
2. `GET .../{id}` → имена обновлены, `active=false`, `code` не изменился.
3. Попытка изменить `code` в `PUT` → отклоняется валидацией (ошибка 4xx) либо `code` остаётся
   прежним (в зависимости от реализации схемы) — зафиксировать фактическое поведение.

### TC-UEC-05 — Удаление категории
_Покрывает: R3.1_
1. `DELETE /api/unplanned-expense-categories/{id}` под ADMIN → **204**.
2. `GET .../{id}` → **404**.

### TC-UEC-06 — MANAGER/FOREMAN/FINANCIER: только чтение

## Регрессия

Отдельная лёгкая регрессия:

- **REG-01.** `resolveWorkspaceTabs` для `DRAFT`-проекта возвращает прежний набор дизайн-табов
   (помещения, смета, оферта, команда, график, подписание, материалы, маржа) — реалайнмент
   исполнения не затронул дизайн-стадию. _Покрывает: R1.4._
- **REG-02.** Паритет локалей: `pl.json` и `ru.json` имеют идентичный набор ключей после правок
   (включая добавленные/удалённые `workspace.tab.*`). _Покрывает: R6.2, R6.3 (P7)._
- **REG-03.** Фикстуры навигации актуальны. _Покрывает: R4.3._ Проверяет, что набор и порядок
   пунктов разделов «Каталог» и «Справочники» в `NAV_CONFIG` соответствуют актуальному контракту
   (включая добавленный `/unplanned-expense-categories`), и что тест `navigation.test.ts` проходит
   без устаревших захардкоженных значений (ранее ломался на снапшоте 9 путей / 11 пунктов).

Иные регрессионные кейсы на данном этапе не требуются: спека не меняет существующую бизнес-логику,
а лишь добавляет справочник и перераскладывает контракт табов.
