# Тест-кейсы: FOR-06-08 — Amendments (авторинг анексов)

## Назначение и характер спеки

Спека **смешанная (MIXED)**: имеет и API-поверхность (`/api/amendments` — CRUD, add-line, merge,
delete, инвариант single-open, ABAC-матрица), и браузерные экраны (вкладка **Aneksy** воркспейса
`ACTIVE`-проекта: список, мастер создания аннекса, чузер разрешения конфликта слияния, диалоги
удаления). Поэтому набор тест-кейсов включает **оба типа**:

- **Часть A. API-тесты** — против поднятого в Docker приложения (`http://localhost:8080`). Каждый
  шаг — HTTP-запрос к `/api/amendments` (и к базовым CRUD-эндпоинтам ресурса `AMENDMENTS`) с проверкой
  статуса, тела и заголовков. Покрывают: создание аннекса (eligibility + инвариант «один OPEN»),
  добавление линии на каждый `Change_Type`, 409 subject-conflict без резолюции и слияние
  (`REPLACE`/`KEEP_EXISTING`/`ADD_TO`), удаление линии и удаление аннекса, OPEN-guard, ABAC-матрицу
  (ADMIN/MANAGER/FINANCIER CRUD, FOREMAN READ, WORKER/CLIENT запрещены).
- **Часть B. Браузерные (UI) сценарии** — против фронтенда (`http://localhost:3000`), исполняются
  браузерным движком (headless-браузер / browser automation). Экраны вкладки **Aneksy** на
  `ACTIVE`-проекте: рендер списка, мастер создания аннекса (три типа изменений), чузер конфликта
  слияния при 409, диалоги удаления линии / удаления аннекса, read-only для FOREMAN (нет write-кнопок).

Результат прогона для обеих частей — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание →
факт → статус). **Скриншоты не требуются.**

### Покрытие требований

Основной фокус задачи — требования **1.1, 2.1, 2.3, 3.1, 5.1, 6.1, 6.2, 9.2**; дополнительно покрыты
смежные критерии (2.2, 2.4, 2.5, 3.5, 3.6, 5.3, 5.4, 5.6, 6.4, 9.3, 10.1, 10.3). Соответствие
«кейс ↔ требование» указано в каждом кейсе строкой `_Покрывает:_`.

> **Границы спеки (важно для ожиданий).** FOR-06-08 **инертна на downstream-данные**: ни один аннекс в
> этой сборке не достигает статуса `EFFECTIVE` (переход — территория FOR-06-09), поэтому ни один кейс
> не проверяет применение дельт к плану/факту/материалам/марже. Проверяется только авторинг «до
> готовности к подписанию»: статусы `OPEN` и `DELETED`, overlay-семантика (базовый estimate/schedule
> не меняются).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции,
   включая changesets `177`–`179` этой спеки), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
3. Первый ADMIN — через переменные окружения `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
   `FOREMEN_ADMIN_PASSWORD`. Логин: `POST /api/auth/login {email, password}` → `accessToken`.
4. Дождаться готовности `backend` и завершения миграций перед прогоном (проверка:
   `GET /api/amendments` отвечает 200/403 под авторизованным токеном, а не 404 — значит контроллер
   `AMENDMENTS` поднят и ресурс засижен).

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown.** Единый на прогон `run-id` (timestamp или uuid,
например `1730000000` или `a1b2c3`) встраивается во все создаваемые идентификаторы (имена проектов,
email тестовых пользователей, `note`/`description` линий), чтобы два последовательных прогона на одной
БД не конфликтовали:

- имена тестовых проектов: `Aneks Test {run-id}`;
- email тестовых ролей: `manager+{run-id}@example.com`, `financier+{run-id}@example.com`,
  `foreman+{run-id}@example.com`, `worker+{run-id}@example.com`, `client+{run-id}@example.com`;
- `note` аннекса / `description` линии: `aneks {run-id}`.

**Teardown каждой группы** выполняется в конце набора в обратном порядке создания:
`DELETE /api/amendments/{id}/lines/{lineId}` для созданных линий, затем `DELETE /api/amendments/{id}`
для созданных OPEN-аннексов (что снимает инвариант «один OPEN» и позволяет повторный прогон), затем
деактивация/удаление созданных тестовых пользователей admin-API и перевод тестовых проектов в
терминальный статус доступным admin-API. Сид-данные (роли, ресурс `AMENDMENTS`, его грант-матрица)
**только читаются, никогда не изменяются**. Каждая группа ниже дополнительно уточняет свою стратегию
строкой `**Повторяемость:**`.

> **Ключевой приём повторяемости для инварианта single-open.** Поскольку на проект допустим лишь один
> `OPEN`-аннекс (partial unique index `ux_amendment_open_per_project`), каждая API-группа, создающая
> аннекс, ОБЯЗАНА в teardown удалить его (`DELETE /api/amendments/{id}`). Без этого второй прогон
> упрётся в 409 `error.amendment.openExists` уже на создании. Как альтернатива — каждая группа
> создаёт **свежий тестовый проект** с `run-id` в имени, у которого заведомо нет OPEN-аннекса.

### Замечание про non-ADMIN роли (ABAC) и eligibility проекта

Бутстрапится только ADMIN. Роли MANAGER / FINANCIER / FOREMAN / WORKER / CLIENT создаются и
приглашаются в тестовый проект через admin-API в группе `Setup`. Матрица ресурса **`AMENDMENTS`:
ADMIN — CRUD; MANAGER — CRUD(own); FINANCIER — CRUD(own); FOREMAN — READ(own); WORKER / CLIENT — без
гранта**. Создание аннекса требует проекта в статусе `ACTIVE` с **подписанным estimate baseline**
(Requirement 2.5) — тестовый проект должен быть доведён до `ACTIVE` (через флоу FOR-05) либо
подготовлен фикстурой; если довести до `ACTIVE` в прогоне невозможно, кейсы eligibility документируют
ожидаемый отказ `error.amendment.notEligible` и покрываются слайс-тестами спеки
(`AmendmentServiceTest`).

# Часть A. API-тесты (docker-стек)

## Фича 0. Setup — токены, роли, eligible-проект

**Повторяемость:** читает сид + создаёт помеченные `run-id` сущности; teardown в конце набора.

### TC-SETUP-01 — Логин ADMIN
- **Предусловия:** стек поднят; ADMIN-бутстрап включён.
- **Шаги:**
  1. `POST /api/auth/login` с телом `{email: FOREMEN_ADMIN_EMAIL, password: FOREMEN_ADMIN_PASSWORD}`.
     Ожидание: `200`, в теле `accessToken` (+ `refreshToken`).
  2. Сохранить `accessToken` ADMIN для последующих запросов.
- **Ожидаемый результат:** получен валидный ADMIN-токен.
- _Покрывает: предусловие прочих кейсов._

### TC-SETUP-02 — Создание тестовых ролей и eligible-проекта
- **Предусловия:** TC-SETUP-01 пройден.
- **Шаги:**
  1. Создать (или переиспользовать) пользователей MANAGER, FINANCIER, FOREMAN, WORKER, CLIENT с
     `run-id` в email через admin-API. Ожидание: `200/201` на каждого.
  2. Создать проект `Aneks Test {run-id}` и довести его до статуса `ACTIVE` с подписанным estimate
     baseline (флоу FOR-05 или фикстура). Ожидание: проект в `ACTIVE`, есть подписанный estimate.
  3. Назначить MANAGER / FINANCIER / FOREMAN членами проекта (project membership) через
     `POST /api/project-members`. Ожидание: `200/201`.
  4. Залогинить MANAGER, FINANCIER, FOREMAN, WORKER, CLIENT → сохранить их `accessToken`.
- **Ожидаемый результат:** готов eligible-проект и набор токенов на все роли.
- _Покрывает: предусловие кейсов eligibility и ABAC._

## Фича 1. Создание аннекса и инвариант «один OPEN» (Requirement 2)

**Повторяемость:** teardown — `DELETE /api/amendments/{id}` для созданного OPEN-аннекса в конце группы.

### TC-AMD-CREATE-01 — Создание первого OPEN-аннекса на eligible-проекте
- **Предусловия:** TC-SETUP-02; у проекта нет OPEN-аннекса.
- **Шаги:**
  1. `POST /api/amendments/open?projectId={projectId}` под токеном MANAGER.
     Ожидание: `200/201`; в теле аннекс со `status="OPEN"`, `seqNo=1` (или следующий по порядку),
     пустым набором линий, `effectiveDate=null`.
  2. `GET /api/amendments?projectId={projectId}` под MANAGER.
     Ожидание: `200`; список содержит созданный аннекс; OPEN помечен/различим (Requirement 1.2).
- **Ожидаемый результат:** создан ровно один OPEN-аннекс с пустым набором линий.
- _Покрывает: 1.1, 2.2._

### TC-AMD-CREATE-02 — Повторный вызов open возвращает существующий OPEN (не создаёт второй)
- **Предусловия:** TC-AMD-CREATE-01 — OPEN-аннекс существует.
- **Шаги:**
  1. Повторный `POST /api/amendments/open?projectId={projectId}` под MANAGER.
     Ожидание: возвращается тот же OPEN-аннекс (тот же `id`/`seqNo`), второй аннекс НЕ создаётся.
  2. `GET /api/amendments?projectId={projectId}`.
     Ожидание: в списке по-прежнему ровно один OPEN-аннекс.
- **Ожидаемый результат:** идемпотентное «открытие» — один OPEN на проект.
- _Покрывает: 2.1, 2.3._

### TC-AMD-CREATE-03 — Прямое создание второго аннекса при существующем OPEN отклоняется (409)
- **Предусловия:** OPEN-аннекс существует.
- **Шаги:**
  1. `POST /api/amendments` (базовый CRUD-create) с телом нового аннекса на тот же `projectId` под
     MANAGER. Ожидание: `409`, тело содержит локализованный ключ `error.amendment.openExists`.
  2. `GET /api/amendments?projectId={projectId}`.
     Ожидание: `200`; второй аннекс не появился.
- **Ожидаемый результат:** инвариант single-open соблюдён на уровне API.
- _Покрывает: 2.1, 2.3._

### TC-AMD-CREATE-04 — Создание на не-ACTIVE проекте / без подписанного estimate отклоняется
- **Предусловия:** есть проект, не находящийся в `ACTIVE` (или без подписанного estimate).
- **Шаги:**
  1. `POST /api/amendments/open?projectId={ineligibleProjectId}` под MANAGER.
     Ожидание: `400`, локализованный `error.amendment.notEligible`; аннекс не создан.
- **Ожидаемый результат:** eligibility-guard работает.
- _Покрывает: 2.5._

## Фича 2. Добавление линии по типам изменения (Requirement 3)

**Повторяемость:** линии добавляются в OPEN-аннекс группы; teardown удаляет линии и аннекс.

### TC-AMD-LINE-01 — Добавление SCHEDULE_CHANGE (сдвиг расписания)
- **Предусловия:** есть OPEN-аннекс.
- **Шаги:**
  1. `POST /api/amendments/{id}/lines` под MANAGER с телом
     `{changeType:"SCHEDULE_CHANGE", scheduleDeltaHalfDays: 4, workCategoryId: null, description:"aneks {run-id}"}`.
     Ожидание: `200/201`; линия создана; `scheduleDeltaHalfDays=4`; целевая категория — null
     (весь проект).
  2. `GET /api/amendments/{id}`.
     Ожидание: линия присутствует с типом `SCHEDULE_CHANGE`.
- **Ожидаемый результат:** schedule-линия добавлена, базовый `ProjectScheduleBar` не изменён (overlay).
- _Покрывает: 3.1, 3.5._

### TC-AMD-LINE-02 — Добавление ADDITIONAL_WORK (полные данные)
- **Предусловия:** есть OPEN-аннекс; известен `workItemId` (вне estimate / флаг extra) и `roomId`.
- **Шаги:**
  1. `POST /api/amendments/{id}/lines` с телом
     `{changeType:"ADDITIONAL_WORK", workItemId, roomId, deltaQuantity: 10, extraUnitPrice: 150.00, description:"aneks {run-id}"}`.
     Ожидание: `200/201`; линия создана со всеми полями.
- **Ожидаемый результат:** доп-работа добавлена с объёмом, комнатой и ценой.
- _Покрывает: 3.1, 3.3._

### TC-AMD-LINE-03 — Добавление VOLUME_CHANGE существующей линии estimate
- **Предусловия:** есть OPEN-аннекс; известна существующая estimate-линия `(workItemId, roomId)`.
- **Шаги:**
  1. `POST /api/amendments/{id}/lines` с телом
     `{changeType:"VOLUME_CHANGE", workItemId, roomId, deltaQuantity: 5, extraUnitPrice: 120.00}`.
     Ожидание: `200/201`; линия создана; `deltaQuantity=5` (signed дельта, не абсолют).
- **Ожидаемый результат:** изменение объёма сохранено как дельта к baseline.
- _Покрывает: 3.1._

### TC-AMD-LINE-04 — Невалидные поля отклоняются (400)
- **Предусловия:** есть OPEN-аннекс.
- **Шаги:**
  1. `POST .../lines` `{changeType:"ADDITIONAL_WORK", workItemId, roomId}` без `deltaQuantity`/`extraUnitPrice`.
     Ожидание: `400`, локализованный `error.amendment.validation.*`; линия не создана.
  2. `POST .../lines` `{changeType:"VOLUME_CHANGE", workItemId, roomId, deltaQuantity: 0, extraUnitPrice: 120}`.
     Ожидание: `400` (нулевая дельта запрещена).
  3. `POST .../lines` `{changeType:"ADDITIONAL_WORK", workItemId, roomId, deltaQuantity: 1, extraUnitPrice: 0}`.
     Ожидание: `400`, `error.amendment.priceInvalid` (не-положительная цена).
- **Ожидаемый результат:** валидация полей по типу работает.
- _Покрывает: 3.6._

## Фича 3. Слияние по совпадающему субъекту (Requirement 5)

**Повторяемость:** merge-кейсы работают внутри OPEN-аннекса группы; teardown удаляет линии и аннекс.

### TC-AMD-MERGE-01 — 409 subject-conflict без Merge_Resolution
- **Предусловия:** в OPEN-аннексе уже есть линия `VOLUME_CHANGE (workItemId=W, roomId=R)`.
- **Шаги:**
  1. `POST .../lines` второй линией с тем же субъектом `(VOLUME_CHANGE, W, R)` **без** `mergeResolution`.
     Ожидание: `409`, локализованный `error.amendment.subjectConflict`; тело несёт существующую линию
     (для открытия чузера на UI); второй линии не создано.
- **Ожидаемый результат:** серверный инвариант «одна линия на субъект» без явного выбора.
- _Покрывает: 5.1, 5.6._

### TC-AMD-MERGE-02 — Разрешение ADD_TO суммирует дельты
- **Предусловия:** TC-AMD-MERGE-01 (субъект-конфликт воспроизводим).
- **Шаги:**
  1. `POST .../lines` с тем же субъектом и `{mergeResolution:"ADD_TO", deltaQuantity: 3, extraUnitPrice: 130}`.
     Ожидание: `200`; осталась **одна** линия субъекта; `deltaQuantity` = сумма (существующая + 3);
     `extraUnitPrice` = новая цена (130).
  2. `GET /api/amendments/{id}`.
     Ожидание: ровно одна линия субъекта `(VOLUME_CHANGE, W, R)`.
- **Ожидаемый результат:** ADD_TO суммирует объём и берёт новую цену.
- _Покрывает: 5.1, 5.3, 5.4._

### TC-AMD-MERGE-03 — REPLACE и KEEP_EXISTING
- **Предусловия:** в OPEN-аннексе есть линия субъекта `(VOLUME_CHANGE, W, R)`.
- **Шаги:**
  1. `POST .../lines` с `{mergeResolution:"REPLACE", deltaQuantity: 9, extraUnitPrice: 200}`.
     Ожидание: `200`; одна линия субъекта; значения = новые (9 / 200).
  2. `POST .../lines` с `{mergeResolution:"KEEP_EXISTING", deltaQuantity: 1, extraUnitPrice: 1}`.
     Ожидание: `200`; одна линия субъекта; значения НЕ изменились (остались 9 / 200).
- **Ожидаемый результат:** REPLACE перезаписывает, KEEP_EXISTING отбрасывает новый ввод.
- _Покрывает: 5.1, 5.4._

### TC-AMD-MERGE-04 — Разный субъект не конфликтует (append)
- **Предусловия:** есть линия субъекта `(VOLUME_CHANGE, W, R)`.
- **Шаги:**
  1. `POST .../lines` `(VOLUME_CHANGE, W, R2)` — другая комната, без `mergeResolution`.
     Ожидание: `200/201`; добавлена **отдельная** линия (не 409).
- **Ожидаемый результат:** различие по `(workItem, room)` даёт distinct-линию.
- _Покрывает: 5.3._

## Фича 4. Удаление линии / аннекса и OPEN-guard (Requirement 6)

**Повторяемость:** группа сама создаёт и удаляет данные; teardown подчищает остатки.

### TC-AMD-DEL-01 — Удаление одной линии (аннекс остаётся OPEN)
- **Предусловия:** OPEN-аннекс с ≥2 линиями.
- **Шаги:**
  1. `DELETE /api/amendments/{id}/lines/{lineId}` под MANAGER.
     Ожидание: `200/204`; линия удалена; аннекс по-прежнему `OPEN`.
  2. `GET /api/amendments/{id}`.
     Ожидание: удалённой линии нет; статус `OPEN`.
- **Ожидаемый результат:** одиночная линия удалена, overlay downstream не затронут.
- _Покрывает: 6.1._

### TC-AMD-DEL-02 — Удаление последней линии оставляет пустой OPEN-аннекс
- **Предусловия:** OPEN-аннекс с одной линией.
- **Шаги:**
  1. `DELETE /api/amendments/{id}/lines/{lineId}` последней линии.
     Ожидание: `200/204`; аннекс остаётся `OPEN`, набор линий пуст.
- **Ожидаемый результат:** пустой аннекс не удаляется автоматически и остаётся OPEN.
- _Покрывает: 6.1._

### TC-AMD-DEL-03 — Удаление всего аннекса освобождает инвариант OPEN
- **Предусловия:** есть OPEN-аннекс.
- **Шаги:**
  1. `DELETE /api/amendments/{id}` под MANAGER.
     Ожидание: `200/204`; аннекс больше не считается OPEN для проекта
     (hard-delete или `status=DELETED`).
  2. `POST /api/amendments/open?projectId={projectId}`.
     Ожидание: `200/201`; создан новый OPEN-аннекс (инвариант освобождён).
- **Ожидаемый результат:** удаление аннекса позволяет создать свежий OPEN.
- _Покрывает: 6.2._

### TC-AMD-DEL-04 — Overlay: базовые данные не тронуты
- **Предусловия:** до/после добавления и удаления линий фиксируются snapshot'ы estimate и schedule.
- **Шаги:**
  1. Снять `GET` по estimate baseline и schedule до операций.
  2. Выполнить add-line + delete-line + delete-amendment.
  3. Повторно снять snapshot'ы.
     Ожидание: estimate-линии, room-qty, schedule-бары, work reports — **идентичны** исходным.
- **Ожидаемый результат:** неподписанный аннекс не влияет ни на что downstream.
- _Покрывает: 6.2._

## Фича 5. ABAC-матрица ресурса AMENDMENTS (Requirement 9)

**Повторяемость:** чисто read/мутации под разными ролями на проекте группы; teardown удаляет аннекс.

### TC-AMD-ABAC-01 — ADMIN/MANAGER/FINANCIER имеют CRUD
- **Предусловия:** eligible-проект; токены ADMIN/MANAGER/FINANCIER; роли — члены проекта.
- **Шаги:**
  1. Под каждым из ADMIN/MANAGER/FINANCIER: `POST /api/amendments/open?projectId`,
     `POST .../lines`, `GET /api/amendments?projectId`, `DELETE .../lines/{lineId}`, `DELETE .../{id}`.

# Часть B. Браузерные (UI) сценарии — вкладка Aneksy

**Окружение:** фронтенд `http://localhost:3000`, backend `http://localhost:8080`. Исполняется
браузерным движком (browser automation). Предусловие всех UI-кейсов: eligible `ACTIVE`-проект с
подписанным estimate (из Setup Части A), логин под нужной ролью, переход на вкладку **Aneksy** проекта
(`/projects/:projectId/amendments`).

**Повторяемость:** UI-сценарии создают OPEN-аннекс и его линии и удаляют их через UI (диалоги удаления)
в конце сценария (teardown через кнопку «Удалить аннекс»); либо прогоняются на свежем `run-id`-проекте.

### TC-UI-01 — Рендер списка аннексов
- **Предусловия:** логин MANAGER; на проекте есть ≥1 аннекс.
- **Шаги:**
  1. Открыть вкладку **Aneksy**. Ожидание: отрисован список-таблица с колонками `seqNo`, статус
     (локализованный chip), число линий, effective date, метаданные создания/обновления.
  2. OPEN-аннекс (если есть) визуально различим. Ожидание: выделен/помечен.
  3. Клик по строке аннекса. Ожидание: раскрываются линии (тип, субъект, дельта; для cost-линий —
     объём, комната, цена).

### TC-UI-02 — Мастер создания аннекса: три типа изменений
- **Предусловия:** логин MANAGER; у проекта нет OPEN-аннекса (или открывается существующий).
- **Шаги:**
  1. Нажать **Создать аннекс** / **Добавить изменение**. Ожидание: открыт popup-мастер с **тремя
     icon-кнопками**: «Изменить расписание», «Добавить доп. работу», «Изменить объём».
  2. Выбрать «Изменить расписание». Ожидание: форма с вводом срока (дни/недели → half-days) и
     опциональным выбором категории. Заполнить и подтвердить → линия `SCHEDULE_CHANGE` появилась.
  3. Повторно открыть мастер, выбрать «Добавить доп. работу». Ожидание: форма требует work/room/объём/
     цену; валидна только при полных данных; подтверждение добавляет линию `ADDITIONAL_WORK`.
  4. Выбрать «Изменить объём». Ожидание: форма с existing work/room + signed дельта + цена;
     подтверждение добавляет линию `VOLUME_CHANGE`.

### TC-UI-03 — Чузер конфликта слияния при 409

- _Покрывает: 5.1._

### TC-UI-04 — Диалоги удаления линии и удаления аннекса
