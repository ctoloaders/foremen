# Тест-кейсы: FOR-06-05 — Materials matrix (матрица материалов «план × факт»)

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерный экран**, поэтому набор тест-кейсов включает **оба типа**:

- **Часть A. API-тесты** — против поднятого в Docker приложения (`http://localhost:8080`). Каждый
  шаг — HTTP-запрос к read-эндпоинту матрицы
  `GET /api/projects/{projectId}/materials-matrix` (ABAC `PURCHASES`/READ) с проверкой статуса, тела
  и заголовков. Проверяются: агрегация факта по планируемому материалу через все аналоги и тиры на
  полный вес, денежный `% выборки` без «потолка» (uncapped), перебор по плану (> 100 %), исключение
  строк с другой единицей из суммы количества (при сохранении их в денежном факте), случай
  `null`-брутто → `—`, дашбордные итоги (по ветке и общий), фильтрация по проекту (project-scope) и
  ABAC-гейт `PURCHASES`/READ.
- **Часть B. Браузерный (UI) сценарий** — против фронтенда (`http://localhost:3000`), исполняется
  браузерным движком (headless-браузер / browser automation) под ролью с грантом `PURCHASES`/READ
  (например MANAGER или FINANCIER) на проекте в статусе `ACTIVE`. Экран: вкладка `Materials`
  (execution-stage tab `materials`), вкладки ветвей construction / finishing, строки матрицы с
  индикатором заполнения (fill bar) и реальной цифрой `% выборки`, подсветка перебора, индикатор
  несовпадения единиц, drawer детализации с перечнем связанных строк-аналогов и тир-бейджами,
  дашборд с итогами, а также режим read-only на проекте `COMPLETED`.

Планируемые материалы (план-сторона из FOR-05-05b) и согласованные закупочные строки (факт-сторона
из FOR-06-04) **засеиваются напрямую** — без живой зависимости от OCR (FOR-06-03). Результат прогона
для обеих частей — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус).
**Скриншоты не требуются.**

### Покрытие требований

Данный набор покрывает требования, перечисленные в задаче 7: **1.2, 1.3, 1.4, 1.6, 2.1, 2.2, 3.2,
4.1, 4.2, 5.1, 5.4, 6.1, 6.4**. Соответствие «кейс ↔ требование» указано в каждом кейсе строкой
`_Покрывает:_`. Регрессионная группа в конце файла перепроверяет, что спека ничего не ломает в
план-стороне (FOR-05-05b), факт-стороне (FOR-06-04) и ресурсе `PURCHASES` (FOR-06-03), в соответствии
с R9.1.

> **Важный архитектурный нюанс.** Это **read-only проекция** над двумя существующими read-моделями.
> Спека **не** вводит новую сущность, ресурс ABAC, справочник или Liquibase-changeset. Поэтому матрица
> не меняет никаких данных: во всех API-кейсах используется только `GET`, а сид факт-данных
> выполняется через внутренние согласованные строки FOR-06-04 (руками через БД/сид-утилиту, не через
> публичный write-API данной спеки — такого API здесь нет).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции),
   `backend` (:8080, профиль `docker`), `frontend` (:3000). Данная спека миграций не добавляет;
   ресурс `PURCHASES` уже засеян FOR-06-03 (changeset `169`).
2. Базовый URL для API-тестов: `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
3. Первый ADMIN — через переменные окружения `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
   `FOREMEN_ADMIN_PASSWORD`. Логин: `POST /api/auth/login {email, password}` → `accessToken`.
4. Дождаться готовности `backend` и завершения миграций перед прогоном (проверка готовности:
   эндпоинт матрицы на любом `ACTIVE`-проекте отвечает 200).

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown.** Единый на прогон `run-id` (timestamp или uuid,
например `1730000000` или `a1b2c3`) встраивается во все создаваемые идентификаторы, чтобы два
последовательных прогона на одной БД не конфликтовали:

- имена проектов: `MatrixTest {run-id}`, `MatrixDraft {run-id}`, `MatrixDone {run-id}`,
  `MatrixOther {run-id}`;
- имена материалов (если создаются тестовые): `Mat {run-id} A`, `Mat {run-id} B`;
- email тестовых пользователей non-ADMIN ролей: `mgr+{run-id}@example.com`,
  `fin+{run-id}@example.com`, `noperm+{run-id}@example.com`;
- поставщики/документы факт-строк: `Supplier {run-id}`, `DOC-{run-id}-NN`.

**Teardown каждой группы** (если не указано иное) выполняется в конце набора в обратном порядке
создания: удаление/деактивация засеянных согласованных закупочных строк и их документов, затем
созданных планируемых материалов/оценок тестовых проектов, затем перевод тестовых проектов в
`CANCELLED`/`COMPLETED` или их удаление доступным admin-API, затем деактивация тестовых пользователей.
Сид-данные (роли, ресурс `PURCHASES`, тир-перечисления) **только читаются, никогда не изменяются**.
Каждая группа ниже дополнительно уточняет свою стратегию строкой `**Повторяемость:**`.

### Замечание про non-ADMIN роли (ABAC)

Бутстрапится только ADMIN. Там, где кейс требует роли MANAGER / FINANCIER или роли без гранта
`PURCHASES`, тестовые пользователи создаются и приглашаются через admin-API в группе `Setup`.
Матрица матрицы (read-эндпоинт) защищена ресурсом `PURCHASES` как операция `READ`; по сиду FOR-06-03
`PURCHASES` READ доступен ADMIN / FINANCIER / MANAGER / FOREMAN (и ESTIMATOR READ). Пользователь без
гранта на `PURCHASES` для проекта должен получать `403`.

## Фича 1. Read-модель матрицы: агрегация факта по планируемому материалу (R1)

**Повторяемость:** читает `PROJECT_ID`, засеянный в Setup; teardown факт-строк в конце набора.

### TC-MATRIX-01 — Строки матрицы = планируемые материалы, план читается verbatim
- **Предусловия:** `PROJECT_ID` с планом из TC-SETUP-02; `ADMIN_TOKEN`.
- **Шаги:**
  1. `GET /api/projects/{PROJECT_ID}/materials-matrix` c `Authorization: Bearer ADMIN_TOKEN`.
     — Ожидание: `200`. В теле `branches[]` содержит `construction` и `finishing`; строки — ровно
     планируемые материалы `M1..M4`, каждая строка несёт `materialName`, `branch`, `category`, `unit`,
     `plannedQuantity`, `plannedBrutto`, прочитанные из FOR-05-05b без искажений.
- **Ожидаемый результат:** одна строка на `(branch, concreteMaterialId)`, план-данные verbatim.
- _Покрывает:_ R1.1 (контекст), R5.1 (данные для UI).

### TC-MATRIX-02 — Агрегация аналогов через все тиры на полный вес (факт-брутто)
- **Предусловия:** для `M1` засеяны **три** согласованные строки под разными продуктами/производителями:
  - L1: `matchedMaterialId=M1`, `matchStatus=AUTO`, `matchTier=EXACT` (100 %), `lineTotal=100.00`;
  - L2: `matchedMaterialId=M1`, `matchStatus=MANUAL_MATCHED`, `matchTier=MANUFACTURER_CATEGORY` (80 %), `lineTotal=50.00`;
  - L3: `matchedMaterialId=M1`, `matchStatus=AUTO`, `matchTier=CATEGORY` (50 %), `lineTotal=30.00`.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M1`: `factBrutto == 180.00` (= 100+50+30 — **каждая строка в полный вес, тир не
     масштабирует**), `linkedLineCount == 3`.
- **Ожидаемый результат:** три аналога суммируются полностью независимо от тира.
- _Покрывает:_ R1.2, R1.3 (числитель), R4.3 (аналоги считаются вместе).

### TC-MATRIX-03 — Денежный `% выборки` и перебор по плану (uncapped > 100 %)
- **Предусловия:** для `M1` `plannedBrutto = PB1 = 150.00`; факт-брутто из TC-MATRIX-02 = `180.00`.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M1`: `fulfilmentPercent == 120.0000` (= 180/150×100, **без потолка**),
     `fillIndicator == 100` (= min(pct,100)), `overPurchased == true`.
- **Ожидаемый результат:** `% выборки` считается от денег, не ограничен 100 %, перебор помечен.
- _Покрывает:_ R1.3, R4.1.

### TC-MATRIX-04 — Нет связанных строк → факт 0 и `% выборки` 0
- **Предусловия:** для `M2` (plannedBrutto=`PB2`, ненулевой) **нет** связанных строк.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M2`: `factBrutto == 0`, `fulfilmentPercent == 0`, `linkedLineCount == 0`,
     `unitMismatch == false`.
- **Ожидаемый результат:** пустой факт даёт 0/0, без деления на ноль.
- _Покрывает:_ R1.4, R2.4.

### TC-MATRIX-05 — `null`/нулевой планируемый брутто → `% выборки` = `null` (`—`)
- **Предусловия:** `M4` имеет `plannedBrutto = null` (или `0`); допускаются связанные строки по `M4`.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M4`: `fulfilmentPercent == null`, `fillIndicator == null`, `overPurchased == false`;
     строка присутствует в теле (количества/связанные строки видны), не вызывает ошибки деления.
- **Ожидаемый результат:** строка без осмысленного знаменателя отдаёт `null` (на UI — `—`).
- _Покрывает:_ R1.4.

### TC-MATRIX-06 — Несвязанные/незапланированные строки не попадают ни в одну строку
- **Предусловия:** засеяны строки, которые **не** должны участвовать:
  - U1: `matchStatus=UNMATCHED`, `matchedMaterialId=null`;
  - U2: `matchStatus=MANUAL_UNMATCHED`, `matchedMaterialId=null`;
  - U3: строка, классифицированная как `UnplannedExpenseCategory` (нет `matchedMaterialId`).
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. Суммарный `factBrutto` всех строк и `linkedLineCount` **не** включают U1/U2/U3; ни одна строка
     матрицы не ссылается на них в своих `linkedLines`.
- **Ожидаемый результат:** матрица — план-vs-факт только для запланированных материалов.
- _Покрывает:_ R1.6.

### TC-MATRIX-07 — Связанные строки сохранены для детали (count + список с тир/статусом)
- **Предусловия:** `M1` с тремя связанными строками (TC-MATRIX-02).
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M1`: `linkedLines[]` содержит 3 элемента; на каждом есть `matchTier`, `tierPercent`
     (100/80/50), `matchStatus`, `rawName`, `manufacturerHint`, `quantity`, `unitHint`, `lineTotal`,
     `documentId`, `supplierName` — микс тиров/статусов не «схлопнут».
- **Ожидаемый результат:** деталь R4.2 обеспечена данными на уровне read-модели.
- _Покрывает:_ R1.5 (контекст), R4.2.

## Фича 2. Факт-количество и несовпадение единиц (R2)

**Повторяемость:** читает `PROJECT_ID`; teardown факт-строк в конце набора.

### TC-UNIT-01 — Факт-количество суммирует только строки с совпадающей единицей
- **Предусловия:** норм-единица `M3` = `кг`. Засеяны связанные строки:
  - Q1: `unitHint="кг"`, `quantity=10`, `lineTotal=40.00`;
  - Q2: `unitHint=" КГ "` (регистр/пробелы — должно совпасть), `quantity=5`, `lineTotal=20.00`;
  - Q3: `unitHint="шт"` (чужая единица), `quantity=7`, `lineTotal=15.00`;
  - Q4: `unitHint=""`/`null` (пустая — не совпадает), `quantity=3`, `lineTotal=9.00`.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M3`: `factQuantity == 15` (= 10+5, только `кг`-совпадающие; сравнение
     регистро/пробел-независимое). Q3 и Q4 исключены из суммы количества.
- **Ожидаемый результат:** количество считается только по совпадающей единице, без конвертации.
- _Покрывает:_ R2.1, R2.3.

### TC-UNIT-02 — `Unit_Mismatch_Count` и флаг; деньги учитывают все строки
- **Предусловия:** те же Q1–Q4 из TC-UNIT-01.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. В строке `M3`: `unitMismatchCount == 2` (Q3 и Q4), `unitMismatch == true`;
     `factBrutto == 84.00` (= 40+20+15+9 — **все** строки в деньгах, единица не влияет);
     соответствующие `linkedLines[].unitMismatch == true` для Q3/Q4.
- **Ожидаемый результат:** несовпавшие единицы помечены и исключены из количества, но учтены в деньгах.
- _Покрывает:_ R2.2.

## Фича 3. Дашбордные итоги (R3)

**Повторяемость:** читает `PROJECT_ID`; teardown факт-строк в конце набора.

### TC-DASH-01 — Итоги по ветке и общий; `null`-брутто исключён из денег
- **Предусловия:** известны `plannedBrutto`/`factBrutto` по строкам `M1..M4`; `M4` — `null`-брутто.
- **Шаги:**
  1. `GET .../materials-matrix` (ADMIN). — Ожидание: `200`.
  2. Для ветки `construction`: `plannedBrutto` = Σ план-брутто `M1,M2` (ненулевые),
     `factBrutto` = Σ факт-брутто `M1,M2`, `aggregatePercent` = factBrutto/plannedBrutto×100 (uncapped).
  3. Для ветки `finishing`: `M4` (`null`-брутто) **исключён** из `plannedBrutto`/`factBrutto` и из
     знаменателя `aggregatePercent`; учитывается только `M3`.
  4. На корне: `grandPlannedBrutto` = Σ по веткам, `grandFactBrutto` = Σ по веткам,
     `grandAggregatePercent` пересчитан из гранд-сумм; гранд-итоги = сумма по-веточных.
- **Ожидаемый результат:** свёртки совпадают по веткам и в целом; `null`-брутто не искажает деньги.
- _Покрывает:_ R3.2, R3.3.
