# Тест-кейсы: FOR-06-02 — Наложение плана/факта на Гант

## Назначение и характер спеки

Спека имеет **и API-поверхность, и браузерные экраны**, поэтому набор тест-кейсов включает **оба
типа**:

- **Часть A. API-тесты** — против поднятого в Docker приложения (`http://localhost:8080`). Каждый
  шаг — HTTP-запрос к read-only эндпоинту плана/факта
  `GET /api/project-schedules/plan-actual?projectId=` (ресурс `WORK_SCHEDULE`, операция READ), с
  проверкой статуса, тела и инварианта «только чтение». Проверяется бакетирование отчётов по
  статусам (confirmed/pending/rejected), расчёт выполнения (quantity-ratio), классификация
  траектории (on-track/at-risk/overdue), money-gate, видимость всех статусов и own-records-скоуп
  воркера в drill-down.
- **Часть B. Браузерные (UI) сценарии** — против фронтенда (`http://localhost:3000`), исполняются
  браузерным движком (headless-браузер / browser automation). Экран: вкладка `planActual`
  воркспейса `ACTIVE`-проекта — read-only наложение (плановые бары с заливкой выполнения +
  отдельный pending-бэнд), список «под риском», drill-down по категории (ячейки `работа × помещение`
  с план/подтверждено/на проверке/отклонено и дип-линками в отчёты), фильтры по статусу и работнику,
  состояния загрузки/пустоты. Проверяется отсутствие любых редактирующих элементов (read-only).

Результат прогона для обеих частей — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание →
факт → статус). **Скриншоты не требуются.**

### Покрытие требований

Тест-кейсы покрывают требования R1 (read-model), R2.2/R2.3/R2.4/R2.5 (выполнение, unplanned,
over-report, взвешенный роллап), R3.1/R3.2/R3.3/R3.4 (видимость всех статусов, drill-down,
own-records воркера), R4.1/R4.2/R4.4/R4.5 (траектория и прогноз от confirmed), R5.1–R5.5 (read-only
панель, pending-бэнд, список под риском, drill-down), R6.1/R6.2/R6.5 (стадийный гейт, доступ,
money-gate), R10.1 (инвариант «ничего не пишет»). Соответствие «кейс ↔ требование» указано в каждом
кейсе строкой `_Покрывает:_`.

## Стратегия повторяемости

Выбранная стратегия — **генератор данных + teardown**:

- **Run-id генератор.** Каждый прогон использует `run-id` = timestamp (`$(date +%s)`), встраиваемый
  в имя проекта (`PlanFact {run-id}`) и в email создаваемых пользователей
  (`pf+{run-id}@example.com`), чтобы прогоны не конфликтовали.
- **Teardown.** Поскольку спека **ничего не пишет в домен** (read-only overlay), чистке подлежат
  только сущности, созданные на **setup** (проект, смета, график, отчёты из FOR-05/FOR-06-01).
  Удаление — обратным порядком создания (отчёты → график → смета → проект → участники), либо через
  деактивацию. Сам эндпоинт плана/факта teardown не требует: он не создаёт строк.
- **Инвариант read-only.** После каждого прогона Части A кейс **TC-API-READONLY** проверяет, что
  `version` в ответе не изменился и новых строк `project_schedules` / `project_schedule_bars` не
  появилось — т.е. повторный вызов идемпотентен по состоянию БД.

## Предусловия окружения (общие)

1. Docker-стек поднят (`docker compose up` в корне): `postgres` (:5432), `liquibase` (миграции),
   `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Первый ADMIN поднят через `FOREMEN_ADMIN_CREATE=true` / `FOREMEN_ADMIN_EMAIL` /
   `FOREMEN_ADMIN_PASSWORD`. Логин — `POST /api/auth/login` → access-токен в заголовок
   `Authorization: Bearer <token>`.
3. Ресурс `WORK_SCHEDULE` засеян (changeset 153) с грантами FOR-05-10 (ADMIN/MANAGER CRUD,
   FOREMAN/ESTIMATOR READ+UPDATE, WORKER/FINANCIER/CLIENT READ).
4. Для осмысленного наложения нужен **setup-проект стадии `ACTIVE`** со сметой (строки + помещения с
   плановыми объёмами), сохранённым планом-Гантом (бары по категориям) и несколькими отчётами
   FOR-06-01 в разных статусах (APPROVED / SUBMITTED / CHANGES_REQUESTED / REJECTED).

## Часть A. API-тесты (feature-группы)

### Группа A1. Read-model и бакетирование по статусам

#### TC-API-BUCKETS — confirmed/pending/rejected считаются раздельно
_Покрывает: R1.1, R1.3, R2.2, R3.1, R3.2_

**Предусловия:** setup-проект `ACTIVE` с категорией `C` (плановый объём 100 для пары
`(работа W, помещение R)`); отчёты по `(W, R)`: APPROVED 40, SUBMITTED 15, CHANGES_REQUESTED 5,
REJECTED 99. Логин ADMIN.

**Шаги:**
1. `GET /api/project-schedules/plan-actual?projectId={id}` →
   ожидание: `200`; в категории `C` — `confirmedQuantity=40`, `pendingQuantity=20`
   (15+5), `rejectedQuantity=99`, `confirmedCompletion≈0.4`.
2. Проверить `totals.confirmedQuantity=40`, `totals.pendingQuantity=20` →
   ожидание: отклонённые не вошли ни в confirmed, ни в pending.

**Ожидаемый результат:** все три бакета раздельны; отклонённый объём не влияет на выполнение.

#### TC-API-COMPLETION — выполнение как отношение количеств (clamp, over-report, unplanned)
_Покрывает: R2.3, R2.4, R2.5_

**Шаги:**
1. Ячейка с планом 50 и подтверждённым 80 → ожидание: `confirmedCompletion=1.0`,
   `overReported=true` в ячейке и в категории.
2. Ячейка без плана (нет `EstimateLineRoomQty`) с подтверждённым 12 → ожидание: `noPlan=true`,
   выполнение ячейки = 1.0, вес плана 0 (unplanned actual).
3. Категория с несколькими ячейками → ожидание: `confirmedCompletion` = взвешенное по плановому
   объёму среднее.

**Ожидаемый результат:** деления на ноль нет; перевыполнение клампится к 100% с флагом; внеплановый
факт помечен `noPlan`.

### Группа A2. Траектория и прогноз

#### TC-API-TRAJECTORY — on-track / at-risk / overdue от confirmed
_Покрывает: R4.1, R4.2, R4.4, R4.5_

**Шаги:**
1. Категория, окно которой полностью истекло (anchor в прошлом), confirmed < 100% →
   ожидание: `trajectoryStatus=OVERDUE`.
2. Та же категория с большим `pendingQuantity` (например 70 при плане 100, confirmed 30) →
   ожидание: статус **остаётся** `OVERDUE` (pending не спасает траекторию).
3. Категория с `confirmedCompletion`, отстающим от доли истёкшего времени более чем на `riskMargin`
   (0.1) → ожидание: `AT_RISK`, `projectedFinishDay` рассчитан (не null).
4. Категория проекта **без даты старта** → ожидание: `ON_TRACK`, `note="noAnchor"`,
   `projectedFinishDay=null`.

**Ожидаемый результат:** классификация зависит только от confirmed; отсутствие якоря не даёт ложных
алертов.

### Группа A3. Доступ, money-gate, read-only, пустой план

#### TC-API-MONEY-GATE — money-роллап только для money-viewer
_Покрывает: R6.5_

**Шаги:**
1. Логин ADMIN (money-viewer) → `GET .../plan-actual` → ожидание: присутствует блок `money`
   (`currency`, `plannedValue`, `confirmedValue`).
2. Логин FOREMAN/WORKER (не money-viewer по `ESTIMATE` READ) → ожидание: блок `money`
   отсутствует/`null`.

#### TC-API-ACCESS — гейт `WORK_SCHEDULE` READ + проектный скоуп
_Покрывает: R6.2, R6.4_

**Шаги:**
1. Пользователь без членства в проекте (или без READ `WORK_SCHEDULE`) → ожидание: `404`/`403`
   (как у обычного чтения графика); overlay не обходит гейт.
2. Участник проекта с READ → ожидание: `200` с наложением.

#### TC-API-WORKER-DRILLDOWN — own-records воркера в drill-down
_Покрывает: R3.4_

**Шаги:**
1. Логин WORKER-участника; в проекте есть отчёты и этого воркера, и другого →
   `GET .../plan-actual` → ожидание: агрегаты ячеек по категории видны полностью, но в `reports[]`
   каждой ячейки присутствуют **только** собственные отчёты воркера.

#### TC-API-EMPTY-PLAN — пустой/отсутствующий график
_Покрывает: R1.5_

**Шаги:**
1. Проект без сохранённого графика (нет баров) → ожидание: `200`; строки категорий из сметы с
   пустым окном (`plannedDurationDays=0`), `trajectoryStatus=ON_TRACK`; новых строк
   `project_schedules` не создано.

#### TC-API-READONLY — эндпоинт ничего не пишет
_Покрывает: R1.6, R10.1_

**Шаги:**
1. Зафиксировать `version` графика (через `GET /api/project-schedules`) и число строк
   `project_schedule_bars`.
2. Вызвать `GET .../plan-actual` 3 раза подряд → ожидание: `200` каждый раз; `version` неизменна;
   число строк графика/баров не изменилось; аудит-строк не добавлено.

## Часть B. Браузерные (UI) сценарии

### Группа B1. Read-only наложение и состояния

#### TC-UI-OVERLAY — плановые бары с заливкой выполнения и pending-бэндом
_Покрывает: R5.1, R5.2, R3.2_

**Предусловия:** setup-проект `ACTIVE`; логин ADMIN/MANAGER; открыта вкладка «Plan/wykonanie».

**Шаги:**
1. Открыть вкладку `planActual` воркспейса проекта → ожидание: рендерится Гант-наложение
   (`[data-testid=plan-actual-gantt]`), на строке категории — плановый бар
   (`plan-actual-bar`) с заливкой подтверждённого выполнения (`plan-actual-bar-confirmed`) и
   отдельным, визуально отличным pending-бэндом (`plan-actual-bar-pending`).
2. Проверить метку процента выполнения и бейдж траектории на строке → ожидание: локализованы (PL/RU),
   без «сырых» ключей.

#### TC-UI-READONLY — отсутствие редактирующих элементов
_Покрывает: R5.5_

**Шаги:**
1. На вкладке `planActual` искать элементы drag/resize/авто-создания/сохранения бара →
   ожидание: таких элементов нет (панель строго read-only); редактирование остаётся на
   design-вкладке `scheduleDesign`.
2. Пустой проект (нет графика/отчётов) → ожидание: показан empty-state
   (`plan-actual-empty`) без ошибки; состояние загрузки `plan-actual-loading` отображается до
   загрузки.

### Группа B2. Список под риском и drill-down

#### TC-UI-AT-RISK — список «под риском»
_Покрывает: R5.3_

**Шаги:**
1. Открыть вкладку → ожидание: блок `plan-actual-at-risk` содержит строки **только** для категорий
   `AT_RISK`/`OVERDUE` с процентом выполнения и прогнозом финиша; если рисков нет — показан
   `plan-actual-at-risk-empty`.
2. Клик по строке риска → ожидание: открывается drill-down соответствующей категории.

#### TC-UI-DRILLDOWN — drill-down по категории с дип-линками
_Покрывает: R5.4, R3.3_

**Шаги:**
1. Клик по строке категории → ожидание: таблица ячеек `работа × помещение` с колонками
   план / подтверждено / на проверке / отклонено и флагами `overReported` / `noPlan`.
2. Проверить ссылки на отчёты (`plan-actual-report-link`) → ожидание: `href` =
   `/projects/{projectId}/workReporting?report={reportId}` (переход во вкладку отчётов).

#### TC-UI-FILTERS — фильтры по статусу траектории и работнику
_Покрывает: R5.6_

**Шаги:**
1. Выбрать в фильтре статуса `AT_RISK` → ожидание: в Ганте остаются только категории под риском.
2. Выбрать работника → ожидание: остаются только категории, где этот работник присутствует в
   плановых барах.

## Регрессия

Перепроверка критичных сквозных путей, затрагиваемых read-only наложением:

- **TC-REG-SCHEDULE-UNCHANGED** — после серии вызовов `plan-actual` обычное чтение графика
  (`GET /api/project-schedules`) и его сохранение/авто-создание (FOR-05-10/10b) работают без
  изменений (overlay не портит план). _Покрывает: R10.2._
- **TC-REG-REPORTING-UNCHANGED** — CRUD/ревью отчётов FOR-06-01 (`/api/work-reports`) и их статусы
  не затронуты чтением наложения. _Покрывает: R10.2._
- **TC-REG-TABS** — стадийный резолвер табов: `planActual` присутствует на `ACTIVE`/`COMPLETED` и
  отсутствует на `DRAFT`; `scheduleDesign` по-прежнему на design-стадии. _Покрывает: R6.1._

Иные регрессионные кейсы на данном этапе не требуются: спека не вводит новых сущностей, таблиц,
ABAC-ресурсов и нотификаций, поэтому поверхность возможной регрессии ограничена перечисленными
сквозными путями.
