# Тест-кейсы: FOR-02-07 Users UI Fixes

Документ описывает ручные/автоматизируемые сценарии проверки исправлений 7 багов в модуле управления пользователями (спека `FOR-02-07-users-ui-fixes`). Спека **смешанная**: часть сценариев — браузерные (UI), часть — чисто API против поднятого docker-стека.

## Область покрытия и типы кейсов

| Баг | Область | Тип кейса |
|-----|---------|-----------|
| 1.1 Прозрачный фон RoleSelect в тёмной теме | UI | Браузерный |
| 1.2 Загрузка всех страниц ролей сразу | UI (+ наблюдение сети) | Браузерный |
| 1.3 Клиентский поиск вместо серверного | UI (+ наблюдение сети) | Браузерный |

## Окружение и предпосылки

### UI-сценарии (браузерный движок)
- Исполняются headless-браузером / браузерной автоматизацией. Каждый шаг — действие в браузере (переход, ввод, клик, ожидание элемента, наблюдение сети через devtools/CDP).
- Результат прогона — **MD-репорты с таблицами** (шаг → действие → ожидание → факт → статус). Скриншоты не требуются.
- Frontend доступен по адресу `http://localhost:3000`. Вход выполняется под учёткой seeded ADMIN.
- Раздел управления пользователями: `http://localhost:3000` → навигация в раздел «Users» (форма создания/редактирования — `UserFormSheet`, выбор роли — `RoleSelect`).

### API-сценарии (HTTP против Docker-стека)
- `docker compose up` в корне поднимает: `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
- Базовый URL для API-тестов: `http://localhost:8080`.
- Auth-эндпоинты — под `/api/auth`. Первый ADMIN поднимается через `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.

### Реальные эндпоинты (проверены по контроллерам)
- `POST /api/auth/login` — тело `{ "email": "...", "password": "..." }` → `200` + `{ accessToken, refreshToken, ... }`.
- `POST /api/users` — тело `{ name, email, phone, roleId, locale, displayPreferences }` → `201` + `UserCreateResponse` `{ id, name, email, phone, roleId, active, locale, displayPreferences }`. Требует `Authorization: Bearer <accessToken>`.
- `PUT /api/users/{id}` — тело `{ name, email, phone, roleId, active, locale, displayPreferences }` → `200` + `UserUpdateResponse`.
- `GET /api/users?page=&size=&query=` — постраничный список (`Page<UserDtoModel>`).
- `GET /api/users/{id}` — расширенная модель `UserDtoExtendedModel` (включает `displayPreferences`).
- `GET /api/roles?page=&size=&query=` — постраничный список ролей; фильтр по имени — `query=name~ct~{input}`.

### Получение admin JWT (общий Setup для всех API-кейсов)
1. `POST http://localhost:8080/api/auth/login` с телом `{ "email": "<FOREMEN_ADMIN_EMAIL>", "password": "<FOREMEN_ADMIN_PASSWORD>" }`.
2. Ожидается `200 OK` и поле `accessToken`.
3. Во всех последующих запросах передавать заголовок `Authorization: Bearer <accessToken>`.

### Получение id ролей (общий Setup для кейсов, работающих с ролями)
- Не-ADMIN роль: `GET /api/roles?query=code~ct~CLIENT` → взять `id` роли с `code == "CLIENT"` (или любую роль, у которой `code != "ADMIN"`).
- ADMIN роль: `GET /api/roles?query=code~ct~ADMIN` → взять `id` роли с `code == "ADMIN"`.

## Стратегия повторяемости (общая)

Все сценарии запускаемы многократно без ручной чистки БД. Используется **комбинация генератора уникальных данных и teardown**:

- **Генератор данных**: на каждый прогон формируется `run-id` (timestamp или uuid). Все создаваемые пользователи используют уникальный email вида `test+{run-id}@example.com` (при нескольких пользователях в одном кейсе — `test+{run-id}-{n}@example.com`).
- **Teardown**: бэкенд использует **мягкое удаление** (soft-delete, `active=false`). В конце сценариев, создающих пользователей, выполняется `PUT /api/users/{id}` с `active=false` для деактивации созданной сущности. Это исключает накопление активных тестовых пользователей и конфликты уникальности email между прогонами (email уникален, поэтому генератор — основной механизм повторяемости; teardown — гигиена данных).
- **UI-кейсы без создания сущностей** (1.1, 1.2, 1.3, 1.5) идемпотентны по своей природе (только чтение/отображение) — специальная чистка не требуется, стратегия — «только чтение».

Каждая группа ниже явно указывает свою стратегию повторяемости.

## Регрессия

**Тип**: комбинированный (API-ориентированный сквозной путь; UI-регресс тем оформления). **Стратегия повторяемости**: генератор уникального email + teardown. **Требования**: 3.1–3.7.

Небольшой регрессионный набор оправдан: фиксы затрагивают общий CRUD-путь пользователя и общий компонент выбора темы/попапа, поэтому нужно перепроверить критичный сквозной сценарий и отсутствие визуальных регрессий тем.

### TC-REG-01 — Полный сквозной путь создания пользователя (валидная локаль + не-ADMIN роль + displayPreferences round-trip)
**Предусловия**: admin JWT; не-ADMIN `roleId`.

| Шаг | Запрос/Действие | Ожидание |
|-----|-----------------|----------|
| 1 | `POST /api/auth/login` (ADMIN) | `200` + `accessToken` |
| 2 | `GET /api/roles?query=code~ct~CLIENT` | `200`; `clientRoleId` |
| 3 | `POST /api/users` `{ name:"E2E User", email:"test+{run-id}-e2e@example.com", phone:"+70000000009", roleId:<clientRoleId>, locale:"pl", displayPreferences:{ "theme":"light", "fontSize":16 } }` | `201`; корректный ответ; ошибок типа jsonb нет |
| 4 | `GET /api/users/{id}` | `200`; `locale=="pl"`, `roleId==clientRoleId`, `displayPreferences` совпадает |
| 5 | `PUT /api/users/{id}` `{ ... roleId:<clientRoleId>, active:true, locale:"ru", displayPreferences:{ "theme":"dark","fontSize":18 } }` | `200`; обновление успешно, `locale=="ru"`, prefs обновлены |
| 6 | Проверка email uniqueness: повторный `POST /api/users` с тем же email | `409`/ошибка уникальности (сохранение 3.5) |
| 7 | **Teardown**: `PUT /api/users/{id}` c `active:false` | `200`; деактивирован |

**Ожидаемый итог**: полный цикл create → read → update → uniqueness-check → deactivate работает; сквозные проверки (email, локаль, роль, persistence) сохранены.
