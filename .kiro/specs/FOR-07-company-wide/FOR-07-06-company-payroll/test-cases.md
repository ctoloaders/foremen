# Тест-кейсы: FOR-07-06 — Зарплаты на уровне работника (по всем проектам)

## Назначение и характер спеки

Спека **смешанная (backend + UI)**, поэтому набор состоит из двух частей:

- **Часть A — API-тесты** против поднятого в Docker приложения (`http://localhost:8080`): выплаты без
  проекта, распределение суммы по неоплаченным строкам отчётов (сначала самые старые, последняя строка
  может быть оплачена частично), аванс-кредит на уровне работника, дополнительные строки и подсказки,
  начальный баланс и цепочка баланса, таблица и карточка, статус оплаты строк в отчётах, ABAC
  (FOREMAN лишён `PAYROLL`), надбавка за стаж и тип работника из профиля пользователя.
- **Часть B — браузерные сценарии** (headless-браузер против `http://localhost:3000`): экран
  `/company/payroll`, фильтры и их сохранение, карточка работника, диалог выплаты, поле стажа в форме
  пользователя, бейджи оплаты в отчётах, отсутствие вкладки Payroll в проекте.

Результат прогона — **MD-репорты с таблицами** (шаг → запрос/действие → ожидание → факт → статус).
**Скриншоты не требуются.**

## Запуск окружения

1. В корне: `docker compose up` — `postgres` (:5432), `liquibase` (включая changesets 192–198),
   `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Первый ADMIN — `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
   Логин: `POST /api/auth/login {email, password}` → `accessToken`.
3. Готовность: `GET /api/payroll/company?from=2026-07-01&to=2026-07-31` под ADMIN → `200`.

## Общая стратегия повторяемости

**Генератор `run-id` + teardown.** На прогон генерируется `run-id` (timestamp/uuid). Все создаваемые
сущности содержат его: проекты `Payroll07 A {run-id}`, `Payroll07 B {run-id}`, пользователи
`worker+{run-id}@example.com`, `foreman+{run-id}@example.com`, `manager+{run-id}@example.com`,
`financier+{run-id}@example.com`, заметки выплат `p07-{run-id}-NN`, названия доп. строк
`Multisport {run-id}`.

Работник создаётся **заново на каждый прогон**, поэтому его выплаты, распределения, доп. строки и
баланс изолированы от предыдущих прогонов, даже если teardown не выполнился (запросы фильтруются по
`workerId`).

**Teardown** в конце каждой группы (в обратном порядке): удалить все `PLANNED`-выплаты работника
(освобождает распределения); удалить доп. строки; проекты перевести в `CANCELLED` (или удалить
admin-API); деактивировать пользователей. `PAID`-выплаты не удаляются — изоляция обеспечивается новым
работником. Сид-данные (роли, ресурс `PAYROLL`, `/worker-types`) только читаются.

Переиспользует общий Setup S0 (ADMIN + FINANCIER + проекты + работник c `run-id`). Дополнительно
