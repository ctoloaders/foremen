# Тест-кейсы: FOR-07-02 — Staffing Gantt UI (общекомпанейский график занятости)

## Назначение и характер спеки

Спека **чисто фронтендовая и read-only**: она рендерит проекцию межпроектной занятости
(`GET /api/company-schedule`, владелец контракта — FOR-07-01) как общекомпанейский Gantt. Строки —
работники / прорабы (по одной на `User`), ось X — абсолютная календарная шкала, каждый бар окрашен
по проекту. Экран добавляет легенду проектов, панель фильтров (роль / проект / участник / окно дат с
гранулярностью неделя|месяц), индикатор конфликта на строке и deep-link из бара на вкладку
планирования графика проекта. Экран достижим из пункта меню **Staffing Gantt** по пути
`/company/staffing-gantt`.

Поскольку это **UI-спека**, набор тест-кейсов — **браузерные сценарии**, исполняемые браузерным
движком (headless-браузер / browser automation) против фронтенда `http://localhost:3000` при живом
бэкенде `http://localhost:8080`. Каждый шаг — действие в браузере (переход, ввод, клик, нажатие
клавиши, ожидание) с проверкой отрисованного DOM/состояния. **Результат прогона — MD-репорты с
таблицами** (шаг → действие → ожидание → факт → статус). **Скриншоты не требуются.**

Спека **не меняет бэкенд**: ресурс `COMPANY_SCHEDULE` (READ → ADMIN + MANAGER) и эндпоинт
`GET /api/company-schedule` переиспользуются как есть. Единственное изменение в общем фронтенд-конфиге
— перенацеливание пункта меню и route-guard с интерима `WORK_SCHEDULE`/READ на реальный
`COMPANY_SCHEDULE`/READ.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции,
   включая сид ресурса `COMPANY_SCHEDULE` из FOR-07-01), `backend` (:8080, профиль `docker`),
   `frontend` (:3000).
2. Базовый URL фронтенда: `http://localhost:3000`; API — `http://localhost:8080`, auth под
   `/api/auth`.
3. Первый ADMIN — через переменные `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
   `FOREMEN_ADMIN_PASSWORD`. Логин в UI: форма `/login` либо `POST /api/auth/login` с подстановкой
   токена в сессию браузера.
4. Перед прогоном дождаться готовности `backend` (миграции применены) и `frontend` (SPA отдаётся).

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown через API; сид не изменяется.** Экран read-only, он
не создаёт и не мутирует проекцию, поэтому сама UI-прогонка побочных эффектов не оставляет. Однако
проекции нужны **предусловные данные** (проекты в графике, назначенные работники/прорабы, пересечение
дат у одного работника, недатируемый бар). Они готовятся через API до UI-прогона и удаляются после:

- единый на прогон `run-id` (timestamp или uuid, например `1730000000` / `a1b2c3`) встраивается во
  все создаваемые имена/email: `mgr+{run-id}@example.com`, `wrk+{run-id}@example.com`,
  проекты `Gantt Test A {run-id}` / `Gantt Test B {run-id}`;
- **Setup (API):** залогиниться ADMIN; создать MANAGER-пользователя (носитель `COMPANY_SCHEDULE` READ
  через грант) и non-privileged пользователя (например WORKER, без гранта); создать два проекта с
  графиком, назначить одного работника на пересекающиеся категории (для конфликта) и одного прораба
  (span); оставить один проект без даты старта (для Undatable_Bar);
- **localStorage:** перед каждым кейсом, зависящим от дефолтного представления, очищать ключ
  `foremen:gantt:company-schedule` (`localStorage.removeItem`), чтобы персистентность прошлого кейса
  не влияла; кейсы персистентности (Фича 8) управляют ключом явно;
- **Teardown (API, LIFO):** удалить созданные членства/назначения, перевести тестовые проекты в
  `CANCELLED`/удалить, деактивировать созданных пользователей. Сид (роли, ресурс `COMPANY_SCHEDULE`,
  гранты) **только читается**.

Каждая группа ниже дополнительно уточняет свою стратегию строкой `**Повторяемость:**`.

### Замечание про роли и ABAC

`COMPANY_SCHEDULE` READ засеян на **ADMIN + MANAGER**. ADMIN проходит через bypass, MANAGER — через
грант; прочие роли (WORKER / CLIENT / FOREMAN / ESTIMATOR / FINANCIER) гранта не имеют — для них пункт
меню скрыт, а маршрут `/company/staffing-gantt` ведёт на `/403`. Non-privileged пользователь в кейсах
ниже — пользователь роли без гранта `COMPANY_SCHEDULE` READ.

# Браузерные (UI) сценарии

Если не указано иное — вход под носителем `COMPANY_SCHEDULE` READ (ADMIN или MANAGER).

## Фича 1. Меню, маршрут и выравнивание ресурса (R1)

**Повторяемость:** читает сид (гранты) + помеченные `run-id` пользователи; teardown пользователей.

### TC-NAV-01 — Пункт Staffing Gantt виден и открывает страницу для ADMIN/MANAGER
**Предусловия:** вход под ADMIN (или MANAGER с грантом `COMPANY_SCHEDULE` READ).
1. Открыть приложение после логина → в навигации виден пункт **Staffing Gantt** (ярлык
   `nav.staffingGantt`: pl «Grafik zespołu», ru «График команды», без сырого ключа).
2. Кликнуть пункт → URL становится `/company/staffing-gantt`, рендерится `Company_Schedule_Page`
   (заголовок `companySchedule.title`), редиректа на `/403` нет.

_Покрывает:_ R1 (1, 4), R11.4.

### TC-NAV-02 — Non-privileged пользователь: пункт скрыт, маршрут ведёт на /403
**Предусловия:** вход под non-privileged пользователем (роль без `COMPANY_SCHEDULE` READ, например
WORKER).
1. После логина → пункт **Staffing Gantt** в навигации **отсутствует** (`isNavItemVisible` = false).
2. Ввести в адресную строку `/company/staffing-gantt` и перейти → браузер редиректится на `/403`
   (Forbidden_Page); `Company_Schedule_Page` не рендерится; сетевой запрос к `/api/company-schedule`
   не уходит (проверить вкладку Network — запроса нет либо он не инициируется до гейта).

_Покрывает:_ R1 (3, 4).

### TC-NAV-03 — Маршрут гейтится COMPANY_SCHEDULE/READ, а не WORK_SCHEDULE
**Предусловия:** MANAGER с грантом `COMPANY_SCHEDULE` READ.
1. Открыть `/company/staffing-gantt` → страница рендерится (MANAGER имеет `COMPANY_SCHEDULE` READ).
2. (Контрактная проверка) Пункт меню и route-guard используют ресурс `COMPANY_SCHEDULE`, а не интерим
   `WORK_SCHEDULE` — подтверждается тем, что носитель только `WORK_SCHEDULE` READ (без
   `COMPANY_SCHEDULE`) на маршрут не проходит (редирект `/403`), а носитель `COMPANY_SCHEDULE` READ —
   проходит. Отдельно покрыто unit-тестами `navigation.test.ts` / `route-permissions.for0702.test.ts`.

_Покрывает:_ R1 (2, 5).

## Фича 2. Загрузка проекции и контракт фильтров (R2)

**Повторяемость:** генератор проектов/назначений (Setup API) + teardown; localStorage очищается.

### TC-FETCH-01 — Страница грузит проекцию и шлёт только поддерживаемые параметры
**Предусловия:** есть минимум один проект с датированным графиком; localStorage ключ очищен (дефолт).
1. Открыть `/company/staffing-gantt` → в Network виден запрос `GET /api/company-schedule`; в дефолте
   (оба/нет ролей, все проекты, все участники, без окна дат) URL **не содержит** `roles`,
   `projectIds`, `memberIds`, `from`, `to`.
2. URL **никогда** не содержит `page`, `size`, `sort`, `query`.
3. Ответ (`rows[]` + `legend[]`) отрисован: строки участников, бары, легенда — ровно как вернул
   сервер (клиентского ре-фильтра скоупа нет).

_Покрывает:_ R2 (1, 3, 5).

### TC-FETCH-02 — Смена фильтра рефетчит; идентичный набор переиспользует кэш
**Предусловия:** ≥2 проекта в легенде.
1. Выбрать один проект в Project_Filter → уходит новый `GET /api/company-schedule?projectIds=...`;
   отрисованный срез меняется.
2. Вернуть фильтр к исходному набору (тот же набор, что уже запрашивался) → повторный сетевой запрос
   не уходит в пределах `staleTime` (30 c) — данные берутся из кэша TanStack Query.

_Покрывает:_ R2 (2).

### TC-FETCH-03 — Параметр roles только при ровно одной выбранной роли
**Предусловия:** в проекции есть и работники, и прорабы.
1. Role_Filter = «оба» (или ничего не исключено) → URL **без** `roles`.
2. Role_Filter = только «работник» → URL содержит `roles=WORKER`; отрисованы только строки-работники.
3. Role_Filter = только «прораб» → URL содержит `roles=FOREMAN`; отрисованы только строки-прорабы.

_Покрывает:_ R2 (4).

## Фича 3. Строки участников: работники и прорабы (R3)

**Повторяемость:** Setup API (назначить работника и прораба) + teardown.

### TC-ROW-01 — По одной строке на участника, в серверном порядке, с именем и ролью
**Предусловия:** проекция содержит ≥2 строк (работник и прораб).
1. Открыть страницу → число строк == числу `rows[]`; порядок строк совпадает с серверным (клиентского
   ре-сорта нет — сравнить последовательность имён с порядком в ответе API).
2. В sticky-ячейке каждой строки показано `userName` и локализованная метка роли
   (`companySchedule.role.worker` / `companySchedule.role.foreman`), без сырого ключа.

_Покрывает:_ R3 (1, 2).

### TC-ROW-02 — Визуальное различение прорабов и работников
1. Строки прорабов визуально отличимы от строк работников (бейдж роли / секция) по `companyRole`, так
   что span прораба читается отдельно от категорийных баров работника.

_Покрывает:_ R3 (3).

### TC-ROW-03 — Ноль строк → empty-state, не пустой каркас грида
**Предусловия:** набор фильтров, под который сервер возвращает `rows: []` (например несуществующий
`memberIds` или окно дат без данных).
1. Применить такой фильтр → отрисован empty-state (`companySchedule.empty.*`), а не пустой грид.

_Покрывает:_ R3 (4).

## Фича 4. Read-only бары на оси дат, окраска по проекту (R4)

**Повторяемость:** Setup API (датированные бары в нескольких проектах) + teardown.

### TC-BAR-01 — Общая календарная ось и позиция бара = инклюзивный интервал дат
**Предусловия:** есть датированные бары (`startDate`/`endDate` не null).
1. Открыть страницу → отрисована общая абсолютная календарная ось; якорь — самый ранний видимый
   `startDate` (или `from` окна при заданном окне).
2. Для датированного бара: левая граница и ширина соответствуют инклюзивному `[startDate, endDate]`
   (`endDay − startDay + 1` дней) — бар с одинаковыми start/end занимает один день, не ноль.

_Покрывает:_ R4 (1, 2).

### TC-BAR-02 — Цвет бара по colorIndex; все бары проекта одного цвета
**Предусловия:** ≥2 проекта с разными `colorIndex`; у одного проекта ≥2 баров.
1. Все бары одного проекта окрашены одинаково (`projectColor(colorIndex)`).
2. Бары разных проектов (разные `colorIndex`) различимы по цвету; цвет совпадает со свотчем легенды
   того же проекта (кросс-проверка с Фичей 7).

_Покрывает:_ R4 (3).

### TC-BAR-03 — Бары строго read-only
1. На баре нет ручек drag/resize, бар не перетаскивается и не растягивается мышью; на странице нет
   контролов save / auto-create / edit.
2. Любое взаимодействие с баром (клик/клавиша) не инициирует мутирующих запросов (в Network нет
   POST/PUT/PATCH/DELETE к `/api/company-schedule` или смежным) — только навигация (deep-link).

_Покрывает:_ R4 (4).

### TC-BAR-04 — Доступные подписи баров: работник vs прораб
1. У `WORKER_CATEGORY` бара в доступной подписи/тултипе присутствуют `workCategoryName`,
   `projectName` и диапазон дат.
2. У `FOREMAN_SPAN` бара присутствуют `projectName` и даты span, **нет** текста рабочей категории.

_Покрывает:_ R4 (5).

### TC-BAR-05 — Выходные и польские праздники затенены на оси
1. На календарной оси субботы/воскресенья и польские праздники (из `polishHolidays`) затенены для
   покрываемых осью годов — согласованно с проектным Gantt (переиспользуются ключи
   `projectSchedule.holiday.*` / `projectSchedule.legend.*`).

_Покрывает:_ R4 (6).

## Фича 5. Undatable-бары без позиции на оси (R5)

**Повторяемость:** Setup API (проект без даты старта → недатируемый бар) + teardown.

### TC-UND-01 — Без окна дат: Undatable-бары в отдельной «undated» области строки
**Предусловия:** окно дат не задано; у строки есть бар(ы) с `unanchored = true`.
1. Открыть страницу (дефолт, без окна дат) → такие бары показаны в выделенной «undated» области
   строки (например левый рейл-чипы, `companySchedule.undated.*`), **не** на оси дат.
2. У недатируемого бара показаны имя проекта и `projectColor`, чтобы читалась принадлежность проекту.

_Покрывает:_ R5 (1, 2).

### TC-UND-02 — С окном дат undated-область отсутствует
**Предусловия:** задано окно дат (неделя/месяц).
1. Применить окно дат → сервер исключает недатируемые бары (FOR-07-01 R7.5), и страница **не** рисует
   undated-область для отфильтрованного результата.

_Покрывает:_ R5 (3).

### TC-UND-03 — Undatable-бар никогда не позиционируется на оси
1. Ни при каком фильтре недатируемый бар не получает left/width на оси дат (он только в undated-рейле

_Покрывает:_ R5 (4).

## Фича 6. Панель фильтров: роль / проект / участник / окно дат (R6)

**Повторяемость:** Setup API + teardown; localStorage очищается перед кейсами дефолта.

### TC-FILTER-01 — Состав панели фильтров
1. Панель содержит: Role_Filter (работник / прораб / оба), Project_Filter (multiselect, опции из
   легенды), Member_Filter (multiselect, опции из строк), Date_Window (тумблер гранулярности
   WEEK|MONTH + пикер периода).

_Покрывает:_ R6 (1).

### TC-FILTER-02 — Любое изменение фильтра пересобирает запрос и рефетчит
1. Изменить каждый фильтр по очереди (роль, проект, участник, окно) → для каждого уходит
   `GET /api/company-schedule` с соответствующими параметрами; отрисованная проекция отражает новый
   выбор.

_Покрывает:_ R6 (2).

### TC-FILTER-03 — Гранулярность детерминированно задаёт окно дат; granularity не уходит на сервер
1. WEEK + выбранная неделя → `from` = понедельник этой ISO-недели, `to` = воскресенье.
2. MONTH + выбранный месяц → `from` = первый день, `to` = последний день месяца.
3. В URL **нет** параметра гранулярности — только вычисленные `from`/`to`.

_Покрывает:_ R6 (3, 4).

### TC-FILTER-04 — «Все даты» убирает окно; сервер возвращает датируемые и недатируемые бары
1. Выбрать «все даты» (`companySchedule.filter.allDates`) → URL **без** `from`/`to`; появляются и
   датированные бары, и недатируемые (undated-рейл).

_Покрывает:_ R6 (5).

### TC-FILTER-05 — «Сбросить фильтры» возвращает дефолт и рефетчит
1. Задать несколько фильтров, затем нажать «сбросить фильтры»
   (`companySchedule.filter.clear`) → состояние возвращается к дефолту (оба роли, все проекты, все
   участники, без окна дат), уходит рефетч без параметров.

_Покрывает:_ R6 (6).

### TC-FILTER-06 — Опции Project/Member показывают человекочитаемые имена
1. В выпадашках Project_Filter показаны `projectName`, Member_Filter — `userName`, а не сырые id.

_Покрывает:_ R6 (7).

### TC-LEG-04 — Интерактивная легенда держит projectIds консистентными с фильтром
**Предусловия:** легенда интерактивна (если реализована как переключатель Project_Filter).
1. Кликнуть запись легенды → фильтрация к/от этого проекта; отправляемый `projectIds` остаётся
   консистентным с контролом Project_Filter (нет рассинхрона между легендой и панелью фильтров). Если
   легенда чисто информационная — зафиксировать это и считать критерий выполненным по варианту
   «informational».

_Покрывает:_ R7 (4).

## Фича 8. Персистентность состояния представления (R8)

**Повторяемость:** кейсы управляют ключом `foremen:gantt:company-schedule` явно (set/remove).

### TC-PERSIST-01 — Выбранные фильтры/гранулярность/период сохраняются в localStorage
1. Задать роль, проекты, участников, гранулярность и период → в localStorage под ключом
   `foremen:gantt:company-schedule` появляется JSON с `{ roles, projectIds, memberIds, granularity,
   period }` (после debounce ~500 мс).

_Покрывает:_ R8 (1).

### TC-PERSIST-02 — Состояние восстанавливается при повторном монтировании
1. С сохранённым состоянием из TC-PERSIST-01 перезагрузить/заново открыть `/company/staffing-gantt`
   → восстановлены те же фильтры, первый фетч уходит с replay-фильтрами, отрисованный срез совпадает
   с сохранённым.

_Покрывает:_ R8 (2).

### TC-PERSIST-03 — Отсутствующее/битое значение → дефолтное представление без ошибки
1. Удалить ключ `foremen:gantt:company-schedule` → при открытии дефолтное представление (оба роли,
   все проекты, все участники, без окна дат).
2. Записать в ключ невалидный JSON (`localStorage.setItem(key, '{broken')`) → при открытии дефолтное
   представление, без падения/ошибки на экране.

_Покрывает:_ R8 (3).

### TC-PERSIST-04 — Сохраняются только измерения представления, не payload проекции
1. Содержимое ключа содержит только `{ roles, projectIds, memberIds, granularity, period }` (+ флаг
   окна дат) и **не** содержит `rows`/`legend`/бары — payload не кэшируется в localStorage.

_Покрывает:_ R8 (4).

2. У строки без конфликтов индикатора нет.

_Покрывает:_ R10 (1).

# Регрессия

Группа перепроверяет критичные сквозные пути экрана. **Повторяемость:** генератор `run-id` + teardown
через API (созданные проекты → CANCELLED/удалить, пользователи деактивировать); сид (роли, ресурс
`COMPANY_SCHEDULE`, гранты) только читается.

### TC-REG-01 — Полный happy-path ADMIN/MANAGER: меню → страница → проекция
1. Войти носителем гранта → кликнуть **Staffing Gantt** → страница грузит проекцию, рисует строки,
   бары, легенду; денежных полей нет; URL дефолта без параметров.

_Покрывает:_ сквозной путь R1 + R2 + R3 + R4 + R9.4.

### TC-REG-02 — Гейтинг доступа: non-privileged → /403, пункт скрыт
1. Войти non-privileged пользователем → пункт меню скрыт; прямой переход на
   `/company/staffing-gantt` → `/403`; запрос проекции не уходит.

_Покрывает:_ R1 (3, 4).

### TC-REG-03 — Deep-link не сломан: бар → вкладка графика проекта
1. Кликнуть/активировать Enter на баре → SPA-навигация на `/projects/{projectId}/scheduleDesign`
   корректного проекта, без полной перезагрузки.

_Покрывает:_ R7 (2), R12 (2).

### TC-REG-04 — Контракт запроса не сломан: только поддерживаемые параметры
1. При любых комбинациях фильтров URL `GET /api/company-schedule` содержит только из
   `{ roles, projectIds, memberIds, from, to }`, `roles` — только при одной роли, и никогда
   `page`/`size`/`sort`/`query`.

_Покрывает:_ R2 (1, 3, 4).

### TC-REG-05 — Персистентность: восстановление среза после перезагрузки
1. Задать фильтры → перезагрузить → срез восстановлен из localStorage; битый JSON → дефолт без ошибки.

_Покрывает:_ R8 (2, 3).

### TC-REG-06 — Паритет локализации pl/ru без сырых ключей
1. Переключить язык pl ↔ ru при открытом экране → все тексты меняются на выбранный язык, сырых ключей
   нет (кросс-проверка с парити-тестом `i18n.keys.test.ts`).

_Покрывает:_ R11 (1, 3).
