# Тест-кейсы: FOR-07-00 — Company foundation (переустройство главного меню)

## Назначение и характер спеки

FOR-07-00 — **чисто фронтендовая** спека переустройства главного меню: из первой (безымянной) секции
`NAV_CONFIG` удаляются три проектных пункта (`Projects` → `/projects`, `Rooms` → `/rooms`,
`Estimate` → `/estimate`), и добавляется новая секция `nav.sections.company` с двумя пунктами,
переиспользующими **существующие** ABAC-ресурсы:

- **Staffing Gantt** → `/company/staffing-gantt`, gated `WORK_SCHEDULE`/READ;
- **Company procurement** → `/company/procurement`, gated `PURCHASES`/READ.

Бэкенд не меняется: нет новой сущности, таблицы, Liquibase-changeset и нового ABAC-ресурса. Проектный
скоуп соблюдается «бесплатно», потому что сервисы за `WORK_SCHEDULE` и `PURCHASES` — это
`ProjectScopedService`-реализации, уже фильтрующие LIST-чтения по доступным проектам вызывающего.

Поскольку браузерных экранов самих компанийных поверхностей в 00 ещё нет (роуты — зарезервированные
слоты, страницы поставят FOR-07-02/03), **тест-кейсы 00 проверяют именно главное меню**: состав
Sidebar / Drawer / BottomNav, видимость/гейтинг пунктов по переиспользуемым ресурсам и сохранность
входа в проект через active-project-поверхность. Это **UI-спека**: сценарии исполняются браузерным
движком (headless-браузер / browser automation) против поднятого в Docker фронтенда
(`http://localhost:3000`), под разными ролями.

Результат прогона — **MD-репорты с таблицами** (шаг → действие → ожидание → факт → статус).
**Скриншоты не требуются.**

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции),
   `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для UI-тестов: `http://localhost:3000`; API (для подготовки фикстур) — `http://localhost:8080`,
   auth под `/api/auth`.
3. Первый ADMIN поднимается через переменные `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`,
   `FOREMEN_ADMIN_PASSWORD`. Логин в UI — экран `/login` (email + пароль).
4. Дождаться готовности `frontend` и `backend` (healthcheck 200) до старта прогона.

## Общая стратегия повторяемости

**Комбинированная: генератор `run-id` + teardown.** FOR-07-00 не создаёт доменных данных через UI
(это меню-спека), поэтому основная часть кейсов **read-only** и повторяема без чистки. Там, где для
проверки скоупа (TC-SCOPE-01/02) и гейтинга (TC-COMP-02/03) нужны non-ADMIN пользователи и фикстура
из двух проектов, подготовительные сущности создаются через admin-API с единым на прогон `run-id`
(timestamp или uuid) во всех идентификаторах, а в конце набора выполняется teardown:

- email тестовых пользователей: `mgr-a+{run-id}@example.com`, `mgr-b+{run-id}@example.com`,
  `nograntuser+{run-id}@example.com`;
- имена проектов: `Company Fixture A {run-id}`, `Company Fixture B {run-id}`.

**Teardown** в конце набора (обратный порядок создания): удалить/деактивировать созданные членства,
затем созданных пользователей, затем перевести тестовые проекты в `CANCELLED` или удалить доступным
admin-API. Сид-данные (роли, ресурсы `WORK_SCHEDULE` / `PURCHASES`, их гранты) **только читаются,
никогда не изменяются**. Каждая группа ниже уточняет свою стратегию строкой `**Повторяемость:**`.

### Замечание про роли и гранты (ABAC)

Бутстрапится только ADMIN. По матрице проекта `WORK_SCHEDULE` и `PURCHASES` имеют READ у ролей,
которым они назначены проектными спеками (FOR-05-10 / FOR-06-03). Для гейтинг-кейсов нужны:

- пользователь, у которого есть `WORK_SCHEDULE`/READ (видит Staffing Gantt);
- пользователь, у которого есть `PURCHASES`/READ (видит Company procurement);
- пользователь, у которого нет ни одного из двух грантов (не видит ни одного компанийного пункта).

Эти пользователи создаются и приглашаются через admin-API в группе `Setup` (назначение подходящих
ролей), либо соответствующие ABAC-ожидания документируются и покрываются unit/seed-тестами
(`isNavItemVisible`, навигационный unit-тест FOR-07-00 задачи 1.3).

# Фича 0. Setup — пользователи, роли, фикстура из двух проектов

**Повторяемость:** читает сид + создаёт помеченные `run-id` сущности; teardown в конце набора.

### TC-SETUP-01 — Логин ADMIN в UI
**Предусловия:** стек поднят, ADMIN забутстрапен.
1. Открыть `http://localhost:3000/login`. → Отображается форма логина (email + пароль).
2. Ввести `FOREMEN_ADMIN_EMAIL` / `FOREMEN_ADMIN_PASSWORD`, нажать «Войти». → Редирект на `/`
   (Dashboard); в app-shell виден Sidebar/TopBar. Сессия ADMIN сохранена как `SESSION_ADMIN`.

_Покрывает:_ инфраструктура (предзависимость всех групп).

### TC-SETUP-02 — Подготовить non-ADMIN пользователей с нужными грантами
**Предусловия:** `SESSION_ADMIN`.
1. Через admin-API создать пользователя `USER_SCHED` (`mgr-a+{run-id}@example.com`) с ролью, которой
   назначен `WORK_SCHEDULE`/READ (и без `PURCHASES`/READ, если это возможно по матрице; иначе
   зафиксировать фактический набор грантов). → **201**; пользователь создан.
2. Создать пользователя `USER_PROC` (`mgr-b+{run-id}@example.com`) с ролью, которой назначен
   `PURCHASES`/READ. → **201**.
3. Создать пользователя `USER_NONE` (`nograntuser+{run-id}@example.com`) с ролью без `WORK_SCHEDULE`/READ
   и без `PURCHASES`/READ. → **201**.
4. Активировать и задать пароли созданным пользователям (invite/password-set-флоу), чтобы в них можно
   было залогиниться в UI. → Пользователи активны.

_Покрывает:_ предзависимость R2.3 (гейтинг), R3.2 (скоуп).

### TC-SETUP-03 — Фикстура из двух проектов для проверки скоупа
**Предусловия:** `SESSION_ADMIN`, `USER_SCHED`.
1. Создать проект `Company Fixture A {run-id}` (`PROJECT_A`) и включить `USER_SCHED` его членом. → **201**.
2. Создать проект `Company Fixture B {run-id}` (`PROJECT_B`) **без** членства `USER_SCHED`. → **201**.
3. (Если в окружении есть данные расписания/закупок — засидить по одной строке `WORK_SCHEDULE` и
   `PURCHASES` в каждый из `PROJECT_A` и `PROJECT_B`, чтобы компанийные списки были непустыми.) →
   Данные готовы. Если засидить нечем — пометить TC-SCOPE-01/02 как **[fixture-dependent]** и
   фиксировать в репорте ⚠️ с обоснованием (нет данных для наблюдаемого скоупа).

_Покрывает:_ предзависимость R3.2.

# Фича 4. Проектный скоуп компанийных списков (R3.2)

**Повторяемость:** генератор `run-id` + teardown (фикстура из двух проектов, TC-SETUP-03).

> **[fixture-dependent]** Эти кейсы требуют наблюдаемых данных расписания/закупок в `PROJECT_A` и
> `PROJECT_B` и реального компанийного списка. Поскольку сами компанийные страницы поставляются
> FOR-07-02/03 (не в 00), наблюдение скоупа в UV возможно только когда соответствующий дочерний
> спек уже поставил страницу. В 00 допускается проверять инвариант на уровне **API** компанийного
> LIST-чтения (через `ProjectScopedService`-эндпоинт `WORK_SCHEDULE`/`PURCHASES`) — результат
> эквивалентен UI-наблюдению. Если ни страницы, ни наблюдаемых данных нет — фиксировать ⚠️ и
> ссылаться на FOR-07-02/03.

### TC-SCOPE-01 — non-ADMIN видит только свои проекты, ADMIN — все
**Предусловия:** фикстура TC-SETUP-03: `USER_SCHED` — член только `PROJECT_A`; данные в обоих проектах.
1. Под `SESSION_ADMIN` открыть компанийный список (Staffing Gantt / Company procurement — или
   эквивалентный `ProjectScopedService` LIST-эндпоинт). → Видны строки **из обоих** проектов
   (`PROJECT_A` и `PROJECT_B`).
2. Под `SESSION_SCHED` (non-ADMIN, член только `PROJECT_A`) открыть тот же список. → Видны строки
   **только** из `PROJECT_A`; строк `PROJECT_B` нет (фильтр `addRequiredQuery` по
   `ProjectAccessCache`).

_Покрывает:_ R3.2.

### TC-SCOPE-02 — Переиспользование ресурса не ослабляет фильтр
**Предусловия:** как TC-SCOPE-01.
1. Убедиться, что non-ADMIN не может через компанийную поверхность получить данные проекта, членом
   которого он не является (`PROJECT_B`). → Данные `PROJECT_B` не отображаются и не доступны.
2. ADMIN по-прежнему видит всё (скоуп-фильтр для ADMIN = null). → Все проекты видны.

_Покрывает:_ R3.2.

### REG-01 — /projects роут и ProjectsPage не осиротели
1. Прямой переход на `/projects` под `SESSION_ADMIN` → `ProjectsPage` открывается (роут,
   route-requirement `{PROJECTS, READ}`, страница целы, несмотря на удаление пункта меню).

_Покрывает:_ R1.3 (регресс).

### REG-02 — Соседние секции меню не задеты
1. Под `SESSION_ADMIN` раскрыть Sidebar. → Секции `catalog`, `warehouse`, `dictionaries`, `system`,
   `settings` и их пункты присутствуют в прежнем составе; секция «Компания» вставлена между первой
   секцией и `catalog`, не ломая остальные.

_Покрывает:_ R1.1, R2.1 (регресс порядка/состава секций).

### REG-03 — Гейтинг соседних пунктов по-прежнему работает
1. Под `USER_NONE` раскрыть Sidebar. → Пункты с `requiredPermission`, на которые у пользователя нет
   грантов, скрыты (общий механизм `isNavItemVisible` не затронут); компанийные пункты также скрыты.

_Покрывает:_ R2.3 (регресс общего механизма видимости).

### REG-04 — Бэкенд не изменён, приложение стартует как раньше
1. Факт успешного старта `backend` (healthcheck 200) и отсутствие нового changeset в `changelog.xml`
   подтверждают, что ABAC-ресурсы `WORK_SCHEDULE` / `PURCHASES` / `PROJECTS` / `ROOMS` / `ESTIMATE`,
   их гранты и матрица не менялись (нав-only изменение).

_Покрывает:_ R1.5, R2.4, R3.1, R5.2 (инвариант «бэкенд не тронут»).
