# Тест-кейсы: FOR-03-05 OTP-аутентификация клиентов

## Назначение и характер спеки

Спека **преимущественно бекендовая**: OTP-флоу и новый эндпоинт регистрации клиента проверяются **API-тестами против работающего в Docker приложения** (не Testcontainers/юнит-слой, а поднятый docker-стек). Каждый шаг — HTTP-запрос к API с проверкой статуса, тела и заголовков. Результат прогона — **MD-репорт с таблицами** (шаг → запрос → ожидание → факт → статус). Скриншоты не требуются.

Единственный фронтовый элемент спеки — исключение ролей `ADMIN`/`CLIENT` из дропдауна в форме пользователя (Requirement 11). Он **не** проверяется браузерным прогоном здесь: покрывается юнит-тестами Vitest в фиче `src/features/users` (см. раздел «Фича 9»). В API-прогоне этой спеки участвует только бекенд.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции, включая `016-create-otp-tokens`), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`.
3. Auth-эндпоинты — под `/api/auth`. OTP-эндпоинты: `POST /api/auth/otp/request`, `POST /api/auth/otp/verify`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
5. Клиентские TTL настраиваются через `FOREMEN_JWT_CLIENT_ACCESS_TTL_MINUTES` (дефолт 120) и `FOREMEN_JWT_CLIENT_REFRESH_TTL_DAYS` (дефолт 30).
6. Дождаться готовности `backend` (health/readiness) перед запуском кейсов.

### Получение OTP-кода в тестах

OTP-код доставляется по email. Для автоматизации кода прогона используется один из способов (указать фактический в отчёте):
- перехват почты через тестовый SMTP (например MailHog/Mailpit), чтение кода из письма;
- либо чтение кода напрямую из БД: `SELECT code FROM otp_tokens WHERE email = ? AND used = false AND expires_at > now() ORDER BY created_date DESC LIMIT 1`.

В шагах ниже это обозначено как «получить код из письма/БД».

## Предусловие-хелпер: активный CLIENT-пользователь

OTP работает **только** для роли `CLIENT` со статусом `ACTIVE`. Клиенты создаются администратором по инвайт-флоу FOR-03-02:

1. `POST /api/auth/login` под ADMIN (`FOREMEN_ADMIN_EMAIL`/`FOREMEN_ADMIN_PASSWORD`) → 200, получить access-токен ADMIN.
2. `GET /api/roles` → 200; найти `id` роли с кодом `CLIENT`.
3. `POST /api/users` (Bearer ADMIN) с телом `{ "name": "...", "email": "<client-email>", "roleId": <CLIENT_id> }` → пользователь создаётся со статусом `INVITED`, `password_hash = null`, отправляется client-portal-приглашение.
4. Активация клиента до `ACTIVE`: клиент не устанавливает пароль. Для тестов OTP пользователь должен быть `ACTIVE`. Использовать один из способов активации, доступный в окружении:
   - если настроен тестовый хелпер активации — активировать пользователя (`status = ACTIVE`);
   - либо обновить статус напрямую в БД для прогона: `UPDATE users SET status = 'ACTIVE' WHERE email = ?`.

   Далее по тексту это предусловие обозначено как «активный CLIENT `<email>`».

**Не-CLIENT пользователь** (сотрудник) создаётся тем же `POST /api/users` с `roleId` любой сотруднической роли (MANAGER/FOREMAN/WORKER/FINANCIER) — используется в кейсах non-enumeration.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые email уникальны:
  - клиент (OTP): `otp+{run-id}+{seq}@example.com`;
  - клиент (регистрация через `/api/users/client`): `cli+{run-id}+{seq}@example.com`;
  - сотрудник (для non-enumeration и для «токена без PROJECTS/EDIT»): `emp+{run-id}+{seq}@example.com`;
  - «неизвестный» email: `ghost+{run-id}@example.com` (пользователь не создаётся).
  - `projectId` для регистрации клиента — уникальный числовой на прогон (`P1..Pn`, производные от `run-id`), т.к. `project_members.project_id` без FK и таблицы `projects` ещё нет.
- **Teardown (обязательный шаг в конце каждого набора):** деактивировать созданных пользователей — `PUT /api/users/{id}` с `active = false` (или `status = DEACTIVATED`) под ADMIN; при необходимости разлогинить выданные refresh-токены (`POST /api/auth/logout`). Строки `otp_tokens` привязаны к email прогона и не мешают повторным запускам, т.к. каждый прогон использует новые email; при желании очищаются `DELETE FROM otp_tokens WHERE email LIKE '%{run-id}%'`.
- Системные роли и seed-данные **не изменяются**. Все манипуляции — над созданными на прогон пользователями. Это делает набор запускаемым многократно без ручной чистки БД.

**Важно про rate limit:** лимит — 5 запросов/час на email, считается по строкам `otp_tokens`. Кейсы rate limiting и «успешный запрос» используют **разные** email прогона, чтобы не исчерпать лимит на одном адресе. Кейс rate limiting намеренно использует отдельный email.

## Фича 1. OTP request — генерация и отправка кода

Проверяет генерацию 6-значного кода, TTL 15 минут, персист и отправку письма для активного CLIENT.

### TC-REQ-01 — Запрос кода для активного CLIENT (200 + код отправлен)

**Предусловия:** активный CLIENT `otp+{run-id}+1@example.com`.

**Шаги:**
1. `POST /api/auth/otp/request` с телом `{ "email": "otp+{run-id}+1@example.com" }` → **ожидание: 200**, тело пустое/без раскрытия деталей.
2. Получить код из письма/БД → **ожидание:** код существует, ровно **6 цифр** (`^[0-9]{6}$`), возможны ведущие нули.
3. Проверить в БД строку `otp_tokens` для email → **ожидание:** `used = false`, `attempts = 0`, `expires_at ≈ created_date + 15 мин` (допуск ±1 мин).

**Ожидаемый результат:** 200; сгенерирован 6-значный код с TTL 15 минут, письмо отправлено.

### TC-REQ-02 — Валидация пустого email (400)

**Шаги:**
1. `POST /api/auth/otp/request` с телом `{ "email": "" }` → **ожидание: 400**, ошибка валидации; код не генерируется.
2. `POST /api/auth/otp/request` с телом `{}` (без email) → **ожидание: 400**.

**Ожидаемый результат:** 400 до какой-либо проверки лимита/поиска пользователя.

## Фича 2. Rate limiting (5 запросов/час на email)

Лимит считается по строкам `otp_tokens` за последний час, применяется ДО поиска пользователя.

### TC-RL-01 — Шестой запрос за час отклоняется (429)

**Предусловия:** активный CLIENT `otp+{run-id}+rl@example.com` (отдельный email, чтобы не мешать другим кейсам).

**Шаги:**
1. Выполнить `POST /api/auth/otp/request` для этого email **5 раз подряд** → **ожидание:** каждый из 5 → **200**.
2. Выполнить `POST /api/auth/otp/request` для того же email 6-й раз → **ожидание: 429**, код `error.auth.otp.rate.limited`.

**Ожидаемый результат:** 6-й запрос в пределах часа отклонён с 429; новый код не создан.

### TC-RL-02 — Rate limit не раскрывает существование клиента (429 одинаков)

**Предусловия:** неизвестный email `ghost+{run-id}@example.com` (пользователя нет).

**Шаги:**
1. Выполнить `POST /api/auth/otp/request` для `ghost+{run-id}@example.com` 5 раз → **ожидание:** каждый → **200** (silent success, см. Фичу 3).
2. 6-й запрос для того же неизвестного email → **ожидание: 429**, код `error.auth.otp.rate.limited` — тот же ответ, что и для реального клиента в TC-RL-01.

**Ожидаемый результат:** rate limit применяется одинаково к любому email (по счётчику, до поиска пользователя); 429 не позволяет отличить клиента от неклиента.

## Фича 3. Silent success / non-enumeration

Для неподходящего email (неизвестный, не-CLIENT, не-ACTIVE) ответ — 200 без кода и без письма, неотличимо от подходящего.

### TC-SS-01 — Неизвестный email → 200 без письма

**Шаги:**
1. `POST /api/auth/otp/request` `{ "email": "ghost+{run-id}+ss@example.com" }` → **ожидание: 200**.
2. Проверить БД/почту → **ожидание:** для этого email код НЕ создан, письмо НЕ отправлено.

**Ожидаемый результат:** 200 без раскрытия; кода нет.

### TC-SS-02 — Сотрудник (не-CLIENT) → 200 без письма

**Предусловия:** активный сотрудник `emp+{run-id}+1@example.com` (роль MANAGER/FOREMAN/…).

**Шаги:**
1. `POST /api/auth/otp/request` `{ "email": "emp+{run-id}+1@example.com" }` → **ожидание: 200**.
2. Проверить БД/почту → **ожидание:** OTP-код для сотрудника НЕ создан, письмо НЕ отправлено.

**Ожидаемый результат:** OTP доступен только роли CLIENT; для сотрудника — silent success.

### TC-SS-03 — INVITED (не-ACTIVE) клиент → 200 без письма

**Предусловия:** CLIENT `otp+{run-id}+inv@example.com` создан, но оставлен в статусе `INVITED` (не активирован).

**Шаги:**
1. `POST /api/auth/otp/request` для этого email → **ожидание: 200**.
2. Проверить БД/почту → **ожидание:** код НЕ создан.

**Ожидаемый результат:** не-ACTIVE клиент не получает код; ответ неотличим (200).

## Фича 4. OTP verify — успех

### TC-VER-01 — Успешная верификация → JWT (200 TokenResponse)

**Предусловия:** активный CLIENT `otp+{run-id}+2@example.com`; выполнен `POST /api/auth/otp/request`; код получен из письма/БД.

**Шаги:**
1. `POST /api/auth/otp/verify` `{ "email": "otp+{run-id}+2@example.com", "code": "<код>" }` → **ожидание: 200**, тело `TokenResponse` с непустыми `accessToken`, `refreshToken`, полем `expiresIn`.
2. Проверить БД → **ожидание:** строка `otp_tokens` помечена `used = true`.
3. Использовать `accessToken` на защищённом эндпоинте (например `GET /api/auth/me`) → **ожидание: 200**, данные текущего клиента.

**Ожидаемый результат:** валидный код обменивается на пару токенов; код помечен использованным.

### TC-VER-02 — Валидация пустых полей verify (400)

**Шаги:**
1. `POST /api/auth/otp/verify` `{ "email": "otp+{run-id}+2@example.com", "code": "" }` → **ожидание: 400**.
2. `POST /api/auth/otp/verify` `{ "email": "", "code": "123456" }` → **ожидание: 400**.

**Ожидаемый результат:** 400 до поиска кода.

## Фича 5. OTP verify — негативные ветки

### TC-VER-NEG-01 — Неверный код увеличивает attempts (400 invalid)

**Предусловия:** активный CLIENT `otp+{run-id}+3@example.com`; запрошен код; известен верный код `C`.

**Шаги:**
1. `POST /api/auth/otp/verify` с заведомо неверным кодом (`000000`, если он ≠ `C`) → **ожидание: 400**, код `error.auth.otp.invalid`.
2. Проверить БД → **ожидание:** `attempts` увеличился на 1, `used = false`.

**Ожидаемый результат:** неверный код отклонён, счётчик попыток +1, токены не выданы.

### TC-VER-NEG-02 — Превышение попыток блокирует код (400 attempts.exceeded)

**Предусловия:** активный CLIENT `otp+{run-id}+4@example.com`; запрошен код `C`.

**Шаги:**
1. Ввести неверный код 3 раза подряд (`POST /api/auth/otp/verify`) → **ожидание:** каждый → 400 `error.auth.otp.invalid` (attempts достигает 3).
2. Ввести 4-й раз (даже верный код `C`) → **ожидание: 400**, код `error.auth.otp.attempts.exceeded`; токены не выданы.

**Ожидаемый результат:** после 3 неудачных попыток код заблокирован; верный код уже не принимается.

### TC-VER-NEG-03 — Просроченный код (400 expired)

**Предусловия:** активный CLIENT `otp+{run-id}+5@example.com`; получен код; выполнено одно из:
- дождаться истечения TTL (15 минут), либо
- для ускорения прогона искусственно состарить строку: `UPDATE otp_tokens SET expires_at = now() - interval '1 minute' WHERE email = ? AND used = false`.

**Шаги:**
1. `POST /api/auth/otp/verify` с корректным кодом просроченной строки → **ожидание: 400**, код `error.auth.otp.expired`.
2. Проверить БД → **ожидание:** `used` не изменился (остался false).

**Ожидаемый результат:** просроченный код отклонён без выдачи токенов.

### TC-VER-NEG-04 — Повторное использование кода (400 invalid)

**Предусловия:** активный CLIENT `otp+{run-id}+6@example.com`; код успешно верифицирован один раз (как в TC-VER-01).

**Шаги:**
1. Повторно `POST /api/auth/otp/verify` с тем же (уже использованным) кодом → **ожидание: 400**, код `error.auth.otp.invalid`.

**Ожидаемый результат:** использованный код одноразовый — повторно не принимается.

### TC-VER-NEG-05 — Код для email, где кода нет (400 invalid)

**Шаги:**
1. `POST /api/auth/otp/verify` `{ "email": "ghost+{run-id}+nv@example.com", "code": "123456" }` (запрос кода не делался) → **ожидание: 400**, код `error.auth.otp.invalid`.

**Ожидаемый результат:** отсутствие подходящей строки трактуется как неверный код.

## Фича 6. Client token TTL (длинная сессия)

### TC-TTL-01 — expiresIn соответствует клиентскому access TTL

**Предусловия:** активный CLIENT `otp+{run-id}+7@example.com`; успешная верификация (TC-VER-01).

**Шаги:**
1. Прочитать `expiresIn` из `TokenResponse` шага верификации → **ожидание:** равно `FOREMEN_JWT_CLIENT_ACCESS_TTL_MINUTES × 60` (дефолт **7200** секунд = 2 часа), а НЕ 1800 (сотруднические 30 мин).

**Ожидаемый результат:** клиентский access-токен живёт 2 часа (по дефолту).

### TC-TTL-02 — Refresh клиента работает и остаётся валидным

**Предусловия:** получен `refreshToken` клиента из TC-VER-01.

**Шаги:**
1. `POST /api/auth/refresh` `{ "refreshToken": "<client refresh>" }` → **ожидание: 200**, новая пара токенов; старый refresh отозван (rotation, как в FOR-03-01).
2. (Опционально) `expiresIn` новой пары → **ожидание:** снова клиентский access TTL (7200).

**Ожидаемый результат:** клиентская сессия обновляется; refresh-ротация работает. (Проверка полного 30-дневного срока refresh — вне рамок прогона; фиксируется, что refresh валиден и ротация проходит.)

## Фича 7. Локализация PL/RU

### TC-I18N-01 — Ошибка OTP локализована (pl vs ru)

**Предусловия:** активный CLIENT `otp+{run-id}+8@example.com`; запрошен код.

**Шаги:**
1. `POST /api/auth/otp/verify` с неверным кодом и заголовком `Accept-Language: pl` → 400; запомнить `message`.
2. Тот же запрос с `Accept-Language: ru` → 400; запомнить `message`.
3. Сравнить → **ожидание:** оба непустые и различаются, код в обоих `error.auth.otp.invalid`.

**Ожидаемый результат:** сообщение об ошибке OTP локализовано в PL и RU.

### TC-I18N-02 — Rate-limit ошибка локализована (pl vs ru)

**Предусловия:** email с исчерпанным лимитом (как в TC-RL-01), `otp+{run-id}+rl2@example.com`.

**Шаги:**
1. Запрос сверх лимита с `Accept-Language: pl` → 429; запомнить `message`.
2. То же с `Accept-Language: ru` → 429; запомнить `message`.
3. Сравнить → **ожидание:** оба непустые и различаются, код `error.auth.otp.rate.limited`.

**Ожидаемый результат:** сообщение rate-limit локализовано PL+RU.

## Фича 8. Регистрация клиента + автопривязка к проекту

Проверяет выделенный эндпоинт `POST /api/users/client`: роль фиксируется сервером как `CLIENT`, `projectId` обязателен, доступ по праву `PROJECTS/EDIT`, клиент создаётся в статусе `INVITED` и сразу привязывается к проекту (`project_members`) в роли CLIENT. Всё в одной транзакции.

### Предусловие-хелпер: токен вызывающего с правом PROJECTS/EDIT

- ADMIN проходит по bypass — можно использовать ADMIN-токен из общего предусловия.
- Для проверки 403 нужен токен пользователя **без** права `PROJECTS/EDIT`: создать сотрудника с ролью, у которой нет EDIT на `PROJECTS` (например WORKER), активировать и залогинить (либо через set-password флоу FOR-03-02). Далее — «токен без PROJECTS/EDIT».
- `projectId` для прогона: произвольный уникальный `Long` на прогон (таблицы `projects` ещё нет; `project_members.project_id` — без FK). Например `projectId = {run-id-numeric}`.

### TC-CLI-01 — Успешная регистрация клиента (201 + автопривязка)

**Предусловия:** ADMIN-токен (или токен с PROJECTS/EDIT); email клиента `cli+{run-id}+1@example.com`; `projectId = P1` (уникальный на прогон).

**Шаги:**
1. `POST /api/users/client` (Bearer ADMIN) с телом `{ "name": "Client One", "email": "cli+{run-id}+1@example.com", "projectId": P1 }` → **ожидание: 201**, тело содержит `id`, `email`, `projectId = P1`.
2. Проверить пользователя в БД/через `GET /api/users/{id}` → **ожидание:** роль = `CLIENT`, статус = `INVITED`, `password_hash = null`.
3. Проверить членство: `GET /api/project-members?projectId=P1` (Bearer ADMIN) → **ожидание:** есть строка с `userId` созданного клиента и project-ролью `CLIENT`.
4. (Опц.) Проверить отправку client-portal приглашения (тестовый SMTP/лог) → **ожидание:** письмо-приглашение клиенту отправлено.

**Ожидаемый результат:** клиент создан с ролью CLIENT (роль в запросе не передавалась), сразу привязан к проекту, отправлено приглашение.

### TC-CLI-02 — Роль в запросе не принимается (роль всегда CLIENT)

**Предусловия:** ADMIN-токен; email `cli+{run-id}+2@example.com`; `projectId = P2`.

**Шаги:**
1. `POST /api/users/client` с телом, где дополнительно указан любой `roleId`/`role` (например `"roleId": <MANAGER_id>`) → **ожидание:** лишнее поле игнорируется; **201**.
2. Проверить роль созданного пользователя → **ожидание:** `CLIENT` (не MANAGER).

**Ожидаемый результат:** сервер фиксирует роль CLIENT независимо от содержимого запроса.

### TC-CLI-03 — Валидация: отсутствует projectId / пустые поля (400)

**Шаги:**
1. `POST /api/users/client` `{ "name": "X", "email": "cli+{run-id}+3@example.com" }` (без `projectId`) → **ожидание: 400**.
2. `POST /api/users/client` `{ "name": "", "email": "cli+{run-id}+3@example.com", "projectId": P3 }` → **ожидание: 400**.
3. `POST /api/users/client` `{ "name": "X", "email": "", "projectId": P3 }` → **ожидание: 400**.

**Ожидаемый результат:** 400 до создания пользователя и привязки.

### TC-CLI-04 — Нет права PROJECTS/EDIT → 403

**Предусловия:** «токен без PROJECTS/EDIT» (например WORKER).

**Шаги:**
1. `POST /api/users/client` (Bearer этого пользователя) с валидным телом → **ожидание: 403**, код `error.access.denied`.
2. Проверить БД → **ожидание:** пользователь не создан, членство не создано.

**Ожидаемый результат:** эндпоинт закрыт правом PROJECTS/EDIT.

### TC-CLI-05 — Дубликат email → 409, без привязки

**Предусловия:** ADMIN-токен; email `cli+{run-id}+1@example.com` уже создан в TC-CLI-01.

**Шаги:**
1. `POST /api/users/client` с тем же email и `projectId = P5` → **ожидание: 409** (существующая ошибка дубликата email).
2. Проверить членство на `P5` → **ожидание:** строки нет.

**Ожидаемый результат:** дубликат email отклонён; новая привязка не создаётся.

### TC-CLI-06 — Атомарность: конфликт членства не оставляет осиротевшего клиента (409)

**Контекст.** Требование 10.7/10.9: создание пользователя и привязка к проекту — одна транзакция. Если `ProjectMemberService.assign` падает (дубликат `(userId, projectId)`), откатывается и создание клиента, и инвайт — осиротевшего CLIENT-пользователя не остаётся. В docker-прогоне «искусственно» подставить конфликт членства для ещё не существующего `userId` нельзя (userId появляется внутри той же транзакции), поэтому:
- **Наблюдаемое поведение** проверяется docker-кейсом ниже (дубликат email перехватывается раньше членства и не создаёт привязку).
- **Полный откат при падении `assign`** проверяется интеграционным тестом (design Property 19, задача 14.7) — вне docker-прогона, фиксируется отдельной строкой в отчёте.

**Предусловия:** ADMIN-токен; клиент `cli+{run-id}+1@example.com` уже создан в TC-CLI-01 на `P1`.

**Шаги (наблюдаемый конфликт email → нет новой привязки):**
1. Повторный `POST /api/users/client` с email `cli+{run-id}+1@example.com` и **другим** `projectId = P6` → **ожидание: 409** (дубликат email, перехватывается до `assign`).
2. `GET /api/project-members?projectId=P6` (Bearer ADMIN) → **ожидание:** строки для этого клиента на `P6` НЕТ (привязка не создана).
3. Проверить, что в системе ровно один пользователь с этим email и ровно одна строка членства (на `P1`, из TC-CLI-01) → **ожидание:** без дублей ни пользователя, ни членства.

**Ожидаемый результат:** конфликт (дубликат email) не порождает частично созданного клиента и лишней привязки. Полный откат при падении `assign` подтверждается интеграционным тестом (Property 19) — отражается строкой в MD-репорте.

## Фича 9. Дропдаун ролей формы пользователя (фронтенд, вне API-прогона)

Requirement 11 — исключение `ADMIN` и `CLIENT` из дропдауна `RoleSelect` в форме создания/редактирования пользователя. Проверяется **юнит-тестами Vitest** в `foremen-frontend/src/features/users/__tests__/` (не входит в docker API-прогон). Здесь фиксируется как чек-лист приёмки:

- В форме **создания** список ролей не содержит `ADMIN` и `CLIENT` (фильтр по `code`).
- В форме **редактирования** список не предлагает `ADMIN`/`CLIENT`; текущая роль редактируемого пользователя-клиента/админа показывается как контекст, но не как выбираемый пункт.
- Другие потребители `/api/roles` (страница ролей) не затронуты.

Прогон: `pnpm test` (или `npm run test`) в `foremen-frontend`. В MD-репорт добавляется строка со статусом фронтовых тестов.

## Teardown (выполняется в конце каждого прогона)

1. Для каждого созданного пользователя (`otp+{run-id}+*`, `cli+{run-id}+*`, `emp+{run-id}+*`): `PUT /api/users/{id}` с `active = false` (деактивация) под ADMIN.
2. Разлогинить выданные клиентские refresh-токены: `POST /api/auth/logout`.
3. Удалить членства прогона (при необходимости): `DELETE /api/project-members?userId=<id>&projectId=<Pn>` под ADMIN для каждого созданного клиента; либо `DELETE FROM project_members WHERE project_id IN (<Pn прогона>)`.
4. (Опционально) очистить OTP-строки прогона: `DELETE FROM otp_tokens WHERE email LIKE '%{run-id}%'`.
5. Проверить отсутствие активных остаточных сущностей с текущим `run-id`.

## Регрессия

Перепроверка критичных сквозных путей и ранее закрытых рисков после изменений в OTP-механизме.

### REG-01 — Полный путь OTP: запрос → верификация → доступ
Активный CLIENT: request → 200 → verify корректным кодом → 200 с токенами → `GET /api/auth/me` с access → 200. Подтверждает связку генерация + верификация + выдача клиентских токенов.
_Покрывает: TC-REQ-01, TC-VER-01, TC-TTL-01._

### REG-02 — Non-enumeration остаётся согласованным
Для клиента, сотрудника и неизвестного email `POST /api/auth/otp/request` возвращает 200 одинаково; rate-limit сверх лимита возвращает 429 одинаково — по внешнему ответу нельзя отличить клиента.
_Покрывает: TC-SS-01, TC-SS-02, TC-SS-03, TC-RL-02._

### REG-03 — Сотруднические флоу не затронуты клиентскими TTL
`POST /api/auth/login` сотрудником → `expiresIn` = сотруднический access TTL (дефолт 1800), НЕ 7200. Подтверждает, что клиентские TTL не сломали employee-логин.
_Покрывает: смежно с TC-TTL-01 (обратная проверка)._

### REG-04 — Одноразовость и блокировка кода
Использованный код и код после 3 неудачных попыток не принимаются повторно.
_Покрывает: TC-VER-NEG-02, TC-VER-NEG-04._

### REG-05 — Регистрация клиента → OTP-вход
Полный сквозной путь клиента: `POST /api/users/client` (201, роль CLIENT, привязка к проекту) → активация клиента до `ACTIVE` → `POST /api/auth/otp/request` → `POST /api/auth/otp/verify` → 200 с клиентскими токенами. Подтверждает, что созданный через новый эндпоинт клиент способен войти через OTP.
_Покрывает: TC-CLI-01 + TC-VER-01._

### REG-06 — CLIENT не создаётся через общий эндпоинт
`POST /api/users` с `roleId`, указывающим на роль `CLIENT`, отклоняется (defense in depth Requirement 10.11); CLIENT создаётся только через `/api/users/client`.
_Покрывает: смежно с TC-CLI-01._
