# Тест-кейсы: FOR-03-07 Menu Visibility (видимость меню и прав)

## Назначение и характер спеки

Спека **UI-facing** (есть браузерные экраны фронтенда). Поэтому тест-кейсы предназначены для «живого тестировщика», но по факту исполняются **браузерным движком** (headless-браузер / browser automation). Каждый шаг — действие в браузере: переход по URL, ввод в поля, клик, ожидание появления/исчезновения элемента. **Результат прогона — не скриншоты, а MD-репорты с таблицами** (шаг → действие → ожидание → факт → статус).

Спека — чисто фронтендовый слой авторизации (видимости): она превращает `roleCode` + `permissions` текущего пользователя (из `GET /api/auth/me`, доставлено FOR-03-06) в три эффекта:

- **Видимость пунктов навигации** (Sidebar / Drawer / BottomNav): пункт виден, только если у него нет `requiredPermission` или право выдано.
- **Permission route guard**: диплинк на запрещённый маршрут → редирект на `/403`; разрешённый маршрут рендерится; после логина пользователя не «выбрасывает» назад в `/403`.
- **Страница `/403`** с локализованным сообщением и контролом **Go_Back**, который возвращает на **последнюю разрешённую страницу** (`Last_Allowed_Location`), с фолбэком на `/`, если такой страницы нет или она совпадает с только что запрещённым маршрутом (`Denied_Location`).
- **Видимость CRUD-действий** на таблицах Users / Roles / Audit: кнопки Create / Edit / Delete(Deactivate) / Audit показываются или скрываются по правам; колонка row-actions схлопывается для read-only роли.

Бекенд — источник правды по правам (ABAC-матрица + серверное enforcement, FOR-03-03 / FOR-03-08). Фронт лишь скрывает то, что сервер всё равно отклонил бы. ADMIN обходит матрицу (bypass по точному литералу `ADMIN`).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL фронтенда для UI-тестов: `http://localhost:3000`.
3. Базовый URL API (для teardown/setup через HTTP): `http://localhost:8080`; auth-эндпоинты — под `/api/auth`.
4. Первый ADMIN поднимается через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL` (в docker-compose: `cto+1@loaders.dev`), `FOREMEN_ADMIN_PASSWORD` (в docker-compose: `alejano123`). В автоматизации подставить фактические значения из окружения прогона.
5. Дождаться готовности `backend` (health/readiness) и доступности `frontend` (`http://localhost:3000` отвечает) перед запуском кейсов.
6. **Логин выполняется через UI** (форма логина фронтенда), т.к. проверяется именно клиентский слой видимости, зависящий от роли залогиненного пользователя. Setup/teardown тестовых пользователей допустимо выполнять через API.

### Кодировки ресурсов и операций (совпадают с бекенд-матрицей, точное строковое равенство)

- Ресурсы: `USERS`, `ROLES`, `AUDIT` (сегодня засижены и enforce-ятся). Проектные модули (`PROJECTS`, `ROOMS`, …) объявлены на будущее и до сидинга видны только ADMIN.
- Операции: `CREATE`, `READ`, `UPDATE`, `DELETE`.
- Соответствие пунктов навигации: `/users` → `{USERS, READ}`, `/roles` → `{ROLES, READ}`, `/audit` → `{AUDIT, READ}`. `/` (дашборд) и `/settings/appearance` — без ограничения (видны любому аутентифицированному).

## Стратегия повторяемости

**Комбинированная — генератор уникальных email + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые не-ADMIN тестовые пользователи получают уникальный email `test+{run-id}+{seq}@example.com`; создаваемые несистемные роли — `code = TESTROLE_{run-id}_{seq}`. Это делает набор запускаемым многократно без ручной чистки БД.
- **Teardown (обязательный шаг в конце каждого набора):** через API — `POST /api/auth/logout` (отзыв refresh-токенов созданных пользователей), деактивация/удаление созданных пользователей через `/api/users`, удаление созданных несистемных ролей `DELETE /api/roles/{id}`. В браузере — logout текущей сессии, очистка localStorage/куки перед следующим кейсом.
- Системный ADMIN и seed-данные **не изменяются**; все манипуляции идут над созданными на прогон ролями/пользователями.
- Каждая группа кейсов ниже явно указывает применяемую стратегию.

### Предусловие-хелпер: активный пользователь с ограниченной ролью R

Для входа под ограниченной ролью нужен ACTIVE-пользователь. Стандартный флоу через API (setup):
1. Логин ADMIN (`POST /api/auth/login`) → получить access-токен.
2. Создать несистемную роль `TESTROLE_{run-id}_{seq}` и выдать ей нужную матрицу прав (`PUT /api/roles/{id}/permissions`), например только `{USERS: [READ]}`.
3. Создать пользователя `test+{run-id}+{seq}@example.com` c этой ролью (`POST /api/users`, статус INVITED).
4. Активировать: получить invite-токен (через тестовый хелпер БД / mailhog) → `POST /api/auth/set-password` → пользователь ACTIVE.

В шагах ниже это предусловие обозначено как «активный пользователь роли R с матрицей M». Пароль тестовых пользователей задаётся на шаге set-password и используется для UI-логина.

### Хелпер: UI-логин

Обозначается «залогиниться в UI как <пользователь>»:
1. Перейти на `http://localhost:3000/login`.
2. Ввести email и пароль, нажать кнопку входа.
3. Дождаться перехода на `/` (дашборд) и появления навигационного шелла (Sidebar/BottomNav).

## Фича 1. Видимость пунктов навигации (Menu Visibility)

Проверяет, что ограниченная роль видит только разрешённые пункты навигации и подмножество нижней навигации, а ADMIN видит всё. Пустые секции не показывают заголовок.

**Стратегия повторяемости группы:** генератор (`TESTROLE_/test+{run-id}`) + teardown созданных ролей/пользователей.
**Валидирует:** Requirements 3.1, 3.4, 3.5, 1.2.

### TC-NAV-01 — Ограниченная роль видит только разрешённые пункты меню

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}` (нет ROLES, нет AUDIT).

**Шаги:**
1. Залогиниться в UI как пользователь роли R. → Ожидание: переход на `/`, шелл навигации отрисован.
2. Осмотреть Sidebar (desktop). → Ожидание: пункт **Users** присутствует; пункты **Roles** и **Audit** отсутствуют в DOM (не просто скрыты стилем).
3. Проверить дашборд-пункт `/` и `/settings/appearance`. → Ожидание: оба видны (без `requiredPermission`).
4. Убедиться, что скрытые пункты отсутствуют в accessibility-дереве (нет focusable disabled-элементов на их месте). → Ожидание: элементов Roles/Audit нет ни в DOM, ни в a11y-дереве.

**Ожидаемый результат:** видны только `/`, `/users`, `/settings/appearance`; `/roles` и `/audit` отсутствуют.

### TC-NAV-02 — Пустая секция не рендерит заголовок

**Предусловия:** активный пользователь роли R, у которой отфильтрованы ВСЕ пункты некоторой секции навигации (например, вся секция «Администрирование», если у роли нет ни USERS/ROLES/AUDIT READ; выдать роли только доступ к дашборду/appearance).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Осмотреть Sidebar/Drawer на наличие заголовка секции, все пункты которой отфильтрованы. → Ожидание: **заголовок секции не отрисован** (нет видимого heading для пустой секции).

**Ожидаемый результат:** секция без единого видимого пункта не показывает свой заголовок.

### TC-NAV-03 — BottomNav фильтрует пункты по правам (подмножество)

**Предусловия:** мобильный вьюпорт (например, 390×844); активный пользователь роли R с матрицей `{USERS: [READ]}`.

**Шаги:**
1. Установить мобильный вьюпорт.
2. Залогиниться в UI как пользователь роли R.
3. Осмотреть BottomNav. → Ожидание: отрисованы только `bottomNav: true`-пункты, разрешённые правами (подмножество), запрещённые отсутствуют; число пунктов ≤ 5 и меньше, чем у ADMIN.

**Ожидаемый результат:** BottomNav показывает подмножество пунктов, соответствующее правам роли.

### TC-NAV-04 — ADMIN видит все пункты навигации

**Предусловия:** доступен ADMIN (`FOREMEN_ADMIN_EMAIL` / `FOREMEN_ADMIN_PASSWORD`).

**Шаги:**
1. Залогиниться в UI как ADMIN.
2. Осмотреть Sidebar. → Ожидание: присутствуют **все** пункты, включая `/users`, `/roles`, `/audit` и проектные модули (ADMIN bypass).
3. Переключиться в мобильный вьюпорт, осмотреть BottomNav. → Ожидание: полный набор `bottomNav`-пунктов (до 5).

**Ожидаемый результат:** ADMIN видит каждый пункт навигации во всех трёх контейнерах (Sidebar/Drawer/BottomNav).

## Фича 2. Permission route guard (защита маршрутов по правам)

Проверяет, что диплинк на запрещённый маршрут ведёт на `/403` (при сохранённой навигации), разрешённый маршрут рендерится, а последующий логин не выбрасывает пользователя в `/403`.

**Стратегия повторяемости группы:** генератор + teardown; между кейсами — logout и очистка localStorage/куки.
**Валидирует:** Requirements 4.2, 4.6, 4.7, 5.1.

### TC-GUARD-01 — Диплинк на запрещённый маршрут → редирект на /403

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}` (нет `ROLES READ`).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. В адресной строке перейти напрямую на `http://localhost:3000/roles` (диплинк). → Ожидание: браузер оказывается на `/403` (редирект `replace`).
3. Проверить, что шелл приложения (навигация) остался на месте. → Ожидание: Sidebar/BottomNav отрисованы, `/403` показан внутри AppShell.
4. Нажать «Назад» в браузере. → Ожидание: пользователь **не** возвращается на `/roles` и не попадает в петлю `/403` (запрещённый URL вытеснен из истории `replace`).

**Ожидаемый результат:** переход на `/roles` без права приводит к `/403` c сохранённой навигацией.

### TC-GUARD-02 — Разрешённый маршрут рендерится и фиксируется как Last_Allowed_Location

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}`.

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `http://localhost:3000/users`. → Ожидание: страница Users отрисована (нет редиректа на `/403`).
3. (Косвенная проверка фиксации Last_Allowed_Location выполняется в TC-403-02.)

**Ожидаемый результат:** маршрут с выданным правом рендерится обычным образом.

### TC-GUARD-03 — ADMIN проходит на любой guarded-маршрут

**Предусловия:** ADMIN.

**Шаги:**
1. Залогиниться в UI как ADMIN.
2. Перейти диплинком на `/users`, затем `/roles`, затем `/audit`. → Ожидание: каждая страница рендерится, редиректа на `/403` нет.

**Ожидаемый результат:** ADMIN обходит проверку прав на всех маршрутах.

### TC-GUARD-04 — После логина нет «отскока» в /403 (Return_Location не пишется при отказе)

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}`; сессия не аутентифицирована (пользователь разлогинен).

**Шаги:**
1. Будучи разлогиненным, перейти диплинком на запрещённый для R маршрут `http://localhost:3000/roles`. → Ожидание: т.к. пользователь не аутентифицирован, guard авторизации FOR-03-06 редиректит на `/login` (а **не** на `/403`).
2. На форме логина ввести креды пользователя роли R и войти. → Ожидание: после успешного логина пользователь оказывается на разрешённой странице (`/` или Return_Location из FOR-03-06), но **не** на `/403`.
3. Убедиться, что нет автоматического редиректа обратно в `/roles`/`/403`. → Ожидание: пользователь на разрешённом маршруте.

**Ожидаемый результат:** отказ по правам не сохраняется как Return_Location; логин не выбрасывает пользователя в запрещённый маршрут или `/403`.

### TC-GUARD-05 — Неаутентифицированный диплинк идёт на /login, не на /403

**Предусловия:** нет активной сессии (очищены токены/куки).

**Шаги:**
1. Перейти диплинком на `http://localhost:3000/users` без логина. → Ожидание: редирект на `/login` (FOR-03-06), **не** на `/403`.

**Ожидаемый результат:** анонимный пользователь всегда попадает на `/login`; permission-guard не срабатывает раньше аутентификации.

## Фича 3. Страница /403 и поведение Go_Back

Проверяет содержимое `/403` и логику Go_Back: возврат на последнюю разрешённую страницу; `/` — когда её нет или она равна запрещённому маршруту.

**Стратегия повторяемости группы:** генератор + teardown; между кейсами — очистка in-memory состояния через полный перезаход (reload сбрасывает Last_Allowed_Location/Denied_Location) и logout.
**Валидирует:** Requirements 5.1, 5.2, 5.4, 5.5, 5.6.

### TC-403-01 — Содержимое страницы /403

**Предусловия:** активный пользователь роли R (любая ограниченная); пользователь залогинен.

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `http://localhost:3000/403` напрямую. → Ожидание: `/403` рендерится внутри AppShell (навигация на месте; `/403` не имеет requiredPermission).
3. Проверить наличие заголовка страницы (`<h1>` / page heading) и поясняющего текста об отсутствии доступа. → Ожидание: заголовок и сообщение локализованы и непусты.
4. Проверить наличие клавиатурно-доступного контрола Go_Back с доступным именем. → Ожидание: кнопка/ссылка «Вернуться назад» присутствует, фокусируется и активируется с клавиатуры.

**Ожидаемый результат:** `/403` показывает heading, пояснение и Go_Back; всё доступно с клавиатуры.

### TC-403-02 — Go_Back возвращает на последнюю разрешённую страницу

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}` (нет `ROLES READ`).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на разрешённую страницу `http://localhost:3000/users` и дождаться её отрисовки (guard зафиксировал Last_Allowed_Location = `/users`).
3. Диплинком перейти на запрещённый `http://localhost:3000/roles`. → Ожидание: редирект на `/403` (Denied_Location = `/roles`).
4. Нажать Go_Back на `/403`. → Ожидание: переход на `/users` (последняя разрешённая страница), которая нормально рендерится.

**Ожидаемый результат:** Go_Back возвращает на `/users` — последнюю успешно отрендеренную разрешённую страницу.

### TC-403-03 — Go_Back → «/» когда нет Last_Allowed_Location (холодный диплинк)

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}`; свежая сессия/полный reload перед кейсом (in-memory Last_Allowed_Location сброшен).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Сразу (без посещения других защищённых страниц) диплинком перейти на запрещённый `http://localhost:3000/roles`. → Ожидание: редирект на `/403`, при этом Last_Allowed_Location отсутствует.
3. Нажать Go_Back. → Ожидание: переход на домашний маршрут `/` (фолбэк), т.к. разрешённой предыдущей страницы нет.

**Ожидаемый результат:** при отсутствии Last_Allowed_Location Go_Back ведёт на `/`.

### TC-403-04 — Go_Back → «/» когда Last_Allowed_Location равен Denied_Location (защита от петли)

**Предусловия:** активный пользователь роли R; сценарий, при котором последняя разрешённая страница совпадает с только что запрещённым маршрутом. Моделируется сменой прав: пользователь находится на странице `/users` (право есть), затем право `USERS READ` отзывается (через API ADMIN-ом), после чего повторный вход на `/users` запрещается.

**Шаги:**
1. Залогиниться в UI как пользователь роли R с матрицей `{USERS: [READ]}`.
2. Перейти на `/users` — страница рендерится (Last_Allowed_Location = `/users`).
3. Через API под ADMIN отозвать у роли R право `USERS READ` (`PUT /api/roles/{R}/permissions` без USERS) и обновить `Current_User` на клиенте (повторная гидратация `/api/auth/me`, напр. перезагрузка страницы `/users`). → Ожидание: guard теперь отказывает на `/users` и редиректит на `/403` (Denied_Location = `/users`, а Last_Allowed_Location тоже `/users`).
4. Нажать Go_Back на `/403`. → Ожидание: переход на `/` (а не обратно на `/users`), чтобы не зациклиться на запрещённом маршруте.

**Ожидаемый результат:** когда Last_Allowed_Location == Denied_Location, Go_Back ведёт на `/`, петля исключена.

## Фича 4. Видимость CRUD-действий (Users / Roles / Audit)

Проверяет, что кнопки Create / Edit / Delete(Deactivate) / Audit показываются или скрываются по правам, а колонка row-actions схлопывается для read-only роли.

**Стратегия повторяемости группы:** генератор ролей/пользователей с разной матрицей + teardown.
**Валидирует:** Requirements 6.2, 6.3, 6.4, 6.5, 6.6, 1.2.

### TC-CRUD-01 — Read-only роль: колонка row-actions схлопнута, Create скрыт

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ]}` (только READ, нет CREATE/UPDATE/DELETE, нет `AUDIT READ`).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `/users`. → Ожидание: страница Users отрисована, таблица видна.
3. Проверить наличие кнопки Create над таблицей. → Ожидание: кнопка Create **отсутствует** (нет `USERS CREATE`).
4. Проверить строки таблицы. → Ожидание: колонка row-actions **отсутствует целиком** (нет ни Edit, ни Deactivate, ни Audit); нет пустого заголовка actions-колонки; таблица остаётся валидной.

**Ожидаемый результат:** для read-only роли Create скрыт и колонка действий схлопнута полностью.

### TC-CRUD-02 — Частичные права: виден только Edit (UPDATE), нет Delete и Create

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ, UPDATE]}` (без CREATE, без DELETE, без `AUDIT READ`).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `/users`. → Ожидание: таблица видна.
3. Проверить кнопку Create. → Ожидание: **отсутствует** (нет CREATE).
4. Проверить row-actions в строке. → Ожидание: **Edit присутствует** (UPDATE), **Deactivate/Delete отсутствует** (нет DELETE), Audit-кнопка отсутствует (нет `AUDIT READ`); колонка действий отрисована (есть хотя бы Edit).

**Ожидаемый результат:** видимость каждого контрола строго соответствует выданной операции.

### TC-CRUD-03 — Право DELETE: виден Deactivate/Delete, нет Edit

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ, DELETE]}` (без UPDATE, без CREATE).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `/users`.
3. Проверить row-actions. → Ожидание: **Deactivate/Delete присутствует** (DELETE), **Edit отсутствует** (нет UPDATE); Create отсутствует.

**Ожидаемый результат:** Delete-контрол управляется правом DELETE независимо от UPDATE.

### TC-CRUD-04 — Audit-контрол управляется правом (AUDIT, READ)

**Предусловия:** два пользователя: R1 с матрицей `{USERS: [READ]}` (без AUDIT), R2 с матрицей `{USERS: [READ], AUDIT: [READ]}`.

**Шаги:**
1. Залогиниться в UI как R1, перейти на `/users`. → Ожидание: per-row кнопка **Audit отсутствует** (нет `AUDIT READ`).
2. Разлогиниться, залогиниться как R2, перейти на `/users`. → Ожидание: per-row кнопка **Audit присутствует** (есть `AUDIT READ`), колонка действий отрисована.

**Ожидаемый результат:** видимость Audit-кнопки зависит именно от `(AUDIT, READ)`, а не от ресурса таблицы.

### TC-CRUD-05 — Create виден при наличии CREATE

**Предусловия:** активный пользователь роли R с матрицей `{USERS: [READ, CREATE]}`.

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `/users`. → Ожидание: кнопка Create над таблицей **присутствует** и кликабельна.

**Ожидаемый результат:** Create отображается при выданном `USERS CREATE`.

### TC-CRUD-06 — ADMIN видит все действия на Users/Roles/Audit

**Предусловия:** ADMIN.

**Шаги:**
1. Залогиниться в UI как ADMIN.
2. Перейти на `/users`. → Ожидание: Create виден; в строках видны Edit, Deactivate и Audit; колонка действий отрисована.
3. Перейти на `/roles`. → Ожидание: соответствующие действия ROLES видны (Create/Edit/Delete по наличию на странице).
4. Перейти на `/audit` (read-only страница). → Ожидание: Create/Edit/Delete не рендерятся по природе страницы; Audit-контрол (если есть) виден по `AUDIT READ` (ADMIN bypass).

**Ожидаемый результат:** ADMIN видит все применимые контролы действий (bypass).

### TC-CRUD-07 — Roles page: гейтинг действий по правам ROLES

**Предусловия:** пользователь роли R с матрицей `{ROLES: [READ]}` (только чтение ролей; без CREATE/UPDATE/DELETE).

**Шаги:**
1. Залогиниться в UI как пользователь роли R.
2. Перейти на `/roles`. → Ожидание: страница Roles рендерится; Create скрыт; колонка row-actions схлопнута (нет Edit/Delete; Audit по `AUDIT READ`, которого нет).

**Ожидаемый результат:** страница Roles применяет тот же гейтинг, что и Users, по ресурсу `ROLES`.

## Teardown (выполняется в конце каждого прогона)

1. В браузере: разлогиниться из текущей сессии; очистить localStorage/sessionStorage и куки, чтобы следующий кейс стартовал чисто.
2. Через API: для каждого созданного пользователя `POST /api/auth/logout` (отзыв refresh-токена) и деактивация/удаление через `/api/users`.
3. Через API: для каждой созданной несистемной роли `DELETE /api/roles/{id}`.
4. Восстановить исходную матрицу ролей, если она менялась в кейсах со сменой прав (TC-403-04): вернуть/удалить временные гранты на созданных ролях (системные роли не трогаются).
5. Проверить отсутствие остаточных сущностей с текущим `run-id`.

## Регрессия

Перепроверка критичных сквозных путей и ранее закрытых рисков после изменений в слое видимости.

### REG-01 — Сквозной путь ограниченной роли: меню → guard → 403 → Go_Back
Ограниченная роль (`{USERS: [READ]}`): в меню виден только Users → диплинк на `/roles` даёт `/403` → Go_Back возвращает на последнюю разрешённую страницу. Подтверждает связку nav-filter + PermissionGuard + Forbidden_Page.
_Покрывает: TC-NAV-01, TC-GUARD-01, TC-403-02._

### REG-02 — ADMIN видит и проходит всё
После любых манипуляций с ролями/правами ADMIN сохраняет полный набор пунктов навигации, проходит на все guarded-маршруты и видит все CRUD-контролы.
_Покрывает: TC-NAV-04, TC-GUARD-03, TC-CRUD-06._

### REG-03 — Нет отскока в /403 после логина
Неаутентифицированный диплинк на запрещённый маршрут → `/login` → после входа пользователь на разрешённой странице, а не в `/403`.
_Покрывает: TC-GUARD-04, TC-GUARD-05._

### REG-04 — Скрытые контролы отсутствуют в a11y-дереве
Проверить, что скрытые по правам пункты меню и CRUD-контролы удалены из DOM и accessibility-дерева (не рендерятся как disabled/скрытые, но focusable), и колонка actions не оставляет пустого заголовка.
_Покрывает: TC-NAV-01 (шаг 4), TC-CRUD-01 (шаг 4)._
