# Тест-кейсы: FOR-03-03 Permission Evaluator

## Назначение и характер спеки

Спека **чисто бекендовая** (нет браузерных экранов). Поэтому тест-кейсы — это **API-тесты против работающего в Docker приложения** (не Testcontainers/юнит-слой). Каждый шаг — HTTP-запрос к API с проверкой статуса, тела и заголовков. Результат прогона — **MD-репорт с таблицами** (шаг → запрос → ожидание → факт → статус). Скриншоты не требуются.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`.
3. Auth-эндпоинты — под `/api/auth`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`.
5. Дождаться готовности `backend` (health/readiness) перед запуском кейсов.

### Особенность этой спеки: как driving-инфраструктура

FOR-03-03 доставляет **механизм** проверки прав + один демонстрационный аннотированный эндпоинт (test-only контроллер). Поскольку в проде эндпоинты ещё не аннотированы (это FOR-03-08), для сквозной проверки enforcement используется **демонстрационный эндпоинт**, аннотированный `@RequiresPermission(resource = "PROJECTS", operation = "READ")`.

- В API-тестах он обозначается как `GET /api/demo/projects-read` (условный путь демонстрационного контроллера; при автоматизации подставить фактический путь из реализации задачи 8.1).
- Матрица прав редактируется через существующий эндпоинт ролей: `PUT /api/roles/{id}/permissions` (доступен ADMIN).
- Список ресурсов/операций для получения их id: `GET /api/resources`, `GET /api/operations`.

**Общий приём выдачи/отзыва прав:** логинимся как ADMIN → редактируем матрицу целевой роли через `PUT /api/roles/{id}/permissions` → логинимся как пользователь целевой роли → дёргаем защищённый эндпоинт.

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые сущности получают уникальные идентификаторы:
  - роли: `code = TESTROLE_{run-id}_{seq}` (несистемные, поэтому удаляемы);
  - пользователи: `email = perm+{run-id}+{seq}@example.com`.
- **Teardown (обязательный шаг в конце каждого набора):** деактивировать/удалить созданных пользователей, удалить созданные несистемные роли (`DELETE /api/roles/{id}`), разлогинить выданные refresh-токены (`POST /api/auth/logout`). Кеш прав инвалидируется автоматически при изменении матрицы роли (`replacePermissions`), отдельной ручной чистки БД не требуется.
- Системные роли (ADMIN, MANAGER, …) и seed-данные **не изменяются** — все манипуляции идут над созданными на прогон ролями/пользователями. Это делает набор запускаемым многократно без ручной чистки БД.

### Предусловие-хелпер: активный пользователь с ролью R

Для входа под конкретной ролью нужен ACTIVE-пользователь. Стандартный флоу: ADMIN создаёт пользователя (`POST /api/users`, статус INVITED) → получение invite-токена (через тестовый хелпер БД или перехват почты/mailhog) → `POST /api/auth/set-password` (пользователь становится ACTIVE и сразу получает JWT). Если в окружении настроен только логин-флоу — использовать заранее засиженного ACTIVE-пользователя нужной роли. В шагах ниже это предусловие обозначено как «активный пользователь роли R».

## Фича 1. Оценка прав и deny-by-default

Проверяет, что защищённый эндпоинт доступен только при наличии точного права `(PROJECTS, READ)` у роли, а при отсутствии записи в матрице доступ запрещается.

### TC-EVAL-01 — Роль с нужным правом получает доступ (200)

**Предусловия:** ADMIN залогинен; создана тестовая роль `TESTROLE_{run-id}_1`; активный пользователь этой роли.

**Шаги:**
1. `POST /api/auth/login` (ADMIN) → 200, получить access-токен ADMIN.
2. `GET /api/resources` и `GET /api/operations` → 200; найти `id` ресурса `PROJECTS` и операции `READ`.
3. `PUT /api/roles/{testRoleId}/permissions` c телом, выдающим `PROJECTS: [READ]` → 200.
4. `POST /api/auth/login` пользователем тестовой роли → 200, получить его access-токен.
5. `GET /api/demo/projects-read` с `Authorization: Bearer <token роли>` → **ожидание: 200**, тело — успешный ответ эндпоинта.

**Ожидаемый результат:** шаг 5 возвращает 200; контроллер отработал.

### TC-EVAL-02 — Роль без записи для ресурса получает отказ (403)

**Предусловия:** тестовая роль без права на `PROJECTS`; активный пользователь этой роли.

**Шаги:**
1. Логин ADMIN → 200.
2. `PUT /api/roles/{testRoleId}/permissions` c пустой матрицей (или только `ROOMS: [READ]`, без `PROJECTS`) → 200.
3. Логин пользователем роли → 200.
4. `GET /api/demo/projects-read` с токеном роли → **ожидание: 403**, тело содержит код `error.access.denied`.

**Ожидаемый результат:** 403 и локализованное сообщение `error.access.denied`.

### TC-EVAL-03 — Ресурс есть, но операция отсутствует (403)

**Предусловия:** тестовой роли выдан `PROJECTS: [CREATE]` (без READ); активный пользователь роли.

**Шаги:**
1. Логин ADMIN → 200.
2. `PUT /api/roles/{testRoleId}/permissions` → `PROJECTS: [CREATE]` → 200.
3. Логин пользователем роли → 200.
4. `GET /api/demo/projects-read` (требует READ) с токеном роли → **ожидание: 403**, код `error.access.denied`.

**Ожидаемый результат:** 403 — точное совпадение операции обязательно.

### TC-EVAL-04 — Пустая матрица запрещает всё (403)

**Предусловия:** тестовой роли выдана пустая матрица; активный пользователь роли.

**Шаги:**
1. Логин ADMIN → 200.
2. `PUT /api/roles/{testRoleId}/permissions` с пустым списком → 200.
3. Логин пользователем роли → 200.
4. `GET /api/demo/projects-read` → **ожидание: 403**, код `error.access.denied`.

**Ожидаемый результат:** deny-by-default для роли без прав.

## Фича 2. ADMIN bypass

### TC-ADMIN-01 — ADMIN всегда допускается, минуя матрицу (200)

**Предусловия:** ADMIN залогинен; матрица ADMIN не изменяется.

**Шаги:**
1. `POST /api/auth/login` (ADMIN) → 200.
2. `GET /api/demo/projects-read` с токеном ADMIN → **ожидание: 200** независимо от содержимого матрицы.

**Ожидаемый результат:** 200; ADMIN не проверяется через матрицу.

## Фича 3. Enforcement до выполнения контроллера + 403 при отказе

### TC-ENF-01 — При отказе тело контроллера не выполняется

**Предусловия:** демонстрационный эндпоинт имеет наблюдаемый побочный эффект/маркер (например, возвращает детерминированный success-body только при выполнении). Роль без права READ на PROJECTS; активный пользователь роли.

**Шаги:**
1. Логин ADMIN → 200; выдать роли матрицу без `PROJECTS`.
2. Логин пользователем роли → 200.
3. `GET /api/demo/projects-read` → **ожидание: 403**; тело — стандартный `ErrorResponse` с кодом `error.access.denied`, а НЕ success-body контроллера.

**Ожидаемый результат:** ответ содержит ошибку авторизации, признаков выполнения тела контроллера нет (проверка до контроллера).

### TC-ENF-02 — Неаннотированный эндпоинт доступен без проверки прав

**Предусловия:** любой существующий неаннотированный эндпоинт (например, `GET /api/resources` под `permitAll` на текущем этапе).

**Шаги:**
1. Выполнить `GET /api/resources` (с токеном любой роли или как сейчас настроено) → **ожидание: 200** без проверки `@RequiresPermission`.

**Ожидаемый результат:** запрос проходит, интерцептор не применяет проверку прав к неаннотированным путям.

## Фича 4. 401 при неаутентифицированном доступе

### TC-AUTH-01 — Запрос без токена к защищённому эндпоинту (401)

**Шаги:**
1. `GET /api/demo/projects-read` **без** заголовка `Authorization` → **ожидание: 401**, код `error.auth.unauthorized`.

**Ожидаемый результат:** 401 с локализованным сообщением `error.auth.unauthorized`.

### TC-AUTH-02 — Невалидный/просроченный токен (401)

**Шаги:**
1. `GET /api/demo/projects-read` с `Authorization: Bearer invalid.token.value` → **ожидание: 401**, код `error.auth.unauthorized`.

**Ожидаемый результат:** 401; контекст не аутентифицирован, доступ к аннотированному эндпоинту закрыт.

## Фича 5. Кеш прав: загрузка, TTL, инвалидация

Через публичный API напрямую наблюдать кеш нельзя; проверяется поведенчески — эффект инвалидации при изменении матрицы.

### TC-CACHE-01 — Изменение матрицы роли применяется на следующем запросе (инвалидация)

**Предусловия:** тестовая роль с правом `PROJECTS: [READ]`; активный пользователь роли.

**Шаги:**
1. Логин ADMIN → 200; выдать роли `PROJECTS: [READ]`.
2. Логин пользователем роли → 200.
3. `GET /api/demo/projects-read` токеном роли → **ожидание: 200** (право есть; набор загружен в кеш).
4. Логин ADMIN → 200; `PUT /api/roles/{testRoleId}/permissions` с матрицей БЕЗ `PROJECTS` → 200 (это инвалидирует кеш роли).
5. `GET /api/demo/projects-read` тем же токеном роли → **ожидание: 403**, код `error.access.denied` (изменение применилось без ожидания TTL).

**Ожидаемый результат:** после `replacePermissions` следующий запрос отражает новую матрицу (кеш инвалидирован по коду роли).

### TC-CACHE-02 — Повторные запросы стабильны в пределах idle-TTL

**Предусловия:** роль с правом `PROJECTS: [READ]`; активный пользователь роли.

**Примечание по TTL:** у кеша прав нет короткого write-based expiry. Запись живёт до явной инвалидации либо до простоя (не читалась) в течение idle-TTL `expireAfterAccess`, дефолт — **1440 минут (24 часа)**, настраивается свойством `foremen.permission.cache-ttl-minutes` (Requirement 8.4, 8.5). Поэтому повторные чтения без изменения матрицы стабильны и не приводят к перезагрузке из БД.

**Шаги:**
1. Выдать право, залогиниться пользователем роли.
2. Выполнить `GET /api/demo/projects-read` подряд 5 раз без изменения матрицы (в пределах idle-TTL) → **ожидание: все 5 → 200**, ответы стабильны.

**Ожидаемый результат:** повторные проверки дают одинаковый результат; набор прав обслуживается из кеша (перезагрузка из БД не требуется), пока запись не инвалидирована и не истёк idle-TTL (по умолчанию 24 часа).

## Фича 6. Локализация сообщений PL/RU

### TC-I18N-01 — 403 сообщение отличается для pl и ru

**Предусловия:** роль без права READ на PROJECTS; активный пользователь роли.

**Шаги:**
1. `GET /api/demo/projects-read` с токеном роли и заголовком `Accept-Language: pl` → 403; запомнить `message`.
2. Тот же запрос с `Accept-Language: ru` → 403; запомнить `message`.
3. Сравнить тексты → **ожидание:** оба непустые и различаются (PL vs RU), код в обоих `error.access.denied`.

**Ожидаемый результат:** сообщение `error.access.denied` локализовано в обоих языках.

### TC-I18N-02 — 401 сообщение отличается для pl и ru

**Шаги:**
1. `GET /api/demo/projects-read` без токена, `Accept-Language: pl` → 401; запомнить `message`.
2. То же с `Accept-Language: ru` → 401; запомнить `message`.
3. Сравнить → **ожидание:** оба непустые и различаются, код `error.auth.unauthorized`.

**Ожидаемый результат:** сообщение `error.auth.unauthorized` локализовано PL+RU.

## Teardown (выполняется в конце каждого прогона)

1. Для каждого созданного пользователя: `POST /api/auth/logout` (отзыв refresh-токена) и деактивация/удаление через `/api/users`.
2. Для каждой созданной тестовой роли: `DELETE /api/roles/{id}` (несистемные роли удаляемы).
3. Проверить отсутствие остаточных сущностей с текущим `run-id`.

## Регрессия

Перепроверка критичных сквозных путей и ранее закрытых рисков после изменений в механизме прав.

### REG-01 — Полный путь выдачи и отзыва права
Выдать роли `PROJECTS: [READ]` → доступ 200 → отозвать право → доступ 403. Подтверждает связку evaluator + кеш + инвалидация.
_Покрывает: TC-EVAL-01, TC-CACHE-01._

### REG-02 — ADMIN не блокируется матрицей
После любых изменений матрицы других ролей ADMIN сохраняет 200 на защищённом эндпоинте.
_Покрывает: TC-ADMIN-01._

### REG-03 — Существующие неаннотированные эндпоинты не сломаны
`GET /api/resources`, `GET /api/operations`, `GET /api/roles` остаются доступны как прежде (интерцептор не вводит непреднамеренных проверок).
_Покрывает: TC-ENF-02; защита от случайной миграции контроллеров (FOR-03-08 out of scope)._

### REG-04 — Матрица прав ролей не повреждена
После прогона `GET /api/roles/{id}/permissions` для системных ролей возвращает исходные seed-права (тестовые прогоны меняют только созданные на прогон роли).
