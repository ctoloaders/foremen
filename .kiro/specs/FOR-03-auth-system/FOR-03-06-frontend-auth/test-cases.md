# Тест-кейсы: FOR-03-06 Frontend Auth

## Назначение и характер спеки

Спека **смешанная** — в ней есть и **браузерные экраны** (LoginPage, SetPasswordPage, OtpLoginPage, Auth_Guard, logout), и **бекендовые API-эндпоинты** (`GET /api/auth/me` с ETag/условными запросами и `POST /api/auth/google`). Поэтому набор делится на две части:

- **UI-часть** — сценарии для «живого тестировщика», по факту исполняемые браузерным движком (headless-браузер / browser automation). Каждый шаг — действие в браузере (переход, ввод, клик, ожидание, проверка URL/DOM). Артефакт прогона — **MD-репорт с таблицами** (шаг → действие → ожидание → факт → статус). Скриншоты не требуются.
- **API-часть** — API-тесты против поднятого в Docker приложения. Каждый шаг — HTTP-запрос к API с проверкой статуса, тела и заголовков. Артефакт прогона — **MD-репорт с таблицами** (шаг → запрос → ожидание → факт → статус).

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL для API-тестов: `http://localhost:8080`. Auth-эндпоинты — под `/api/auth`.
3. Базовый URL для UI-тестов: `http://localhost:3000`.
4. Первый ADMIN создаётся через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Эти учётные данные используются как «сидовый» ACTIVE-администратор для входа и для управления пользователями.
5. Для сценариев Google-входа нужен рабочий верификатор Google ID-токена. В прод-окружении настраивается `FOREMEN_GOOGLE_CLIENT_ID` (бекенд) и `VITE_GOOGLE_CLIENT_ID` (фронтенд). Для автотестов реальный Google-токен получить нельзя, поэтому используется **стаб** `GoogleIdTokenVerifier` (тестовый профиль/бин), возвращающий заранее заданный verified-email. Способ получения тестового токена явно указан в предусловиях соответствующих кейсов (см. Фичу 8).
6. Дождаться готовности `backend` (health/readiness) и `frontend` перед запуском кейсов.

### Предусловие-хелпер: активный пользователь с известным статусом

Многие сценарии требуют пользователя в конкретном статусе (`ACTIVE` / `INVITED` / `DEACTIVATED`). Стандартный флоу подготовки:

1. Логин под сидовым ADMIN (`POST /api/auth/login`) → access-токен ADMIN.
2. `POST /api/users` (ADMIN) — создать пользователя, статус `INVITED`. Email — из генератора (см. «Стратегия повторяемости»).
3. Получить invite-токен: через тестовый хелпер БД или перехват почты (mailhog). Обозначается как `<inviteToken>`.
4. Для получения `ACTIVE`: `POST /api/auth/set-password { token: <inviteToken>, password }` → пользователь становится `ACTIVE` и сразу получает JWT.
5. Для получения `DEACTIVATED`: ADMIN деактивирует пользователя (`PATCH`/`DELETE /api/users/{id}` — в зависимости от контракта FOR-02).

В шагах ниже это предусловие обозначено как «подготовлен пользователь `{email}` в статусе `X`».

## Стратегия повторяемости

**Комбинированная — генератор + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp или uuid). Все создаваемые пользователи получают уникальный email вида `test+{run-id}+{seq}@example.com` (например `test+20240517T131500+1@example.com`). Это гарантирует, что повторный прогон не сталкивается с уже существующими записями.
- **Teardown (обязательный шаг в конце каждого набора):**
  - разлогинить выданные refresh-токены (`POST /api/auth/logout { refreshToken }`);
  - деактивировать/удалить созданных на прогон пользователей (ADMIN);
  - в UI-браузере очистить `localStorage` (`foremen-access-token`, `foremen-refresh-token`, `foremen-locale`) и `sessionStorage` (`foremen-return-to`), либо использовать свежий инкогнито-контекст на каждый кейс.
- Сидовый ADMIN и seed-данные **не изменяются** необратимо — все манипуляции идут над созданными на прогон пользователями. Это делает набор запускаемым многократно без ручной чистки БД.
- Для UI-кейсов, где нужен «чистый» стейт браузера, предпочтителен свежий browser-context/incognito на каждый TC — это автоматически изолирует `localStorage`/`sessionStorage`.

# Часть A. UI-сценарии (браузерный движок)

Все UI-кейсы стартуют с чистого browser-context (пустые `localStorage`/`sessionStorage`), если в предусловиях не сказано иное. Базовый URL — `http://localhost:3000`.

## Фича 1. Вход сотрудника по паролю (LoginPage)

_Покрывает Requirements 5.4, 12.3._

Стратегия повторяемости: генератор email + чистый browser-context на кейс; teardown — logout + деактивация созданного пользователя.

### TC-UI-LOGIN-01 — Успешный вход по паролю → редирект на `/`

**Предусловия:** подготовлен пользователь `test+{run-id}+1@example.com` в статусе `ACTIVE` с известным паролем; browser-context чистый.

**Шаги:**

**Предусловия:** browser-context чистый; локаль `ru`.

**Шаги:**

**Ожидаемый результат:** форма показывает серверно-локализованное сообщение; редиректа нет.

2. В адресной строке перейти на `/login`.
3. Проверить, что приложение немедленно редиректит с `/login` на `/` (или на Return_Location, если она была).

**Ожидаемый результат:** пользователь не задерживается на `/login`.

## Фича 3. OTP-вход клиента (OtpLoginPage)

_Покрывает Requirements 7.2, 7.7, 7.11._

Стратегия повторяемости: генератор email клиента + чистый browser-context; teardown — logout. Код OTP берётся из тестового хелпера БД / mailhog.

### TC-UI-OTP-01 — Полный флоу: email → сегментированный код → автосабмит → аутентификация

**Предусловия:** подготовлен CLIENT-пользователь `test+{run-id}+3@example.com`, имеющий право на OTP-вход.

**Шаги:**
1. Открыть `http://localhost:3000/auth/otp` → шаг 1: поле email + кнопка «запросить код».
2. Ввести email, нажать «запросить код» → уходит `POST /api/auth/otp/request { email }`, ответ `200`; приложение переходит на шаг ввода кода (независимо от того, eligible ли email — anti-enumeration).
3. На шаге кода проверить: сегментированный ввод из ровно 6 боксов, замаскированный email-эхо, контрол verify, контрол resend с таймером cooldown.
4. Получить реальный код из хелпера/mailhog. Ввести первую цифру в первый бокс → фокус перешёл на второй бокс.
5. Довести ввод до 6 цифр → при заполнении всех 6 боксов происходит **автоматический** сабмит (без нажатия verify): уходит `POST /api/auth/otp/verify { email, code }`, ответ `200`.
6. Проверить автологин и навигацию на `/`.

**Ожидаемый результат:** после шага 6 пользователь аутентифицирован на `/`; автосабмит сработал один раз.

### TC-UI-OTP-02 — Вставка 6 цифр распределяется по боксам

**Предусловия:** дошли до шага кода (как в TC-UI-OTP-01, шаги 1–2).

**Шаги:**
1. Скопировать в буфер 6-значную строку (например `123456`).
2. Вставить (paste) в любой бокс кода.
3. Проверить, что цифры распределились по всем 6 боксам по порядку и (при валидном коде) сработал автосабмит.

**Ожидаемый результат:** 6 боксов заполнены `1`,`2`,`3`,`4`,`5`,`6` соответственно.

### TC-UI-OTP-03 — Backspace в пустом боксе возвращает фокус; resend cooldown

**Предусловия:** дошли до шага кода.

**Шаги:**
1. Ввести 2 цифры (фокус в 3-м боксе). Нажать Backspace в пустом 3-м боксе → фокус перешёл на 2-й бокс.
2. Проверить, что контрол resend задизейблен и показывает обратный отсчёт.
3. Дождаться окончания cooldown → контрол resend снова активен.
4. Нажать resend → уходит повторный `POST /api/auth/otp/request` для того же email, cooldown перезапускается.

**Ожидаемый результат:** фокус-логика и cooldown работают согласно ACs 7.5, 7.17–7.19.

### TC-UI-OTP-04 — Неверный код → inline-ошибка, остаёмся на шаге кода (400)

**Предусловия:** дошли до шага кода.

**Шаги:**
1. Ввести 6 неверных цифр → автосабмит `POST /api/auth/otp/verify`, ответ `400`.
2. Проверить, что под полем кода показано локализованное сообщение, пользователь остаётся на шаге кода.

**Ожидаемый результат:** inline-ошибка отображена; перехода нет.

## Фича 5. Вход через Google (UI-ветки)

_Покрывает Requirements 14.4, 14.5, 14.8, 14.9._

> Примечание: в UI-прогоне ветвление зависит от ответа `POST /api/auth/google`. Для детерминизма используется **стаб** `GoogleIdTokenVerifier` (тестовый бин), сопоставляющий фиксированный тестовый credential с нужным verified-email; либо мокается ответ бекенда на `POST /api/auth/google`. Способ подмены токена указан в предусловиях.

Стратегия повторяемости: генератор email + чистый browser-context; teardown — logout + деактивация.

### TC-UI-GOOGLE-01 — ACTIVE-аккаунт → AUTHENTICATED → редирект на `/`

**Предусловия:** подготовлен `ACTIVE`-пользователь с email, привязанным к тестовому Google-credential.

**Шаги:**
1. Открыть `/login`, нажать «Войти через Google».
2. Во время обмена контрол задизейблен + спиннер; уходит `POST /api/auth/google { idToken }`, ответ `200 { status: "AUTHENTICATED", tokens }`.
3. Проверить, что токены сохранены, выполнена гидратация и навигация на `/` (или Return_Location).

**Ожидаемый результат:** пользователь аутентифицирован на `/`.

### TC-UI-GOOGLE-02 — INVITED-аккаунт → ACTIVATION_REQUIRED → редирект на set-password (без токенов)

**Предусловия:** подготовлен `INVITED`-пользователь, привязанный к тестовому Google-credential; предварительно захвачена Return_Location deep-link (опционально для проверки 12.8).

**Шаги:**
1. (Опц.) Открыть защищённый deep-link без сессии → редирект на `/login`, Return_Location сохранена.
2. На `/login` нажать «Войти через Google» → `POST /api/auth/google` возвращает `200 { status: "ACTIVATION_REQUIRED", setPasswordToken }`.
3. Проверить, что приложение **не** сохранило токены и **не** считает пользователя аутентифицированным, и навигировало на `/auth/set-password?token=<setPasswordToken>`.
4. Установить пароль → автологин; проверить, что навигация ведёт на ранее сохранённую Return_Location (или `/`).

**Ожидаемый результат:** ветка ACTIVATION_REQUIRED не считается ошибкой; токены не сохранены до set-password; Return_Location переживает второй редирект.

### TC-UI-GOOGLE-03 — Нет привязанного аккаунта → distinct contact-admin сообщение (403)

**Предусловия:** тестовый Google-credential с email, которого нет среди пользователей.

**Шаги:**
1. На `/login` нажать «Войти через Google» → `POST /api/auth/google` возвращает `403 error.auth.google.no.account`.

### TC-UI-GOOGLE-04 — DEACTIVATED-аккаунт → сообщение деактивации, без токена (403)

# Часть B. API-сценарии (Docker-стек, `http://localhost:8080`)

Стратегия повторяемости для всей части B: **генератор email `test+{run-id}+{seq}@example.com` + teardown** (logout выданных refresh-токенов, деактивация созданных пользователей). Сидовый ADMIN не изменяется.

## Фича 6. `GET /api/auth/me` — сильный ETag и условные запросы

_Покрывает Requirements 13.1, 13.2, 13.3._

### TC-API-ME-01 — `/me` возвращает сильный ETag; повтор с `If-None-Match` → `304`

**Предусловия:** подготовлен `ACTIVE`-пользователь `test+{run-id}+4@example.com`; получен его `<accessToken>`.

**Шаги:**
1. `GET /api/auth/me` с `Authorization: Bearer <accessToken>` → **200**; тело — `CurrentUserResponse { id, name, email, roleCode, permissions }`; в заголовках присутствует сильный `ETag` (в кавычках) и `Cache-Control: no-cache, private`. Сохранить значение как `<etag>`.
2. `GET /api/auth/me` с `Authorization: Bearer <accessToken>` и `If-None-Match: <etag>` → **304 Not Modified**, тело пустое.

**Ожидаемый результат:** шаг 1 — 200 + ETag; шаг 2 — 304 с пустым телом.

### TC-API-ME-02 — ETag меняется после изменения роли/прав пользователя

**Предусловия:** ADMIN залогинен; `ACTIVE`-пользователь `test+{run-id}+4@example.com` с известной ролью; получен `<etag>` из TC-API-ME-01.

**Шаги:**
1. `GET /api/auth/me` (пользователь) → 200; сохранить `<etagBefore>`.
2. ADMIN изменяет права роли пользователя (`PUT /api/roles/{id}/permissions`) или меняет его роль → 200.
3. `GET /api/auth/me` (пользователь) с `If-None-Match: <etagBefore>` → **200** (не 304), новый `ETag` `<etagAfter>` ≠ `<etagBefore>`; тело отражает изменённые permissions.
4. (Контроль неизменности) Повторный `GET /api/auth/me` с `If-None-Match: <etagAfter>` без дальнейших изменений → **304**.

**Ожидаемый результат:** ETag изменился после изменения прав (шаг 3 = 200), и стабилен при отсутствии изменений (шаг 4 = 304).

### TC-API-ME-03 — `/me` без/с невалидным токеном → `401`

**Предусловия:** нет.

**Шаги:**
1. `GET /api/auth/me` без заголовка `Authorization` → **401**.
2. `GET /api/auth/me` с `Authorization: Bearer <мусор>` → **401**.

**Ожидаемый результат:** оба запроса — 401.

## Фича 7. `POST /api/auth/google` — обмен Google ID-токена

_Покрывает Requirements 14.4, 14.5, 14.8, 14.9._

> **Как получить тестовый Google-токен:** реальный ID-токен Google в автотестах недоступен. В docker/тестовом окружении бекенд использует **стаб** `GoogleIdTokenVerifier`, который для заранее заданного тестового значения `idToken` (например `"test-google-token-{verifiedEmail}"`) возвращает соответствующий verified-email без обращения к Google. Все кейсы ниже подставляют такой стаб-токен. Если стаб не настроен — кейсы помечаются как «пропущено» с указанием причины.

### TC-API-GOOGLE-01 — ACTIVE-аккаунт → `200 AUTHENTICATED` с токенами

**Предусловия:** подготовлен `ACTIVE`-пользователь `test+{run-id}+5@example.com`; стаб-токен маппится на этот email.

**Шаги:**
1. `POST /api/auth/google { idToken: "<stub for test+{run-id}+5@example.com>" }` → **200**; тело `{ status: "AUTHENTICATED", tokens: { accessToken, refreshToken, expiresIn }, setPasswordToken: null }`.
2. Проверить, что `tokens.accessToken`/`refreshToken` непустые.
3. (Проверка сессии) `GET /api/auth/me` с полученным `accessToken` → 200.

**Ожидаемый результат:** статус AUTHENTICATED, токены присутствуют, setPasswordToken отсутствует.

### TC-API-GOOGLE-02 — INVITED-аккаунт → `200 ACTIVATION_REQUIRED`, токен принимается set-password

**Предусловия:** подготовлен `INVITED`-пользователь `test+{run-id}+6@example.com`; стаб-токен маппится на этот email.

**Шаги:**
1. `POST /api/auth/google { idToken: "<stub for test+{run-id}+6@example.com>" }` → **200**; тело `{ status: "ACTIVATION_REQUIRED", tokens: null, setPasswordToken: "<spt>" }` (непустой `setPasswordToken`, токены отсутствуют).
2. `POST /api/auth/set-password { token: "<spt>", password: <valid> }` → **200** TokenResponse (токен из Google-моста принят и активировал аккаунт).
3. (Проверка) повторный `POST /api/auth/set-password` с тем же `<spt>` → **400** (токен уже использован).

**Ожидаемый результат:** ACTIVATION_REQUIRED без токенов; `setPasswordToken` консюмится существующим set-password эндпоинтом.

### TC-API-GOOGLE-03 — Нет привязанного аккаунта → `403 error.auth.google.no.account`

**Предусловия:** стаб-токен маппится на email, которого нет среди пользователей.

**Шаги:**
1. `POST /api/auth/google { idToken: "<stub for unknown+{run-id}@example.com>" }` → **403**; тело ForemenApiException с кодом/сообщением `error.auth.google.no.account`.
2. Проверить отсутствие токенов в теле.

**Ожидаемый результат:** 403 с distinct no-account кодом, без сессии.

### TC-API-GOOGLE-04 — DEACTIVATED-аккаунт → `403 error.auth.account.deactivated`

**Предусловия:** подготовлен `DEACTIVATED`-пользователь `test+{run-id}+7@example.com`; стаб-токен маппится на этот email.

**Шаги:**
1. `POST /api/auth/google { idToken: "<stub for test+{run-id}+7@example.com>" }` → **403**; тело с кодом `error.auth.account.deactivated`, без токенов.

**Ожидаемый результат:** 403 деактивации, без сессии.

### TC-API-GOOGLE-05 — Невалидный Google-токен → `401 error.auth.google.token.invalid`

**Предусловия:** стаб настроен отвергать неизвестные/битые токены.

**Шаги:**
1. `POST /api/auth/google { idToken: "garbage" }` → **401**; тело с кодом `error.auth.google.token.invalid`.

**Ожидаемый результат:** 401 при непроверяемом токене.

### TC-API-GOOGLE-06 — Эндпоинт публично доступен (не security-401)

**Предусловия:** валидный стаб-токен для существующего `ACTIVE`-пользователя.

**Шаги:**
1. `POST /api/auth/google { idToken: "<stub>" }` **без** `Authorization` → запрос доходит до контроллера и возвращает бизнес-ответ (`200 AUTHENTICATED`), а не security-`401` от фильтра.

**Ожидаемый результат:** публичная доступность `/api/auth/**` подтверждена (200, не 401 от security-слоя).

## Фича 8. Смежные auth-контракты, потребляемые фронтендом

_Покрывает Requirements 3.5 (refresh-провал), 4.1 (гидратация через `/me`), 8.1 (logout)._

### TC-API-AUX-01 — refresh-ротация и провал невалидного refresh (для авто-refresh на 401)

**Предусловия:** подготовлен `ACTIVE`-пользователь; получена пара токенов через `POST /api/auth/login`.

**Шаги:**
1. `POST /api/auth/refresh { refreshToken: <r1> }` → **200** новая пара (`<a2>`, `<r2>`), `<r2>` ≠ `<r1>` (ротация).
2. Повторный `POST /api/auth/refresh { refreshToken: <r1> }` (старый) → **401** (старый refresh отозван).
3. `POST /api/auth/refresh { refreshToken: "garbage" }` → **401**.

**Ожидаемый результат:** ротация подтверждена; невалидный/отозванный refresh даёт 401 (это ветка, на которой фронтенд форсирует logout и захватывает Return_Location — Req 3.5).

### TC-API-AUX-02 — logout идемпотентен (для UI-logout)

**Предусловия:** получена пара токенов.

**Шаги:**
1. `POST /api/auth/logout { refreshToken: <r> }` → **204**.
2. Повторный `POST /api/auth/logout { refreshToken: <r> }` → **204** (идемпотентно).
3. `POST /api/auth/refresh { refreshToken: <r> }` → **401** (refresh отозван).

**Ожидаемый результат:** logout возвращает 204 повторно; отозванный refresh не работает.

# Регрессия

Регрессионный прогон запускается перед релизом FOR-03-06 и после изменений в auth-слое (FOR-03-01/02/05, security-конфиг, CORS). Проверяются критичные сквозные пути и ранее закрытые риски.

### TC-REG-01 — Сквозной путь сотрудника (password login → защищённый маршрут → reload → logout)

**Шаги:**
1. Password-логин (`ACTIVE`) → `/`.
2. Перезагрузить страницу на защищённом маршруте с валидным сохранённым токеном → остаёмся аутентифицированными (гидратация через `/me`, возможен `304`).
3. Logout → `/login`, токены очищены.

**Ожидаемый результат:** полный цикл входа/сессии/выхода стабилен.

### TC-REG-02 — Deep-link round-trip после истечения access-токена

**Шаги:**
1. Аутентифицированный пользователь на защищённом маршруте; истекает access-токен (или подставляется просроченный).
2. Действие, вызывающее `401` → Api_Client делает один авто-refresh и ретрай; при успехе запрос проходит, пользователь остаётся на месте.
3. Если refresh невалиден (симуляция отозванного refresh) → форс-logout, захват Return_Location, редирект на `/login`; после повторного входа — возврат на исходный маршрут.

**Ожидаемый результат:** авто-refresh не зацикливается; при провале refresh — корректный round-trip через `/login`.

### TC-REG-03 — CORS: заголовок `ETag` доступен клиенту

**Шаги:**
1. `GET /api/auth/me` cross-origin (с фронтенда `:3000` на бекенд `:8080`) → в ответе `Access-Control-Expose-Headers` содержит `ETag`, и браузер может прочитать `ETag`.

**Ожидаемый результат:** клиент читает `ETag` (иначе условные запросы `If-None-Match` невозможны).

### TC-REG-04 — Локализация серверных ошибок по `Accept-Language`

**Шаги:**
1. `POST /api/auth/login` с неверным паролем и `Accept-Language: ru` → сообщение об ошибке на русском.
2. То же с `Accept-Language: pl` → сообщение на польском.

**Ожидаемый результат:** тело ошибки локализовано согласно `Accept-Language`.
