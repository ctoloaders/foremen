# Тест-кейсы: Журнал сессий (Session Log)

Документ описывает тест-кейсы для фичи «Журнал сессий» Telegram-бота сбора чеков (Requirement 11). Тексты — на русском, спека — на английском (см. requirements.md / design.md).

## Тип спеки и формат прогона

Это **бэкенд/API-спека без браузерных экранов**. Проверяемая система — Telegram-бот (Google Cloud Function / локальный polling-режим) + Google Sheets (лист `session_log` в workbook `WORKERS_SPREADSHEET_ID`).

- Каждый шаг сценария — это либо действие в диалоге с ботом (эмуляция сообщения/нажатия кнопки через Telegram Bot API или тестовый драйвер бота в polling-режиме), либо чтение состояния Google Sheets через Sheets API v4.
- **Скриншоты не требуются.** Результат прогона — MD-репорт с таблицами (шаг → действие/запрос → ожидание → факт → статус).
- Проверки строятся на чтении итоговых строк листа `session_log` (колонки A–Q) и сравнении со сметой проекта.

## Окружение и предусловия (общие для всех кейсов)

1. Поднят бот с включённым OCR (`OCR_ENABLED=true`, задан `GEMINI_API_KEY`) — если проверяется OCR-путь. Для ручного пути используется `OCR_ENABLED=false` (отдельная конфигурация прогона).
2. Тестовый workbook (`WORKERS_SPREADSHEET_ID`) содержит листы `workers`, `project_access`, `bot_state`, `session_log`. Лист `session_log` имеет заголовки A–Q согласно design.md (addendum).
3. В `workers` заведён тестовый работник с ролью (например `foreman`) и известным `telegram_id` тестового драйвера; в `project_access` он привязан к тестовому проекту, у проекта заполнены Drive/Sheets URL (тестовая папка и тестовая смета).
4. Сервисный аккаунт имеет доступ к workbook, тестовой Drive-папке и тестовой смете.
5. Тестовый драйвер умеет: отправлять `/start`, `/cancel`, текст, фото, нажимать inline-кнопки, и читать `session_log` через Sheets API.

## Стратегия повторяемости

**Выбранная стратегия: генератор данных (run-id) + отсутствие ручной чистки БД.**

- В начале каждого прогона генерируется `run-id` = timestamp/uuid (например `20260904-123340-a1b2`).
- Все создаваемые данные помечаются `run-id`: описание чека вида `TEST {run-id}`, магазин `Store {run-id}`, сумма из диапазона, отведённого под тесты.
- Лист `session_log` — **append-only** (строки не удаляются штатным потоком), поэтому ручная чистка между прогонами НЕ требуется: каждый прогон добавляет новые строки со своим `run-id`, а проверки фильтруют строки по `run-id`/`session_id` текущего прогона.
- `session_id` каждого сценария сохраняется тестовым драйвером в момент старта (из строки `bot_state`/`session_log`) и используется как ключ для последующих ассертов.
- Побочные артефакты (файлы в тестовой Drive-папке, строки тестовой сметы) не мешают повторности, так как проверки идут по `run-id`. Опциональный teardown Drive-папки — вне области тест-кейсов журнала.

## Группа 1. Успешные сессии

### TC-SL-01. Успешная сессия (ручной путь, одно фото): in_progress → success

**Предусловия:** `OCR_ENABLED=false`; работник авторизован и привязан к проекту.

**Шаги:**
1. Отправить `/start`. **Ожидание:** бот показывает кнопки проектов; в `session_log` появляется новая строка: `status=in_progress`, заполнены `session_id` (UUID), `telegram_id`, `worker_name`, `role`, `started_at≈now`, `last_activity_at≈now`, `step` — начальный. Сохранить `session_id`.
2. Нажать кнопку тестового проекта. **Ожидание:** строка обновлена: `project_name`, `project_drive_url`, `project_sheets_url` заполнены; `step=await_photo`; `last_activity_at` обновлён (позже, чем в шаге 1).
3. Отправить фото чека. **Ожидание:** `photo_file_ids` = JSON-массив с 1 элементом; `step=await_sum`; `last_activity_at` обновлён.
4. Отправить сумму `123.45`. **Ожидание:** `sum=123.45`; `step` перешёл к описанию; `last_activity_at` обновлён.
5. Отправить описание `TEST {run-id}`. **Ожидание:** `description=TEST {run-id}`; `step=await_store`.
6. Отправить магазин `Store {run-id}`. **Ожидание:** бот отвечает «⏳ Сохраняю...».
7. Дождаться подтверждения. **Ожидание:** бот отвечает «✅ Записал: ...»; строка `session_log` переходит в `status=success`, `photo_links` = JSON-массив с 1 ссылкой, `sum=123.45`, `error_trace` пуст, `last_activity_at≈now`.

**Ожидаемый результат:** ровно одна строка журнала для этого `session_id`, финальный `status=success`; `photo_links` совпадает со ссылкой, записанной в тестовую смету (та же ссылка переиспользована, повторной загрузки нет).

### TC-SL-02. Успешная сессия (OCR-путь, мультистраница): массивы file_ids и links

**Предусловия:** `OCR_ENABLED=true`, задан `GEMINI_API_KEY`.

**Шаги:**
1. `/start` → выбрать проект. **Ожидание:** строка `in_progress`, сохранить `session_id`.
2. Отправить страницу 1 (фото). **Ожидание:** `photo_file_ids` = 1 элемент; `step=await_more_pages`.
3. Нажать «📄 Ещё 1 страница», отправить страницу 2. **Ожидание:** `photo_file_ids` = 2 элемента.
4. Нажать «✅ Готово». **Ожидание:** идёт OCR/Gemini; `step` проходит `processing_ocr`; после распознавания `description`/`store_name` заполнены из OCR; `step=await_sum`.
5. Ввести сумму, совпадающую с распознанной (без mismatch). **Ожидание:** сохранение стартует.
6. Дождаться «✅ Записал: ...». **Ожидание:** `status=success`; `photo_links` = JSON-массив из 2 ссылок; `sum` = введённое значение; `error_trace` пуст.

**Ожидаемый результат:** мультистраничный чек отражён массивами из 2 элементов в `photo_file_ids` и `photo_links`; `photo_links` = набор ссылок, записанный в смету (`formatPhotoLinks`).

### TC-SL-03. OCR mismatch подтверждён сотрудником — success, та же сессия

**Предусловия:** `OCR_ENABLED=true`; тестовое фото, где распознанная сумма отличается от вводимой.

**Шаги:**
1. `/start` → проект → фото → «✅ Готово». **Ожидание:** `step=await_sum`, сохранить `session_id`.
2. Ввести сумму, отличную от распознанной. **Ожидание:** бот просит подтверждение (кнопки «Да, сохранить» / «Ввести заново»); строка обновляется (`step=confirm_sum`), `session_id` НЕ меняется.
3. Нажать «✅ Да, сохранить». **Ожидание:** сохранение; `status=success`; в смете `sumNote` отражает подтверждение (проверка сметы), в журнале `sum` = введённое значение; `session_id` тот же, что в шаге 1.

**Ожидаемый результат:** подтверждение mismatch не создаёт новую сессию; итог `success`.

## Группа 2. Отменённые сессии

### TC-SL-04. Отмена командой /cancel → cancelled

**Шаги:**
1. `/start` → выбрать проект → отправить фото. **Ожидание:** `status=in_progress`, сохранить `session_id`.
2. Отправить `/cancel`. **Ожидание:** бот отвечает «Отменено...»; строка `session_log` переходит в `status=cancelled`, `last_activity_at≈now`; строка НЕ удалена.

**Ожидаемый результат:** отменённая сессия остаётся в журнале со `status=cancelled`.

### TC-SL-05. Отмена кнопкой «Отмена» (callback) → cancelled

**Шаги:**
1. `/start` → проект → фото → на шаге ввода суммы нажать inline «❌ Отмена». **Ожидание:** `status=cancelled`; строка сохранена.

**Ожидаемый результат:** callback-отмена финализирует сессию как `cancelled` (аналогично /cancel).

### TC-SL-06. Повторный /start в середине потока → прежняя сессия остаётся in_progress (abandoned), стартует новая

**Шаги:**
1. `/start` → проект → фото. **Ожидание:** сессия A: `in_progress`, сохранить `session_id=A`.
2. Отправить `/start` заново (не завершив A). **Ожидание:** создаётся новая строка `session_id=B` со `status=in_progress`; строка A остаётся `status=in_progress` (не тронута, считается брошенной).
3. Завершить сессию B успешно. **Ожидание:** B → `success`; A по-прежнему `in_progress`.

**Ожидаемый результат:** одновременный/последовательный повторный старт не портит прежнюю запись; abandoned-сессии видны как «зависшие» `in_progress`.

## Группа 3. Сбойные сессии и трейс ошибки

### TC-SL-07. Сбой записи в смету (Sheets) после ретраев → failed + error_trace

**Предусловия:** смоделировать недоступность целевой сметы (например, невалидный `project_sheets_url` для тестового проекта, либо у сервисного аккаунта нет доступа к смете).

**Шаги:**
1. Пройти полный успешный ввод до этапа сохранения (фото/сумма/описание/магазин). **Ожидание:** сохранить `session_id`.
2. Дождаться завершения сохранения. **Ожидание:** бот отвечает «❌ Ошибка записи в таблицу...»; строка `session_log` переходит в `status=failed`; колонка `error_trace` НЕ пуста (message + stack).

**Ожидаемый результат:** сбойная попытка зафиксирована как `failed` с непустым `error_trace`.

### TC-SL-08. Сбой загрузки в Drive после ретраев → failed + error_trace

**Предусловия:** смоделировать недоступность Drive-папки (невалидный `project_drive_url`/нет доступа).

**Шаги:**
1. Пройти ввод до сохранения. **Ожидание:** сохранить `session_id`.
2. Дождаться результата. **Ожидание:** бот отвечает «❌ Ошибка загрузки фото...»; `status=failed`; `error_trace` непуст; `photo_links` пуст (загрузка не удалась).

**Ожидаемый результат:** сбой Drive зафиксирован как `failed`, ссылки не проставлены.

### TC-SL-09. Санитизация error_trace — секреты отсутствуют

**Предусловия:** любой из сбойных сценариев (TC-SL-07/08), при котором в стек/сообщение потенциально могли попасть чувствительные значения.

**Шаги:**
1. Спровоцировать сбой (см. TC-SL-07). **Ожидание:** строка `failed`.
2. Прочитать `error_trace`. **Ожидание:** значение НЕ содержит: токен бота, приватный ключ сервисного аккаунта, `GEMINI_API_KEY`, webhook-секреты, query-строки URL с секретами (все заменены на `***REDACTED***`); при этом сообщение об ошибке и кадры стека присутствуют.

**Ожидаемый результат:** трейс информативен, но без секретов (Requirement 11.10 / 9.6).

### TC-SL-10. Сбой самого журнала не ломает пользовательский поток (best-effort)

**Предусловия:** смоделировать недоступность листа `session_log` (например, временно переименовать лист / отозвать доступ) при работающей смете и Drive.

**Шаги:**
1. Пройти полный успешный ввод чека. **Ожидание:** бот отвечает «✅ Записал: ...» (чек реально попал в смету и Drive), несмотря на невозможность записи в журнал; в структурных логах присутствует `session-log write failed` (ERROR).

**Ожидаемый результат:** запись в смету имеет приоритет; отказ журнала не прерывает и не ломает диалог.

## Группа 4. Разделение с bot_state

### TC-SL-11. session_log не чистится при успехе/отмене, в отличие от bot_state

**Шаги:**
1. Завершить сессию успешно (TC-SL-01). **Ожидание:** в `bot_state` строка по `telegram_id` очищена (пустая) — эфемерное состояние; в `session_log` строка `status=success` сохранена.
2. Отменить другую сессию (TC-SL-04). **Ожидание:** `bot_state` очищен; `session_log` содержит `status=cancelled`.

**Ожидаемый результат:** `bot_state` эфемерен, `session_log` персистентен (variant B).

### TC-SL-12. Корреляция session_id между bot_state и session_log

**Шаги:**
1. `/start` → проект → фото. **Ожидание:** `session_id` в новой колонке `bot_state` (col N) совпадает с `session_id` в строке `session_log`.

**Ожидаемый результат:** один и тот же `session_id` связывает эфемерное состояние и журнал в рамках активной сессии.

## Регрессия

Раздел перепроверяет ранее закрытые/критичные сквозные пути, которые могли быть затронуты внедрением журналирования (журнал добавляет вызовы в start/photo/text/callback/cancel).

- **REG-01.** Полный happy-path сохранения чека (ручной путь) продолжает работать: строка в смете + файл в Drive создаются, подтверждение «✅ Записал» отправляется. (Перепроверка Requirement 4 после добавления вызовов журнала в `text.ts`.)
- **REG-02.** OCR-путь happy-path (мультистраница, совпадающая сумма) сохраняет чек и пишет строку сметы корректно. (Перепроверка после добавления вызовов в `callback.ts`.)
- **REG-03.** `/cancel` и кнопка «Отмена» очищают `bot_state` (эфемерное состояние) как прежде, дополнительно финализируя журнал. (Перепроверка Requirement 3.8.)
- **REG-04.** Расширение `bot_state` до колонки N (session_id) не ломает чтение/запись состояния и авто-очистку stale >24ч. (Перепроверка `store.ts` после смены диапазона `A:M`→`A:N`.)
- **REG-05.** Обратная совместимость сериализации фото: одно фото сохраняется как одноэлементный массив, старый формат одиночного `file_id` читается корректно.

Обоснование объёма: регрессия сфокусирована на путях, куда внедрены вызовы журнала и где изменён диапазон `bot_state`; более широкий регресс не требуется, так как остальные компоненты (auth, выбор проекта, Apps Script webhook) журналом не затрагиваются.
