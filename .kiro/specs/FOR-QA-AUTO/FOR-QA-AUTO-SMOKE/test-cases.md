# Тест-кейсы: FOR-QA-AUTO-SMOKE (смоук-набор E2E, Java BDD + Playwright)

## Назначение и характер спеки

Спека **UI-facing**: смоук-набор проверяет поведение, видимое в браузере, по верхнеуровневым
требованиям уже готовых спек FOR-01 … FOR-04. Тест-кейсы предназначены для «живого тестировщика», но
по факту исполняются **браузерным движком** (Playwright-for-Java, Chromium headless) в рамках
BDD-фреймворка `foremen-qa-auto`. Каждый шаг — действие в браузере (переход, ввод, клик, ожидание,
проверка URL/DOM). API используется только для **setup/teardown** и для проверки контрактов,
невидимых в UI, но от которых зависит браузерный сценарий (например, наличие токенов в
`localStorage`).

**Результат прогона — два артефакта:**

1. **Клиентский демо-отчёт (HTML со скриншотами на каждый шаг)** — основной артефакт для
   представителя заказчика: читается как задокументированное демо, сгруппирован по спекам
   (`@FOR-0N`) и фичам; для каждого сценария — пронумерованные шаги на простом языке с ожиданием,
   фактом, статусом и **скриншотом на каждом шаге**. Для CRUD-сценария (например роли) видны все шаги:
   создание → подтверждение, что сущность создана (со скриншотом) → чистка созданных ресурсов.
2. **MD-репорты с таблицами** (шаг → действие → ожидание → факт → статус) — для стандарта QA/CI, плюс
   стандартные Cucumber HTML/JSON.

Скриншоты снимаются на **каждом значимом шаге UI** (не только при падении).

> Этот файл описывает смоук-сценарии. Глубокие сценарии по каждой спеке начиная с FOR-05 живут в
> отдельных дочерних спеках `FOR-QA-AUTO-0N-*`.

## Запуск окружения

1. В корне репозитория: `docker compose up` — поднимает `postgres` (:5432), `liquibase` (миграции),
   `backend` (:8080, профиль `docker`), `frontend` (:3000).
2. Базовый URL UI-сценариев: `http://localhost:3000`. Базовый URL API (setup/teardown):
   `http://localhost:8080`, auth-эндпоинты — под `/api/auth`.
3. Первый ADMIN поднимается через переменные окружения бекенда: `FOREMEN_ADMIN_CREATE=true`,
   `FOREMEN_ADMIN_EMAIL` (в docker-compose: `cto+1@loaders.dev`), `FOREMEN_ADMIN_PASSWORD` (в
   docker-compose: `alejano123`). В автоматизации подставляются фактические значения из окружения
   прогона.
4. Перед стартом кейсов фреймворк ждёт готовности бекенда (actuator health) и доступности фронтенда.
5. Запуск смоука: `./gradlew :foremen-qa-auto:smokeTest` (выбор по тегу `@smoke`). Срез по спеке:
   `-DQA_TAGS="@smoke and @FOR-03"`.

## Стратегия повторяемости

**Комбинированная — генератор уникальных данных + teardown:**

- **Генератор:** на каждый прогон формируется `run-id` (timestamp/uuid). Создаваемые сущности
  получают уникальные ключи: пользователи `test+{run-id}+{seq}@example.com`; строки справочников
  `code=qa{run-id}{seq}`; проекты `QA Project {run-id}`; несистемные роли `TESTROLE_{run-id}_{seq}`.
- **Teardown (обязательный шаг):** созданные пользователи деактивируются (`PUT /api/users/{id}`
  `active=false`) и их refresh-токены разлогиниваются; созданные строки справочников/проекты
  удаляются через свои `DELETE /api/{resource}/{id}`; созданные несистемные роли удаляются. Каждый
  сценарий использует свежий incognito browser-context, поэтому `localStorage`/`sessionStorage`/куки
  не протекают между кейсами.
- **Сидовый ADMIN и seed-данные не изменяются** необратимо. Набор запускаем многократно без ручной
  чистки БД (проверяется двойным прогоном — см. регрессию).

## Переиспользуемое провижининг тестовых юзеров (прямая вставка в БД)

Единственный способ увидеть УИ под конкретной ролью — залогиниться ACTIVE-пользователем с известным
паролем. Фреймворк предоставляет **две переиспользуемые Gherkin-фичи** (шаги), реализованные только
внутри тестового кода (`TestUserFixture` + `TestUserSteps`); прогон идёт против **изолированной
тестовой БД**, поэтому пользователь **вставляется напрямую в БД по JDBC**, пароль хранится как
**bcrypt**-хеш:

- **Создать юзера в роли X** — генерирует уникальные email/пароль, резолвит `role_id` по
  `roles.code = X`, вставляет строку `users` со `status=ACTIVE`, `active=true`, `password_hash=bcrypt`.
  Логин/пароль/id запоминаются в `World`; юзер регистрируется на авто-teardown.
- **Удалить юзера в роли X и почистить ресурсы** — удаляет в порядке FK: `project_members`,
  `refresh_tokens`, `invite_tokens`, `otp_tokens` (по email), затем созданные за прогон строки
  справочников/проекты, затем сам `users`.

Роль параметризуема (ADMIN/MANAGER/FOREMAN/WORKER/FINANCIER/CLIENT/`TESTROLE_*`); для CLIENT пароль
тоже задаётся (для UI-логина). Эти два шага — базовые блоки, используемые в предусловиях остальных
фич.

**Ожидаемый результат:** ни юзера, ни его ресурсов не осталось; сидовые данные не тронуты. Шаг
идемпотентен (повтор — no-op).

**Шаги (для каждой роли из ADMIN/MANAGER/FOREMAN/WORKER/FINANCIER/CLIENT):** создать юзера в роли →
UI-логин → проверить, что оболочка отрисована и роль отражена → teardown.

**Ожидаемый результат:** для каждой роли (в т.ч. CLIENT с паролем) UI-логин успешен; teardown чистит
данные.

# Форматы отчётов прогона

## 1. Клиентский демо-отчёт (HTML со скриншотами)

Структура (генерируется в `qa-report/<run-id>/`):
- `index.html` — сводка прогона (окружение, run-id, дата; итоги по фичам/сценариям; навигация по
  спекам `@FOR-0N`).
- Страница на фичу — сценарии → пронумерованные шаги; каждый шаг: описание на простом языке,
  ожидание, факт, статус (зелёный/красный), скриншот (превью → клик для увеличения).

Пример «истории» CRUD-сценария ролей (как это читает заказчик, каждый шаг со скриншотом):

| # | Шаг (демо) | Ожидание | Скриншот |
|---|-----------|----------|----------|
