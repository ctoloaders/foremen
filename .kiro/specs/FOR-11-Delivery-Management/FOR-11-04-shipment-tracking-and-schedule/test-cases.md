# Тест-кейсы: FOR-11-04 — Отслеживание поставок и график

Спека содержит и API, и UI. Часть A — API-тесты против работающего Docker-стека, часть B — сценарии
браузерного движка. Результат прогона — MD-репорты с таблицами (шаг → запрос/действие → ожидание → факт →
статус), скриншоты не требуются. Реальные перевозчики **не вызываются**: везде используется тестовый
адаптер `STUB`.

## Окружение

- Стек: `docker compose up` в корне (postgres :5432, liquibase, backend :8080 профиль `docker`, frontend :3000).
- Первый ADMIN: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Auth-эндпоинты под `/api/auth`.
- Переменные для прогона (в `.env.local` / override):
  - `FOREMEN_PROCUREMENT_TRACKING_ENABLED=true`
  - `FOREMEN_TRACKING_STUB_ENABLED=true`
  - `FOREMEN_PROCUREMENT_TRACKING_CRON=0/20 * * * * *` (каждые 20 с, чтобы проверить планировщик; без дня недели)
  - `FOREMEN_PROCUREMENT_TRACKING_MIN_SHIPMENT_INTERVAL=10s` (иначе отправка не опрашивается чаще раза в 30 минут)
  - `FOREMEN_PROCUREMENT_DEADLINE_SWEEP_CRON=0/20 * * * * *`
  - реальные адаптеры перевозчиков выключены (по умолчанию `false`).
- Пользователи (создаются в Setup): ADMIN, BUYER, MANAGER (член проекта), FOREMAN (член проекта),
  FOREMAN-2 (член **другого** проекта), FINANCIER, CLIENT (член проекта).
- Поведение тестового адаптера `STUB` по префиксу номера:

| Префикс номера | Результат адаптера |
|----------------|--------------------|
| `STUBTRANSIT…` | `IN_TRANSIT`, ETA = сегодня + 2 |
| `STUBLATE…` | `IN_TRANSIT`, ETA = сегодня + 9 |
| `STUBDELIV…` | `DELIVERED` |
| `STUBFAIL…` | ошибка `TIMEOUT` |
| `STUBBLOCK…` | ошибка `BLOCKED` (пауза перевозчика) |

## Стратегия повторяемости (обязательно)

**Генератор данных + teardown.** На каждый прогон генерируется `run-id` (timestamp в миллисекундах).
Все сущности называются с суффиксом `-{run-id}`: проект `FOR1104-{run-id}`, e-mail пользователей
`for1104+{role}-{run-id}@example.com`, номера отслеживания `STUBTRANSIT{run-id}` и т.п. Teardown в конце
каждого набора: отмена созданных отправок (`POST /api/shipments/{id}/cancel`), отмена позиций, удаление /
деактивация созданных проектов и пользователей. Сценарии не зависят от состояния БД после прошлых прогонов.

## Набор данных прогона (Setup)

1. Логин ADMIN, создание пользователей всех ролей из раздела «Окружение» с e-mail по генератору.
2. Создание проекта `FOR1104-{run-id}` с датой старта = сегодня и проекта-«чужого» `FOR1104-OTHER-{run-id}`;
   добавление MANAGER, FOREMAN, CLIENT в первый проект, FOREMAN-2 — во второй.
3. Создание продавца и двух позиций `AGREED` (позиция P1 количество 10, позиция P2 количество 4) и одной
   позиции `CLIENT_OWN` (P3, количество 2) в первом проекте.
4. Через API FOR-11-02/03 довести P1 и P2 до `SUPPLIER_PAID`: принятие клиентом, проформа, оплата
   (ручная привязка платежа), внешний заказ `EO1` на P1 (6 шт.) и P2 (4 шт.), отправка на оплату,
   отметка «оплачен» финансистом. P3 перевести вручную в `IN_DELIVERY`.
5. Создание графика проекта с категорией работ `C1`, начинающейся на 5-й день (бары через
   `PUT /api/project-schedules/bars`), и привязка P1 к `C1` (`workCategoryId`).
6. Для P1 задать `orderByDate` = вчера (для A9), для P2 — `needByDate` = сегодня + 3.

# Часть A. API-тесты

Базовый URL: `http://localhost:8080`. Заголовок `Authorization: Bearer <token>` роли из шага.

## A1. Создание отправки

### TC-A1-01. Создание отправки перевозчиком (STUB), смена этапа позиций

- **Предусловия:** Setup. Роль BUYER.
- **Шаги:**
  1. `POST /api/shipments` `{projectId, externalOrderId: EO1, deliveryMethod: "CARRIER", carrierCode: "STUB", trackingNumber: "STUBTRANSIT{run-id}", lines:[{positionId:P1, quantity:4},{positionId:P2, quantity:4}]}`.
     → `201`, статус `CREATED`, `etaSource=MANUAL` не задан (ETA пусто), события: 1.
  2. `GET /api/purchase-positions/{P1}` и `{P2}` → статус `IN_DELIVERY`.
  3. Подождать до 40 с (планировщик/первый refresh) и `GET /api/shipments/{id}` → статус `IN_TRANSIT`,
     `etaDate` = сегодня + 2, `etaSource=TRACKING`, событие `TRACKING IN_TRANSIT`.
  4. `GET /api/purchase-positions/{P1}` → `plannedDeliveryDate` = сегодня + 2.
- **Ожидание:** этапы и даты как указано; `trackingPageUrl` не пуст или `null` для STUB без ошибок.

### TC-A1-02. Отправка магазина и телефонный контакт

- **Шаги:**
  1. `POST /api/shipments` метод `SHOP_DELIVERY`, `shopOrderLink` = `https://shop.example.com/o/1`,
     `driverPhone` = `+48 600 100 200`, линия P3 (1 шт.) → `201`.
  2. `POST` метод `PHONE_CONTACT` без `driverPhone` → `400 error.shipment.method.fieldsMissing`.
  3. `POST` метод `PHONE_CONTACT` с `driverPhone` и `etaDate` = сегодня + 1 → `201`, `etaSource=MANUAL`.
- **Ожидание:** поля чужого метода возвращаются `null`; P3 остаётся в `IN_DELIVERY`.

### TC-A1-03. Валидация линий и лимитов

- **Шаги:**
  1. Линия P1 с количеством 7 при уже отправленных 4 и заказанном 10 по `EO1` = 6 → `400 error.shipment.line.exceedsOrderLine`.
  2. Отправка без `externalOrderId`: P1 = 6 (4 + 6 = 10, равно лимиту заказанного) → `201`; затем ещё P1 = 1 (сумма 11 > 10) → `400 error.shipment.line.exceedsCap`.
  3. Дубль позиции в запросе → `400 error.shipment.line.duplicate`; пустые линии → `400 error.shipment.line.empty`.
  4. Позиция в `ORDERED` (не оплачена) → `400 error.shipment.position.notShippable`.
  5. Позиция из другого проекта → `400 error.shipment.project.mismatch`.
  6. Номер отслеживания `ab` → `400 error.shipment.trackingNumber.invalid`; `carrierCode: "XYZ"` → `400 error.shipment.carrier.unknown`.
  7. `shopOrderLink: "ftp://x"` → `400 error.shipment.link.invalid`.
- **Ожидание:** ни одна отправка не создана, этапы позиций не изменились.

## A2. Ручной ввод, ETA и статус

### TC-A2-01. Ручной ETA не перетирается перевозчиком

- **Шаги:**
  1. Для отправки TC-A1-01: `PUT /api/shipments/{id}` `{etaDate: сегодня+5, etaTimeFrom:"09:00", etaTimeTo:"12:00"}` → `200`, `etaSource=MANUAL`.
  2. `POST /api/shipments/{id}/refresh` (после паузы 60 с) → `200`, `etaDate` остаётся сегодня + 5.
  3. `POST /api/shipments/{id}/eta/revert` → `200`, `etaSource=TRACKING`, затем ETA = сегодня + 2.
- **Ожидание:** приоритет ручного ETA и возврат к данным перевозчика работают.

### TC-A2-02. Ручной статус и терминальные состояния

- **Шаги:**
  1. `PUT` статус `OUT_FOR_DELIVERY` → `statusSource=MANUAL`, событие `MANUAL`.
  2. `PUT` статус `DELIVERED` → `deliveredAt` проставлен; позиции остаются `IN_DELIVERY`.
  3. `PUT` любое поле кроме `note` → `409/400 error.shipment.terminal`; `note` меняется.
- **Ожидание:** `DELIVERED` не меняет этап позиции.

## A3. Отмена отправки

### TC-A3-01. Отмена и возврат этапа

- **Шаги:**
  1. Создать отправку только с P2 (4 шт.) → P2 `IN_DELIVERY`.
  2. `POST /api/shipments/{id}/cancel` → `200`, `status=CANCELLED`.
  3. `GET P2` → `SUPPLIER_PAID`; `plannedDeliveryDate` вернулась к дате запроса (или `null`).
  4. Повторить, но у P1 есть другая активная отправка → после отмены одной P1 остаётся `IN_DELIVERY`.
  5. Отмена `CLIENT_OWN` (P3) → P3 остаётся `IN_DELIVERY`.
  6. Повторная отмена → `error.shipment.terminal`.
- **Ожидание:** обратный переход только при отсутствии других активных отправок и `acceptedQuantity = 0`.

## A4. Отслеживание и ручное обновление (STUB)

### TC-A4-01. Лимит ручного обновления

- **Шаги:** `POST /refresh` дважды подряд.
- **Ожидание:** первый — `200`; второй — `429`, тело содержит `retryAfterSeconds`, ключ `error.shipment.refresh.tooSoon`.

### TC-A4-02. Ошибка перевозчика не даёт 5xx

- **Шаги:** создать отправку `STUBFAIL{run-id}`; `POST /refresh`.
- **Ожидание:** `200`, `refreshResult=FAILED`, причина `TIMEOUT`; `consecutiveFailures` растёт; ручной ввод ETA работает.

### TC-A4-03. Блокировка перевозчика

- **Шаги:** отправка `STUBBLOCK{run-id}` → `POST /refresh` → `FAILED/BLOCKED`; затем refresh другой отправки STUB.
- **Ожидание:** вторая отправка получает `error.shipment.refresh.carrierPaused` (пауза перевозчика).

### TC-A4-04. Планировщик обновляет открытые отправки и пропускает терминальные

- **Шаги:** создать `STUBTRANSIT` и `STUBDELIV` отправки; подождать 2 цикла (≈ 45 с); прочитать обе.
- **Ожидание:** первая `IN_TRANSIT`, `lastCheckedAt` обновляется; вторая `DELIVERED` и после этого `lastCheckedAt` не меняется.

## A5. Upcoming и график материалов

### TC-A5-01. Расширенный `upcoming`

- **Шаги:** `GET /api/purchase-positions/upcoming?days=14&projectId={p}` ролью FOREMAN.
- **Ожидание:** для позиций с активной отправкой есть `shipmentId`, `shipmentStatus`, `etaDate`,
  `driverPhone`, `trackingPageUrl`, `shipmentCount`; прежние поля не изменились; в ответе нет полей с
  `price`, `cost`, `amount`, `margin`, `vat`.
- Дополнительно: `?shipmentId={id}` возвращает только позиции этой отправки; `days=0` → `400`.

### TC-A5-02. Изоляция проектов

- **Шаги:** тот же запрос ролью FOREMAN-2.
- **Ожидание:** пусто (или только его проект); `GET /api/shipments/{id}` чужой отправки → `404`.

### TC-A5-03. Overlay

- **Шаги:** `GET /api/purchase-positions/schedule-overlay?projectId={p}` ролью MANAGER.
- **Ожидание:** категория `C1` с `worksStartDate` = старт проекта + 4 дня; позиция P1 с `downtimeRisk=true`,
  когда её ETA позже старта работ (выставить ETA = старт + 6), и `false` при ETA = старт + 2;
  `orderByMissed=true` у позиции со сроком заказа «вчера» в этапе до `ORDERED` (создать для этого
  дополнительную позицию P4 в `WITH_BUYER`, `orderByDate` = вчера) и `false` у P1 после заказа; в ответе нет
  денежных полей. Проект без графика → `200` и пустые `categories`.

## A6. Дедлайны и уведомления

### TC-A6-01. Order-by: одно уведомление на дату

- **Шаги:** подождать 2 цикла sweep; `GET /api/notifications` ролью MANAGER.
- **Ожидание:** ровно одно `notification.position.orderBy` на P1 (повторные циклы не добавляют);
  ссылка `/deliveries?project={p}`. Сменить `orderByDate` P1 на другую прошедшую дату → в следующем цикле
  появляется ещё одно.

### TC-A6-02. `shipped`, `delayed`, `downtimeRisk`

- **Шаги:** BUYER создаёт отправку; затем PUT ETA на сегодня + 6 (позже старта работ C1) и ещё на
  сегодня + 8 (позже).
- **Ожидание:** MANAGER и FOREMAN получили `notification.shipment.shipped`; после переноса вперёд на ≥1
  день — `notification.shipment.delayed`; при ETA позже старта работ — `notification.shipment.downtimeRisk`
  (один раз на каждое значение ETA); BUYER (актор) ничего не получил; у MANAGER ссылка
  `/deliveries/shipments?shipment={id}`, у FOREMAN `/deliveries/upcoming?shipment={id}`. Перенос ETA на ту
  же дату не создаёт уведомлений.

## Фича B1. Список и создание отправки (BUYER)

### TC-B1-01. Создание отправки из оплаченного заказа

1. Войти BUYER → `/deliveries/external-orders` → открыть оплаченный `EO1`.
   → видна кнопка «Dodaj przesyłkę»/«Добавить отправку» (по языку интерфейса).
2. Нажать кнопку → открыт `shipment-form`, заказ и позиции предзаполнены, видно «отправлено / лимит».
3. Выбрать метод «Перевозчик», перевозчик `STUB`, номер `STUBTRANSIT{run-id}`, количества 4 и 4 → «Сохранить».
   → диалог закрыт, переход на `/deliveries/shipments`, строка с чипом «Создана».
4. Подождать ≤ 40 с, обновить → чип «В пути», ETA = сегодня + 2.
5. Ввести количество больше лимита → ошибка у поля, диалог не закрывается.

### TC-B1-02. Фильтры и URL

1. Выбрать фильтр статуса «В пути» → в URL появился параметр, список отфильтрован.

## Фича B2. Детали, ручной ввод, обновление

### TC-B2-01. Обновление с таймером

1. Открыть строку → `shipment-drawer`; нажать «Обновить сейчас» → кнопка заблокирована с обратным отсчётом.
2. Быстрый повторный клик невозможен; после окончания отсчёта кнопка снова активна.

### TC-B2-02. Ручной ввод и возврат к данным перевозчика

1. «Ввести вручную» → дата + окно 09:00–12:00, телефон водителя → «Сохранить» → видна пометка «Статус/ETA введены вручную».
2. «Вернуть дату перевозчика» → пометка исчезла, ETA = данные перевозчика.

### TC-B2-03. Сбой перевозчика

1. Создать отправку `STUBFAIL{run-id}` → «Обновить сейчас» → сообщение «Нет данных от перевозчика, введите вручную»,
   ручной ввод доступен.

### TC-B2-04. Отмена

1. «Отменить отправку» → подтверждение → чип «Отменена»; кнопки действий скрыты.

## Фича B3. Экран прораба «Ближайшие поставки»

### TC-B3-01. Мобильный список

1. Войти FOREMAN, ширина окна 360 px → нижняя панель содержит 4 слота, последний «Ожидаемые поставки».
2. Открыть `/deliveries/upcoming` → список по датам, группа «Просрочено» первой (если есть).
3. Карточка показывает материал, количество, дату и окно, чип статуса, перевозчика, кнопку «Позвонить»
   (`tel:`) и ссылку «Открыть страницу перевозчика».
4. Выбор «7 / 14 / 30 дней» меняет список; пустой период показывает пустое состояние.
5. Перейти по ссылке уведомления `/deliveries/upcoming?shipment={id}` → нужная карточка выделена и прокручена в видимую область.
6. Денежных значений на экране нет.

### TC-B3-02. Права

1. FOREMAN-2 открывает экран → видит только свой проект.
2. FOREMAN открывает `/deliveries/shipments` → список и детали доступны только для чтения (кнопок
   «Создать», «Обновить», «Отменить» нет). WORKER и CLIENT при прямом переходе на этот адрес получают
   страницу «нет доступа».

## Фича B4. Gantt: слой «Материалы»

### TC-B4-01. Переключатель и маркеры

1. MANAGER → вкладка «График» проекта → включить «Материалы» → под строкой `C1` видны маркер «срок заказа» (P1) и
   маркер поставки; P1 с риском простоя отображён в стиле предупреждения, подсказка «придёт N дн. позже начала работ».
2. Выключить → разметка Gantt как раньше; состояние переключателя сохраняется после перезагрузки.
3. Перетаскивание маркеров невозможно.
4. FOREMAN → read-only Gantt (план/факт): маркеры срока заказа скрыты по умолчанию, маркер поставки виден.
5. Эмуляция ошибки overlay (остановить backend-эндпоинт или вернуть 500) → небольшое сообщение, Gantt работает.
