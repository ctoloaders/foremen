# Тест-кейсы: FOR-11-06 — Уточнения по экранам доставок

Спека содержит и API, и UI. Часть A — API-тесты против работающего Docker-стека (`http://localhost:8080`),
часть B — сценарии браузерного движка (`http://localhost:3000`, польская локаль). Результат прогона — MD-репорты
с таблицами (шаг → запрос/действие → ожидание → факт → статус); скриншоты не требуются. Реальные внешние
сервисы не вызываются: перевозчики на `STUB`, автоотслеживание выключено (`FOREMEN_PROCUREMENT_TRACKING_ENABLED=false`).

Покрываемые требования: R1–R15, R17 (по `requirements.md`); сам файл закрывает R16.

## Окружение

- Стек: `docker compose up` в корне (postgres :5432, liquibase, backend :8080 профиль `docker`, frontend :3000).
  После изменения кода пересобрать: `docker compose up -d --build backend liquibase frontend`.
- Первый ADMIN: `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Auth — `/api/auth`.
- Хранилище изображений и PDF проформ должно работать (ADC GCS), иначе TC-A2-03/04 дают `502` — тогда кейсы
  помечаются «пропущено» с указанием причины. Шрифт PDF встроен в сборку (Liberation Sans).
- Пользователи (создаются в Setup): ADMIN, MANAGER (член проекта), MANAGER-2 (**не** член проекта), CLIENT (член проекта),
  CLIENT-2 (член другого проекта), FINANCIER, BUYER, FOREMAN (член проекта), WORKER (член проекта, роль проекта `WORKER`),
  WORKER-2 (член проекта), WORKER-X (член **другого** проекта), WORKER-I (член проекта со статусом `INACTIVE`).

## Стратегия повторяемости (обязательно)

**Генератор данных + teardown.** На каждый прогон генерируется `run-id` (timestamp в миллисекундах). Все сущности
именуются с суффиксом `-{run-id}`: проекты `FOR1106-{run-id}` и `FOR1106-OTHER-{run-id}`, e-mail
`for1106+{role}-{run-id}@example.com`, номера заказов `ORD-{run-id}-{n}`, ссылки `https://pay.example.com/{run-id}/{n}`,
IBAN тестового счёта берётся из набора валидных тестовых IBAN (`PL61 1090 1014 0000 0712 1981 2874` и
`DE89 3704 0044 0532 0130 00`), комментарии `rcpt-{run-id}-{n}`. Каждое событие приёмки идёт с новым `clientRequestId`.

**Teardown** (выполняется даже при падении шагов): аннулировать события приёмки прогона; отменить созданные отправки,
заказы и проформы (черновики удалить); снять делегирования; удалить позиции прогона SQL-ом по `project_id`
(как в хелперах FOR-11-03/05); деактивировать проекты и пользователей `FOR1106-*-{run-id}`. Изоляция — уникальный проект
на прогон: все списки запрашиваются с `projectId` прогона.

## Набор данных прогона (Setup)

1. Логин ADMIN, создание пользователей всех ролей из «Окружения».
2. Проекты `FOR1106-{run-id}` (ACTIVE, старт — сегодня) и «чужой» `FOR1106-OTHER-{run-id}`; членство: MANAGER, CLIENT,
   FOREMAN, WORKER, WORKER-2, WORKER-I — в первом; CLIENT-2, WORKER-X — во втором.
3. Профиль компании со счётом `PL61 1090 1014 0000 0712 1981 2874`; счёт проекта не задан.
4. Смета проекта с отделочными материалами: 2 выбранных материала (с фото) и 1 строка **без выбранного материала**
   (тип отделочного материала с диапазоном цен); график работ с датами начала. Если сметы нет — Setup создаёт строки
   BoM через API FOR-05 и помечает смету «готова».
5. Продавец и 6 позиций `AGREED` (SQL/API): P1, P2 — `PLANNED`; P3 — `PROPOSED` (раунд открыт); P4, P5 — `ACCEPTED`
   (с ценой продажи); P6 — `WITH_BUYER` (оплачена проформой). Позиции проекта `FOR1106-OTHER` — P7 `WITH_BUYER`.
6. График платежей по работам проекта: опубликован, 3 транша (даты: прошлая, ближайшая, дальняя).
