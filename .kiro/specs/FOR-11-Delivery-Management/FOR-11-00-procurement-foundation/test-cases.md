# Тест-кейсы: FOR-11-00 — Фундамент закупок

> Спека full-stack (бэкенд-фундамент + тонкий UI), поэтому тест-кейсы разделены на
> **Часть A (API-тесты против поднятого в Docker приложения)** и **Часть B (сценарии браузерного
> движка)**. Результат прогона — MD-репорты с таблицами (шаблон в конце). Документ на русском
> (requirements/design/tasks — на английском, per `.kiro/steering/test-cases.md`).

## Окружение

- Docker-стек: `docker compose up` в корне — `postgres` (:5432), `liquibase` (миграции), `backend`
  (:8080, профиль `docker`), `frontend` (:3000). Базовый URL API: `http://localhost:8080`,
  аутентификация — `/api/auth`.
- Первый ADMIN поднимается через `FOREMEN_ADMIN_CREATE=true` + `FOREMEN_ADMIN_EMAIL` +
  `FOREMEN_ADMIN_PASSWORD`.
- **Реестр NIP (R5, R6):** по умолчанию `foremen.nip-lookup.enabled=false`, активен
  `DisabledNipLookupService`; реальный сервис не подключён и не проверяется. Ветка «реестр найден»
  покрывается только юнит-тестами (`MockRestServiceServer`), в этом документе — только ветки
  DICTIONARY / NONE / `registryAvailable=false`.
- **Свип просрочки (R13):** по умолчанию cron отключён (`"-"`). Кейсы с пометкой `[требует cron]`
  запускаются, когда стек поднят с `FOREMEN_PROCUREMENT_OVERDUE_SWEEP_CRON=0 * * * * *` (раз в минуту).
- **SYSTEM-переходы позиций** (`PROPOSED … CLIENT_PAID`, `ORDERED` и далее) не доступны через REST,
  они покрыты интеграционными тестами бэкенда; здесь проверяется, что REST их **не** допускает.
- Роли для прогона: ADMIN, MANAGER, FOREMAN, BUYER, FINANCIER (учётки создаются генератором).

## Стратегия повторяемости (обязательно)

**Генератор + Teardown.** Каждый прогон использует `run-id` = UNIX-timestamp или короткий uuid:

- Пользователи: `qa.buyer+{run-id}@example.com`, `qa.manager+{run-id}@example.com`,
  `qa.foreman+{run-id}@example.com`, `qa.financier+{run-id}@example.com`.
- Проекты: `Проект QA A {run-id}` (ACTIVE, MANAGER и FOREMAN — участники) и `Проект QA B {run-id}`
  (ACTIVE, **без** BUYER и FOREMAN). Проект `DRAFT` — `Проект QA D {run-id}`.
- Материалы проекта: `model = "QA-MAT-{run-id}"`; продавцы: код `qa_seller_{run-id}`, NIP из
  генератора валидных NIP (контрольная сумма: веса 6,5,7,2,3,4,5,6,7 по mod 11), уникальный на прогон.
- **Teardown (в обратном порядке зависимостей):** удалить заявки, затем позиции (сначала перевести в
  `CANCELLED`, если не `PLANNED`), затем материалы проекта, затем проекты и участников, затем
  продавцов, затем пользователей. Уведомления получателей удаляются владельцами (колокольчик) при
  необходимости.

Все сценарии запускаемы многократно без ручной чистки БД.

# Часть A — API-тесты

## Фича A1. Роль BUYER и доступ

### TC-A1-01 — создание и вход BUYER
**Предусловия:** авторизован ADMIN.
**Шаги:**
1. `GET /api/roles` → ожид. `200`, в списке роль `BUYER` (RU «Закупщик», PL «Specjalista ds. zakupów»).
2. Создать пользователя с ролью `BUYER` (`qa.buyer+{run-id}`), завершить активацию → ожид. `200/201`.
3. Войти `POST /api/auth/...` → ожид. `200`, токен получен.
**Ожидаемый результат:** BUYER создаётся и входит; роль выбирается в API без кода фронта.

### TC-A1-02 — BUYER видит закупки всех проектов без членства
**Предусловия:** TC-A1-01; в проектах A и B есть по одной позиции (создал MANAGER/ADMIN); BUYER не
участник ни одного проекта.
**Шаги:**
1. Токеном BUYER `GET /api/purchase-positions` → ожид. `200`, обе позиции (проекты A и B).
2. `GET /api/purchase-positions?filter=project.id~eq~{A}` → ожид. только позиции проекта A.
3. `GET /api/procurement/projects` → ожид. `200`, оба `ACTIVE` проекта (A, B), без `DRAFT`.
**Ожидаемый результат:** BUYER работает по всем проектам; MANAGER из проекта A видит только свой.

### TC-A1-03 — BUYER не имеет доступа вне закупок
**Шаги:** токеном BUYER запросить: `GET /api/bank-transactions`, `GET /api/payroll/...`,
`GET /api/payment-schedules/...`, `GET /api/estimates/...`, `GET /api/users` → ожид. `403` на каждый.
**Ожидаемый результат:** BUYER не получает грантов за пределами перечня R14.

### TC-A1-04 — справочные чтения BUYER
**Шаги:** токеном BUYER `GET /api/finishing-materials`, `/api/material-sellers`,
`/api/delivery-categories`, `/api/delivery-statuses`, `/api/vat-rates`, `/api/measurement-units` →
ожид. `200`. `POST /api/delivery-statuses` → ожид. `403`.
**Ожидаемый результат:** справочные READ есть, записи в справочники нет (кроме продавцов).

## Фича A2. Материалы проекта

### TC-A2-01 — создание материала проекта
**Предусловия:** проект A `ACTIVE`.
**Шаги:** MANAGER `POST /api/project-materials` (`projectId`, `categoryId`, `materialId`, `unitId`,
`model="QA-MAT-{run-id}"`, `link`, `producerId`, `sellerId`) → ожид. `201`, в ответе `projectId`.
**Ожидаемый результат:** материал создан внутри проекта.

### TC-A2-02 — материал проекта скрыт в общем справочнике
**Шаги:**
1. `GET /api/finishing-materials?filter=model~eq~QA-MAT-{run-id}` → ожид. пусто.
2. `GET /api/project-materials?projectId={A}` → ожид. материал присутствует.
3. `GET /api/finishing-materials/{id}` по id материала проекта → ожид. `200` (доступ по id работает).
**Ожидаемый результат:** в списках и пикерах общего каталога материала нет.

### TC-A2-03 — проект материала неизменяем
**Шаги:** `PUT /api/project-materials/{id}` с другим `projectId` → ожид. отказ
`error.projectMaterial.project.immutable`.

### TC-A2-04 — удаление используемого материала
**Предусловия:** позиция ссылается на материал.
**Шаги:** `DELETE /api/project-materials/{id}` → ожид. `409 error.projectMaterial.inUse`; после
удаления позиции — `204`.

### TC-A2-05 — проект не в реализации
**Шаги:** `POST /api/project-materials` в проект `DRAFT` → ожид. `409
error.projectMaterial.project.notActive`.

### TC-A3-06 — поиск: невалидный NIP и права

## Фича A4. Позиции закупки

### TC-A4-01 — создание позиции
**Предусловия:** проект A `ACTIVE`; материал проекта из TC-A2-01.
**Шаги:** MANAGER `POST /api/purchase-positions` (`projectId`, `kind=FINISHING`,
`sourcingPath=AGREED`, `plannedMaterialId`, `quantity=3`, `needByDate`) → ожид. `201`,
`status=PLANNED`, `unit` = единица материала, `purchaseVatRate`=23%, `saleVatRate`=8%
(если ставки есть в справочнике), `orderedQuantity=0`, `acceptedQuantity=0`.

### TC-A4-02 — валидации создания
**Шаги:** по очереди: `quantity=0` → `400`; `kind=CONSTRUCTION` → `error.purchasePosition.kindNotSupported`;
материал проекта B для проекта A → `error.purchasePosition.material.projectMismatch`; проект `DRAFT` →
`409 error.purchasePosition.project.notActive`; отрицательная цена → `400`.

### TC-A4-03 — ограничения редактирования
**Шаги:** `PUT` с `status` / `orderedQuantity` / `deliveryCostShare` → ожид. `400`
(`error.purchasePosition.field.readOnly`); смена `quantity` в `PLANNED` → `200`; после перевода в
`WITH_BUYER` (PACKAGE-позиция) смена `quantity` → отказ; `actualPurchasePrice` в `PLANNED` → отказ.

### TC-A4-04 — удаление
**Шаги:** `DELETE` позиции `PLANNED` → `204`; `DELETE` позиции в `WITH_BUYER` → `409
error.purchasePosition.delete.notAllowed`; `DELETE` токеном BUYER → `403`.

### TC-A4-05 — фильтры и сортировка
**Шаги:** `GET` с фильтрами `status`, `sourcingPath`, `needByDate`, сортировка `needByDate,asc` →
ожид. корректные выборки; значения без даты — в конце.

## Фича A5. Жизненный цикл и блокировка «проформа оплачена»

### TC-A5-01 — AGREED нельзя отправить закупщику вручную
**Шаги:** `POST /api/purchase-positions/{id}/transition {"target":"WITH_BUYER"}` для `AGREED`-позиции
в `PLANNED` → ожид. `409` (`error.purchasePosition.transition.gateViolation` или `.notAllowed`),
статус не изменился.

### TC-A5-02 — PACKAGE идёт сразу закупщику
**Шаги:** для `PACKAGE`-позиции `transition` в `WITH_BUYER` → `200`, `status=WITH_BUYER`.

### TC-A5-03 — CLIENT_OWN идёт сразу в доставку
**Шаги:** для `CLIENT_OWN`-позиции `transition` в `IN_DELIVERY` → `200`.

### TC-A5-04 — отмена и возврат
**Шаги:** `transition` в `CANCELLED` → `200`; затем в `PLANNED` → `200`; из `RECEIVED`-подобного
состояния отмена недоступна (проверяется интеграционным тестом).

### TC-A5-05 — служебные статусы недоступны вручную
**Шаги:** `transition` в `PROPOSED`, `ACCEPTED`, `IN_PROFORMA`, `CLIENT_PAID`, `ORDERED` → ожид. `409`
для каждого; `transition` токеном FOREMAN → `403`.
**Ожидаемый результат:** обход блокировки через REST невозможен.

## Фича A7. Заявки закупщику

### TC-A7-01 — создание заявки и привязка позиций
**Шаги:** MANAGER `POST /api/purchase-requests` (`projectId`, `referenceNumber`, `referenceLink`,
`expectedDeliveryDate`) → `201`; `POST /api/purchase-requests/{id}/positions {"positionIds":[...]}` →
`200`; ожид. `positionCount`, `status=OPEN`.

### TC-A7-02 — ограничения привязки
**Шаги:** позиция проекта B в заявку проекта A → ошибка
`error.purchaseRequest.position.projectMismatch`; позиция, уже входящая в другую заявку → `.alreadyAssigned`;
отменённая позиция → отказ.

### TC-A7-03 — назначение закупщика
**Шаги:** `assignedBuyerId` = пользователь не-BUYER → `400 error.purchaseRequest.buyer.invalid`; =
BUYER → `200`; у BUYER в колокольчике появилось `notification.request.assigned` с ссылкой
`/deliveries?request={id}`; повторное сохранение без смены закупщика — второго уведомления нет.

### TC-A7-04 — производные поля
**Шаги:** заявка без позиций → `OPEN`; все позиции `CANCELLED` → `CANCELLED`; `expectedDeliveryDate` в
прошлом при `OPEN` → `overdue=true`; в будущем → `false`.

### TC-A7-05 — отвязка и удаление
**Шаги:** отвязка позиции в `PLANNED` → `200`; отвязка позиции в `WITH_BUYER` → `409
error.purchaseRequest.position.detachNotAllowed`; удаление заявки с позициями → `409`
`error.purchaseRequest.delete.notEmpty`; пустой заявки → `204`.

## Фича A8. Просрочка и уведомления

### TC-A8-01 — разовое уведомление о просрочке `[требует cron]`
**Предусловия:** заявка с назначенным BUYER, `expectedDeliveryDate` вчера; MANAGER — участник проекта.
**Шаги:** подождать цикл свипа; у BUYER и MANAGER проверить колокольчик → ожид. по одному
`notification.request.overdue`; подождать ещё цикл → новых нет.

### TC-A8-02 — сброс при переносе даты `[требует cron]`
**Шаги:** `PUT` заявки с `expectedDeliveryDate` в будущем; затем снова в прошлом (через редактирование
данных теста) → после свипа приходит новое уведомление; незаданный закупщик → уведомление получают
все активные BUYER.

## Фича A11. История вариантов позиции

### TC-A11-01 — замена варианта (аналог)
**Предусловия:** позиция `AGREED` в `PLANNED` с материалом M1 и ценой продажи 100; материал M2 того же
типа.
**Шаги:** `POST /api/purchase-positions/{id}/variants/replace {"materialId":M2,"salePrice":120,
"reason":"ANALOG","note":"..."}` → ожид. `200`; `GET /api/purchase-positions/{id}` → основной вариант
M2/120, `variantCount=1`; `GET .../variants` → одна запись M1/100, `reason=ANALOG`.
**Ожидаемый результат:** в списке позиций виден только основной вариант, история — по запросу.

### TC-A11-02 — возврат к известному варианту
**Шаги:** `POST .../variants/{variantId}/restore` → ожид. основной снова M1/100, в истории M2/120
(`reason=MANUAL`), `variantCount=1`; восстановленная запись из истории исчезла.

### TC-A11-03 — подсказки аналогов
**Предусловия:** в проекте есть другие позиции того же типа материала с историей.
**Шаги:** `GET .../variants/suggestions?limit=5` → ожид. `200`, различные материалы того же типа
из текущих вариантов и истории позиций **этого проекта**, без текущего материала позиции, с последней
известной ценой; материалы другого проекта не попадают.

### TC-A11-04 — ограничение по стадии
**Шаги:** для позиции в `WITH_BUYER` (PACKAGE) `replace` → `409
error.purchasePosition.variant.stageNotAllowed`; для той же цены и материала `replace` в `PLANNED` →
`409 error.purchasePosition.variant.sameAsCurrent`.

### TC-A11-05 — видимость денег и права
**Шаги:** `GET .../variants` токеном FOREMAN → материалы видны, цены `null`; `replace` токеном
FOREMAN → `403`; токеном BUYER → `200` для позиции в `PLANNED`.

### TC-A11-06 — каскад и защита материала
**Шаги:** `DELETE /api/project-materials/{M1}` пока M1 только в истории → `409
error.projectMaterial.inUse`; удалить позицию (она в `PLANNED`) → история удалена, затем удаление M1
→ `204`.

## Фича A13. Ближайшие поставки для бригадира

### TC-A13-01 — состав и порядок
**Предусловия:** FOREMAN — участник проекта A; заявка проекта A с `expectedDeliveryDate` =
сегодня+3, три позиции в статусах `WITH_BUYER`, `IN_DELIVERY`, `PLANNED`; вторая заявка с датой
сегодня−2 и позицией `ORDERED`; позиция без заявки.
**Шаги:** токеном FOREMAN `GET /api/purchase-positions/upcoming?days=14` → ожид. 3 позиции
(`WITH_BUYER`, `IN_DELIVERY`, `ORDERED`), `PLANNED` и позиция без заявки отсутствуют; порядок по
дате: просроченная (`overdue=true`) первой; у элементов `projectName`, `materialLabel`, `quantity`,
`unitName` на языке пользователя, **нет** денежных полей.

### TC-A13-02 — окно дней и валидация
**Шаги:** `days=2` → позиции с датой сегодня+3 не попадают, просроченные попадают; `days=0` и
`days=61` → `400 error.purchasePosition.upcoming.days.invalid`.

### TC-A13-03 — скоуп
**Шаги:** FOREMAN не видит поставки проекта B; BUYER видит A и B; `projectId={A}` сужает выборку.

### TC-A13-04 — синхронизация даты
**Шаги:** изменить `expectedDeliveryDate` заявки → `plannedDeliveryDate` у её не терминальных
позиций обновилась; отвязать позицию → `plannedDeliveryDate=null` и она исчезла из списка;
позиция `RECEIVED` сохранила прежнюю дату.

## Фича A14. Виджеты дашборда

### TC-A14-01 — библиотека виджетов
**Шаги:** `GET /api/dashboard/widgets/library` (или соответствующий эндпоинт библиотеки) токенами:
FOREMAN, MANAGER, BUYER → ожид. виджеты `UPCOMING_DELIVERIES`, `PROCUREMENT_BY_STAGE`,
`POSITIONS_WITH_BUYER` присутствуют; токеном WORKER и CLIENT → отсутствуют.

### TC-A14-02 — данные виджета «Ближайшие поставки»
**Шаги:** запросить данные виджета токеном FOREMAN → только позиции проектов, где он участник,
отсортированы по `plannedDeliveryDate`; токеном BUYER (не участник) → позиции **всех** проектов;
токеном MANAGER проекта A → только проект A.

### TC-A14-03 — дефолты ролей
**Шаги:** создать нового пользователя BUYER и FOREMAN → при первом открытии дашборда у BUYER
виджеты `POSITIONS_WITH_BUYER`, `UPCOMING_DELIVERIES`, `PROCUREMENT_BY_STAGE`, у FOREMAN —
`UPCOMING_DELIVERIES`; существующие пользователи не получили новых виджетов автоматически.

### TC-A14-04 — «Закупки по этапам» и «Ждут закупки»
**Шаги:** данные `PROCUREMENT_BY_STAGE` — разбивка по статусам без `CANCELLED`; `POSITIONS_WITH_BUYER`
— число позиций в `WITH_BUYER`; значения совпадают с `GET /api/purchase-positions` (BUYER).
