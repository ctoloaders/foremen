# Тест-кейсы: FOR-11-01 — Планировщик закупок и доска закупщика

> Спека full-stack (небольшой бэкенд + экраны), поэтому тест-кейсы разделены на **Часть A (API-тесты
> против поднятого в Docker приложения)** и **Часть B (сценарии браузерного движка)**. Результат
> прогона — MD-репорты с таблицами (шаблон в конце). Документ на русском (requirements/design/tasks — на
> английском, per `.kiro/steering/test-cases.md`).

## Окружение

- Docker-стек: `docker compose up` в корне — `postgres` (:5432), `liquibase` (миграции, включая `233`),
  `backend` (:8080, профиль `docker`), `frontend` (:3000). Базовый URL API: `http://localhost:8080`,
  аутентификация — `/api/auth`.
- Первый ADMIN поднимается через `FOREMEN_ADMIN_CREATE=true` + `FOREMEN_ADMIN_EMAIL` +
  `FOREMEN_ADMIN_PASSWORD`. Срочность: `FOREMEN_PROCUREMENT_URGENT_DAYS` (по умолчанию 14; в прогоне
  не менять).
- **Ограничение REST (из FOR-11-00):** переходы `PROPOSED … CLIENT_PAID`, `ORDERED` и далее выполняет
  только система (SYSTEM) и через REST недоступны. Поэтому позиции в стадиях `ACCEPTED`, `CLIENT_PAID`,
  `ORDERED`, `SUPPLIER_PAID` готовятся **SQL-фикстурой** (шаг «Fixture»):
  `docker compose exec postgres psql -U <user> -d <db> -c "UPDATE purchase_positions SET status='ACCEPTED' WHERE id=<id>"`.
  Фикстура применяется только к позициям текущего прогона (по `notes LIKE 'qa-{run-id}%'`). Стадии
  `WITH_BUYER` (путь `PACKAGE`) и `IN_DELIVERY` (путь `CLIENT_OWN`) достижимы через REST
  `POST /api/purchase-positions/{id}/transition`.
- **Рабочие даты:** все даты прогона считаются от «сегодня» (Europe/Warsaw) смещениями (`+N`/`-N` дней),
  чтобы сценарии были повторяемы в любой день.
- **Графики работ:** для кейсов со стартом работ в проекте A создаётся график с одной полосой по
  категории работ (через UI/API FOR-05-10); дата старта проекта задаётся генератором.
- Роли прогона: ADMIN, MANAGER, FOREMAN, BUYER, FINANCIER (учётки создаются генератором). Нотификаций
  в этой спеке нет — проверяется только то, что 00-уведомление `request.assigned` приходит один раз при
  создании заявки с закупщиком (TC-A5-03).

## Стратегия повторяемости (обязательно)

**Генератор + Teardown.** `run-id` = UNIX-timestamp или короткий uuid:

- Пользователи: `qa.manager+{run-id}@example.com`, `qa.buyer+{run-id}@example.com`,
  `qa.buyer2+{run-id}@example.com`, `qa.foreman+{run-id}@example.com`, `qa.financier+{run-id}@example.com`.
- Проекты: `Проект QA A {run-id}` (ACTIVE; MANAGER и FOREMAN — участники; есть график работ),
  `Проект QA B {run-id}` (ACTIVE; **без** BUYER и FOREMAN).
- Материалы: `model = "QA-MAT-{run-id}-{n}"`; материал проекта A: `QA-PM-{run-id}`; продавцы:
  `qa_seller_{run-id}`, NIP из генератора валидных NIP (веса 6,5,7,2,3,4,5,6,7 по mod 11).
- Позиции: `notes = "qa-{run-id}-{номер}"`; заявки: `referenceNumber = "QA-{run-id}-{n}"`.
- **Teardown (в обратном порядке зависимостей):** открепить позиции от заявок → удалить заявки →
  перевести позиции в `CANCELLED` (фикстурой при необходимости вернуть в `PLANNED`/`CANCELLED`) и
  удалить → удалить материалы проекта → удалить график, проекты и участников → продавцов →
  пользователей. `localStorage` браузера очищается между сценариями Части B.

Все сценарии запускаемы многократно без ручной чистки БД.

# Часть A — API-тесты

## Фича A1. Список планировщика

### TC-A1-01 — сортировка по дате поставки на объект
**Предусловия:** Setup выполнен; токен MANAGER.
**Шаги:**
1. `GET /api/purchase-positions/planner?projectId={A}` → `200`, страница `PlannerRowDto`.
2. Проверить порядок строк по `siteDeliveryDate` (= `plannedDeliveryDate`, иначе `needByDate`) по
   возрастанию, строки без даты — в конце; при равных датах — по `id`.
3. `?sort=siteDeliveryDate,desc` → порядок обратный (строки без даты по-прежнему последние для asc;
   для desc проверить контракт: nulls last сохраняется).
4. `?sort=unknownField` → `400`, ключ `error.purchasePlanner.sort.invalid`.
**Ожидаемый результат:** сортировка корректна, неизвестное поле отклоняется.

### TC-A1-02 — состав строки
**Шаги:**
1. Взять строку P3. Проверить: `material.model/sku/producerName/sellerName`, `quantity=12.500`, `unitName`
   на языке заголовка `Accept-Language: pl` и `ru`, `requestReferenceNumber = R1`, `siteDeliveryDate`,
   `allowedActions` (для MANAGER содержит `EDIT`, `CANCEL`).
2. Для P3 `money.saleNetTotal = 1150.00`, `money.saleGrossTotal = 1242.00` (VAT 8%),
   `money.costNetTotal = 768.75`, `money.marginAmount = 381.25`, `money.marginPct = 0.3315`.
**Ожидаемый результат:** значения совпадают, суммы строк равны округлённым по строке.

### TC-A1-03 — фильтры и их композиция
**Шаги:**
1. `?projectId={A}&status=ACCEPTED` → только P3, P4.
2. `&sourcingPath=AGREED` → без изменений; `&requestId={R1}` → только P3.
3. `?projectId={A}&noRequest=true` → позиции без заявки (P1, P4, P5, P7, P8, P10, P12).
4. `?q=QA-MAT-{run-id}` → позиции с такими материалами; `?q=%25` и `?q=_` не работают как wildcard
   (возвращают пустой список или точное совпадение).
5. `?buyer=MINE` токеном BUYER → позиции заявки R2 (P6, P9); `?buyer=UNASSIGNED` → без заявки или
   заявка без закупщика (P1…P5, P7, P8, P10, P12).
**Ожидаемый результат:** фильтры комбинируются по AND, пагинация и `totalElements` корректны.

### TC-A1-04 — скрыть доставленные
**Шаги:**
1. Без параметра: P10 (RECEIVED) в списке.
2. `&hideDelivered=true` → P10 отсутствует, остальные на месте, `totalElements` на 1 меньше.
**Ожидаемый результат:** фильтр применяется в запросе, итоги верны.

### TC-A1-05 — компания-wide вид закупщика
**Шаги:**
1. Токеном BUYER (не участник проектов) `GET /api/purchase-positions/planner` без `projectId`.
2. Проверить, что в ответе есть позиции проектов A и B (P11).
3. Токеном MANAGER тот же запрос → нет P11 (проект B без членства).
**Ожидаемый результат:** BUYER видит все проекты, MANAGER — только свои.

## Фича A2. Срезы и срочность

### TC-A2-01 — определения срезов
**Шаги:** для `projectId={A}`:
1. `slice=LATE` → P2 (дата поставки/needBy в прошлом) и позиции с `orderByDate` в прошлом и стадией до
   `ORDERED`; не содержит P10 (RECEIVED).
2. `slice=ON_SCHEDULE` → активные позиции, не вошедшие в LATE.
3. `slice=CHANGED` → P8 (есть варианты).
4. `slice=PAID` → P5 (AGREED, CLIENT_PAID); не содержит PACKAGE/CLIENT_OWN (P6, P7, P9).
5. `slice=NOT_PAID` → AGREED до CLIENT_PAID: P1, P2, P3, P4, P8, P12; не содержит CANCELLED.
6. `slice=garbage` → `400`, `error.purchasePlanner.slice.invalid`.
**Ожидаемый результат:** срезы взаимоисключающие значения фильтра, определения совпадают с требованиями.

### TC-A2-02 — счётчики срезов
**Шаги:**
1. `GET /api/purchase-positions/planner/slice-counts?projectId={A}` → `{ALL, ON_SCHEDULE, LATE, CHANGED, PAID, NOT_PAID}`.
2. Сравнить каждый счётчик с `totalElements` соответствующего `planner?slice=…` (те же фильтры).
**Ожидаемый результат:** счётчики равны размерам выборок.

### TC-A2-03 — срочные
**Шаги:**
1. `?projectId={A}&urgent=true` → не терминальные позиции до `ORDERED` с датой поставки ≤ сегодня + 14
   или просроченные: ожидаются P2, P3, P6, P9, P12; P1 (`+30`), P4, P8 (нет даты), P5 и P7 не входят.
2. Флаг `urgent` в строках совпадает с фильтром.
**Ожидаемый результат:** фильтр и флаг согласованы.

## Фича A7. Связь с графиком работ (авто по норме расхода + ручная правка)

> Данные прогона: тип материала `MT1` (тип чистовых материалов); в каталоге работ норма расхода
> (`work_material_consumptions`, ветка `finishing`) связывает `MT1` с работой категории **C1**
> (и с работой категории **C2**); в смете проекта A есть строка работы категории C1; в графике проекта A
> есть полосы категорий C1 (старт `+7`) и C3 (старт `+20`); C2 в графике **нет**. Материал `QA-MAT-MT1`
> имеет тип `MT1`; материал `QA-MAT-NOTYPE` — без типа; материал `QA-MAT-MT9` — тип без норм расхода.

### TC-A7-01 — автоматическое связывание (ярус 1: смета)
**Шаги:** токен MANAGER.
1. Создать позицию P12 в проекте A с материалом `QA-MAT-MT1`, без `workCategoryId`.
2. `GET /api/purchase-positions/planner?projectId={A}` → строка P12: `workCategoryId = null`,
   `effectiveWorkCategoryId = C1`, `workCategorySource = AUTO`, `workStartDate` = дата старта полосы C1,
   `suggestedNeedByDate` = она же, `workCategoryCandidates = []`.
3. Если `siteDeliveryDate` позже `workStartDate` → `deliveryRisk = true`; иначе `false`.
**Ожидаемый результат:** категория определена по типу материала через норму расхода работы из сметы.

### TC-A7-02 — ярус 2 (каталог) для материала вне сметы
**Шаги:**
1. Убрать из сметы проекта A работу C1 (или взять проект без неё) так, чтобы норма типа `MT1` не
   встречалась в строках сметы, но в графике есть полоса категории C1.
2. Строка P12 → `effectiveWorkCategoryId = C1`, `workCategorySource = AUTO` (определено по каталогу
   работ, с пересечением с запланированными категориями).
3. Категория C2 (есть в каталоге, нет в графике) **не** выбирается.

### TC-A7-03 — несколько совпадений: побеждает самый ранний старт
**Шаги:** добавить в график проекта A полосу для категории C2 со стартом `+3` (раньше C1).
1. Строка P12 → `effectiveWorkCategoryId = C2`, `workCategorySource = AUTO`,
   `workCategoryCandidates = [C1 …]` (с датами старта).
2. Выровнять старты так, что они равны → побеждает по названию, затем по id (детерминированно);
   повторный запрос возвращает тот же результат.

### TC-A7-04 — не найдено
**Шаги:** позиции с материалами `QA-MAT-NOTYPE` и `QA-MAT-MT9` → `effectiveWorkCategoryId = null`,
`workCategorySource = NONE`, `workStartDate = null`, `deliveryRisk = false`; строка отображается обычным
образом.

### TC-A7-05 — ручная правка и сброс
**Шаги:**
1. `PUT /api/purchase-positions/{P12}` с `workCategoryId = C3` → `200`, в DTO `workCategoryId = C3`; в
   строке `workCategorySource = MANUAL`, `effectiveWorkCategoryId = C3`, `workStartDate` = старт C3 (`+20`).
2. Сменить материал позиции на `QA-MAT-NOTYPE` → ручная категория **сохраняется** (MANUAL).
3. `DELETE /api/purchase-positions/{P12}/property?properties=workCategory` → `204`; повторный `planner` возвращает `workCategoryId = null` и снова авто-результат (или `NONE` для материала без типа). `PUT` с `workCategoryId = null` путём сброса **не** является (поле не очищается). Для позиции в стадии `ORDERED` (фикстура) тот же `DELETE` → `409`.
4. Ручная категория, которой **нет в графике** (C2 без полосы) → `200`, `workCategorySource = MANUAL`,
   `workStartDate = null`, `deliveryRisk = false`.
5. Несуществующая/неактивная категория → `400` `error.purchasePosition.workCategory.invalid`.
6. Для позиции в стадии `ORDERED` (фикстура) изменение категории → отклоняется (стадия).
