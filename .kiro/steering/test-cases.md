# Стандарт: test-cases.md — обязательный артефакт спеки

## Правило обязательности

Каждая спека (папка `.kiro/specs/**/<spec>/`) ОБЯЗАНА содержать файл `test-cases.md` наряду с `requirements.md`, `design.md`, `tasks.md`.

- Файл `test-cases.md` создаётся на фазе **tasks** спек-воркфлоу, сразу после генерации `tasks.md`, до завершения спеки.
- Это относится ко ВСЕМ типам воркфлоу: feature (requirements-first и design-first), bugfix, quick spec.
- `tasks.md` каждой спеки ОБЯЗАН содержать отдельную задачу «Author test-cases.md» (см. раздел «Интеграция с tasks.md»).
- Документ `test-cases.md` пишется на русском языке (в отличие от requirements/design/tasks, которые на английском).

## Тип тест-кейсов зависит от характера спеки

Определи тип спеки и выбери формат:

### UI-спеки (есть браузерные экраны)
- Тест-кейсы предназначены для «живого тестировщика», но по факту исполняются браузерным движком (headless-браузер / browser automation).
- Каждый шаг — действие в браузере (переход, ввод, клик, ожидание).
- **Результат прогона — не скриншоты, а MD-репорты с таблицами** (шаг → ожидание → факт → статус). Скриншоты не требуются.

### Чисто API-спеки (нет браузерных экранов, например бэкенд JWT/CRUD/миграции)
- Тест-кейсы — это **API-тесты против работающего в Docker приложения** (не Testcontainers/юнит-слой, а поднятый docker-стек).
- Каждый шаг — HTTP-запрос к API с проверкой статуса/тела/заголовков.
- **Результат прогона — MD-репорты с таблицами** (шаг → запрос → ожидание → факт → статус).

## Общие требования к структуре test-cases.md

1. **Группировка по фичам** — заголовок на каждую фичу/функциональную область, внутри — тест-кейсы.
2. **Подробные пошаговые сценарии** — каждый тест-кейс: ID, название, предусловия, шаги (нумерованные), ожидаемый результат на каждом шаге.
3. **Повторяемость (обязательно)** — сценарии должны быть запускаемы многократно без ручной чистки БД. Реализуется одним из способов:
   - **Генератор данных**: уникальные идентификаторы на каждый прогон (например, email вида `test+{run-id}@example.com`, где `run-id` — timestamp/uuid).
   - **Clean-up**: явный шаг удаления/деактивации созданных сущностей в конце сценария (teardown).
   - Каждый набор кейсов ОБЯЗАН явно указывать выбранную стратегию повторяемости (Setup / Teardown / генератор).
4. **Отдельная группа регрессионных тест-кейсов** — в конце файла раздел «Регрессия» с кейсами по необходимости (перепроверка ранее закрытых багов и критичных сквозных путей). Если регресс не нужен — явно указать «Регрессионные кейсы не требуются на данном этапе» с обоснованием.
5. **Формат отчёта** — в конце файла привести шаблон MD-репорта с таблицами, который заполняется по итогам прогона.

## Запуск окружения для API-спек (Foremen)

Docker-стек проекта: `docker compose up` в корне поднимает `postgres` (:5432), `liquibase` (миграции), `backend` (:8080, профиль `docker`), `frontend` (:3000). Auth-эндпоинты — под `/api/auth`. Первый ADMIN поднимается через переменные `FOREMEN_ADMIN_CREATE=true`, `FOREMEN_ADMIN_EMAIL`, `FOREMEN_ADMIN_PASSWORD`. Базовый URL для API-тестов: `http://localhost:8080`.

## Интеграция с tasks.md

При генерации `tasks.md` любой спеки ОБЯЗАТЕЛЬНО добавляй в конце (перед финальным чекпойнтом) задачу вида:

- [ ] N. Author test-cases.md
  - Create `test-cases.md` in the spec folder following the `.kiro/steering/test-cases.md` standard (feature grouping, step-by-step scenarios, repeatability via generator/clean-up, regression group, MD report template). For API-only specs, scenarios are API tests against the Dockerized app; for UI specs, browser-engine scenarios. Result artifacts are MD reports with tables.
  - _Requirements: (reference the requirements covered by the test cases)_

Итог: X пройдено / Y провалено / Z пропущено. Run-id: `<timestamp/uuid>`. Стратегия повторяемости: `<генератор|teardown>`.
